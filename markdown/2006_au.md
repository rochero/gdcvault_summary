### Overview
Test-Driven Development (TDD) is a relatively new technique that, despite gathering a lot of momentum, has made very few inroads in our industry. However, this is a technique that is too useful to overlook any longer. In an industry where we're constantly pushing the boundaries and exploring the unknown, the benefits of TDD are a very good match for many of our development problems.  Developing software with TDD might seem backwards at first glance: First a short unit test is written, then the code to make that unit test pass is implemented, and finally the code can be refactored (without changing its functionality). At that point, the cycle is repeated over and over, always starting with a unit test. The cycle itself should be short, in the order of a couple of minutes and all of the tests are required to run before moving forward.  TDD has some very interesting consequences: It creates a safety net of unit tests, which allows for major refactorings  or introducing new features late in development without fear of breaking existing code, it forces the developer to use his own code first, so it is always written from the point of view of the user of the code, it encourages more modular, simpler code that can be easily modified and reused, and it serves as a form of documentation that, unlike comments or documents, can never get out of date. Last but not least, it provides the developer with instant feedback, building his confidence in the code and even making the programming experience much more enjoyable.  The talk starts with a general overview of TDD, followed by a detailed explanation of how to put it into practice, and a live TDD demonstration implementing a high-level game task fully in TDD. The second half of the session is dedicated to some of the unique aspects of game development, such as having different hardware platforms, dealing with graphics, or using middleware and how they affect TDD. Finally, the session concludes with the lessons learned at High Moon Studios from using TDD in a variety of projects.

### Content Summary
[TLDR]
测试驱动开发 (Test-Driven Development) 虽前期投入较大，但能显著提升代码质量与设计，长期看反而更高效且不易返工。

[Background]
许多项目后期常遇代码失控、重构怕翻车、构建频繁挂的痛点。本文分享了在高蒙工作室 (High Moon Studios) 的实际落地经验，适合受困于 Bug 和复杂性困扰的游戏程序老哥参考。

[Recaps]
各位搞开发的都知道，随着硬件升级，代码越堆越厚，后期容易变成雪崩一样的烂摊子，改不动还全是隐雷。这时候就得请出测试驱动开发 (Test-Driven Development) 这员大将。简单说，就是把常规流程反着来：别急着写功能，先针对小功能写个单元测试 (Unit Test) 让它失败，然后补代码让它通过，接着重构优化。这一套闭环下来，能保证每次只解决极小的问题，而且因为先定了验收标准，最终出来的代码结构更清晰，专门服务于使用者而非实现细节，极大降低了后期维护的难度。

实战中有几个关键原则得拿捏好。首先是安全感，有了大量测试做防护网，你重构的时候心里就有底，哪怕为了性能去折腾底层逻辑也不怕破坏现有功能。其次是反馈速度，单元测试要是跑得慢，谁愿意天天跑？最好几秒内搞定，千万别涉及显卡初始化或硬盘读写。遇到图形 API 这种麻烦东西，就用模拟对象 (Mock Object) 骗过去，或者直接隔离调用，别直接拿硬件本身当白老鼠。还有那些随机音效、粒子效果，测试前得把随机数种子定死，否则逻辑无法复现验证。

至于大家最关心的开发速度，其实 TDD 刚上手确实会觉得慢了，毕竟要写双倍甚至更多的测试代码。但这玩意儿就像工地上的脚手架，交付给客户的是成品建筑，但没脚手架根本干不了复杂活儿。只要团队磨合好了，配合持续集成 (Continuous Integration)，后期的改动成本会呈指数级下降。总之，别指望天上掉馅饼，但坚持下来你会发现，那种面对庞大代码库无从下手的恐惧感消失了，这才是最大的红利。

## Building a Better Battlestar
- **Speaker:** Ronald Moore ()
- **Duration:** 68 分钟

### Overview
Sequels and reboots in Hollywood have now become more common in gaming. In this "vision track" keynote, the creator and producer of the new Battlestar Galactica TV series discusses how he developed and adapted the existing story behind a large franchise into a new series.

### Content Summary
[TLDR]
成功改编经典 IP 的关键在于保留其核心精神骨架，同时用现代现实逻辑重塑人物关系与世界观设定。

[Background]
每个制作人都有过“既要讨好老粉又要吸引新客”的改作难题。罗恩·摩尔分享《太空堡垒卡拉狄加》重启经验，为影视及游戏行业的 IP 改编提供了极具参考价值的实战方法论。

[Recaps]
摩尔开宗明义，改编老 IP 不能瞎搞，得先找到它的“核心架构 (Architecture)"，也就是原作真正让人记住的根本元素。比如那个经典的殖民地被灭门开场，原版只是太空歌剧式的爽片，新版则把它拍成了类似 9/11 事件后的真实灾难。他不想要观众看得开心，而是要让他们感到压抑和恐惧，这样大家才能代入那种家园毁灭的切肤之痛。整个项目从那一刻起就定下了现实主义基调，后续所有的决策都要服务于这个氛围，而不是单纯的特效堆砌。

人物设计这块更是大有文章。摩尔把那艘飞船当成一个大家庭来经营，指挥官阿达玛不再是传统意义上的铁面无私英雄，而是一个有缺陷、会犹豫甚至犯错的老父亲。为了平衡军权，他加了个女总统罗斯林当“母亲”角色，处理文官与军事的政治拉扯。还有个骚操作是把王牌飞行员斯塔尔巴克改成了女性，让他从原本的油腻浪子变成了一个内心受伤但技术顶尖的复杂个体。这种对经典角色的解构与重组，既保留了记忆点，又赋予了现代深度，避免了脸谱化。

除了人物，技术和叙事上的取舍同样精彩。当初因为预算有限，没法做大量昂贵的 CGI，结果反手决定让敌人长得像人类，这意外引出了关于宗教和人性的更深探讨。为了让空战镜头更有临场感，他们放弃完美的推拉摇移，改用“手持摄影 (Handheld Camera)”去模拟真实摄像机的抖动和限制。叙事上采用了 ABC 三层故事线的结构，A 层单集结局，B 层跨集推进，C 层贯穿全季主线，保证每集都有爆点又不脱离长剧情的大框架。

最后摩尔强调了改编者的初心：不要为了救活一部剧而毁了它原本的灵魂。哪怕地球其实是编出来的谎言，只要能给绝望中的幸存者希望和动力，这就足够合理。作为创作者最难的不是开始，而是知道何时停下，别等口碑崩了才收尾，保住作品的品质才是留给观众最好的遗产，这也是所有 IP 传承的核心法则。
