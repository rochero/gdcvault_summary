## Tools Summit: Embedded Scripting with Zero Overhead in Final Builds
- **Speaker:** Arturo Cepeda (Deck13 Interactive)
- **Duration:** 1771 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1027310
- **Slide Page:** https://www.gdcvault.com/play/1027069
- **Custom ID:** 1027310

### Overview
This talk explains the process followed for the integration of the current scripting system in Deck13's in-house engine Fledge, allowing not only programmers, but also people from other departments such as game design and art, to benefit from a more agile workflow, thanks to the hot-reloading and the debugging features, without paying any additional costs in terms of performance in final builds, which is one of the biggest disadvantages of using scripting languages in games.nnIn addition to that, it goes through the different approaches used in previous versions of the Fledge engine in a post-mortem fashion, analyzing their pros and cons and indicating the reasons why they eventually were discarded.

### Content Summary
[TLDR]
通过自研 Cflat 引擎，让脚本在发布版直接编译成原生 C++ 代码，彻底消除运行时代码开销。

[Background]
传统脚本方案（如 Lua）在发布版仍有内存和运行时的性能开销，拖累游戏性能。本分享针对追求高帧率与灵活性的项目，解决“脚本依赖 vs 性能损耗”的矛盾。

[Recaps]
以前用 Lua 配合 sol2，虽然有热重载 (Hot Reloading)，但发布版仍有内存碎片、堆分配和垃圾回收 (Garbage Collection) 的压力，运行时代码开销没法避免。为了解决这个“既要灵活性又要高性能”的痛点，演讲者认为脚本在正式版不用热更，干脆让其变成 C++ 代码。于是团队自研了 Cflat，核心思路是：开发版本走解释器模式，发布版本通过条件编译把脚本直接当成源码头文件包含，由编译器生成原生机器码 (Native Machine Code)。

这招真香之处在于实现了“零开销”。利用预处理器宏 (Preprocessor Macros)，代码获取变量或调函数在调试时会查表执行，而发布版则直接访问内存或调用函数指针，完全绕过中间层。为了配合工作流，他们用了 VS Code 写脚本，不仅支持语法高亮，还把脚本声明当文档生成。此外，通过实现线程锁接口，解决了多线程下环境访问的安全问题，连可视化节点的动态调用也能在发布版通过封装器自动映射。

当然，这套方案也有坑。因为本质是 C++ 语法的子集，不是所有编译器允许的写法 Cflat 都认，得小心别踩雷。比如脚本里的函数不能是非静态的且跨多 cpp 引用，否则链接会报错；全局命名空间也最好别乱用，防止污染宿主文件。最后提醒大伙，每次改脚本都要确保它在宿主 cpp 里也能编译通过。总之，这是种能把脚本当“内联优化”对待的高级玩法，适合对性能敏感的项目参考。

## Tools Summit: Free Up the Cognitive Load: UX in Animation Workflow
- **Speaker:** Irene Zhu (343 Industries)
- **Duration:** 1407 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1027309
- **Slide Page:** https://www.gdcvault.com/play/1027122
- **Custom ID:** 1027309

### Overview
Like computers, the human brain has limited amount of processing power(cognitive load). When the amount of information coming in exceeds the ability to handle it, fatigue happens, performance declines. We may miss important details or even abandon the task completely, which is not what we want to see happen. This is especially relevant in a work from home environment. Because back in the office, there were short walks in and out of a meeting room, the water-cooler conversations, and lunches with coworkers. Each acts like a mini reboot for our brain, which allows us to go back to work relatively refreshed. Now, most of us sit in one spot and stare at the screen all day. But we often find ourselves more easily exhausted and less productive. In situations like this, every bit of brain power counts. And we as tool developers want to be aware of the state our users might be in, and be mindful about how much brain power we are asking for in our tools. This talk uses 3 animation tools as examples to demonstrate how to start thinking about the level of cognitive load our tools are asking for, and ways to reduce it.

### Content Summary
[TLDR]
别让大脑死机！用“熟面孔”、统一标准、自动算账三招，把动画工具设计得轻松好上手。

[Background]
动画工具太臃肿，新人上手慢还容易出错，远程办公更是费脑。本演讲给 UX 设计师和工具开发者指路：如何降低认知负荷，提升协作效率。

[Recaps]
先说个核心概念，什么叫认知负荷 (Cognitive Load)。简单讲就是咱们大脑的 CPU 算力，信息太多脑子就转不过来了。特别是现在大家都在家远程办公 (Remote Work)，少了办公室摸鱼聊天的“重启”时间，注意力更难集中。如果工具设计得太复杂，占用了大脑处理图片、记步骤的资源，不仅效率低，干久了还容易出 bug 甚至想放弃。咱们做工具的目标，就是把那些不影响理解内容的无用负担给减掉。

怎么减？第一招，多用“熟面孔”。别为了创新而创新，尽量用用户已经懂的操作逻辑。比如以前动画编辑器要把人物名字和下面的一堆代码对上号，太费劲。后来改成了像视频剪辑软件那样的时间轴，人物和动作一行对一行，大家拿起来就会用，根本不用背菜单在哪。这就叫利用 Familiarity，让大脑少猜谜。

第二招，标准统一但保留个性。以前游戏性动画、过场、剧情三拨人各有一套导出工具，工程师修得头晕，用户也分不清哪套好用。后来直接合并成一个万能导出器，就像税务软件一样灵活，既能通吃又能满足特殊情况。这样不仅省了一堆工作量，还把几个团队之间的隔阂给打破了。

最后一招，能替用户算的就别让他们动手。比如分配动作权重值的时候，原来得人工凑数字加起来等于 1，稍微算错就废了。后来改成系统自动补全，你想指定多少就填多少，空着就让系统分。这下连心算都省了，以后回头看数据也不会一脸懵。

总之，这套操作下来，以前新人培训得几个月，现在一周就能独立出活。工具顺心了，脑子不累了，做出来的活儿质量自然就上去了。

## Zen of Streaming: Building and Loading 'Ghost of Tsushima'
- **Speaker:** Adrian Bentley (Sucker Punch Productions)
- **Duration:** 3343 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1027205
- **Slide Page:** https://www.gdcvault.com/play/1027545
- **Custom ID:** 1027205

### Overview
Ghost of Tsushima is ~15x larger than previous Sucker Punch games and won praise from users for its fast load times and compact patch sizes. This talk examines the technology choices that made this transition possible, from its bumpy start to its even finish. It will delve into our world building strategy and how it evolved. It will also show the details of our various streaming technologies and the tradeoffs encountered in switching to a fine-grained streaming model. It will cover a variety of memory, disc and performance optimizations made to systems including terrain, pathing, physics, AI and rendering. Lastly, this talk will discuss the process of shipping Ghost with an emphasis on ensuring fast loading times and how our technology held up (or not) working from home during a pandemic.

### Content Summary
[TLDR]
利用精细纹理流式 (Fine Grain Texture Streaming) 和 GPU 加速 (GPU Compute)，在 PS4 硬件极限下实现了无缝大地图加载。

[Background]
这次演讲旨在分享如何用有限内存装下超大开放世界。适合想突破主机性能限制的程序看，解决了从城市题材转向广袤自然景观后的资源爆炸痛点。

[Recaps]
这次讲座主要讲的是怎么在 PS4 有限的内存和硬盘空间里，塞进一个比前作大几十倍的开放世界《对马岛之魂》。以前做《声名狼藉：第二之子》(Infamous Second Son) 时候的城市环境，固定光照能凑合，但这次是日本乡村地形复杂，树多草多视野远，原来的那套方法直接崩盘，连磁盘都装不下，内存更是不够用。简单算笔账就知道，光贴图的体积就把光盘撑爆了，必须得有新科技来匹配这个愿景。

核心解决思路是“精细粒度纹理流式传输 (Fine Grain Texture Streaming)"。团队搞了个总清单系统 (Manifest Boot)，贴图读取只需要一次，配合虚拟内存 (Virtual Memory) 管理碎片问题。他们只给了 1GB 的显存预算给贴图，通过优先级机制和动态压缩，保证关键区域高清，远处自动糊一点，既省空间又不穿模。这种手段比单纯的预加载要灵活得多，解决了大地图切换时的卡顿，甚至允许开发者在远程办公环境下也能顺利构建。

为了压榨性能，他们把大量活儿交给了 GPU (Graphics Processing Unit) 去算，比如植被生成和遮挡剔除 (Occlusion Culling)。另外还搞了个“美学距离堆 (Aesthetic Distance Heap)"来处理休眠对象，不用每帧都检查几百个 NPC 和物体，省下了大量 CPU (Central Processing Unit) 时间。加上编译时的合并数据优化和自动路径规划 (Pathing)，最终让游戏在极限规格下也能跑得稳，甚至远程开发也没把项目拖垮，证明了好架构比堆人头更重要。

## Model Collision: Balancing Speed and Size in 'Black Ops Cold War'
- **Speaker:** Andrew Shurney (Activision: Central Tech)
- **Duration:** 3369 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1027348
- **Slide Page:** https://www.gdcvault.com/play/1027116
- **Custom ID:** 1027348

### Overview
With the promises of infinite system memory and disk bandwidth devoured by 4k assets, it is once again beneficial to balance performance against utility and memory footprint. Occasionally, however, by taking advantage of ubiquitous hardware features and paying close attention to your data bit by bit, gains can be made on both fronts. This session is a highly technical deep dive into the process of optimizing the high-accuracy model collision in Call of Duty: Black Ops Cold War to reduce memory footprint to less than one-fifth it's size while simultaneously conferring a two-fold speed increasing.

### Content Summary
[TLDR]
利用三角形条带与定点数压缩，将碰撞数据体积压至原长的 1/5，速度反倒提升一倍，这是一次硬核的手动优化典范。

[Background]
地图越来越大，内存吃紧。演讲者发现静态模型碰撞数据占了总静态内存的 30%，传统换空间换速度的路子走不通，必须双管齐下挤水分。

[Recaps]
起初三角面用的是平面法线存储，算起来快但太占地方。试着改存顶点配合**定点数 (Fixed Point)**，虽然能省空间，但交叉积计算太慢，还得搞复杂的**单指令多数据流 (SIMD)**解包，容易得不偿失。

真正破局的是引入了**三角形条带 (Triangle Strip)**。普通列表一个三角要 3 个顶点，条带只要 N+2 个，空间直接腰斩。更骚的操作是把条带转回标准列表时，直接用**单指令多数据流 (SIMD)**指令集并行解包，几乎不耗性能，反而因缓存友好跑得更飞快。

连带的**轴对齐包围盒树 (AABB Tree)**也没放过。之前节点设计太臃肿，演讲者把子节点索引改为连续排序，删掉无用的材质位掩码，甚至对节点尺寸做了动态压缩。最后还发现补丁里的空余位可以存高比特数据，进一步省空间。

这一套组合拳下来，静态碰撞数据从 80MB 干到了 16MB，整体运行速度接近 2 倍提升。这证明了对于静态数据，大胆使用**定点数 (Fixed Point)**、**三角形条带 (Triangle Strip)** 以及自定义内存布局，往往比通用方案能榨出更多性能。

## Math In Game Development Summit: Practical Quaternions: An Easy Guide to 3D Rotations for Non-Mathematicians
- **Speaker:** Patrick Martin (Google)
- **Duration:** 1765 分钟
- **Category:** Math In Game Development Summit
- **Video Page:** https://www.gdcvault.com/play/1027334
- **Slide Page:** https://www.gdcvault.com/play/1027047
- **Custom ID:** 1027334

### Overview
Have you heard cool things about quaternion math but loose the thread as soon as someone starts talking excitedly about four dimensional hyperspheres? Join Patrick as explains how he visualizes, debugs, and works with quaternion math as a practical implementor rather than their pure mathematics. By the time you walk out, you'll see quaternions not as a mathematical oddity but as a collection of common operations you use day to day to solve real world puzzles.

### Content Summary
[TLDR]
别被数学公式劝退，掌握七条实战法则（乘法即应用、SLERP 插值等），轻松搞定旋转并避开万向节死锁。

[Background]
很多程序员一见到旋转算法就头大，因为传统欧拉角 (Euler angles) 容易掉进万向节死锁 (Gimbal Lock) 的大坑。演讲者 Patrick 结合 Sphero 玩具和移动端经验，把枯燥的纯数学砍成七条接地气的规则，专门拯救被旋转代码折磨的同行们。

[Recaps]
第一段：为啥非要用四元数？大家平时喜欢用欧拉角 (Euler angles) 搞旋转，像抬头低头、左转右转这种，听着挺简单但有个致命毛病。当两个旋转轴接近重合时，就会发生万向节死锁 (Gimbal lock)，这时候角色或飞船会原地疯转，就像演讲里那个失控的宇宙飞船演示那样。而四元数 (Quaternion) 就是为了救这个场，它不依赖固定轴，怎么转都稳得住。最直观的理解是，它的虚部代表旋转轴，实部带着角度的一半，别看名字吓人，其实就是个带方向的向量加上一个标量而已。

第二段：演讲者总结了一套七大实用法则。首先，四元数之间的乘法就等于连续应用旋转，不过顺序很关键，像拿笔在手上一样，先转 Y 再转 Z 结果完全不同。其次，求逆运算不需要做复杂除法，直接取共轭 (Conjugate) 就是把虚部的符号全反一下，相当于反向旋转。还有最重要的动画过渡，别偷懒用普通的线性插值 (Lerp)，一定要用球体线性插值 (Slerp)，不然模型移动起来体积会忽大忽小。另外要注意引擎差异，比如 Unity 里四元数的存储顺序可能跟纸上推导的相反，写代码时得留个心眼。

第三段：实战里的避坑技巧和调试方法也都很干货。坐标系统是一大坑，从左手坐标系 (Left-handed coordinate system) 换到右手坐标系 (Right-handed coordinate system) 通常得把 Z 轴或者其他某个分量取反才能对齐。调试的时候，直接盯着实部 (w 或 s) 看，它的大小基本对应你转了多少度，比如实部为 0.9 大概就是转了 45 度左右，能帮开发者快速判断是不是逻辑写偏了。最后听句劝，别去纠结底层数学证明，相信工具库 (Library)，把精力放在怎么让旋转更平滑上才是正经事。多拿几个场景练手，比背公式管用多了。

## Math In Game Development Summit: Mathematical Analysis of Classic Card and Board Games
- **Speaker:** Nick Berry (DataGenetics)
- **Duration:** 1569 分钟
- **Category:** Math In Game Development Summit
- **Video Page:** https://www.gdcvault.com/play/1027341
- **Slide Page:** https://www.gdcvault.com/play/1027055
- **Custom ID:** 1027341

### Overview
In this presentation, Nick will show how simple mathematical techniques can be used to model classic card and board games such as Chutes and Ladders, Candy-land, Risk, Darts, Yahtzee, and Poker.You will learn about techniques such as Markov-Chains, Directed Graphs, Monte-Carlo Simulations, Probability Density Functions, and Bayesian and Frequentist Probabilities, and how these can be used to model games.The presentation is chock-full of graphs, animations, and videos to demonstrate the concepts and builds on these simple techniques to show how they can be employed to model more complex games.Learn techniques to analyze your own games to ensure they are balanced, fair, and good fun.

### Content Summary
[TLDR]
别瞎猜游戏平衡了，用蒙特卡洛和马尔可夫链数学建模，把概率算明白才是真本事。

[Background]
很多策划拍脑袋定数值，结果上线被玩家喷不平衡。这篇演讲分享如何用数学模型精准量化游戏规则背后的概率，帮咱们避开直觉陷阱，让数值设计有据可依。

[Recaps]
各位老哥，判断游戏公不公平，光靠直觉不够，得看数据。主要有两招：一是跑代码暴力测试，叫蒙特卡洛模拟 (Monte-Carlo Simulations)，就是拿随机数生成器疯狂开几亿局；二是数学建模，给系统画状态图，这招叫马尔可夫链 (Markov Chain)。前者准但累，后者快但难建。比如《黑杰克》里数牌，概率会变，但这模型假设“无记忆系统 (Memoryless System)"，只管当前不看过去，只要规则不依赖历史，这方法就特别好用。

拿《蛇梯棋》当例子，这是典型的无记忆状态。通过构建转移矩阵 (Transition Matrix)，我们能算出平均回合数到底是 20 还是 36，还能看出中位数是多少。像《糖果乐园》因为有抽牌机制，前一张牌影响下一张，就不是纯马尔可夫了，得用特化版本模拟。特别是最后几步，有些规则要求正好点数才能赢，有些不用，这在建模时必须作为特殊条件加进矩阵里，确保概率行相加为 1.0，否则结果会偏得离谱。

到了竞技类，《德州扑克 (Texas Hold'em Poker)》也得看人数，人越多顺子越常见，起手牌的价值也跟着变，同花牌价值就更高了。大富翁风格的《Risk》也很有意思，防御者平手即赢，所以进攻方手里得有至少 5 个兵才算稳赢，这时候的胜率才转正。这就是期望值 (Expected Value) 的计算，虽然风险大，但收益也高。还有《Yahtzee》这种骰子游戏，利用状态机算出三掷内摇出全同体的几率只有 4.6%，五个骰子全是目标点数就是个“吸收态 (Absorbing State)"，进去就不动了。

最后那个飞镖最实用，揭示了一个反常识的点。高手瞄准高分区，因为容错率低；新手如果乱瞄可能掉进低分区甚至脱靶，反而应该瞄准分高的区域边缘或者直接打中间保平均分。这得结合标准差 (Standard Deviation) 建模，画出高斯分布误差云，找到你技能水平下的最大收益点。简单说，就是别让手感骗了你，数据模型能告诉你啥才是最优解。

## Math In Game Development Summit: Getting There in Style: Intro to Interpolation and Control Systems

### Overview
Procedurally animating an object towards a desired position is ubiquitous in game development. Most developers know lerp, but struggle if lerp doesn't "feel right". When the target point is moving, or when the situation is continuous, instead of transition over a fixed duration, often additional layers of lerp, or other ad-hoc solutions are created. ### Content Summary
[TLDR]
告别生硬的数值跳变，善用 Smoothstep 与 PD 控制器，让你的动画和镜头系统丝般顺滑。

[Background]
很多新人写代码直接给数值赋值或简单插值，导致画面卡顿、速度突变很假。这篇来自 Valve 大佬的干货，专门给新手程序员解决这些“断崖式”变化的毛病，教你怎么用最基础的数学公式让操作手感变好。

[Recaps]
在游戏开发里，最烦人的就是东西动得太生硬，比如选框突然出现、子弹瞬间加速。这种场景最适合用定时过渡，但千万别只用基础的`线性插值 (Linear Interpolation)`，因为那玩意儿起停瞬间加速度是无穷大，物体动起来像机械一样死板。想要那种有重量感的顺滑效果？直接把时间参数套进`平滑步进 (Smoothstep)`，利用多项式曲线做缓入缓出，物理质感立马就回来了，这可是基础中的基础。

要是目标本身也在乱跑，普通的 Lerp 就显得特别假，角色容易在原地漂移或者反方向移动。这时候得换个思路，用`追逐式过渡 (Chase Style Transition)`。这招不记起跑线在哪，每帧只盯着当前差了多远，按比例吃掉剩余误差。不管目标怎么跳，角色永远是冲着目标直飞过去，逻辑更清晰，代码变量还能少存一个，避免很多低级 bug。

要是没有明确的结束时间，比如摄像机跟随或者 UI 缓冲，那就不是过渡了，得用`控制系统 (Control Systems)`。这里面有个常用的`一阶滞后 (First-Order Lag)`，本质是指数衰减，能消除突变但起步会有顿挫感，而且理论上永远碰不到目标。虽然很多人这么用，但这还不是最佳方案，因为惯性还是不够平滑。

终极方案推荐`PD 控制器 (Proportional-Derivative Controller)`，这就是经典的弹簧阻尼模型。它属于二阶系统，直接操控加速度而不是速度，所以起步不会猛抖。通过调节`阻尼比 (Damping Ratio)`和`固有频率 (Natural Frequency)`这两个科学参数，就能精准控制会不会过冲或震荡。建议默认设置为临界阻尼，既稳健又流畅，别再凭感觉瞎调数了，这才是老手的做法。

## Math In Game Development Summit: Conservative Mesh Decimation for Collision Detection and Occlusion Culling
- **Speaker:** Gino van den Bergen (Dtecta)
- **Duration:** 1886 分钟
- **Category:** Math In Game Development Summit
- **Video Page:** https://www.gdcvault.com/play/1027336
- **Slide Page:** https://www.gdcvault.com/play/1027097
- **Custom ID:** 1027336

### Overview
Collision detection and occlusion culling can be sped up considerably by reducing the complexity of the used triangle meshes. A popular method for decimating a mesh is the Garland-Heckbert algorithm. This approach uses edge contractions to reduce the number of triangles. The maximum error of the decimated mesh is bounded by a so-called quadric error metric (QEM). In this talk, properties of QEMs are discussed. We show what causes issues when using QEMs to find positions for newly created vertices and how to improve mesh quality. We show how to choose the new vertex positions conservatively, i.e. such that the decimated mesh either completely encapsulates the original mesh for the purpose of collision detection, or is completely encapsulated by the original mesh for the purpose of occlusion culling. Performance tweaks and termination criteria are addressed, and trade-offs are discussed.

### Content Summary
[TLDR]
针对动态地形，利用带约束的保守网格简化技术，在保证几何安全前提下大幅减少三角形面数以提升遮挡剔除效率。

[Background]
《模拟农场 22》团队面临动态可破坏地形的遮挡剔除难题，原有高精度模型无法直接用于软件光栅化处理，急需一种既能快速变形又能确保几何安全的简化方案。

[Recaps]
为了在巨大的可变地形上跑通遮挡剔除 (Occlusion Culling)，开发团队决定把原本高达两百万三角面的地形通过网格简化 (Mesh Decimation) 来瘦身。核心思路是利用边收缩 (Edge Contraction) 把多余的面合并，但单纯追求少面数不够，因为地形起伏变化会导致模型穿透或露馅，所以他们引入了四边形误差度量 (Quadric Error Metric) 来估算压缩后的形状偏差，这个指标比严格的哈斯多夫距离 (Hausdorff Distance) 算起来更高效，适合实时需求。

关键难点在于“保守性”，也就是简化后的地形不能突出来撞到玩家物体，也不能缩进去漏了本该被挡住的物件。这种为了保证几何安全的技术被称为保守网格简化 (Conservative Mesh Decimation)。传统方法解出来的新顶点位置容易飘到外面去，为了解决这个问题，作者加了个类似橡皮筋的机制，给顶点一个弹性拉力，强迫它尽量待在原位置附近。这样不仅避免了面片翻转，还防止生成了像针一样细长的畸形三角，让后续的碰撞检测更稳定可靠。

考虑到全量计算保守解太慢（耗时二十分钟），他们搞了个骚操作提速：在优先级排序阶段先忽略保守约束，只算最快的误差预估，等到选出真正要收缩的边时，再运行一次昂贵的保守解算器。此外，为了防止地块接缝处出现缝隙，边界顶点还被强制限制在垂直平面内移动。这套组合拳下来，把处理时间压缩到了半分钟内，完美解决了动态地形的大规模实时优化问题。

其次是怎么知道小车到底在哪。单靠车载传感器（IMU，惯性测量单元）容易漂移，就像人闭着眼走几步就偏了，所以他们搞了一套自家的 SLAM (即时定位与地图构建) 方案。利用扩展卡尔曼滤波 (Extended Kalman Filter)，结合 IMU 的运动预测和电脑视觉 (Computer Vision) 抓到的门框特征点，不断修正位置。就算你开得飞快把门框挡住了，系统也能根据之前的轨迹猜个大概，保证虚拟车身不会掉进墙里。

最后是关于玩家自己画的赛道怎么用。既然赛道是玩家家里摆出来的，没法预设地图，他们就搞了个赛道空间 (Trackspace) 的概念。玩家开一圈铺满路标后，系统就把这一圈定义成标准距离，比如 800 厘米长。道具、硬币、甚至红色的乌龟壳，都按这个赛道上的相对距离来生成。这样不管你家客厅多大，AI 都能顺着你画的线跑，不用担心跑到奇怪的地方去。

整个过程中，延迟和渲染是个大坑。他们发现强行追求快反而会露馅，最好的做法是等一帧完整的处理完再一起画出来，虽然会有毫秒级的延迟，但能保证画面和视频绝对同步。毕竟在混合现实里，一旦画面卡顿或者跟实物对不上号，沉浸感就全崩了。总结起来就是，别硬刚技术短板，盯着能稳住体验的功能死磕。

为啥这么重要？两个原因，一是学得块，二是回得快。你看那些搞特效或者建模的同学，每天要在 Maya、Unity、Unreal Editor 这些数字内容创作 (Digital Content Creation) 软件之间跳来跳去。如果平移、旋转、缩放 (TRS) 这种控制块的布局大家都一样，你哪怕闭着眼睛看坐标数值都能知道物体在哪。要是某个软件非要把 XY轴顺序调个反，那你每次换软件都得重新适应，脑子累不说，干活还慢。这就是为什么我们得像微软 Office 那样，把切复制粘贴这种基础控件的位置死死定住，形成肌肉记忆 (Muscle Memory)。

那在育碧具体是怎么做的呢？他们没搞什么大而无当的规范，而是做了一个内部的用户体验指南 (UX Guidebook)。步骤很简单：先摸清大伙儿手里都在用什么常用软件，比如 Outlook、JIRA、3ds Max 啥的；然后截图分析这些软件里相同功能的界面长啥样；最后找出共同点，提炼出几条最核心的推荐规则，控制在三到七条以内，别让设计师被厚厚的文档劝退。这本质上就是个精简版的组件库 (Pattern Library)，专门为了配合咱们公司内部的工具生态。

结论其实很直白：别总想着自己发明轮子，尤其是人家已经磨得贼顺溜的那些基础交互。花时间研究现有的成熟套路，做成内部规范推广给所有人用，这样不仅能让大家少踩坑，还能省下来的时间去琢磨真正难搞的技术挑战。所谓的直觉，不是凭空捏造的魔法，而是对行业惯例和团队习惯的最大尊重。

### Content Summary
[TLDR]
英伟达通过 NVTRX 分支为 UE4 提供光追优化方案，解决性能与功能痛点，提升开发效率。
[Background]
开发者在使用 UE4 进行光线追踪开发时常面临性能瓶颈和缺乏现成优化方案的痛点。本文适合希望深入理解 UE4 光追底层逻辑和落地实践的开发者和程序美术阅读。

[TLDR]
Unity Burst 默认优化已覆盖 99% 场景，安卓端极限压榨仍需手写 Neon 内联函数结合数据布局调优。

手机发烫掉帧让人头大，这场 GDC 分享展示了 Unity 和 Arm 如何联手优化移动端 CPU 性能。适合所有担心手机端卡顿的开发者，教大家在默认优化基础上再抠一点帧率，少走弯路。

[Recaps]
咱们首先聊聊核心主角 **Unity Burst 编译器 (Unity Burst Compiler)**。这玩意儿本质上是用 **LLVM 后端 (LLVM backend)** 把你的 C# 代码直接翻译成极致的原生机器码，让电脑少干活多出力。现场演示了一个物理模拟画面，开启这功能后，不仅帧率直接翻倍，设备还不容易过热降频了。演讲者强调，对于绝大多数情况，这个编译器自带的优化就已经能搞定，不用额外折腾。

那要是剩下的 1% 非要从 CPU 那儿再榨点血呢？这就得请出 **Arm Neon 指令集 (Arm Neon instruction set)** 里的 **Neon 内联函数 (Neon Intrinsics)** 了。别以为手写汇编级的代码就一定快，有个点积测试打脸了。虽然写了专用指令，但因为没做 **循环展开 (Loop unrolling)** 和优化，反而被编译器生成的代码吊打。后来他们研究透了指令组合，用了 SMLAL2 等高级指令才勉强赢了 20%。这说明啥？光懂指令不够，还得懂 CPU 架构的脾气。

最后是个碰撞检测的实战案例，这也是很多游戏最头秃的地方。这里有个巨大的误区：你以为代码写得紧就行？其实 **数据布局 (Data Layout)** 才是王道。原本大家以为需要复杂的计算，结果加个 `NoAlias` 属性告诉编译器数据不重叠，它立马能做 **自动向量化 (Auto-vectorization)**，性能直接暴涨几倍。像轴对齐包围盒 **(Axis Aligned Bounding Box)** 这种检测，通过调整数据结构，能把四组判断合并成一单指令处理。

总结一下，搞移动端优化真得讲究策略。别一上来就死磕汇编，先用好 Burst 的自动优化。真的遇到性能墙了，再上 Neon 内联函数，但这时候一定要注意数据拆分和尾数处理。而且千万记住，别在电脑上信誓旦旦，一定要用真机上的 **性能分析器 (Profiler)** 实测，硬件千差万别，只有真机跑的数才是实锤。

程序化这块的干货不少。他们搞了一套运行在 GPU 上的字节码表达式系统，用来判断哪里该放树、哪里该长草。关键是个“热区 (Hot Zone)"机制，只把摄像机附近的 3x3 地块数据加载进来计算，省内存。还用了 有向距离场 (Signed Distance Fields) 来算物体间的距离，比如离水近还是远。生态区域 (Ecotopes) 就是把海滩、森林分类，不同区域套用不同的生长规则。虽然工具很强大，但资产碰撞问题也没完全解决，有些得靠人工后期修补，不过大部分时候表现还好，算是运气加设计共同作用。

渲染层面也有黑科技。为了省显存和算力，他们用了 地形切片贴图 (Clipmaps)，提前把地形材质混合好存成几张图，渲染时直接采样，不用现场算太复杂的混合算法。还有个 代理集 (Proxysets) 技术，专门对付密密麻麻的植物和石头，把实例化管理移到了 GPU 端处理，极大降低了 CPU 开销。配合 随机实例衰减 (Stochastic Instance Falloff)，远处的景物能自动减少绘制，画面没太大损失但帧数稳了。最后还用了 基于深度的遮挡剔除 (Depth-based Occlusion Culling)，配合 极坐标搜索 (Epipolar Search) 填补相机移动时的空洞，解决了物体闪烁穿帮的问题。

整体经验就是：别指望一步到位，工具迭代要快。虽然编译慢了点、热区大小有限制，但核心思路是对的。如果你也在做开放世界，这种“小步快跑”的程序化管线值得参考。特别是他们在主机受限环境下还能玩出这么多花样，确实硬核。后续改进方向包括扩大热区、支持更大范围的高度编辑等，看来游戏技术永远在路上。

## Rope Simulation in 'Uncharted 4' and 'The Last of Us 2'
- **Speaker:** Jaroslav Sinecky (Naughty Dog, Inc.)
- **Duration:** 3415 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1027351
- **Slide Page:** 
- **Custom ID:** 1027351

### Overview
For Uncharted 4 a new rope technology had to be developed to allow for Drake's grapple rope and jeep winch to bend and wrap around collision while setting a new high bar for grapple rope presentation in games. In The Last Of Us 2 this technology was taken a step further to support rope puzzles where the player has the freedom to throw 14m of rope into the environment and pick it up at any point. This presentation will go over the history of development of this technology and the major challenges encountered on the way. Then it will dive into the details of the soft body simulation as well as the technique used to solve the problem of taut rope wrapping around collision.

### Content Summary
[TLDR]
游戏里的绳子别一股脑全扔给物理引擎，分清“视觉用的动态绳”和“玩法用的紧绷绳”才是正道。

[Background]
作者是 Naughty Dog 的资深开发，深知通用绳索模拟在商业游戏里极难搞。这次分享旨在解决“绳子物理感差”和“玩法交互卡死”的痛点，专门为想自建绳子的同行提供避坑指南和技术参考。

[Recaps]
演讲开头就定调子：别把一根绳子当一种算。团队分了两套方案，一套是动态绳索模拟 (Dynamic Rope Simulation)，用来做视觉效果，比如角色背包里的绳捆或者抛出去的绳子，允许有松弛；另一套是紧绷绳索模拟 (Taut Rope Simulation)，这是《神秘海域 4》抓钩玩法的核心，绳子必须时刻绷直最短路径，不能断链。这俩底层逻辑完全不同，千万别混着用。

讲技术细节时，先聊动态绳。作者用的是位置动力学 (Position Based Dynamics)，基础算法就是不断调整节点位置来防止拉伸和穿模。难点在于摩擦力计算不准，还有长绳子收敛慢。他们试过上 GPU，但发现由于求解过程串行，CPU 反而更稳。后来引入了多网格 (Multigrid) 和过松弛 (Over-relaxation) 来提速，还搞了一套针对碰撞平面的简化策略，确保性能不掉队。为了防穿模，他们还做了静态绳索张力分析 (Static Rope Tension analysis) 来估算接触力，让绳子能稳稳挂在柱子上不滑落。

至于紧绷绳，其实就是个求最短路径的问题。算法核心是交替进行移动阶段和碰撞检测阶段。端点要动到目标，中间碰到障碍物（凸边）就停住或滑过去。这里全是数学细节，特别是遇到多条边交叉的顶点时，得根据拓扑关系判断绳子往哪边滑。最棘手的是数值稳定性，稍微有点精度误差就会卡进墙壁里，所以容忍度设置非常讲究。像《神秘海域 4》里吉普车滑坡那段，虽然没人盯着绳子看，但这测试了算法极限，差点出丑。

最后总结了几个血泪教训。首先，没有完美的模拟系统，几何复杂度越高越容易出错，最好限制绳子活动的区域。其次，别低估调试的难度，作者强烈推荐自建基于内存环缓冲的调试工具，因为确定性回放能让你瞬间复现 BUG。总之，想拿绳子做核心玩法，这活儿比想象中大得多，小心别被物理引擎坑惨了，尽量简化环境模型，把精力花在刀刃上。

咱先得明白个道理，传统的日志记录 (Logging) 和监控图表根本不够看，它们都是事后诸葛亮，只能告诉你以前发生过的已知问题。真正的牛 X 是拥有可观测性 (Observability)，能让你在面对那种“莫名其妙”的卡顿或服务崩溃时，还能追根溯源，搞清楚到底哪一环掉链子了。演讲的大佬们强烈建议大家在代码里直接埋点，尤其是推行行业标准 OpenTelemetry (开放遥测)，别到时候想查数据发现手里没货。

具体咋整呢？分三步走。首先是在基础设施层，比如你跑在 Kubernetes (容器编排系统) 上的服务，可以直接利用自带的收集器抓取原始数据。其次是软件层，通过 SDK 把 API 请求和用户行为变成结构化数据发出去。最容易被忽视的是构建流水线，很多公司编译打包动辄几小时，有了 BuildEvents (构建事件) 这种工具，你就能看清是哪步操作卡了脖子，把构建时间从几小时压缩到十几分钟，效率提升那是杠杠的。

数据来了还得会看，这才是精髓所在。传统的指标 (Metrics) 报表只能盯着预设的几个维度硬看，但像 Honeycomb 这类工具支持实时聚合，能随时问出你之前想不到的问题。比如你能框选一段异常时间，自动给你“气泡提示”，告诉你为啥这一波请求特别慢，是因为某个特定国家的网络波动还是新版本的包有 Bug。这样上线前测漏，上线后修复都能快人一步，再也不用对着一堆毫无关系的 Dashboard 抓瞎了。

最后还得说说团队协同的事儿。以前开发组和运营组各管一摊，出了错互相甩锅。现在有了这套体系，大家拿着同一份数据说话，不管是排期、匹配系统还是支付交易出了问题，一眼就能定位到是不是服务器负载或者新版本代码的问题。记住啊，别迷信自动化运维把一切丢给 AI，核心还是要工程师手里有勺，自己去汤碗里搅一搅，才能知道味道咋样。

### Content Summary
[TLDR]
投影几何代数 (Projective Geometric Algebra) 用统一理论终结了图形变换的拼凑感，让旋转平移操作像加减法一样优雅高效。

[Background]
传统图形学处理三维变换全靠四元数 (Quaternions) 和矩阵硬凑，遇到点线面运算时公式混乱且难维护。本文献给对数学底层原理较真的引擎开发者，想彻底搞懂几何操作的来这。

[Recaps]
把传统的四元数 (Quaternions) 和对偶四元数 (Dual Quaternions) 比作游戏开发里的“缝合怪”，虽然能转也能平，但遇到点线面混合运算就露馅，本质上是因为数学体系不够完整。演讲核心是把齐次坐标 (Homogeneous Coordinates)、克拉普勒坐标等散碎知识统一进投影几何代数 (Projective Geographic Algebra) 的大框架下，不再需要死记硬背各种孤立公式。基础部分重点讲了格拉曼代数 (Grassmann Algebra) 里的楔积 (Wedge Product)，这是把低维对象组合成高维对象的工具，比如两点确定一线。

这里引入了“对偶性 (Duality)"概念，一个物体从不同角度看可以是点 (Point) 也可以是平面 (Plane)，通过补集操作可以实现无缝切换。同时把物体的属性拆成“体 (Bulk)"和“重 (Weight)"两部分，分别管位置信息和姿态信息，这种拆分让很多距离计算变得直截了当。高级玩法是引入了几何反积 (Antiproduct) 形成完整的几何代数体系，诞生了专门负责运动的“电机 (Motor)"和负责镜像的“反射器 (Flector)"。

相比旧的对偶四元数，电机 (Motor) 存储更省空间且更容易做插值，这在角色蒙皮动画里特别有用，能避免模型扭曲变形。电机本质上是螺旋运动算子，符合萨利定理，任何刚体运动都能表示出来。此外，整个数学体系在结构上达到了高度平衡，让复杂的几何变换变得可预测且易维护，比四乘四矩阵更高效。

### Content Summary
[TLDR]
FPGA 数学运算别照搬 CPU 思路，掌握位级优化与专用算法，能实现千倍性能提升并大幅降低硬件成本。

[Background]
很多做硬核开发、模拟器或自研硬件的朋友，容易把 CPU 那套浮点库直接搬进芯片里，结果又慢又占资源。这篇干货就是为了教大家如何用“底层思维”在 FPGA（现场可编程门阵列）上写数学函数，避坑省时。

[Recaps]
FPGA 上的算数和 CPU 完全是两码事，直接用厂商库只能获得一点点并行，真正能快上千倍的是位级优化。比如平方运算，利用二进制乘法里的对角线对称性，能砍掉大量重复位的计算开销。输入如果是定点数 (Fixed Point)，还可以根据数值范围用查表或低阶多项式来近似，整个流程甚至能流水线化到每时钟周期输出一个结果。

常数乘法和除法也有骚操作。乘以常数不必用整块乘法器，可以用移位加加减减组合，还能查预计算的表格找最优表达式。有个叫 Ken Chapman’s Method (KCM) 的技巧，把输入拆成小段查 查找表 (Lookup Table) 再相加，特别适合乘以像π这种实数。除以小整数更不用全 Divider，分段查余数表或者用乘法加法凑一下就能搞定。

生成复杂函数如开方、三角函数，核心是 逐位回归算法 (Digit Recurrence)。虽然传统方法耗时许久，但配合高基数迭代或流水线就能提速。泰勒展开式很适合 FPGA，因为幂次越高位数越短，乘法器也能跟着变窄。这里引入了 比特堆 (Bit Heap) 的概念，只保留有效位，配合 压缩树 (Compressor Tree) 统计每一位的数量，开源工具 FloPoCo 能自动生成这些电路代码。

最后提了几个经典招式。50 年前的 CORDIC（坐标旋转数字计算机算法）依然有用，通过调整参数能算正弦余弦或对数，不过要注意输出有缩放系数得修正。大范围的 查找表 可以用 双部分表 (Bipartite Table) 拆分索引来节省空间。还有用矩阵运算生成的 离散振荡器 (Discrete Oscillator)，能动态调频调幅，只要记得加个自动增益控制防止波形发飘就行。

传统粒子系统太费人，地形一变发射器就得重摆，而且 CPU 读 GPU 数据慢如蜗牛。本文分享了 Naughtly Dog 如何用屏幕空间信息自动化处理《最后生还者 2》里的雨天细节和血腥场面，给程序同行省点心也省内存。

最后吐槽一下调试，这种复杂的 Shader 逻辑不记日志根本排错。这套方法虽然不能保证 100% 完美（比如被遮挡），但性价比极高，还能触发游戏事件（比如被雨淋到做受击动作）。不仅限于血和水，下雪、虫子爬行都能套这思路。总之就是把屏幕里的像素变成超级强大的传感器，让物理效果动起来更有灵魂，开发者只要把管道搭好就能用。

再说身体形变和工具流。为了做艾比那种夸张肌肉效果，团队开发了一套热图聚类工具，自动生成最优骨骼位置替代硬编码。最绝的是搞了个 Look Manager（外观管理器），把 Maya 编辑器和游戏引擎的数据彻底打通。之前艺术家常遇到的“软件里看着对，进游戏就崩”的头疼事基本消失了，而且支持实时编译 C++ 代码到插件，调试起来丝般顺滑。NPC 那边还做了 LOD（Level of Detail, LOD）降级处理，远处的 Crowd 骨骼直接减半，性能省下来了还不影响视觉。

最后是那个让人血脉喷张的 gore 系统和细节落地。他们没搞一刀切，而是定义了通用的伤口覆盖层 (Gore Cap)，不同武器对应不同伤害区域，甚至尸体腐烂、血迹流淌都能程序化处理。背包也不是死物，加了物理碰撞让辫子和装备互不穿模。这些看似不起眼的小设计，比如角色整理衣领、下雨披斗篷，其实才是让玩家相信这个世界真实存在的关键，这才是真正的次世代水准。

- **Speaker:** Mangal Srinivasamurthy, Brian Trevethan (Microsoft, Microsoft)

### Overview
Migrating technology stacks can be scary. But it doesn't have to be. This talk will show you how Mojang ported Minecraft Realms from a custom infrastructure-as-a-service implementation to a managed solution running on Azure, while limiting impact to players.

### Content Summary
[TLDR]
从 AWS 搬往 Azure 虽然痛苦且耗时，但善用托管服务如 PlayFab 和多阶段迁移策略，能彻底卸下运维包袱，让团队回归游戏开发。

[Background]
微软收购 Mojang 后，决定将核心服务 Minecraft Realms 从 AWS 搬迁至 Azure。历经两年，团队踩过大量技术和管理坑，现总结实战经验，供想做大规模云迁移的开发者避坑参考。

[Recaps]
这次搬家其实分两步走，首先是干掉那些繁琐的基础设施维护代码。主讲人 Brian 提到，最好的代码是用 Delete Key 敲出来的。他们没硬抗，而是引入了 PlayFab 多人服务器 (PlayFab Multiplayer Servers)，让微软自家的这套方案来负责管理虚拟机 (Virtual Machine) 池的扩容缩容。以前还要自己在机器上跑 Agent 代理脚本收发指令，现在全靠 API 调用，不仅减少了故障点，还半夜不会被报警电话吵醒。世界数据方面也没搞一刀切的全量复制，而是采取懒加载策略，玩家第一次玩的时候再从 AWS 的 S3 存储拉到 Azure 的 Blob 里，既平滑了流量压力，又避免了长时间停机。

第二步是核心数据库和服务器的迁移，这里坑更多。DBA 同学用了 Azure 数据库迁移服务 (Azure Database Migration Service) 配合 VNet 网络互通。最惨痛的经验教训来自带宽和版本问题，一开始选了错误的站点到站点虚拟专用网络 (Site-to-Site VPN) SKU，导致生产环境流量扛不住，后来才发现得提前压测。数据库版本也是，AWS 上的 MySQL 5.6 性能和 Azure 原生版有差异，硬着头皮升级到 5.7 才解决了性能瓶颈。为了安全起见，他们采用了蓝绿部署 (Blue-Green Deployment)，两边都跑一遍代码再切流量，确保随时能回滚。

最后聊聊血泪成本和管理心得。这次迁移光数据搬运就花了 300TB，用了 Azcopy 工具并行跑了好久。最直观的是成本翻倍，因为要同时维持两套环境运行。技术上缺乏自动化测试也是个雷，迁移过程中还是出过几次小宕机。人力方面更是个痛点，程序员都不喜欢干这种枯燥的基建活，得靠调整人员配置才能凑齐靠谱的攻坚组。总的来说，这活儿肯定能成，但要做好长期作战的准备，毕竟没有哪个人是抱着修服务器的热情入职的，目标还是得放在让玩家玩得爽上。

## Azure PlayFab Multiplayer Servers Quick Start (Presented by Microsoft)
- **Speaker:** Dimitris Gkanatsios, Lester Jackson (Microsoft, Microsoft)
- **Duration:** 1851 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1027496
- **Slide Page:** 
- **Custom ID:** 1027496

### Overview
This session is an introductory level overview of Azure PlayFab Multiplayer Servers, with guided steps demonstrating (a) how to wrap an existing game server with the PlayFab Multiplayer Game Server SDK and (b) deploy the game server in Azure PlayFab Multiplayer Servers hosted service. We'll use a Linux build of an open-source game named OpenArena, a clone of the popular first-person-shooter Quake III. Because MPS requires Docker containers for Linux builds, we'll also demonstrate how to build, package and deploy a Linux container into Azure PlayFab Multiplayer Servers.

### Content Summary
[TLDR]
借助 Azure PlayFab 和 Docker 技术，开发者无需关心底层运维，即可实现多人游戏服务器的云端自动扩缩容。

[Background]
传统自建多人游戏服务器运维成本高、门槛高。本演讲分享如何利用 Azure PlayFab 服务，把复杂的后端基础设施封装成“黑盒”，让玩家连接像搭积木一样简单。

[Recaps]
咱先说结论，这次 GDC 其实就是教大伙儿如何用 Azure PlayFab 多机服务 (PlayFab Multiplayer Server) 来搞定多人游戏的服务器托管。以前咱们自己做联机服务器，那是真得自己买机器、配网络、搞负载均衡，属于是给后端开发挖大坑。现在人家基于 Azure 计算服务 (Azure Compute Services)，把你的游戏直接打包成 Docker 容器 (Docker Container) 扔上去，剩下的扩容、全球分发全自动化。说白了，就是把运维的脏活累活全包圆了，让策划专心优化玩法，别操心服务器动不动就炸。

想让云平台认你的服务器，第一步得集成游戏服务端 SDK (Game Server SDK), 业内常称 GSDK。这库是官方开源的，Unity 和 Unreal 都能用。你得动代码，主要是两个接口，一个叫 Start，启动后发心跳告诉平台我还活着；另一个叫 ReadyForPlayers，表示加载完了，现在进入待机状态。演示里用的 OpenArena 是个老 FPS，开发者没敢动源码，而是套了个 .NET Core 的外壳，靠监听日志输出来触发接口，这种“白盒化”的封装手段对老项目移植特别香，不伤原文件。

具体干活分三步。第一是在本地环境测试，比如在 Windows 上装 Windows 子系统 (Windows Subsystem for Linux) 配合 Docker，再用本地多玩家代理 (Local Multiplayer Agent) 模拟客户端验证流程对不对。第二步是把镜像推送到 Azure 容器注册表 (Azure Container Registry)，最后在游戏管理后台建个 Build，设定好每个虚拟机里跑几个进程、备着多少个空号。第三步就是通过 API 分配会话 ID，系统会自动处理端口映射，玩家拿到 IP 就能连进去了。要是出 bug，还能直接 SSH 登录到那台虚拟机里查日志，debug 非常方便，比在那瞎猜强多了。
