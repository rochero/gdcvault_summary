## Stylization with a Purpose: The Illustrative World of TEAM FORTRESS 2
- **Speaker:** Jason Mitchell (Valve Software)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/279
- **Custom ID:** 279

### Overview


### Content Summary
[TLDR]
用复古插画风结合自研渲染算法，确保战斗信息清晰可读，打造经得起时间考验的经典 FPS。

[Background]
多人射击游戏最容易翻车的就是战场混乱看不清人。Valve 这帮画师和技术大佬憋了个大招，揭秘《军团要塞 2》如何通过独特的艺术设计和底层图形学黑科技，解决识别度问题，顺便聊聊游戏长寿秘诀。适合美术策划和技术美术想提升画面表现力的兄弟参考。

[Recaps]
首先得明白为啥要把画面做成这样。核心就是为了“可读性 (Readability)"和“品牌化 (Branding)"。传统的写实风格有时候太乱，容易让玩家分不清谁是敌谁是友。团队决定走复古商业插画路子，参考 20 世纪初的大师作品，比如 J.C. Leyendecker。阴影不涂黑色，而是往冷色调偏移，高光往暖色调偏移。最关键的是不用黑线描边，而是用边缘亮光把角色轮廓勾勒出来，这在业内叫“轮廓光 (Rim Lighting)"，保证角色在任何背景下都能跳脱出来。

技术上这部分是最硬菜。大家习惯的光照模型是写实的，但这游戏玩的是“非真实感渲染 (Non-Photorealistic Rendering, NPR)"。他们修改了经典的“半兰伯特 (Half Lambert)"光照曲线，让光照可以绕到物体背面一点点，避免死黑。再加上“视图相关 (View Dependent)"和“视图无关 (View Independent)"的光照项叠加，配合一个类似“菲涅尔 (Fresnel)"的侧逆光效果，相当于手动给角色加了个虚拟背光灯，彻底解决了角色和环境融合的问题，保证了战场上的绝对清晰。

环境设计也花了心思。红蓝两队的基地风格完全相反，一方是自然粗犷，另一方是工业规整，通过材质色调 (Material Hue/Value/Saturation) 和几何形状来区分阵营。贴图风格模仿印象派油画，既美观又有层次感。加上配套的角色短片，不仅丰富了内容，还让每个职业的性格深入人心，甚至形成了玩家社区的亚文化。

最后聊聊上线后的运营策略。这游戏不是做完就不管了，靠着 Steam 平台的快速更新机制，Beta 测试后发了 28 次补丁。不管是修复漏洞、出新武器还是新模式，始终保持活跃。这告诉我们，好美术只是第一步，长期的技术支持和社区互动才是让一款 multiplayer 游戏活十年的关键。

## Stupid Spherical Harmonics (SH) Tricks
- **Speaker:** Peter-Pike Sloan (Microsoft)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/273
- **Custom ID:** 273

### Overview


### Content Summary
[TLDR]
用球谐函数 (Spherical Harmonics) 做游戏光照虽高效，但得学会处理振铃效应 (Ringing) 并懂得利用窗函数优化代码才行。

[Background]
当年为了在显卡性能捉襟见肘的时候搞定高质量实时光照和全局照明 (Global Illumination)，开发组常拿球谐函数 (Spherical Harmonics) 压缩环境光数据。但这东西一旦处理不当，画面容易出现诡异的“鬼影” (Ringing)。这篇就是微软老哥总结实战经验，专门教程序员怎么把这堆数学公式落地又不翻车。

[Recaps]
说白了，球谐函数 (Spherical Harmonics) 就是三维版的傅里叶级数，把球面上的光照信息变成一串系数 (Coefficients) 存起来。以前我们得存整个立方体贴图 (Cube Map) 或者环境探针 (Light Probe)，现在直接用这几个系数就能代表光照了。好处是旋转特别稳，不会因为角色转来转去灯光就乱跳产生锯齿，比之前 Valves 搞的 Ambient Cube 基更平滑。核心用法主要是生成辐照度环境贴图 (Irradiance Environment Maps)，这对漫反射材质特别有用，还能算上软阴影和间接反弹光。

不过这玩意儿有个大坑，就是截断次数不够的时候会出现吉布斯现象 (Gibbs Phenomenon)，也就是所谓的振铃效应 (Ringing)。简单说就像你切蛋糕切歪了，边缘会有多余的波浪纹。尤其在 HDR 高动态范围光照下，那些不该有的负值会导致颜色发紫或发蓝，非常难看。解决的办法一般是用窗函数 (Windowing Function)，比如把高频的系数强行压平一点点，牺牲一点锐度换取干净的画面。还有种高级点是内容感知窗函数 (Content Sensitive Windowing)，只在高光区不模糊，暗部再降噪，这样看起来更自然。

除了渲染，还得考虑计算成本。两个球谐函数相乘（比如遮挡关系乘以光照）通常很费事，但如果其中一个固定不变，可以提前算好一个乘积矩阵 (Product Matrix)，这样运算量直接减半。另外要是遇到旋转对称的光源，用轴对称谐函数 (Zonal Harmonics) 会比通用球谐快三倍。最后推荐兄弟们写代码前先用符号数学软件（如 Maple）推导一遍公式，别自己瞎按计算器，顺便参考一下 DirectX SDK 里的现成实现，能省不少 debugging 的时间。

## How to Go from PC to Console Development without Shooting Yourself in the Foot
- **Speaker:** Elan Ruskin (Valve)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/249
- **Custom ID:** 249

### Overview


### Content Summary
[TLDR]
主机移植别想最后补票，从立项起就按最严标准和架构来搞，虽然辛苦但能反哺 PC 版质量。
[Background]
Valve 老哥总结自家搬砖经验，专治跨平台开发中的效率低、认证挂、内存爆等疑难杂症，适合任何想啃下主机这块硬骨头的游戏团队。
[Recaps]
Valve 这哥们掏心窝子讲怎么从 PC 转主机还不死机。首要任务是组好队，找个懂规则的兄弟吃透“技术认证要求 (Technical Certification Requirements)"，不然过审能把你整崩溃。PC 开发爽，主机调试累，得稳住 PC 主线，别瞎折腾资产格式，尽量让工具自动兼容平台差异。人员上要分派专人维护开发套件，别让核心程序员陷入琐碎的环境搭建。

内存这块儿是命门，主机那点 RAM 根本不够挥霍。别再搞什么“动态分配 (Dynamic Allocation)"，随机申请内存就像开盲盒，容易随时崩盘。建议自己造个轮子，弄个“自定义内存分配器 (Custom Memory Allocator)"，每一笔开销都记清楚。资源压缩得狠一点，别等上线前再砍内容，那时候黄花菜都凉了。

还有加载速度和画面也得拿捏。主机厂商强制要求“异步加载 (Asynchronous Loading)"，同步读写就是卡玩家的元凶。CPU 架构也不一样，x86 之外的那些老古董指令比较直，乱堆代码掉帧严重，得用上"SIMD 指令 (SIMD Instructions)"来榨干硬件性能。联机部分更要早点介入，局域网测试骗不了人。总而言之，按主机标准死磕，回头再看 PC 版，那叫一个流畅丝滑。

## Fast Water Simulation for Games Using Height Fields
- **Speaker:** Matthias MÃ¼ller-Fischer (AGEIA)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/203
- **Custom ID:** 203

### Overview


### Content Summary
[TLDR]
拒绝 3D 粒子流，用高度场 (Height Field) 降维计算，低成本实现游戏内稳定且逼真的水面效果。

[Background]
传统离线渲染太慢，游戏每帧只有十几毫秒预算。演讲者分享如何用高度场 (Height Field) 技术把 3D 流体压成 2D，适合想做大面积水域效果的程序猿。

[Recaps]
核心就是把水面看成一堆垂直水柱的集合，每个格子存个高度值 u，再配个速度值 v。这不就是简单的二维数组嘛，利用波动方程 (Wave Equation) 算水波咋扩散。有点像弹簧，周围高了就把你压下去，低了就弹上来，这样波浪自然就动了。

为了让这模型在游戏里不崩，还得加阻尼 (Damping) 和限制最大坡度，不然数值会爆炸。物体丢水里也不用算复杂碰撞，直接占位就行，剩下的水往旁边挤，这就是阿基米德原理。边界处理也讲究，开放边界的波浪能直接出去不反射，看着就像大海。

视觉效果全靠“作弊”，底模简单但着色器 (Shader) 搞得精细，反射折射全是贴图骗过来的。浪太大就发射粒子系统 (Particle System) 模拟飞溅，平时不动也不亏。最后建议直接用 PhysX SDK 的现成功能，自己写也就是几行代码的显式欧拉积分 (Explicit Euler Integration) 逻辑，性价比极高。

## Designing and Implementing a Dynamic Camera System
- **Speaker:** Phil Wilkins (SCEA Santa Monica)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/192
- **Custom ID:** 192

### Overview


### Content Summary
[TLDR]
别再用代码硬写摄像机了，这套分层架构能让策划主导视角设计，实现丝滑且无碰撞的自动运镜。

[Background]
传统游戏自动转场容易穿模卡顿，还得程序死磕。本讲座来自索尼开发者，专门解决如何让设计师能自定义、同时保证镜头安全顺滑的系统方案。

[Recaps]
这系统的核心思路就是分层管理，把镜头控制拆成了五大模块，最基础的是“区域划分 (Zoning)"。简单说就是把地图切成不同区块，每个区块里藏好静态机位，当玩家进入哪个区，系统就根据“优先级 (Priority)"挑选合适的机位接管视角，不用玩家动手，也不会穿墙。为了让挑出来的镜头切换不突兀，系统维护了一个“提交列表 (Submission List)"，新的相机请求会被插入顶端并按时效排序，确保始终显示最新的意图。

有了机位还得动起来，这里涉及“动态控制 (Dynamics)"和“混合过渡 (Blending)"。动态部分主要是给镜头加约束条件，限制它对准玩家的角度或距离世界平面的远近，防止飞出去。过渡则是关键，不能硬切。演讲里提到了用“希尔德米特样条曲线 (Hermite Spline)"配合“定时列表 (Timer List)"来做“缓动函数 (Ease function)"，引入“混合空间 (Blend Space)"的概念，让镜头在两个状态间平滑过渡，就像音乐淡入淡出一样自然，彻底消除机械感。

更高级的玩法是“轨道 (Rails)"和“场域 (Fields)"。轨道让镜头像电影摇臂一样沿着预设路径滑动，根据角色离路的距离计算权重，决定镜头该贴多近。而场域则更进一步，直接用数学公式算出连续的值来混合镜头，而不是像区域那样跳变。最后还提了处理多个目标、画面抖动这些细节，整体就是为了打造一个程序员少操心、美术策划能随便折腾还能保持体验稳定的自动运镜神器。

## CRYSIS Next-Gen Effects
- **Speaker:** Tiago Sousa (Crytek)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/247
- **Custom ID:** 247

### Overview


### Content Summary
[TLDR]
通过高效的渲染管线与巧妙的后期优化，让中端硬件也能跑出高保真次世代画面效果。

[Background]
Crytek 团队揭秘《孤岛危机》开发时的技术攻坚，重点讲怎么在画饼（性能）有限的情况下，把水面、冰雪和后期做得逼真又流畅。适合想了解底层优化逻辑的开发者或技术美术。

[Recaps]
先聊聊最吃资源的水面，人家没用那种死板的静态贴图，而是用了统计学的 Tessendorf animation model (泰森多夫动画模型)。这算法跑在 CPU 上算波动数据，再丢给 GPU 做顶点偏移，既真实又省资源。反射这块更是狠活，本来一加反射就要增加 1500 个 draw calls (绘制调用)，最后硬是优化到平均 300 个，用的是半分辨率的 Render Target (渲染目标) 配合动态更新机制，还加了 Anisotropic Reflection (各向异性反射) 防锯齿，这波血赚不亏。

再看那个“冻土”特效，很多人觉得得逐个模型调整，太累了。Crytek 直接上了程序化思路，不用特制资产，直接把雪积在模型顶，根据法线方向混合，再用 3D Perlin noise (珀林噪声) 搞点随机纹理变化，加点闪光粒子特效，视觉上就很有质感。唯一的缺点是依赖光照，光照不行看起来就没那么像冰原，但这属于低成本下的最优解。

最后说说后期特效，核心思想就是“能省则省”。运动模糊分两层，先是 CMB (Camera Motion Blur)，再是 OMB (Object Motion Blur)。他们不搞全图计算，而是先算 Velocity Mask (速度遮罩)，有动的地方才算模糊，没动的地方直接跳过。还有著名的 Sun Shafts (阳光光束)，本质是投影加径向模糊，配合 Color Grading (色彩分级) 调色调。总结一下，想在现有硬件上骗过玩家眼睛，就得在精度和性能之间找平衡，这锅 CPU 和 GPU 还是要背。

## Creating a Character in DRAKE'S FORTUNE
- **Speaker:** Christian Gyrling (Naughty Dog Inc.)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/190
- **Custom ID:** 190

### Overview


### Content Summary
[TLDR]
大狗工作室靠解耦架构与叠加动画技术，让少人手也能产出高质量、多变化的角色动作数据，性能表现还杠杠的。

[Background]
PS3 次世代刚出那会儿，大家指望动画量翻十几二十倍，但人手根本没增加。Naughty Dog 这演讲就是为了救急，分享他们在一个程序员配一个动画师的情况下，怎么搞定复杂动作逻辑和资源迭代，给想学动作架构的同行提个醒。

[Recaps]
这次演讲的核心痛点是资源跟不上需求。以前是一代主机，现在要面对几十倍的动作量，还得兼顾 AI 逻辑。他们没法把所有东西都做到极致，只能挑重点打磨，比如战斗和掩体系统。为了解决美术资产制作慢的问题，他们把相关的动画文件合并到同一个 Maya 工程里，减少了加载冲突。更狠的是做了一个游戏内测试工具，新做的动画几分钟就能进游戏调试，比传统流程快得多，这样即便只有一两个动画师盯着一个人物，也能快速验证关键帧，减少 Bug 排查的时间。

架构设计上，他们把复杂的逻辑藏起来，不让 AI 直接调底层。整个系统围绕 动画状态 (Animation State) 转成核心，每个状态里定义了切换规则和混合曲线。AI 不需要知道具体跳什么舞步，只要发个“进入掩体”的指令就行，由 动画控制器 (Animation Controller) 去处理。为了区分不同层级的动作，比如跑动和脸部表情互不干扰，引入了 动画层级 (Animation Layer) 的概念。最上层负责基础移动，中层处理特殊动作，下层管面部，最后统一合成。同时还有一个 动画信息 (Animation Info) 接口，专门用来处理微调，比如瞄准角度或者转向这种小改动，不需要改变当前的 动画状态 (Animation State)，避免频繁刷新脚本效率低。

为了让角色看起来不死板且内容丰富，他们大量用了 叠加动画 (Additive Animations)。比如想要“累了的跑步”，不用重新录一套动作，直接在基础跑步上加一层上半身疲惫数据，混合后效果自然，省了大量内存。以前做眼神追踪常犯僵硬毛病，用了基于骨骼的 程序化反向动力学 (Procedural IK) 又容易穿模，改用叠加动画就能保留主体动作纹理。针对 动作包 (Action Packs)，比如上车或打掩体，他们设定了两个定位器，世界坐标直接驱动动画。最后，他们还用极短的帧叠加姿势来制造多样性，60 多种死亡方式、70 多种受击反应，都是靠基础素材组合出来的，既保证了视觉丰富度，又把性能开销压到了最低，甚至能在 SPUs 上几乎免费地进行混合运算。

## Adventures in Data Compilation and Scripting for UNCHARTED: DRAKE'S FORTUNE
- **Speaker:** Dan Liebgold (Naughty Dog, Inc.)

通过自研的数据编译系统模糊代码与数据界限，让配置调优既享受脚本灵活性又有 C++ 的性能。

[Background]
2008 年 GDC 上，顽皮狗资深工程师 Dan Liebgold 分享《神秘海域》开发背后的工具链革新。为解决传统引擎中“非代码非数据”的配置难题，他揭秘了一套能自动将高级脚本转为底层结构的实用方案。

[Recaps]
老哥们做游戏开发都懂个理儿：有些东西必须写成**代码 (Code)**，有些则是静态**数据 (Data)**。但像**粒子定义 (Particle Definitions)**、**动画状态及混合树 (Animation States & Blend Trees)**、任务脚本这些玩意儿，经常卡在中间尴尬区域。顽皮狗早期用过很多种 Lisp，但后来停了，急需个新办法替代旧工具的功能，同时还得保留 Lisp 那种**代码即数据 (Code-as-Data)** 的独特优势。

于是团队搞了个基于 Scheme 的**数据编译 (Data Compilation)** 系统。这系统的骚操作在于，你可以在脚本里定义**类型 (Type Definition)**，比如一个向量结构，它会自动翻译成 C++ 的结构体。这不仅省去了手写的转换工作，还能利用 Lisp 风格的**宏 (Macros)** 和**符号表 (Symbol Table)** 来扩展功能，让数据结构既高效又灵活。

最后这套东西被广泛用在各种调优场景里。无论是**武器平衡 (Weapon Balancing)**、音效配置还是剧情关卡控制，都能直接在脚本里定义并通过导出接口供 C++ 运行时查找。这就好比给策划开了个上帝视角，不用重新编译整个引擎就能调整复杂参数，真正实现了好记又好用的高性能开发流。

### Content Summary
[TLDR]
Valve 资深技术大牛揭秘如何通过智能算法，在 DX9/DX10 及主机硬件差异下，完美统一多平台的光照色彩与动态模糊效果。

[Background]
做跨平台开发最头疼的就是不同机器表现不一样，PC 和 X360 的渲染管线简直就是两个物种。这篇演讲主要给图形程序员看，聊聊 Valve 当年怎么在《橙盒》项目中填平这些技术鸿沟，把光追前的老本行做到极致。

[Recaps]
说到调色这块，最早 DX9 和 DX10 以及主机上的 Alpha 混合 (Alpha Blending) 规矩都不一样，直接贴图会导致烟雾、光晕忽明忽暗。Valve 发现 PC 用的是真实 sRGB (sRGB) 曲线，而 X360 是个分段线性的近似值。解决办法很简单，要么改着色器 (Shader) 代码模拟曲线，要么让美工预处理纹理。最后大家选了后者，只改了四千个材料里不到五十个，既快又省事儿。但要注意硬件自带的 sRGB 读取在黑暗端有精度损失，做后期特效时得自己手写计算别偷懒。

关于 HDR 的高动态范围色调映射 (Tone Mapping)，最初他们用直方图 (Histogram) 算中位数亮度来自动调整屏幕亮暗，结果发现天黑场景太死，大火场景反而被压暗。后来换了套逻辑：保留前百分之九十五的高亮像素作为上限，同时用中位数作为防过黑的下限。为了防止闪烁灯光导致画面呼吸，还加了一个“粘性箱”机制，让数值变化更平滑。这套组合拳下来，不仅解决了画面发灰的问题，还能防止因为灯光闪烁导致的频闪眩晕。

最后是动态模糊 (Motion Blur) 的实现，为了省内存和性能，他们决定不搞复杂的全场景模糊，只做摄像机旋转产生的视差。比如低头左转的时候，画面会轻微滚动，这个效应用简单的向量叠加就能实现。特殊场景还得特殊处理，像传送门掉落时要手动生成向前运动向量；遇到系统卡顿丢帧超过 0.1 秒，就直接关掉模糊防止糊成一团；帧数跌到 30 以下也要缩减模糊强度，不然容易晕车。这一套流程下来，九成以上玩家根本察觉不出背后的优化细节。
