### Overview


### Content Summary
[TLDR]
为了践行玩家至上的使命，团队摒弃过度设计，利用弹性架构与全链路监控，实现在规模剧增下服务的稳定与内容无门槛开放。

[Background]
这位来自拳头游戏的首席可扩展性架构师，讲述了如何把《英雄联盟》从一个测试服推向数百万人的运营过程。针对技术迭代快与玩家体验要好的矛盾，给同行提供了高并发服务落地的真实案例。

[Recaps]
首先得明确一点，技术是为玩家服务的，而不是反过来。拳头公司有个铁律，如果一个新功能上线后不能让所有人马上玩，那就是给玩家送“烂圣诞礼物”，只会惹毛大家。所以在技术选型上，他们不迷信所谓的新潮语言，而是选 Java (Java) 这种生态成熟、招人容易的技术栈。底层数据存储则用了非关系型数据库 (NoSQL) 比如 Oracle Coherence (Oracle Coherence)。这套组合不仅能轻松实现水平扩展 (Horizontal Scaling)，还能让工程师像调用本地内存一样操作分布式集群，一行代码就能并行跑几百个核心，完全不用操心底层的传输管道问题。

其次，架构设计的黄金法则就是“越简单越好”。千万别搞过度设计，复杂往往是质量的敌人。他们有个叫“预先分配工作”的策略，就是把输入数据提前切分好，直接交给对应线程处理，比那种复杂的线程同步协调要干净得多。而且系统必须是动态的 (Dynamic System)，配置项不能写死在代码里，服务器挂了或者外部网络抖了，系统都得能实时拉取新配置或自动摘掉坏节点，绝不能让用户感觉到停机维护。

最后是监控与测试。别指望运维人员盯着日志大海捞针，一切全靠自动化 (Automate)。他们有一套每日对比报告，哪里的数据指标红条出来了就立刻报警。更关键的是自愈合机制，让服务器根据健康状况自己决定是不是下线，宁可牺牲单机也要保玩家体验。测试方面，压力测试 (Load Testing) 是常态，甚至主动破坏机器来验证容错能力。切记，文档里写的容灾方案往往不灵，只有真刀真枪测出来的数据才敢信。

## You Got Art In My Test Suite!
- **Speaker:** Seth Gibson (Intel Perceptual Computing)

### Overview
When developing a test suite for Technical Art tools, one of the main considerations that should be addressed is that many components of a Tech Art codebase are designed to operate on art content, and as such, should be tested against art content. Fortunately, Maya's Python integration provides the necessary functionality for addressing this consideration. This poster session introduces the concept of "unit test content", which can take the form of simple art files included within a test suite for testing art-specific code, or scenes generated by a test case at runtime. Topics covered include setting up a Python IDE to recognize Maya's native Python interpreter, using Maya's Python interpreter with external unit testing frameworks, and best practices for building test cases that incorporate unit test content.

### Content Summary
[TLDR]
善用 Google 服务栈与浏览器底层特性，从架构到变现全方位优化 Web 游戏性能与体验。

[Background]
2012 年网页游戏刚起步，常遇卡顿、掉线、收费难问题。作者作为谷歌开发者代表，分享如何用云服务 + 浏览器新特性，把网页游戏做到能跟客户端一样流畅且好赚钱，适合想做大流量 Web 游戏的开发者阅读。

[Recaps]
老手都知道，Web 游戏最怕的就是服务器扛不住和加载慢。资源别一个个往回传，打包成资源归档 (Archiving) 最划算，配合浏览器的缓存机制，能让页面秒开。后端推荐使用应用引擎 (App Engine)，数据库和查询结果都要加内存缓存 (Memcache)，别总去扫硬盘，把缓存过期时间设好，服务器压力直接减半。遇到大文件传输，可以用 Blob 存储 API (Blobstore API) 来扛，这招能把复杂的文件逻辑变得像静态网页一样简单。

至于跑起来稳不稳，得防着点显卡驱动的坑。程序得自己检测是不是被屏蔽了，不然一玩就崩。玩家切出网页干别的事时，游戏得懂事儿点，通过可见性变化 (Visibilitychange) 事件自动挂起或降频，不然电量狂飙还发热。报错不能光甩代码，得抓环境信息上传调试，但给玩家看的时候得客气点，保护隐私，千万别用技术术语吓人，让人家以为游戏坏了。

最后说说怎么搞钱和留人。别让用户手动填信用卡，直接用 Google 钱包 (Google Wallet) 这种现成接口，集成到游戏里，支持点击几下就付款。花钱和打怪得到的两种货币系统能拉高粘性，还要做 A/B 测试 (AB Testing) 看哪种方案更吸金。一切以数据为准，用 Google 分析 (Google Analytics) 看玩家在哪卡关，哪里流失严重。不管是用 HTML5 模板还是 WebGL，核心就是尽量利用 Chrome 的特性，少造轮子，让服务器和浏览器一起干活，这样你的游戏才能在 Chrome 应用商店 (Chrome Web Store) 里跑得比别人快。

船只那些也不用搞什么重物理，直接采样波浪面来贴姿态就行。最骚的是室内看海那关，搞了个遮罩裙 (Skirt) 模拟水下雾，省资源又逼真。这种方案让死模型都能跟着浪头动，真实感拉满。

## Vault, Slide, Mantle: Building Brink's SMART System
- **Speaker:** Arne Olav Hallingstad (Splash Damage)
- **Duration:** 25 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1015813
- **Slide Page:** https://www.gdcvault.com/play/1015930
- **Custom ID:** 1015813

### Overview


### Content Summary
[TLDR]
利用预计算导航网格实现动态智能移动，让 FPS 角色自动翻墙无需关卡设计师手动标记障碍物。

[Background]
针对传统 FPS 多人战斗里角色撞墙、卡脚丫的痛点，Splash Damage 团队分享了如何在大场景里实现丝滑的移动，无需美术到处摆辅助标记。适合想做自主移动系统的开发者参考。

[Recaps]
Splash Damage 团队在做《Brink》时发现，很多玩家吐槽角色在复杂地形里走路太生硬，老是被桌子椅子卡住。为了改这毛病，他们一开始打算用实时碰撞检测 (**Collision Detection**)，也就是每帧都射射线去测障碍物。结果一试发现，60 人的对战场景下，算力根本扛不住，帧率掉得没法玩。而且要是全靠程序实时算，以后换张图全得重算，太费事。

后来大伙儿想了个招，干脆把活儿挪到**地图编译步骤 (Map Compile Step)** 干。他们本来有个给电脑 AI 用的**导航网格系统 (NavMesh/NAMMesh)**，用来规划 AI 怎么走位。工程师们灵机一动，觉得既然 AI 需要知道哪里能跨过去，那把这数据借来给玩家用也行啊！于是他们在编译地图时就提前算好所有能翻墙、能跳跃的地方，生成一系列**可达性路径 (Reachability)**。这样玩家跑起来时，系统直接查表就知道该干嘛，不仅省资源，还保证了人和 AI 走的路线逻辑一致，不会有人能走到墙里面去。

具体到落地执行，他们还分了轻、中、重三种**角色体型 (Body Type)**，不同的体重能做的动作不一样，比如重的就不能跳墙。核心逻辑是看墙壁高度，矮点就**翻越 (Vault)**，高点就**架身 (Mantle)**，实在太低了就**滑行 (Slide)**。最骚的是加了个“智能按键”，平时按住加速跑自动触发动作，高手嫌慢还能手动按跳。最后他们总结，复用现有的导航系统比重新造轮子香多了，不过要注意**物理状态 (Physics State)** 的网络同步带宽，不然联机容易飘。

## The Odd Couple: Maya and Python
- **Speaker:** Adam Mechtley (Candlelight Interactive, LLC)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1015911
- **Custom ID:** 1015911

### Overview


### Content Summary
[TLDR]
用 Python 写 Maya 工具别硬套老 MEL 路子，理顺环境部署和架构逻辑才是生存之道。

[Background]
很多技术美术（TA）写 Maya 工具时容易陷入“字符串式编程”的坑，且遇到跨部门部署混乱的问题。本文旨在解决如何在 Maya 复杂的系统架构中优雅地组织代码并处理环境变量。

[Recaps]
首先，写代码千万别再把命令当字符串拼了。很多老手习惯用 MEL (Maya Embedded Language) 那种思路去调用函数，这在 Python 里是大忌。正确做法是直接引用函数指针或者导入模块，比如直接用 cmds.polySphere() 而不是把它包在一串引号里传进去。这样代码更整洁，调试起来也顺手，毕竟 Python 的优势就在于这种动态执行的灵活性，别把它硬写成旧版脚本的样子。

其次是环境部署这块儿特别容易翻车。不同工作室的服务器配置不一样，你的脚本可能在本地跑得好好的，一发网络就报错。关键是要搞清楚 PYTHONPATH (路径变量) 这种环境变量怎么配，还有像 sitecustomize.py (初始化脚本) 这样的初始化文件怎么用。别指望所有人都把路径写在死地方，最好根据脚本所在文件夹自动计算相对路径，少些假设，多靠代码逻辑去适配各种情况，这样才能保证你在公司、在家或者出差都能稳定运行。

最后得注意 Maya 自身的架构陷阱。特别是界面 UI 加载和后台命令执行的时间点不对，经常会导致对象属性混淆。比如类属性和实例属性的区别，有时候你以为它是全局变量结果它只是个局部，或者在 __Main__ (入口模块) 入口判断失误。正确的姿势是在加载插件时注册好功能，再按顺序加载 UI，尽量利用单例模式管理窗口。总之就是：先搞清楚代码到底在哪跑，什么时候跑，再动手写逻辑，不然很容易变成“一运行就崩”的灾难现场。

## Technical Artist Boot Camp
- **Speaker:** Ben Cloward, Rob Galanakis, Seth Gibson, Wes Grandmont III, Jason Hayes, Adam Pletcher, Arthur Shek, Will Smith (Bioware, CCP Games, Reykjavik, Intel Perceptual Computing, Microsoft Studios (343 Industries), Volition, Inc, Volition, Inc, Microsoft Studios (Turn 10), Volition, Inc)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1015493
- **Custom ID:** 1015493

### Overview
Technical Art is evolving rapidly. In many studios TAs play key roles in developing efficient tools pipelines and ensuring art content is visually striking and optimized for performance. TAs bridge content and engineering, helping make both more successful.

### Content Summary
[TLDR]
技术美术的核心不是炫技或写脚本，而是建立工程化思维，通过构建稳健的基础设施、量化工作价值和深度跨部门协作，真正驱动生产管线的高效运转。

[Background]
这场演讲发生在 2012 年的 GDC 技术美术训练营，针对当时行业里普遍存在的“技术美术到底该干啥”、“为什么老板不理解我们”的痛点。多位一线大佬通过自己的血泪经验，想告诉大家技术美术不能只做拿着锤子到处找钉子的修补工，而应该成为懂艺术、精通编程、能搭建地基的系统工程师。这适合所有刚入行觉得迷茫、或者在团队里推不动技术优化的同行看看。

[Recaps]
首先得摆正心态，技术美术（Technical Art）的身份界定非常模糊，有人管建模、有人管绑定、有人纯写工具，但万变不离其宗的是要解决问题的本质。罗布·加拉纳基斯提到，很多新手 TA 容易陷入“彼得原理”，就是做得越好越被提拔到不擅长的岗位。要想避免这个坑，必须引入正规的制作流程，比如设立支持任务流程（Support Process）和强制性的代码审查（Code Review）。这就好比盖房子，不能让每个 TA 各盖一间房然后拼起来，得有统一的标准和架构。千万别觉得自己会写 Python 就天下无敌，核心在于你能不能把这些工具整合成一个稳定的系统，而不是为了一个功能写一堆临时脚本。

其次，工欲善其事必先利其器，基础设施（Infrastructure）比单点工具更重要。亚当·普莱彻和赛斯都强调，别光顾着给艺术家做一键按钮，得先想清楚怎么管理代码。哪怕是用 PowerShell 这种 Windows 自带脚本，只要结合好了版本控制和单元测试（Unit Test），都能大大提升效率。比如沃尔顿·史密斯提到的案例，他们甚至用 PowerShell 直接操作 Excel 报表，或者处理复杂的文件路径。关键是别让管线（Pipeline）变成一堆杂乱无章的脚本堆砌，要做好文档编写、接口隔离，这样以后换人或加需求才不会崩盘。不要过度设计（Overengineering），够用的简单代码才是好代码，太追求通用性往往会导致难以维护的复杂依赖。

最后，在图形技术和跨部门合作上，得有数据思维和落地能力。韦斯·格兰德蒙特展示了大量渲染（Rendering）层面的硬核技巧，比如把漫反射信息压缩进法线贴图里节省显存，或者用世界坐标映射来解决建筑窗户纹理重复的问题。这些不仅仅是技术演示，更是为了解决实际性能瓶颈。同时，威拉德·史密斯和亚当都提到了一个“黑暗面”策略：主动坐到程序员的工位上去办公。别等程序调好工具再反馈，直接参与进去，用帧率和内存的具体数据去证明你的优化有价值，而不是凭感觉说“我觉得快了很多”。只有建立了信任（Trust），让艺术家和程序员都看到彼此的努力，才能真正消除隔阂。

### Overview
Technical Art is evolving rapidly. In many studios TAs play key roles in developing efficient tools pipelines and ensuring art content is visually striking and optimized for performance. TAs bridge content and engineering, helping make both more successful.

### Content Summary
[TLDR]
特效不只是好看，得让玩家一眼看懂玩法机制，通过不断迭代优化视觉反馈来服务游戏体验。

[Background]
Volition 美术大神分享实战案例，直击特效只重美观忽视玩法传达的行业痛点。建议所有想做好关卡交互的策划和特效师阅读。

[Recaps]
说白了，所谓的视觉效果 (Visual Effects) 绝不只是一堆华丽的爆炸粒子，它们的核心任务是进行视觉沟通 (Visual Communication)。在 实时破坏 (Real-time Destruction) 项目中，如果你做出来的东西让玩家看不懂意图，那就白做了。举例子说，那个爆炸桶的设计标准很严，得确保无论在明亮还是黑暗的环境下都显眼，而且外观要看着像个不稳定的家伙，这样玩家一看见就知道“嘿，这玩意儿能炸”，这才是有效的效果传达。

到了武器设计环节，这就更得讲究逻辑了。同一个家族的技能，叫 Rifle 就是步枪，非破坏性的；要是改名叫 Cannon 或者 Beam，立马就变成了破坏性的大杀器。这种命名直接关联功能预期。开发时新手容易犯的错误是把 首轮效果 (First Pass Effects) 当成最终成品，其实那只是雏形。像那把主力冲锋枪，从概念图到最终实机，中间不知道改了多少版，目的就是为了让它既有独特的打击感，又在视觉上足够清晰，有时候甚至得牺牲真实感来换取识别度。

最后说说辅助系统的导航特效，比如那个 GPS 寻路点。别整得太复杂，一定要跟 UI 界面上的 二维用户界面 (2D HUD) 风格匹配，虽然它在 三维空间 (3D Space) 里存在，但看起来最好别太立体，免得跟小地图脱节。找灵感别闭门造车，去抄作业，用现有的技术快速拼个原型试水。那个导航点从 V1 磨到 V6 才定稿，这说明啥？特效工作就是个不断微调的过程，所有的修改都是为了让玩家在战场上少犯迷糊，玩得顺手。

## Stable SSAO in Battlefield 3 with Selective Temporal Filtering
- **Speaker:** Louis Bavoil (NVIDIA)

One of the most rapidly growing fields is physical simulation, as shown by many of the latest games, from those on mobile platforms to AAA console games. ### Content Summary
[TLDR]
游戏流体无万能解，按场景选：烟雾用网格，水花用粒子，海面用频域算法，稳定流畅比物理精准更重要。

[Background]
面对复杂的流体物理，很多开发者直接被劝退。Insomniac 的大牛 Jim Van Verth 把这套理论拆解成了能落地的工程方案，专门教大家在性能和画面之间找平衡，最适合做特效或底层优化的程序员。

[Recaps]
咱先捋捋基础，流体本质就是密度和速度在空间里的变化规律。控制这货的核心是纳维 - 斯托克斯方程 (Navier-Stokes equations)，里面包含外力和粘性等一堆参数。但直接把这公式扔进游戏引擎太烧脑，必须得把它拆解成可执行步骤，不然电脑当场就得瘫痪。

第一种主流方案叫网格法 (Grid-Based)，也可以理解为欧拉法。你可以把游戏世界想象成被切成了无数微小方格，每个格子里存着流体数据。最经典的参考是 Jos Stam 提出的“稳定流体”算法，这招特别适合做烟雾，因为胜在稳定，不容易炸裂。像《Little Big_Planet》里的毒气、气泡破裂都用这招，不过一旦涉及大面积飞溅，精度容易糊掉。

第二种是粒子法，全名叫平滑粒子流体动力学 (SPH)。这派系把流体当成无数个小豆子，通过豆子的运动带动整体流动。好处是自动满足质量守恒，不用像网格法那样费劲算压力投影，非常适合做那种水花四溅的效果。NVIDIA 的 PhysX 就支持这个，但想要画质好就得用大量粒子，对硬件消耗不小，渲染表面也不容易。

最后是针对海水的特殊做法，不用去算整个水体，只算水跟空气交界的那层皮就行。Insomniac 用的 R20 技术利用快速傅里叶变换 (FFT) 把波浪处理成正弦波的叠加。这样能在频率域里偷懒，效率极高，还能完美呈现波浪的色散效果。最终结合高度图渲染加光影贴图，看着就像真的一样，互动性也强。

[Background]

[Recaps]
老哥我是从 EA 过来看技术的，今天聊聊游戏开发里最头疼的“人物撞击感”。很多新手以为角色倒地就是放个死模型，其实那是“布娃娃 (Ragdoll)"的基础形态。纯靠动作捕捉 (Motion Capture) 虽然姿势帅，但一被打就不动，像个假人；要是完全用物理模拟，那动作估计比丧尸还扭曲。咱们目标是找个中间路子，既要防止“物体穿插 (Interpenetration)"这种穿模丑态，还得让玩家觉得操作顺手。这就是经典的“恐怖谷效应”问题，太假不行，太真反而不伦不类。

[Recaps]
搞碰撞检测这活儿，核心目标很简单，就是找出哪些物体撞到了一起，还要算出碰在哪儿、往哪个方向弹。但现实很骨感，硬算的话 CPU 扛不住。大佬们的思路是先把两个物体的碰撞检测，转化成在“配置空间 (Configuration Space)"里检查原点有没有钻进一个怪形状的体积里，这个怪形状叫“配置空间障碍物 (Configuration Space Obstacle)"。这样就把双物体问题变成了单点查询问题，效率直接上一个台阶。而且为了省时间，旋转这种麻烦事通常忽略不计，只盯着平动处理，毕竟连续旋转带来的穿模问题在游戏里经常肉眼不可见，不用过度优化。

[Background]
搞 3D 引擎或图形学的兄弟最怕处理旋转数据，用错格式容易导致动画鬼畜、计算爆炸。这篇 GDC 干货就是为了帮开发者理清各种旋转表达方式的优劣，特别是为什么现代 3D 引擎基本都抛弃欧拉角，而拥抱四元数的底层逻辑。

[Recaps]
首先咱们得把概念分清楚，这里说的“姿态 (Orientation)"是指坐标系的朝向，“旋转 (Rotation)"则是从一个朝向变到另一个朝向的过程。在 2D 场景下，直接用角度最简单，加加减减就能拼接，插值也方便。但一旦到了 3D，很多老手习惯用的欧拉角 (Euler Angles) 其实是个深坑。这种通过三个轴向依次旋转的方式，虽然对用户友好，但在内部计算里极易遇到万向锁 (Gimbal Lock)，就是某个时刻丢失自由度，导致物体控制失灵或者动画突然翻转。

再说常用的矩阵 (Matrix)，这玩意儿确实是图形学的干活主力，做变换和拼接非常快，尤其是配合向量处理器。但拿矩阵来做插值就很头疼，简单的线形插值 (Lerp) 会让基向量失去单位长度，不再是有效旋转矩阵，得搞一堆正交化操作甚至要用更难的球面线性插值 (Slerp)。另外像轴角 (Axis-Angle) 表示法，虽然理论上不错，但拼接计算成本太高，通常只作为中间过渡格式，不适合长期存储。

所以结论很明确，3D 引擎内部的数据流转和旋转计算，四元数 (Quaternion) 才是王道。它本质是改进版的轴角表示，只用 4 个数值就能完整描述旋转，不仅没有万向锁风险，数学性质也好。虽然四元数乘法稍微复杂点，但拼接和旋转效率极高。唯一的注意点是要小心四元数及其反号 $q$ 与 $-q$ 代表同一旋转的问题，插值前记得检查点积防止绕远路。记住：给用户界面看的时候用欧拉角，引擎底层跑数据时老老实实用四元数。

[Background]
搞图形程序的都知道，手动推公式太头疼，数值计算还容易崩。这篇演讲就是给大伙儿送福利，教怎么用简单的数学工具把自动求导 (Automatic Differentiation) 硬嵌入到 C++ 里，顺便解决刚体运动 (Rigid-Body Transform) 和模型变形的经典难题，特别适合不想被高数劝退的程序猿看。

[Recaps]
首先得搞清楚啥是对偶数 (Dual Numbers)。这东西跟咱们熟悉的复数 (Complex Numbers) 有点像，也是由实部和虚部组成，但那个特殊单位 ε 有个硬核规矩：它的平方永远等于 0。这就带来了一个爽歪歪的效果，不管你怎么运算，所有二阶以上的高阶项都会自动归零，泰勒级数 (Taylor Series) 直接截断成闭式表达。这意味着你在写函数的时候只要多带一个 ε 分量，就能在算出结果值的同时，直接把导数也一并算出来了，完全不需要再用那种麻烦的数值差分法去瞎猜精度了。

接着是怎么落地的工程问题。别直接拿 float 或者 double 写死代码，得用 C++ 模板 (C++ Template) 做抽象层。把标量类型统一定义为 Scalar，然后重载所有的加减乘除运算符。就像演讲里给的 smoothstep 例子一样，稍微改改函数泛型结构，就能让它同时兼容普通浮点数和对偶数对象。这样你以后要是想算导数，直接把参数塞进对偶数类型里，核心逻辑都不用动一行，简直是工程上的偷懒神器，既保证了类型安全又提高了开发效率。

最后聊聊这东西能干点啥实事。比如求曲线切线，以前得靠微小步长差分，误差大还容易越界，现在直接套个向量模板，输入对偶坐标，实部是位置，虚部归一化就是切线方向。还有几何求交，引入普吕克坐标 (Plücker Coordinates)，两直线相交或交叉的方向都能用一个点积算出来。最绝的是动画方面，传统的骨骼蒙皮 (Skinning) 混合矩阵容易导致“糖果纸 (Candy Wrapper)"效果，也就是模型中间会被吸进去凹下去。这时候用上对偶四元数 (Dual Quaternions) 做混合，配合螺旋理论 (Screw Theory)，就能保证每个过渡帧都是标准的刚体变换，彻底把这个视觉瑕疵治好了。

- **Speaker:** Eric Lengyel (Terathon Software LLC)
- **Duration:** 55 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1015534

### Overview


### Content Summary
[TLDR]
别再用叉乘硬套逻辑了，用格拉斯曼代数 (Grassman Algebra) 统一视角，把叉乘看作双矢量 (Bivector)，彻底搞懂法线变换和几何求交的本质。

[Background]
3D 开发常被点乘叉乘绕晕，尤其是法线为何要用逆转置矩阵 (Inverse Transpose Matrix) 变换。演讲者想打破只背公式不懂本质的现状，揭示这些离散工具其实源于一个大一统数学系统。

[Recaps]
各位兄弟平时写图形引擎，肯定都被法线变换坑过。很多人死记硬背“法线要用逆矩阵的转置”，却不知道为什么，甚至不知道叉乘出来的东西根本不是普通向量。这里就要引入核心概念**双矢量 (Bivector)**。叉乘结果本质是一个有向面积，叫双矢量，它有正反方向，顺序一换符号就变。同理，三个向量相乘是**伪标量 (Pseudoscalar)**，代表有向体积。咱们常说的向量只是**矢量 (Vector)**，是一维的。格拉曼把这些分得更细，**多矢量 (Multi-vector)** 把它们打包在一起，像**梯度 (Grade)** 一样分级管理。

再聊聊大家头疼的法线变换。物理上讲，法线其实是**反对向量 (Anti-vector)** 或称为对偶矢量，它跟位置矢量的行为不一样。如果你只做旋转（正交矩阵），可能看不出问题，但如果模型做非均匀缩放，直接套同一套矩阵，法线立马就不垂直于表面了。这是因为普通向量是切向量，而法线这种叉乘产物属于高阶几何元素。只有理解了它们是**反矢量 (Anti-vector)**，才会明白为什么要除行列式并取转置来修正变换，这才是底层逻辑。

真正的硬货在四维**齐次坐标 (Homogeneous Coordinates)** 里的应用。以前我们用参数方程画线很麻烦，现在看**普吕克坐标 (Plucker Coordinates)**，它就是四维空间的一个**双矢量 (Bivector)**。两点**楔积 (Wedge Product)** 就是线，三点**楔积**就是面。更重要的是引入了**反楔积 (Regressive Product)**，专门做交集。这就好比集合论的并集和交集，算直线相交、平面求点，直接乘一下就行，不用写一堆 `cross` 和 `dot` 混合的丑代码。

最后说说实际效果。射线与三角形求交一直是精度噩梦，容易误判。如果基于这些代数概念，利用双矢量性质，可以天然避免很多浮点溢出或 epsilon  hack 的情况。而且 C++ 里可以用 `^` 运算符重载直接实现这些**楔积 (Wedge Product)** 和**反楔积 (Regressive Product)**，代码可读性提升一大截。总之，这套理论虽深，但能把原本割裂的几何运算打通，值得琢磨。

首先，老生常谈的球谐函数 (Spherical Harmonics) 虽然好用，但存在大硬伤。它生成的信号总是全局平滑的，导致光照边缘产生不自然的振铃，而且因为全是实数积分，经常算出负值，不符合物理现实（比如反照率永远不能是负的）。像 Haar 小波虽然能局部化，但在球面上拼接会产生缝隙，GPU 处理起来也不顺手。

为了解决这些痛点，演讲引入了“帧”的概念。传统的标准正交基限制太多，我们得放宽规则，采用过完备系统（Over-complete System），也就是帧理论 (Frame Theory)。特别是“紧框架”(Tight Frame)，它既能保留能量守恒（帕塞瓦尔恒等式），又能灵活选择系数数量，比正交基更能适应 GPU 的并行计算需求。

具体的解决方案是“球面针状函数”(Spherical Needlet)，这玩意儿本质上是第三代小波技术的变种。通过球面 T 设计 (Spherical T-design) 进行采样，它能实现高度的空间局域化，光线方向性强，基本没有负瓣干扰。这意味着投影和旋转操作都可以变成查表和线性插值，速度飞快，特别适合做光照探针 (Light Probe) 和高光 BRDF 的表达。

最后，作者透露目前还在攻坚稀疏性 (Sparsity) 问题，未来有望结合压缩感知技术，只传输几个关键系数就能还原画面。虽然离直接落地还有距离，但这套基于希尔伯特空间 (Hilbert Space) 的新方法，大概率会取代现在的旧方案，成为下一代图形引擎的核心算法。

## Faster C++: Move Construction and Perfect Forwarding
- **Speaker:** Pete Isensee (Microsoft)
- **Duration:** 58 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1015728
- **Slide Page:** https://www.gdcvault.com/play/1015458

### Overview


### Content Summary
[TLDR]
C++11 移动语义让编译器在临时对象上“偷家”而非拷贝，大幅优化深层对象性能。

[Background]
针对 C++ 深拷贝对象开销大、临时变量易导致性能瓶颈的痛点，适合关心运行时效率的程序猿，分享如何利用 C++11 新特性无感提速。

[Recaps]
讲起痛点，C++ 默认按值传递，复制一个带指针的**深对象 (Deep Object)** 时，不仅要分配内存还要逐字节拷贝，数据量大时线性增长的成本简直没法看。现在 C++11 出了个**右值引用 (Rvalue Reference)**，配合**标准移动 (std::move)** 函数，能让代码直接“窃取”临时对象的内部资源，把线性时间复杂度变成常数级，性能起飞。

核心区别在于区分**左值 (Lvalue)** 和**右值 (Rvalue)**。简单说，有名字能取地址的是左值，不能动；临时生成的没名字的才是右值，可以随意拆散。实现**移动构造 (Move Constructor)** 或**移动赋值 (Move Assignment)** 时，参数必须是非 `const` 的右值引用，这样才有权限修改源对象，把它的指针置空防止重复释放。

进阶玩法是**完美转发 (Perfect Forwarding)**，利用模板和 `std::forward (std::forward)` 函数，不用写一堆重载就能让函数根据传入的参数类型自动选择拷贝还是移动。这招配合新的 STL 库，升级编译器都不用大改代码就能白嫖性能提升。

最后给点实战建议，遵循“规则的三条”加上新加的“移动两条”，别用 `const` 去限制右值引用，写完记得调试确认真走了移动逻辑而不是拷贝。反正只要更新支持 C++11 的编译器，整个标准库自带移动语义，这波羊毛不薅白不薅，赶紧回炉重造你的类库吧。

[Background]

[Recaps]
现在的游戏里，贴图数据的**纹理占用 (Texture Footprint)** 往往是最吃内存的累赘，尤其是 PC 以外的主机和移动端，显存和内存都捉襟见肘。很多开发者习惯把 DXT 压缩好的贴图直接丢进 ZIP 包，运行时再解压到显存，这虽然方便但会把整个巨大的压缩包都留在内存里，导致大量无用数据（如关卡初始化后不再变动的数据）长期霸占资源，实在浪费。

演讲者提出了一条更稳妥的路径：离线阶段先把 DXT 数据进一步压缩，运行时一次性解压回标准的 DXT 再给显卡。他尝试了多种算法优化，比如 **数据解交织 (Deinterleaving)** 把相关数据凑在一起，配合 **霍夫曼编码 (Huffman Coding)** 和 **差分编码 (Delta Encoding)** 来增加重复符号以提升效率。最绝的一招是大胆把传统的 4x4 色块改成 8x8，肉眼几乎看不出区别，却能把颜色通道数据减半。

最终测试结果显示，这套方法能把贴图压到大概 1.32 **每像素比特数 (Bits Per Pixel)**，也就是不到传统方案的三分之一，跟著名的 **Crunch 纹理压缩 (Crunch texture compression)** 效果差不多。不过 Crunch 大神跑出的解压速度更快。演讲最后建议，复杂的数学计算最好放在 **离线处理 (Offline Processing)** 阶段，针对不同材质类型（法线贴图或漫反射）单独调优，别指望一套算法通吃。

### Content Summary
[TLDR]
想让粒子特效在动态光照下真实？核心是用 HL2 投影思路结合顶点算光，顺便还能搞定阴影接收与投射。

[Background]
Bitsquid 团队分享如何在小团队高画质需求下，解决粒子特效像“纸片”太假的问题，确保它们能无缝融入动态光影环境。

[Recaps]
大伙都知道，以前的粒子特效没经过处理就像一张画在纸上的图飘在空中，特别假。这演讲的核心就是解决 `贴花 (Billboard)` 材质怎么在 `动态局部光源 (Dynamic Local Lights)` 和 `全局光照环境 (Global Lighting Environment)` 里存活。最省钱的办法是在 `顶点着色器 (Vertex Shader)` 算光，把每个顶点的入射光存下来，让 `像素着色器 (Pixel Shader)` 只负责调色。但这会导致光照方向丢失，显得扁平。所以作者复活了个经典思路：基于 `HL2 风格 (HL2-basis)` 的方法，把光照环境投影到三个轴向，这样既便宜又能看出光的方向感。

想要更逼真？那就得给粒子加阴影。直接在顶点阶段查 `阴影贴图 (Shadow Map)` 很省事，但需要硬件支持快速读取。更进阶的是利用 DX11 的 `细分 (Tessellation)` 技术，把累加光照的逻辑从顶点推到 `域着色器 (Domain Shader)` 里。虽然性能开销稍微大了点，但精度大幅提升，能捕捉到细微的衰减。对比下来，完全靠后期算光是真的费帧数，前两者才是工业界的正确打开方式。

另外还讲了阴影投射和自阴影的处理。投射阴影得按深度顺序渲染粒子，用单通道保存 `半透明 (Translucency)` 信息，再和实心物体的阴影贴图合并。至于粒子自己的 `自阴影 (Self-shadowing)`，那些高级算法像 `傅里叶阴影映射 (Fourier Shadow Mapping)` 虽然牛，但在大场景里吃不消，除非是做精致过场动画。最后补个福利，给粒子背面打 `背光 (Back-lighting)`，配合半透明度，瞬间增加层次感，成本极低但效果拔群。

[Background]
主讲人为育碧物理引擎开发者，聚焦游戏中常见的物体穿透几何体的痛点。针对传统方案要么性能开销过大、要么引发虚假碰撞的问题，分享了这套兼顾稳定性与性能的工程化解决思路。

[Recaps]
开场就抛出一个尴尬案例：即便在最新大作里，玩家击杀敌人后，尸体手臂也会直接插进地板里。这就是典型的 穿模 (Tunneling issue)。演讲者吐槽说，以往大家常用的 线性凸体投射 (Linear convex cast) 只能预测何时撞上，没法完全阻止；而另一种廉价的 推测接触点 (Speculative contact point) 方法，虽然能挡住一部分，但在物体快速自旋或相互干涉时容易产生幽灵般的虚假反弹，根本治标不治本。

核心方案在于重构物理管线流程。首先在粗略阶段 (Broad phase)，不再只检测当前位置重叠，而是结合速度计算出物体的运动轨迹线段，提前筛选出潜在的碰撞对。到了精确阶段 (Narrow phase)，摒弃传统的增量 接触流形 (Incremental Manifold) 做法，改用全量计算模式，直接在一步之内算出真实的接触点以及距离为正的潜在接触点。这就相当于在物体还没撞到墙的时候，先给它加个虚拟护盾减速，保证下一帧必然停在表面，而不是直接钻过去。

除了结构改动，细节处理也很关键。为了保留真实的物理弹性，计算 恢复系数 (Restitution) 时必须使用上一帧的速度数据，否则会因为之前的减速导致弹跳能量丢失。此外，求解器 (Solver) 的顺序也有讲究，必须把最关键的接触约束放在最后执行，这样即便瞬间断开连接，也能在下一帧迅速修复，避免穿模。

最后在实际项目《幽灵行动》中实测，这套方案带来了约 15% 的 CPU 开销增长，但在老旧主机上依然稳健运行。虽然在面对两个极快移动的动态物体互撞时仍有理论限制，但对于绝大多数 布娃娃系统 (Ragdoll System) 和高速旋转场景，这已是一套足够可靠且不拖后腿的工程级解决方案。

现场 demo 特别真实，作者拿个射击 demo 一跑，**片段着色器 (Fragment Shader)** 直接 96% 负载，明显爆了。后来把特效砍一刀，虽然画面糙了点，但帧数稳在 30FPS 以上。他还教了一招：用**离线着色器编译器 (Offline Shader Compiler)** 提前算算指令周期，别在手机上堆太多复杂运算。顺便提一句，**多重采样抗锯齿 (Multi-sampling AA)** 在 Mali 上几乎不耗资源，建议大家直接开满，画质涨一大截还不掉速。

最后总结了未来的方向，目标就是让手机跑得跟主机一样爽，同时还得扛得住电量。新架构支持**OpenCL**、**DirectX 11**这些高级接口，工具也有免费的社区版给安卓开发者。总之就是那句老话：别光盯着代码改参数，学会用官方工具看底层的管线状态，才能真正把手机性能吃干抹净，既流畅又省电。

- **Speaker:** Tom Mathews (Microsoft)
- **Duration:** 46 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1015605
- **Slide Page:** 
- **Custom ID:** 1015605

### Overview


### Content Summary
[TLDR]
音频调试别光靠人耳试错，善用傅里叶变换 (Fourier Transform) 加 DSP 算法，能比耳朵更准地揪出爆音断流等底层隐患。

[Background]
微软资深音频工程师现身说法，指出行业普遍缺乏有效的音频诊断工具，往往依赖人工监听导致难以发现细微或偶发性音频 BUG。这篇演讲旨在提供一套基于信号处理的自动化排查方案，帮大家提前排除致命缺陷。

[Recaps]
首先得懂点击声（Click）的物理本质。一个突然的脉冲相当于无限振幅的信号，其能量谱会横跨整个频率域。哪怕幅度很小，只要发生波形跳变，在频谱图上就会显示出一根直达顶部的长条。这解释了为什么我们的耳朵对这种瞬态变化极其敏感，即便被掩盖也能察觉。演讲者纠正了转写中的"FOIA"为正确的频谱分析逻辑，即利用 `傅里叶变换 (Fourier Transform)` 将复杂波形拆解为正弦波叠加，从而直观量化问题。

针对如何自动抓 Bug，不能只靠监听，得把 `数字信号处理器 (DSP)` 当成调试工具。最简单的做法是计算相邻采样的差值，但低频噪音干扰大，容易误报。更靠谱的方法是让卷积核自卷积（类似 Photoshop 里的锐化），大幅压低底噪并提升信噪比，这样微小的爆音也会变成明显的尖峰。还有一个绝招是直接往管线里插正弦波文件，因为正弦波最纯净，一旦有内存破坏或断点，波形立刻畸变，比真实素材更容易暴露问题。

除了爆音，还有几种隐形杀手。比如 `丢帧 (Dropouts)`，可能是硬盘读取慢或光盘换层缓冲不足；或是 `声音卡顿 (Stalls)`，通常源于编程上的 `优先级反转 (Priority Inversion)`，低优先级线程锁住了资源却占着 CPU，害得音频线程干等着。另外，浮点数运算也要小心，当数值极小时会出现 `非规范化运算 (Denormalization)`，会让单颗音效占用数倍于常态的 CPU 资源，直接拖垮性能。

最后，作者呼吁大家不要迷信测试员的“黄金耳朵”，要建立自己的诊断标准。比如在语音重叠处理时，必须强制判断 `零交叉点 (Zero Crossing)` 以避免爆音；在发布前用脚本跑一遍频谱热力图。与其事后被动修复，不如主动开发专用 DSP 工具进行实时监控，毕竟在零售版发售后再修这些细节代价太大了。

### Overview


### Content Summary
[TLDR]
掌握 NDK 原生开发技巧并优化编译参数，是实现安卓游戏在 ARM 与 x86 多架构上高性能运行的核心关键。

[Background]
移动端硬件环境极其破碎，C++ 开发者常因不同芯片和驱动的差异频频踩坑。本次分享主要面向使用 NDK 进行原生开发的开发者，旨在解决跨平台移植中的兼容性痛点，提供实战经验。

[Recaps]
想要搞定安卓多端运行，首选策略是利用**本地开发套件 (Native Development Kit)** 提供的抽象能力。NDK 内置了复杂的构建系统，能帮你自动适配不同的**应用程序二进制接口 (Application Binary Interface)**。对于开发者来说，最实用的招数是打“大胖包”，也就是把所有架构的库文件打包进同一个**应用程序包 (Android Package Kit)** 里。虽然包体积看起来大了，但因为 APK 本质是压缩包，设备在安装时只解压当前型号需要的版本，既解决了商店上架的麻烦，又省了存储空间。

代码层面的核心挑战是 CPU 指令集的不兼容。ARM 架构常用的 NEON 指令集和 x86 的 SSE 指令集都属于**单指令多数据流 (Single Instruction Multiple Data)** 技术，但底层互不相通。最稳妥的办法是在运行时通过 SDK 查询 CPU 特征，动态加载对应的加速库。另外还得警惕内存对齐问题，ARM 对 64 位数据类型有严格对齐要求，而 x86 默认紧凑存储。如果你直接把存档里的二进制数据当成对象读取，在 x86 上很容易因为地址偏移错误导致崩溃，必须要在加载逻辑里加一层修复程序。

最后是编译器配置和生态稳定性。ARM 和 x86 的编译标志（如 fPIC、浮点加速）千万不能混用，否则会导致性能下降甚至启动报错。记得别轻信厂商魔改的系统库，只有 NDK 官方发布的库才能保证长期稳定。此外，推荐大家使用新的图形性能分析工具（GPA），它能连手机直连抓取帧率数据，再配合原生支持的 x86 安卓模拟器，能让调试效率大幅提升。

[Recaps]
这次演讲的核心就是想搞事情，把游戏世界从死板的“静态烘焙”里彻底解放出来。演讲者 Matt 提出用一种叫 `有向距离场 (Signed Distance Field)` 的新东西代替传统的网格模型。简单说就是给空间每个点打个分，告诉你离表面有多远。这样一来，不管是切个洞还是两个物体融在一起，全靠算几个数学公式就能搞定，不用像以前那样担心网格拓扑崩盘，特别适合做那种玩家能随时破坏或改变的游戏场景，比如《毁灭战士》那种风格。

有了场数据还得变回能让人看的眼前画面。以前用 `移动立方体算法 (Marching Cubes)` 转成三角形面片时，因为每个位置生成的三角数不一样，导致显卡线程忙闲不均，效率很低。这里就展示了 `DirectX 11` 的厉害之处：利用 `计算着色器 (Compute Shader)` 配合 `流压缩 (Stream Compaction)` 技术，先统计好数据再输出。这招就像把一堆乱码分类打包，直接告诉 GPU 该干多少活，瞬间把生成时间砍了一大半，还方便后续把生出来的模型缓存起来反复使用，比之前依赖 `几何着色器 (Geometry Shader)` 要高效得多。

最后聊聊实际效果怎么落地。不仅能把物理碰撞做得更准，比如用 `平滑粒子流体动力学 (SPH)` 结合这个距离场来算水流和物体的互动；还在光照上玩了把大的，替代了常见的 `屏幕空间环境光遮蔽 (SSAO)`。通过 `时序重投影 (Temporal Reprojection)` 配合简单的光线追踪，虽然一开始会有噪点，但稍微加点补偿就能达到非常干净的效果。特别是通过负载均衡优化线程，原本一帧几十毫秒的开销现在能压到两毫秒左右，这意味着这套方案完全有资格用在真·实时的商业大作里，让未来的游戏地图变得真正灵活且高效。
