## TR1: C++ on the Move
- **Speaker:** Pete Isensee (Microsoft)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/533
- **Custom ID:** 533

### Overview


### Content Summary
[TLDR]
借微软 TR1 新工具包搞定数组和哈希表，配合智能指针自动管理内存，写 C++ 代码不再手抖怕崩盘。

[Background]
玩 C++ 开发的都知道，手动管理内存累不累，旧版标准库不好用更是坑，经常为了几个基础功能还得自己造轮子。这位微软的大佬特意来给大伙儿送福利，讲的是刚出炉不久的 TR1 技术规范，告诉咱们怎么利用官方新出的工具把程序写得更快更安全，特别适合那些想在性能优化上再进一步的中高级开发者。

[Recaps]
首先咱得知道这个 TR1 到底是啥玩意儿，全称叫 技术报告 (Technical Report)，虽然不是正式的 标准版 (Standard) 代码，但其实就是未来标准的预告片。这东西最早 2001 年就开始琢磨了，到现在 2006 年已经能用了，里面塞了不少好东西，比如固定大小数组、哈希表还有智能指针等等。对于咱们写游戏的来说，不用再去搜那些杂七杂八的开源库，直接用标准库里的就行，省得以后跨平台迁移代码麻烦。

再说几个核心好用的工具。一个是固定大小数组 (Fixed-sized arrays)，这东西跟以前的 C 风格数组长得一样，性能也一样猛，但是它是真正的容器，有 begin end 这些接口，安全性高得多，不用担心越界访问。另一个是大杀器 哈希表 (Hash Tables)，以前查数据要么遍历要么平衡树，现在用它查询速度平均是 O(1)，相当于瞬间定位，不过要注意不能保证顺序，而且得注意设置合适的 哈希函数 (Hash Functions)。演讲里实测了在 Xbox 360 这种硬件上跑也没问题，负载因子 (Load Factors) 控制好了还能自动调整内存占用，真香。

最后是解决内存泄露的神器 智能指针 (Smart pointers)，特别是那个 shared_ptr。以前咱们得自己记得 delete，忘了就崩溃，现在把这个指针对象赋值给别人，内部会算引用次数 (ref count)，没人用了自动回收，根本不会漏内存。虽然稍微有一点点性能开销，但这点钱相对于内存爆炸导致的崩溃还是划算太多了。总的来说，这玩意儿能让我们从繁琐的资源管理里解放出来，专心去调数值和优化逻辑，毕竟工具再好也得自己肯用。

## Sort-Independent Alpha Blending
- **Speaker:** Houman Meshkin (Perpetual Entertainment)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/535
- **Custom ID:** 535

### Overview


### Content Summary
[TLDR]
告别繁琐的深度排序，用数学近似法实现顺序无关的 Alpha 混合，让粒子特效渲染更稳更快。

[Background]
半透明物体渲染总得按远近排队，排序太费劲还容易穿模。这内容适合被性能卡脖子的特效程序员，教你怎么用公式换空间。

[Recaps]
搞图形技术的都知道**Alpha 混合 (Alpha Blending)** 有多折磨人。以前想要画个烟或者玻璃，必须把物体从后往前排好队再画，不然后面亮的会吃掉前面暗的。但这事儿太难了，对象一多还要算交点、处理凹凸，排序的成本简直爆炸。Houman 老哥直接动手拆公式，把复杂的混合逻辑分成了“跟顺序无关”和“跟顺序有关”两块。既然咱们大多数情况画的都是火苗、烟雾这种半透明的**粒子系统 (Particle System)**，顺序带来的误差其实很小，不如直接把那个讨厌的顺序依赖给砍了。

他专门做了个**误差分析 (Error Analysis)**，对比了不同透明度下的视觉效果。结论挺有意思，忽略掉顺序那部分公式后，由于正负项互相抵消，画面看起来几乎没区别，甚至因为公式结构更简单，精度反而比老老实实排序要高。但这招也有代价，原来的 8 位精度不够用了，得用上 16 位的缓冲区来存中间数据，防止计算过程中精度流失。硬件方面现在很多也支持这种高精度的缓冲写法，虽然代码复杂点，但换来的性能提升绝对物超所值。

具体实现上也不难，核心就是利用多个**渲染目标 (Render Target)** 分批记账。第一遍用加法混合把所有物体的颜色和透明度信息存进去，相当于先记账；第二遍在着色器里按新公式把账本合一下，顺便处理背景色。整套流程完全省去了排序步骤，对于像粒子特效这种数量巨大的一刀切场景是神器。当然，如果是那种特别厚实的不透明玻璃，还是得老实排队，这技术主要就是为了低透明度优化的。

## Shared Technology at Rare: Good and Bad
- **Speaker:** Tom Grove (Rare Ltd / Microsoft Game Studios)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/521

### Overview


### Content Summary
[TLDR]
共享技术部别光造轮子，核心是把技术当服务做，搞定客户关系比技术本身更重要。

[Background]
多家工作室共用引擎导致资源浪费，早期共享技术组因忽视协作被项目组拉黑。本文复盘如何转型做服务、拆组件，适合多人并行开发的工作室借鉴。

[Recaps]
Rare 早年为了省成本搞了个共享技术组，想统一引擎防止各队重复造轮子。一开始这帮搞技术的太理想主义，光顾着折腾次世代特效和底层动画，把艺术家想要的工具做得不错，结果交付周期对不上，代码质量也一般。项目组觉得这是“你们玩你们的酷，我们修我们的 BUG"，关系搞得很僵，属于典型的“用爱发电”翻车现场。

后来痛定思痛，他们改成了组件化 (Component Based) 模式，不再硬憋一个大引擎，而是提供一个个独立的组件包，比如物理碰撞、渲染管线或者美术工具插件。中间件 (Middleware) 能整合就整合，让客户自己挑合适的。更重要的是定位转变，从卖产品变成做服务，重视源码管理 (Source Control) 和构建时间 (Build times)，甚至制定了废弃策略，不然新版本升级会把项目组累死。技术不再是唯一难题，如何服务客户才是关键。

最关键的还是人。以前技术组和项目组是“敌我矛盾”，现在实行敏捷开发 (Agile development) 里的专人对接制，每个项目都配一个专属对接人 (Case Officer)。这人得常驻项目组，既代表技术组利益，也要替项目组去吵架争取权益。每月一起规划冲刺，请吃饼干聊技术，把壁垒打破了。最后结论就是：技术再牛，客户不爽也是白搭，还得靠人情味来维持生态。

## Saints Row Multiprocessing Architecture
- **Speaker:** Randall Turner (Volition Inc)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/644
- **Custom ID:** 644

### Overview


### Content Summary
[TLDR]
通过动态任务调度（Scheduler）解决多线程资源垄断，让《黑道圣徒》稳定跑满 CPU 并规避卡顿风险。

[Background]
很多游戏从单线程转多线程时，容易遇到核心争抢、音频抢占导致的卡顿。这篇干货专门给做架构优化的同行讲怎么避免这些坑，属于实战派的技术分享。

[Recaps]
开篇先定义了“调度器”（Scheduler）和“任务”（Job）的概念。简单说就是把大工程拆成小包分给线程，但要小心别让一个线程塞太多活儿。早期团队用的先进先出（FIFO）队列有个大毛病：一旦有块大任务进来，后面所有兄弟线程都得排队干等着，稍微来个音频流这种“抢手头的”事，整个队列就堵死了。所以解决方案是搞了个“任务偏见”（Job Bias）机制，类似搞专线车道，让模拟逻辑（Sim）和渲染（Render）各跑各的，互不干扰。

物理引擎那块更是重灾区。自带的 Hawok 工具太死板，线程内存都要单独分配，经常变回串行处理。团队没妥协，直接指定三根专用线程给它干活，外面再包一层自己的调度器。这样既能掌控线程数量，又能灵活调整，完全不让它卡住主流程。至于音频这种最高优先级的“抢占式事件”（Preemptive events），策略是让正在做的活儿先干完再退场，别硬断，不然容易出 BUG。

最后是性能细节的硬核干货。为了效率，能不用锁就别用锁，比如队列结构用“无锁结构”（Lockless）比“临界区”（Critical Sections）快得多。还有一点很关键，任务切分不是越细越好，太小开销大，太大响应慢。实测下来每个活儿控制在 250 到 500 微秒是最优解。这套打法下来，CPU 占用率直接拉满到 90%，既稳又快，这才是现代游戏多线程调度的正确姿势。

## Projection Matrix Tricks
- **Speaker:** Eric Lengyel (Terathon Software)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/548
- **Custom ID:** 548

### Overview


### Content Summary
[TLDR]
别死磕标准投影矩阵，微调它就能搞定无限远渲染、深度精度陷阱和高效镜像反射裁剪。

[Background]
很多程序员被远景渲染和深度精度坑过，做镜像反射还怕性能损耗。Eric 总结了一套投影矩阵微调方案，直击底层图形学痛点，适合图形方向开发阅读。

[Recaps]
很多开发者被标准的投影矩阵 (Projection Matrix) 给整迷糊了，其实这玩意儿本质上就是个线性变换，在齐次空间 (Homogeneous Space) 里它只管预处理，真正的透视投影发生在透视除法 (Perspective Divide) 那一刻。把远平面推到无穷远能解决天空盒和星星渲染的问题，还能用在阴影体积上，但这会让深度值卡在边界上出问题，需要小心处理。

最头疼的是深度缓存区 (Depth Buffer) 精度问题。当视点转换到视口 (Viewport) 时，远平面通常映射到 1.0，导致碎片剪裁或者精度丢失。虽然有厂商特定方案，但为了通用性，建议直接修改投影矩阵，让远平面映射到 1.0 附近的小偏移量。这样既保留了归一化设备坐标 (Normalized Device Coordinates) 的范围，又给了浮点数一点缓冲空间，避免硬件误判物体跑远。

另外还有个黑科技叫倾斜近裁剪平面 (Oblique Near Clipping Plane)。以前做镜子或水面反射得开额外的硬件裁剪平面，老显卡不支持还会掉帧。现在通过数学推导调整矩阵，直接把近裁剪平面搬到任意位置，不需要额外指令。虽然这会影响到远平面的朝向，但只要计算得当，能让新的视锥体 (View Frustum) 尽量紧凑，既省资源又把精度保住了，绝对是大神级的实用干货。

## Pre-computed Light Carving into Meshes
- **Speaker:** Stephan Etienne (High Moon Studios)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/559
- **Custom ID:** 559

### Overview


### Content Summary
[TLDR]
别死磕大体积的光照贴图，直接把光照算进网格顶点里，既省显存又省纹理读取开销。

[Background]
这讲解决了传统光照贴图太大且限制多的问题。High Moon Studios 的大佬现身说法，教咱们怎么把光线“刻”进模型，适合想优化渲染性能又不想牺牲光影效果的团队和技术人员围观学习。

[Recaps]
咱先说这核心思路，叫预计算光照雕刻 (Precomputed Light Carving)。简单说就是把光照信息直接嵌进网格模型里，而不是像以前那样靠一张张巨大的纹理贴图硬扛。因为处理顶点边的增减挺麻烦，所以建议用翼边数据库 (Winged-Edge database) 来存结构，这样后期改起来不折腾。第一步得搞清楚谁挡谁的光，对方向灯和点光源分别处理，利用包围球 (Bounding spheres) 是否相交来做初步判断，然后算出角度或者投影距离，确定谁接收阴影，再把轮廓线切进去，这就是阴影切割 (Shadow cutting) 的关键流程。

细节决定了上限，如果网格切得太糙，光影过渡会断层，所以得用网格细分 (Mesh tessellation)。根据面积大小和边缘长度给每个三角面加权，需要细节的地方就切得更碎，直到顶点数量或光影变化阈值达标。这时候再在每个顶点上算出最终接收的光强，这一步推荐配合全局光照 (Global illumination)，让光影看起来更有层次，毕竟只是硬算顶点颜色可能会显得比较平。

最后一步是简化 (Simplification)，别被上面增加的顶点吓住，还是要清理无用数据。把不重要的小顶点合并到邻居身上，优先保留对颜色影响大的，具体参考颜色梯度 (Color gradient) 的值。操作时要小心别弄出退化三角形 (Degenerate triangles) 这种鬼畜情况，四边形还要分清楚对角线怎么连才好看。这招的好处是比传统贴图省显存，近距离时填充率 (Fill-rate) 更高，代价就是顶点变换成本增加了，远看模型如果太密反而可能更卡。

## OpenGL ES 2.0: Start Developing Now
- **Speaker:** Dan Ginsburg (AMD)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/699

### Overview


### Content Summary
[TLDR]
借助 PC 模拟器加脚本回退机制，开发者能在硬件落地前完成 OpenGL ES 2.0 引擎的提前适配与开发。

[Background]
OpenGL ES 2.0 发布初期硬件迟迟不到货，开发者的引擎制作被迫卡壳。这次 AMD 分享主要是为了解决“无硬件可用”的痛点，适合想抢跑移动端图形技术开发的程序员参考。

[Recaps]
面对新 API 出来但硬件还缺席的情况，AMD 直接给大伙儿整了一套 PC 端的**模拟器 (Emulator)**。这玩意儿能让你在 Windows 电脑上跑 ES 2.0 的代码，不用干等新手机出来才能写引擎。配合**RenderMonkey**这个**特效编辑工具**，美术和程序可以先把**着色器 (Shader)** 效果做出来，甚至支持从桌面版显卡映射到移动端的指令，基本实现了“先软后硬”，提前把路铺好。

引擎架构这块，AMD 拿自家的 Sushi Demo 当样板房，核心挑战是怎么兼容不同平台的 API。**应用程序编程接口 (API)** 抽象层是个大难题。他们没选“削足适履”的低共同标准路线，而是按最高标准（类似 DX10）设计资源管理和渲染状态。如果某些机型太老跑不动，就通过 Lua 脚本切换到底层的降级渲染路径，保证内容在不同性能的设备上都能跑，哪怕画质稍微降点。

最后是跨语言和系统兼容的苦活累活。很多**着色器 (Shader)** 是写 HLSL 的，想跑到移动端得转成 ES SL，他们自己开发了 HLSL2GLSL 工具自动转换。而且掌机环境很苛刻，不能用 C++ 标准库（STL），也不许抛**异常**。所以他们手写了一套基础库来处理内存和数学运算，强制关闭高级特性。这套组合拳下来，本质就是为了应对那个年代“技术要新但设备受限”的矛盾，让开发周期不被硬件供应链卡脖子。

## Meeting Players Halfway: Using Adaptive Systems to Prevent Player Frustration
- **Speaker:** Lida Tang (Irrational Games, LLC)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/724
- **Custom ID:** 724

### Overview


### Content Summary
[TLDR]
拒绝一刀切的静态教学，用自适应系统根据玩家失误实时补课，兼顾上手门槛与游戏深度。

[Background]
传统新手教程常陷入“太短玩家懵圈”和“太长玩家厌烦”的怪圈。Irrational Games 团队分享了如何用技术手段将教学设计成活的，适合希望优化玩家留存、不想降低游戏难度的开发者阅读。

[Recaps]
很多游戏为了照顾小白搞了一堆无脑引导，反而破坏了沉浸感。Irrational Games 提出的解决方案是 **自适应训练 (Adaptive Training)**，别把玩家当复读机教那些他们早就会的跳跃按键，而是等他们在实战里“翻车”了，再针对性地给提示。这样既保证了核心玩法的深度不被稀释，又能防止新手开局就劝退。

为了实现这个效果，团队借鉴了 AI 领域的 **专家系统 (Expert System)** 思路。本质上就是把策划的经验封装成无数条 IF-THEN 规则。比如检测玩家在保安区域触发了警报，就在内部的事实库把“安保知识”扣分，同时弹出教学弹窗；反之则加分。这种机制不再依赖线性的脚本顺序，而是能根据玩家的实时行为做出反应，类似于医生看病时的问诊逻辑。

在具体逻辑上，这套系统区分了两种模式：**后向推理 (Backward Chaining)** 是为了达成某个目标倒推条件，适合解谜；而游戏教学更侧重 **前向推理 (Forward Chaining)**，也就是数据驱动。系统维护一个 **事实数据库 (Fact Database)**，每当玩家操作改变游戏状态，就更新里面的事实，然后规则引擎自动扫描这些新事实来决定要不要触发提示。为了不让规则一多就卡顿，他们优化了逻辑运算流程，使用了 **Rete 算法 (Rete Algorithm)**，把规则变成网络流，只有当事实在变动时才重新计算，极大节省了性能开销。

这套方案已经应用到了《生化奇兵》的脚本系统里，虽然演讲者承认效果还在验证中，但测试玩家普遍觉得有用。未来的方向是把这套智能教学和难度系统打通，主动给玩家制造一些需要学习的场景，而不是被动等待出错。总之，这就是用代码去理解玩家，而不是用说明书去要求玩家。

## Dragged Kicking and Screaming: Source Multicore
- **Speaker:** Tom Leonard (Valve Software)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/543
- **Custom ID:** 543

### Overview


### Content Summary
[TLDR]
Valve 实战经验表明，搞定多核不能靠盲目加锁，得靠数据隔离和无锁机制，配合简易工具链才能真正发挥多核性能。

[Background]
2007 年前后 CPU 开始普及多核架构，但 Valve 的引擎代码多是单线程遗留问题。面对硬件变革，如何让现有代码在不崩溃的前提下利用多核算力成了最大痛点，本文分享了他们在多线程改造中的核心思路与避坑指南。

[Recaps]
刚开始 Valve 想把游戏客户端和服务端直接分在不同核心跑，结果发现到处都是共享数据，比如全局变量或者静态对象。很多人第一反应是加锁保护（Thread safety），但这玩意儿一旦滥用就会变成性能杀手。简单的 Mutex（互斥锁）会导致线程排队等待，不仅容易出错，还没法随核心数量扩展。所以他们的结论是：能不加锁最好，每个线程拿一份私有数据处理各自的任务，这种“无等待”（Wait-free）的设计才是王道。

在具体执行上，Valve 采用了一种混合多线程（Hybrid Threading）策略。并不是把所有东西都强行拆分，而是根据情况分配，比如渲染管线需要重新设计，让多个视角同时构建场景。为了解放普通游戏程序员的手脚，他们没选底层操作系统 API 或太晦涩的编译器扩展，而是自研了一套 Threading Infrastructure（线程基础设施）。这套工具封装好了函数并发、数组并行和队列任务，让写逻辑的人感觉像是在调正常函数，大大降低了上手门槛，鼓励大家去尝试并行优化。

遇到实在躲不开的共享资源怎么办？比如内存分配器这种高频竞争点，他们就上了无锁算法（Lock-free Algorithms）。利用原子操作和比较并交换（Compare-and-Swap）指令来维护数据结构，像链表这样的基础组件都能做到不阻塞。虽然实现起来复杂，需要处理 ABA 问题等细节，但相比锁带来的停顿效率提升巨大。总之，这是一套从理念到工具再到具体算法的全套解决方案，目标是让游戏特性能分解到更多核心上，而不是单纯追求帧数。

- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:**

- **Custom ID:** 500

### Overview


### Content Summary
[TLDR]
搞定模型切线空间 (Tangent Space) 计算，让法线贴图无缝复用，告别接缝和撕裂。

[Background]
很多玩家做法线贴图时，模型转角处容易出接缝 (seams) 或者镜像错位。本文提供了一套成熟的计算方法，特别适合技术美术和图形程序员，能帮你省下大量调试时间。

[Recaps]
这次分享的核心，就是解决怎么给模型算“切线空间”数据。传统的物体空间法线贴图 (Object space normal maps) 虽然直观，但限制了纹理复用，换个角度还得重画。换成基于切线的方案 (Tangent space normal maps) 后，数据独立于物体朝向，怎么转怎么贴都行。通过 TBN 矩阵 (Tangent-Binormal-Normal Matrix) 转换坐标系，能让着色器运算更快，还能节省显存。这就是为啥业界都爱用切线空间法线贴图。

算法部分其实有套标准流程，作者分了三步。第一步在每个小三角面上算基矩阵，避开小面片主导计算结果。第二步累加邻居的法线并加权，第三步处理 UV 的切线信息。最关键的是用角度权重处理那些 L Shape Problem（直角拐角），确保细分网格时接缝看不出破绽。如果遇到镜像翻转贴图或者超过 90 度折角，就必须触发顶点分割 (Vertex Splitting) 来隔离坐标系统，不然光影会出错。

最后给点避坑指南。数据压缩时要留个系数支持镜像翻转，输入模型尽量别让几何形状发生剪切变形 (Shearing)。渲染光照时建议直接用世界空间 (World Space) 计算，这样解码精度更高。这套方案经过 Crytek 验证，甚至免费开源在 Far Cry SDK 里，想搞次世代特效的老哥可以参考 ShaderX4 里的源码，照着做就能稳住质量。

## Everything about Particle Effects
- **Speaker:** Lutz Latta, http://www.2ld.de/gdc2007/ (EA)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/501
- **Custom ID:** 501

### Overview


### Content Summary
[TLDR]
别死守 CPU 算粒子，看准哪块硬件空闲就丢过去，优化到位能轻松跑百万粒子效果。

[Background]
以前做特效全靠 CPU 硬扛，算力不够还拖慢游戏逻辑。这篇演讲是 GDC 干货，教咱们怎么把计算任务挪到 GPU 或其他核心，让特效更猛不卡顿。适合想提升画质和帧数的程序美术看。

[Recaps]
这玩意儿其实就是一堆会动的点，叫粒子系统 (Particle System)。它们咋动呢？主要是靠力和约束，比如重力或者风力。最简单的做法是用闭式函数 (Closed-Form Function) 直接算位置，省存储但不够灵活；常用的还有欧拉积分 (Euler Integration)，虽然计算简单但要记着每个点的速度和位置。不过要想稳，得看硬件，现在大家早就不光盯着 CPU 了，图形处理器 (GPU) 才是算力大户，尤其是那些不用管逻辑的特效，丢给 GPU 去算简直完美。

硬件选型有个铁律：谁闲着用谁。要是 CPU 还有空核，那就多线程分摊计算；要是上传数据太费劲或者着色器带宽有余，那就用顶点着色器 (Vertex Shader)、像素着色器 (Pixel Shader) 甚至几何着色器 (Geometry Shader) 来搞。特别是像素着色器，能把位置和速度存纹理里，通过双缓冲不停迭代更新，这样能处理海量粒子而不卡脖子。对于像 Xbox 360 或 PS3 这种机器，它们的专用处理器如 Cell SPUs 也能派上用场，关键看你引擎哪个部分最闲。

干活的时候得注意几个坑。碰撞检测 (Collision Detection) 别全量搞，只算重要的，不然费钱。渲染的时候记得合批 (Batching)，别一个一个调接口，把状态一样的粒子打包一起画，效率翻倍。内存也别用默认的分配方式，提前建个池子统一回收。另外，因为粒子大多是“花活”，对结果精度要求不高，所以别纠结确定性，优先搞性能和缓存友好度。只要把这些细节抠好，百万级粒子也不是梦，画面看着还丝滑。
