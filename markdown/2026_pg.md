## 'Borderlands 4' Launch Load Testing
- **Speaker:** Jeffrey Waldron (Gearbox Software)
- **Duration:** 0 分钟
- **Category:** Game & Production Technology
- **Video Page:** 
- **Slide Page:** https://gdcvault.com/play/1035738
- **Custom ID:** 1035738

### Overview
Gearbox Software shares how its online engineering team prepared the backend platform for the launch of Borderlands 4 through large-scale, full-system load testing. Rather than validating individual features in isolation, the team built a unified test that simulated real player behavior across all online systems, from matchmaking to cross-platform play. This session details how the team generated realistic data, leveraged AWS and Serverless technology, and balanced test fidelity against cost and complexity. Attendees learn how Gearbox overcame late-stage technical challenges such as spot instance terminations and adopting Serverless Redis, and how these efforts led to both platform stability and improved team readiness. The talk provides practical takeaways for studios looking to conduct high-fidelity load testing at scale and highlights how holistic testing can strengthen both technical confidence and cross-team collaboration before launch.

### Content Summary
[TLDR]
Gearbox 用玩家行为模拟替代单纯接口压测，靠强可观测性与云原生架构搞定 BO4 上线，成本管控与实战演练缺一不可。

[Background]
随着《无主之地 4》在线内容大爆发，旧压测工具彻底拉胯。Gearbox 急需一套能平衡成本、真实模拟流量且不影响开发的新方案，避免上线那天直接炸服给玩家留黑历史。

[Recaps]
这次 Gearbox 最大的转变是从“测机器”变成了“测玩家”。以前用的是 Python 写的 Locust.io 脚本来测各种 API 接口，但这种方式容易漏掉真实用户的操作习惯。他们果断换了 K6 框架，定下了“一个测试统摄全局”的原则，不再死磕 56 个 HTTP 调用，而是模拟玩家开机、匹配、加好友这一套完整逻辑，总共写了 24 个动作覆盖全场景。这样虽然代码量涨了，但更能反映真实压力，避免了为了压测而压测的情况。

在实操过程中，团队踩了不少雷。原本以为 K6 是现成的工具，上手就能用，结果因为团队主力是 Golang 开发者，转 JS 语言搞得焦头烂额，还遇到了 Redis 连接没及时断开、AWS Fargate 的 Spot 实例频繁被回收等坑。特别是临近上线两周才发现账号认证服务太老旧，抗不住高并发，差点暴雷。他们不得不通过调整压测节奏来掩盖这个问题，这也让他们明白，盲目追求最新的 Serverless Redis 和廉价算力，有时候代价是把 Bug 留给上线当天。

最后给大家划个重点，钱不能白花，监控不能少做。压测持续了 15 个月，云资源成本甚至超过了游戏首月收入，所以他们学会了盯着成本账单调，非工作时间自动启停环境。最关键的是“可观测性 (Observability)"，也就是日志、指标和监控大盘，他们要求任何性能问题必须能在 2 分钟内定位。这次上线其实算成功了，没爆服也没人加班，这说明不管技术有多先进，团队对工具的熟练度和对成本的敏感度才是真正保命的关键。

### Overview
Agentic systems are creating new opportunities in LiveOps, from player segmentation to automated game operations. Amazon Bedrock AgentCore provides the foundation teams need to move from prototype to production with confidence. In this session, we demonstrate how AgentCore simplifies multi-agent orchestration, provides built-in security controls, enables comprehensive monitoring, and supports robust evaluation frameworks. Using real-world LiveOps examples, you'll see how teams can build scalable, production-grade agents while maintaining the reliability and observability that LiveOps demands. Whether you're building your first agent or scaling existing automation, you'll leave with a practical framework for deploying agentic AI in production gaming environments.

### Content Summary
[TLDR]
别再让人工死磕在线运营 (LiveOps) 的数据筛选活了，把活儿甩给智能体 (Agent)，配合 AWS 工具链加速落地，才能真正释放精力去搞创意。

[Background]
很多同行在做长线游戏时，被海量运营数据搞得晕头转向，本地跑通的概念验证 (POC) 到了生产环境就挂。这次演讲主要是给团队指条路，介绍如何利用生成式 AI (Gen AI) 和智能体技术把繁琐的运营工作自动化，并安全、快速地部署到正式生产系统中。

[Recaps]
现在的长线游戏动不动就运营十年以上，随着玩家代际变化，在线运营 (LiveOps) 的复杂度越来越高。以前搞个活动或投放广告，想做个精准的用户分群 (Segmentation)，光是从数据库多张表里组合条件，就能算出几百万种可能性，光排查这些数据就得耗掉几天时间，纯靠人肉干活不仅慢，还容易出错，这就是典型的流水线痛点。

解决办法就是引入智能体 (Agent)。这帮家伙能 24 小时不睡觉干活，把原本需要几天才能完成的日常观察和假设验证 (Hypothesis) 过程，直接压缩到几小时甚至十几分钟。人类开发者得把自己从这些重复劳动里解放出来，专门负责那些需要创意和策略的高阶决策环节，跟 AI 搭档干活，这才是未来提效的核心。

不过光有思路不够，很多企业本地跑个 Demo (POC) 挺溜，一上生产环境就凉。AWS 这次推的 Amazon Bedrock Agent Core 和 Kero 就是为了填这个坑。前者是个现成的托管平台，管好了底层的网络、记忆管理和细粒度的安全权限，不用担心智能体乱动东西；后者就是个带 AI 的编程助手，能帮人按现有规范写代码，确保做出来的东西能稳当当地跑在服务器上，而不是只停留在实验阶段。这样一套组合拳下来，能真正实现从概念验证 (POC) 到生产就绪 (Production Ready) 的跨越，大家赶紧去试试官方提供的 Workshop，手把手教你怎么用几行代码部署出一个安全的智能体环境。

## Architecting DDoS-Resilient Multiplayer Game Servers on Amazon GameLift (Presented by Amazon Web Services)
- **Speaker:** Michael Jackson (AWS)
- **Duration:** 49 分钟
- **Category:** Game & Production Technology
- **Video Page:** https://gdcvault.com/play/1035624
- **Slide Page:** 
- **Custom ID:** 1035624

### Overview
Reliable player connectivity is foundational to modern multiplayer games, yet increasingly difficult to maintain in the face of sophisticated network-based attacks. This session focuses on how multiplayer games can defend player traffic - without adding latency, operational complexity, or forcing studios to redesign their networking stack. The Amazon GameLift team will walk through the multiplayer-specific DDoS threat model, common failure modes observed in live service games, and architectural patterns for protecting player connections in real time. We'll explore how protection can be integrated directly into the game server hosting layer, allowing studios to absorb large-scale attacks while preserving gameplay performance and developer velocity. Attendees will gain a practical understanding of how to approach player connectivity protection as a first-class part of their multiplayer architecture, including key design tradeoffs, adoption considerations, and lessons learned from real-world game workloads.

### Content Summary
[TLDR]
亚马逊 GameLift 上线了内置 DDoS 防护方案，专为 UDP 网游定制，免费且几乎不增加延迟，有效抵御恶意玩家发起的攻击。

[Background]
多人联机游戏是 DDoS 攻击 (DDoS Attack) 的重灾区，尤其是恶意玩家为了上分主动搞破坏。传统防御方案容易误伤同 IP 的真玩家，且维护成本高。这主要适合正在使用云服务的后端团队，帮助其低成本解决对抗性攻击与启动日的稳定性难题。

[Recaps]
演讲开场 Mike 就先泼了盆冷水，指出现今游戏业近半数攻击都冲着工作室来。很多是恶意玩家为了不想输，花几十块买僵尸网络 (Botnet) 去堵自家服务器口，甚至想通过打流媒体直播来砸商场的名声。传统的防御手段要么按 IP 限制会误杀住在同一公寓的邻居，要么靠静态特征码检测，结果就像锁匠一样，钥匙一破防线就全崩。

亚马逊这次的核心大招是改底层架构，不再让客户端直连游戏服务器，而是加了一个中继层叫 Player Gateway。玩家必须先连到这个网关，拿到访问令牌 (Access Token)，验证通过了数据才会透传到后台。这样一来既藏起了服务端真实的公网 IP，又做了动态端点轮换，谁敢攻击哪个端口就会瞬间被封禁并自动切换新的 IP，不会影响到同一局里的其他玩家。

性能方面特意针对 UDP (用户数据报协议) 流量和高包速率做了优化，这与普通网页请求完全不同，确保低延迟体验。集成也不难，只要在游戏会话创建流程里调用新接口 Get Player Connection Details (API) 就能跑通。虽然目前仅限七大地域且支持 UDP 协议，但对云原生的 GameLift 客户来说是白送的福利，实测延迟增加不到 3 毫秒，真正做到了攻防一体且无感接入。

## Augmenting NPCs with LLMs: Practical Experience from NC State University & Arm Developer Labs (Presented by Arm)
- **Speaker:** Kieran Hejmadi (Arm)
- **Duration:** 29 分钟
- **Category:** Game & Production Technology
- **Video Page:** https://gdcvault.com/play/1035613
- **Slide Page:** 
- **Custom ID:** 1035613

### Overview
Nonplayer characters (NPCs) are moving beyond prescripted trees to responsive agents that converse, plan, and act in context. In this talk we share practical lessons from an Arm Developer Labs project run in partnership with North Carolina State University (NCSU), where a team of Master's students is building a proofofconcept, puzzlestyle game that showcases LLMaugmented NPCs running on Armbased devices. nnWe walk through the endtoend approach the student team uses to keep gameplay smooth while adding intelligence: selecting and sizing models for ondevice inference, applying quantization to meet 3060 FPS budgets, and using structured generation so model outputs map deterministically to inengine actions.

### Content Summary
[TLDR]
本地化运行小参数大语言模型能让手机 NPC 具备动态语音和剧情生成能力，且无需联网、成本低廉，是移动端 AI 落地的可行方向。

[Background]
开发者普遍担忧手机带不动本地大模型，或者联网依赖导致体验割裂。此演讲由 ARM 与高校合作，通过真实项目验证了移动端本地 AI 的可行性，并分享了从硬件选型到工程落地的全套避坑指南。

[Recaps]
先说结论，手机跑本地大模型绝对靠谱。虽然受限于电池功率和内存，但配合**量化 (Quantization)** 技术和**中央处理器 (CPU)** 的普及，目前市面上主流的**大语言模型 (Large Language Models)** 只要参数压到合适范围就能在手机上跑。斯坦福的数据显示，随着模型效率提升，未来两三年内高性能模型也会变成手机端标配。比起强制上**图形处理器 (GPU)**，在现有**中央处理器 (CPU)** 上做文章反而更稳妥，毕竟 ARM 架构覆盖了绝大多数的安卓设备。

为了演示效果，学生团队做了个太空逃亡游戏，直接把**大语言模型 (Large Language Models)** 做成了飞船的智能管家。他们没走云端路线，而是把模型下载到本地，通过**应用程序接口 (API)** 进行对话和逻辑判断，还集成了语音转文字功能。这样的好处很明显，既不需要联网也不怕延迟，玩家在断网环境下照样能跟 NPC 互动。这种玩法特别适合那些想要沉浸式单机的独立开发者，能极大丰富 NPC 的反应深度。

当然，落地过程也不是没有坑。最大的阻碍是体积问题，加上模型文件很容易超过应用商店的一百兆限制，所以设计时必须采用首包小、后补全资源的策略。另外，模型太小容易胡编乱造，需要人工微调才能保证准确性。最后的建议是，别指望一把梭哈，要根据用户手机性能动态加载不同精度的模型，既能省电又能保质量。整体来看，这套技术方案现在门槛已经很低了，开源社区的资源也非常丰富，值得尝试。

## Automatic Wrapping of Facial Expression Scans with WrapAI (Presented by Faceform)
- **Speaker:** Andrei Krovopuskov (Faceform)
- **Duration:** 36 分钟
- **Category:** Game & Production Technology
- **Video Page:** https://gdcvault.com/play/1035647
- **Slide Page:** 
- **Custom ID:** 1035647

### Overview
In this talk, we'll present a pipeline for fully automated wrapping and cleanup of dozens of FACS scans using Faceform WrapAI. Building a likeness rig from real FACS scans often involves a lot of manual work. We'll demonstrate how this can be solved in just a few clicks, with a level of quality suitable for silver-level likeness characters.

### Content Summary
[TLDR]
大佬推了个新工具，用全自动管线搞定了从真人扫描到游戏可用混合形状的一键批量处理。

[Background]
以前手动调扫描数据表情得熬好几个月，想做大厂的高拟真角色更是头疼。这方案专门治这个病，适合需要攒数据练 AI 或者批量做真人的团队。

[Recaps]
这玩意儿叫 RAPAI，底子是靠 RAP 那个节点图 (Node Graph)。思路很骚，先用旧角色素材拼个基础表情（Cybalera），再用差异转移 (Delta Transfer) 把真人脸的特征压上去。相当于有了个通用模板，不用从零捏每个表情，速度起飞。

光有模型不行，还得洗数据。以前大家靠几个点硬稳头，现在直接上头部稳定化 (Head Stabilization) 算法分析整张皮怎么动。脖子那儿容易失真，改用包裹 (Wrapping) 技术保体积，配合光流 (Optical Flow) 算清楚纹理，毛孔都不带乱的。

最后就是绑定前的收尾工作。张嘴笑力度不一这种归一化问题，脚本自动算最佳解。连嘴唇闭缝、眼皮防穿这些细活儿都打包好了，甚至支持左右脸不对称拆分。弄完这一套，直接导进引擎就能用，一天能干几十个人的活。

[Background]
行业正处艰难期，开发成本涨了 Yet 消费疲软，还得跟短视频抢时间。这次分享主要给大伙吃定心丸：ARM 和头部厂商联手把 AI 算力和图形黑科技搬到了手机端，让开发者能少踩坑多搞出好画面，适合所有关心手游性能和效率的老哥们。

[Recaps]

### Content Summary
[TLDR]

[Recaps]
演讲开篇先给新手扫盲了什么是 PCG (Procedural Content Generation)，这可不是简单的蓝图连线，而是能在场景里写逻辑自动生成蘑菇林或建筑的工具。Chris 用两分钟搭好蘑菇群的演示展示了它有多快，但他也坦诚自己早期就犯过错误，喜欢搞超大个的单一大图 (Monolithic Graph)。在大项目里，这种把所有石头树木逻辑塞进一个图的写法是大忌，一旦团队协作很容易撞车，而且改个参数可能得重头算起。

要在大地图上干活，首要敌人就是性能和协作。存不下所有东西、修改时源文件 (Source Control) 冲突严重、编辑器打开太慢，这些坑大家都踩过。解决方案的核心在于“分区” (Partitioning)，把世界切成网格，不同层级的物体分配在不同大小的格子里。这样既能减少内存占用，还能让树知道哪不能长石头，避免重叠。同时要把计算压力分摊出去，关键的重算放在离线阶段 (Offline Generation)，复杂的运算跑在编辑器外，运行时只负责渲染动态细节 (Runtime Generation)。

为了进一步压榨性能，Chris 给了几个实用建议。别随便在节点之间传大量无用属性，尤其是上传 GPU 之前，先把垃圾数据过滤掉，否则数据传输开销会让你怀疑人生。多用 GPU 节点连起来算，少切回 CPU，利用 PCG Profiler 定位瓶颈节点也很重要。另外，现在的 Landscape Layer（地形图层）不仅能贴图，还能存逻辑元数据，比如标注某区域是城市还是荒野，供 PCG 读取决策。未来 5.8 版本还会加入手动非破坏性编辑支持，让我们能直接挪动生成的森林，而不用炸重整个节点。

[Background]
针对新机旧机混用的尴尬现状，适合移动端新手。主要解决手机发烫、功耗高、帧率低的问题，教你怎么用工具排查并合理牺牲画质换性能。

[Recaps]
演讲的核心观点很实在：优化别指望一招鲜，而是靠无数个小细节堆出来的。约翰先指出，手机不像电脑那样能一直满载运行，受限于散热，移动端的 **GPU（图形处理器）** 必须精打细算。普通的 **分析器（Profiler）** 和 **帧调试器（Frame Debugger）** 只能看到应用层的情况，要看清楚硬件到底干了啥，得用 **Arm 性能工作室（Arm Performance Studio）** 里的 **流形（Streamline）** 和 **帧顾问（Frame Advisor）**。最关键的技术点在于 **分块渲染（Tile-Based Rendering）**，这虽然省了显存，但会让 **几何体处理（Geometry Processing）** 变贵，因为每个三角形都要被分类一遍，所以千万别给 GPU 塞太多没用的三角面。

具体的优化方案就是避开常见坑。比如场景里有几百万个三角面，必须开启 **烘焙遮挡剔除（Baked Occlusion Culling）** 或 **GPU 遮挡剔除（GPU Occlusion Culling）** 把看不见的物体踢出去。对于透明物体造成的 **过绘（Overdraw）** 问题，别直接用半透明，试着用 **Alpha Clip** 或者调整 **精灵网格（Sprite Mesh）**。还要警惕 **微三角（Micro Triangles）** 这种覆盖像素极少的碎片，它们会让 **片元处理（Fragment Processing）** 效率大跌，最好的办法就是上 **细节层次（Level Of Detail / LODs）**。同时检查后期处理，把不必要的模糊或景深关掉，往往能省下好几毫秒，积少成多才是王道。

后半段多米尼克接着讲大杀器 **上采样（Upscaling）**。现在的技术分三类：**空间上采样（Spatial Upscalers）** 效果一般，**时序上采样（Temporal Upscalers）** 需要用到 **运动矢量缓冲（Motion Vector Buffer）**，而 **机器学习上采样（Machine Learning Upscalers）** 像 **DLSS** 虽然强但依赖特定硬件。移动端要特别注意电池和发热，太重的算法会导致降频。虽然 **FSR** 等技术在 PC 上很猛，但在手机上可能需要专门的 **ARM ASR**。另外强调，上采样不是免死金牌，如果底层优化没做，开了上采样也救不了性能，甚至可能因为自定义渲染通道没适配好导致画面鬼影，集成起来其实挺麻烦，建议老手带新人一起搞。

## The Evolution of Real-Time Global Illumination in 'Love and Deepspace' (Presented by Arm)
- **Speaker:** Tianlong Ruan (Infold Games)
- **Duration:** 45 分钟
- **Category:** Game & Production Technology
- **Video Page:** https://gdcvault.com/play/1035619
- **Slide Page:**

### Overview
Love and Deepspace is a mobile game dedicated to providing players with a near-realistic romantic experience. Providing realistic rendering on mobile devices is our constant goal. Global illumination is one of the most challenging technical issues. Mobile platforms have significant constraints in terms of memory, bandwidth, and hardware performance, making traditional algorithms difficult to directly apply. ### Content Summary
[TLDR]
为了在手机上跑动玩家自由装修的高品质光照，《恋与深空》自研了一套不依赖硬件光追的表面辐射级联解决方案。

[Background]
《恋与深空》要做动态昼夜和玩家自建家园，传统静态烘焙搞不定动态光影，现有方案要么太吃手机性能，要么没法适配 UGC，工程师必须另辟蹊径。

[Recaps]
各位同行先别急，咱们先看背景。《恋与深空》这项目要搞动态昼夜和玩家自制家园，这就对**全局光照 (Global Illumination)** 提出了变态要求。传统用的**烘焙贴图 (Lightmaps)** 改不了动态光影，而现有的**路径追踪 (Path Tracing)** 方案大多依赖硬件**光线追踪 (Ray Tracing)**，普通手机根本带不动，这就是当时的死结。

一开始团队也走了弯路，第一版想用**球谐函数 (Spherical Harmonics)** 来近似环境光，结果精度不够，画面太虚；第二版尝试简化版的**路径追踪**，画质是好了，但容易出现**鬼影 (Ghosting)**，而且还得靠美术手动放**探针 (Probes)**，这对于**UGC（用户生成内容）** 场景完全不友好，一旦玩家随便造东西，光照就穿帮，迭代效率低到没法看。

最后他们憋出了大招：**Surface-Based Radiance Cascade GI**。简单来说就是把场景物体拆成一个个小**基础曲面 (Surface)**，然后用**软件光线行进 (Software Ray Marching)** 去计算遮挡。这玩意儿自带**哈希网格 (Hash Grid)** 加速，还能通过**辐射级联 (Radiance Cascade)** 根据距离自动调整光线密度。此外还特别修复了**光照泄漏 (Light Leaks)**，比如用透明外环封堵缝隙，保证室内室外不漏光。最关键的是探测点自动跟镜头走，不需要人工干预，完美解决自定义场景的照明问题。

为了压榨性能，后期还加了**超分算法 (Super Resolution)** 给低端机做了降级方案，甚至允许不同设备加载不同的资源等级。结果在 iPhone 12 上跑起来只要两毫秒，比预期快得多。这套方案不仅现在好用，未来也能平滑升级到硬件光追，算是给移动端实时光照打了个样，值得老哥们参考。

- **Speaker:** Paul Georges (Epic Games)

### Overview

### Content Summary
[TLDR]
Mobile 开发核心在于利用 UE5 的 `可伸缩性 (Scalability)` 机制，针对碎片化硬件制定“低配优先、向上扩展”的动态画质策略，确保玩家覆盖率最大化。

[Background]
移动端芯片型号无数，安卓生态更是极度 `碎片化 (Fragmentation)`。如果不针对硬件差异做 `性能优化 (Performance Optimization)`，容易导致低端机卡顿或高端机白忙活，这简直是用爱发电。本文适合所有负责 UE5 移动版开发的 `程序 (Programmers)` 和 `技术美术 (Tech Artists)` 参考避坑。

[Recaps]
搞定移动端的核心就是 `可伸缩性 (Scalability)`，它不是简单的开关，而是根据硬件能力动态调整 `视觉质量 (Visual Quality)`、性能和资源占用的能力。起步别乱设，先用 UE5 的 `模板项目 (Template Projects)` 里的移动预设，但这不够，必须深入底层。重点要搞清楚 `控制台变量 (CVARs)` 的优先级链：项目设置的 `覆盖链 (Override Chain)` 决定了最终值，而 `插件 (Plugins)` 必须做一次审计，很多默认开启的插件会吃掉宝贵的 `二进制包体积 (Binary Size)`，对于手游更新和下载体验至关重要。

针对不同机型的识别靠的是 `设备配置档案 (Device Profiles)`。系统启动时会根据硬件信息加载对应的 Profile，里面打包了一堆 CVARs。iOS 好处理，安卓因为机型太多，得用 `正则表达式 (Regular Expressions)` 匹配 `GPU 家族 (GPU Family)` 和内存等特征。更高级的做法是使用 `设备配置片段 (Device Profile Fragments)`，就像乐高一样拼凑配置，避免 Profile 列表爆炸。别忘了 `Config Rules`，它能作为热修复手段，在初始化前就拦截不支持的设备，还能动态下发配置。

在内容制作和流程上，有几个实用技巧。第一，`细节层次 (Level of Detail)` 要打开，自动优化网格体顶点数；第二，材质里用 `材质质量切换 (Material Quality Switches)`，不同档位用不同的计算复杂度；第三，也是最重要的，别只盯着电脑屏幕跑测试。学会连真机调 `设备输出日志 (Device Output Log)`，甚至用四指点击屏幕呼出控制台修改参数实时看效果。最后强烈建议上自动化性能测试，每次改动配置就跑一遍回归测试，否则你根本不知道自己是在优化还是变慢了。记住，设计时先从最低配设备考虑，在此基础上往上扩画质，千万别反过来做。
