## High Performance Physics Solver Design for Next Generation Consoles
- **Speaker:** Vangelis Kokkevis (Google)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1013474
- **Custom ID:** 1013474

### Overview
This presentation guides developers though the unique code and data design considerations required to build high-performance game engine components for the next generation console hardware.  Using examples from specific physics solvers such as fluids, cloth, rigid and articulated bodies, it highlights the necessary steps for designing and implementing efficient code that makes full use of the hardware's impressive potential.

### Content Summary
[TLDR]
针对 PS3 Cell 架构搞物理引擎，核心是靠多线程并行、数据流式传输加软件缓存，把内存小的缺点变废为宝。

[Background]
当年 PS3 开发机难调，Cell 架构核心多但内存小且访问慢，传统引擎代码基本没法直接跑。索尼资深大佬掏心窝子分享移植和优化实战经验，专为卡在这个坑里的同行准备。

[Recaps]
先说大框架。PS3 的 Cell 架构很特殊，PPU (PowerPC Processing Unit) 管主逻辑，SPU (Signal Processing Unit) 负责算力。最大瓶颈是 SPU 只有 256K 本地存储 (Local Store)，放不下所有数据。解决办法就是“流式读取”加“双缓冲”，把数据按块通过 DMA (Direct Memory Access) 搬进搬出，让计算和传输同时跑，别闲着等搬运，这是提速的关键。

再看具体物理系统。做布料仿真 (Cloth Simulation) 时，调整节点距离得随机访问，所以把顶点全放本地，只流式传边；刚体系统则搞了个软件缓存 (Software Caching)，重复用的几何模型缓存在 SPU 里，避免了每次都去慢速的主存拉数据。这招在窄相位碰撞检测里特别管用，相当于给经常访问的数据加了个小保险柜。

最后是工程技巧。代码里的数据结构很重要，“结构数组 (Structure of Arrays, SoA)"比“数组结构 (Array of Structures, AoS)"更能吃满 SIMD (Single Instruction Multiple Data) 性能。他们有个鸭子 Demo，把水、布、船刚体分给不同 SPU，虽然能加速，但要注意任务平衡。特别是像高斯赛德尔求解器这种强依赖的步骤，硬上并行反而会因为等待拖累速度，得根据实际依赖情况决定串还是并。

## Crowd Simulation on PS3
- **Speaker:** Craig Reynolds (Sony Computer Entertainment America)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1013476
- **Custom ID:** 1013476

### Overview
Crowds and other forms of flock-like group motion are modeled with interacting particle systems.  These multi-agent simulations are computationally expensive because each agent must identify its nearest neighbors.  Time to run the simple implementation grows as the square of the number of agents, so large groups can be prohibitively expensive.  This lecture will describe experiments running crowd/flock simulations with thousands of individuals at 60 frames per second on the PLAYSTATION3.  It will discuss how a traditional crowd system can be recast to map efficiently onto the Cell architecture of the PS3.  The lecture will include implementation details and live demos will be shown.

### Content Summary
[TLDR]
Craig Reynolds 揭秘如何利用 PS3 的 Cell 架构和空间分桶技术，实现万单位角色的 60 帧实时仿真。

[Background]
当年 PS3 刚发布，那个 Cell 处理器结构太特么古怪，传统算法一跑上千人就崩。这篇主要给引擎组和技术大牛指路，讲讲在性能极限下如何让一群 NPC 跑得飞起，属于硬核技术分享。

[Recaps]
这位大佬 Craig Reynolds 当年主要就讲了一件事：怎么让 PS3 那玩意的 Cell 架构 (Cell Architecture) 跑起来上千个独立的虚拟角色。核心就是搞了个叫 PSCrowd 的库，利用通用处理单元 (PPU) 调度，配合六个协同处理单元 (SPU) 来干粗活，硬生生把 1 万个简易角色塞进 60 帧里，这在 2006 年简直是黑科技，直接解决了大规模群体运动的计算量问题。

难点在于群体运动本质是“粒子系统”(Particle System) 里的交互问题，普通做法复杂度是 O(n²)，人越多卡得越死。Reynolds 的思路是把空间切成小格子，也就是“空间分区”(Spatial Subdivision)，对应到代码就是“桶”(Bucket) 概念。每个 SPU 只负责算自己管的那一片桶，互不干扰，这就变成了并行更新。找邻居不再满世界搜，只看周围几个桶，速度直接起飞，彻底告别了暴力遍历。

为了省算力，他还玩了个“摸鱼”大招，叫 skipThink。所有人不用每一帧都重新思考行为逻辑，可以轮流跳过，只要上一帧的转向力还能凑合就行。再加上快速数据搬运的 DMA(直接内存访问) 技术，最终效果能跑 7000 条鱼或者 1 万人，而且用了传统的鸟群算法 (Boids)，看起来跟真的一模一样，这对咱们平时做开放世界游戏的优化思路启发很大。

## Best Practices for Game Development
- **Speaker:** Grady Booch (IBM)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1013466
- **Custom ID:** 1013466

### Overview
In game development, software complexity has reached a critical mass, the artistic element has spiked, and for both domains, reuse is minimal. The game community is experiencing issues that other software-intensive domains have passed through and will benefit from drawing upon best practices in defense, embedded, and enterprise systems. We will examine best practices and application to game development.

### Content Summary
[TLDR]
游戏开发别光靠堆大神，核心在于搭建稳健的**软件架构 (Software Architecture)**，不然规模一扩大项目必崩。

[Background]
这是 2006 年 IBM 大佬 Grady Booch 的分享，当时游戏复杂度爆炸，好多大厂项目因为骨架没搭好直接烂尾。他拿建筑学和电影工业打比方，专门给咱们技术和管理层提个醒：想长久赚钱，光招聪明人没用，得有章法的工程实践，适合开发者、制作人及想转型的老手看。

[Recaps]
现在代码量涨得太吓人了，物理世界的桥梁和建筑都能稳定几百年，软件却总像无头苍蝇。以前觉得**软件架构 (Software Architecture)**就是画图纸写文档，其实它是系统的骨架和决策集合。就像建楼要算承重，游戏越做大，越不能全靠**部落记忆 (Tribal Memory)**，也就是老员工脑子里那点经验。你得像物理系统一样，靠反复试错和量化评估来沉淀，而不是拍脑袋定方案。

说到具体游戏项目，过去死掉的大作比比皆是，比如《虚幻竞技场》(Unreal Tournament) 缺中央设计文档，《天国计划》(Tropico) 前期规划不足，《神偷》(Deus Ex) 没提前规避风险。这就好比瞎指挥，结果全是返工。现在的开发环境也变了，CPU 从单核变多核，还得搞**多线程 (Multi-threading)**，服务器要应付海量用户，广告收入也得整合进来。这时候照搬以前的流水线肯定不行，得多借鉴电影工业那种严格的资产管理和审查流程。

最后，架构到底咋弄？别迷信某个具体技术，像 Eclipse 插件机制那样，通过标准接口让不同部分拼起来，既能扩展又不乱套。这就是**模块化 (Modularization)**和**组件 (Component)**的力量。成功的架构得有意为之，结构清晰且可见。效率提升不只靠人，还要结合工具、流程和团队技能，最终目的是实现**业务驱动开发 (Business-Driven Development)**，让每一行代码都产生价值，别让项目死在内部复杂度上。
