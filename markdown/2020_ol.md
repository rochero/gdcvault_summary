## Online Game Technology Summit: Machine Learning for Optimal Matchmaking
- **Speaker:** Josh Menke (343 Industries)
- **Duration:** 54 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1026624
- **Slide Page:** https://www.gdcvault.com/play/1026585
- **Custom ID:** 1026624

### Overview
Matchmaking has changed little since it was first automated. The general approach is to look for an ideal match across one or more preferred metrics, and then expand the ideal until a match is found. Issues with this approach make it difficult to trade-off the importance of each metric, hard to customize to specific player populations including geographic ones, and expanding forces players to wait longer than necessary. This session will present TrueMatch, a new matchmaking approach that allows developers to more intuitively express the value of each metric, and then uses machine learning to automatically optimize over the desired metrics in real-time. The results give better matches in less time and are customized to each player's characteristics and each region's real-time concurrency as it changes over time.

### Content Summary
[TLDR]
别再用死板规则匹配玩家了，用机器学习实时预测并优化规则，在等待时间和公平性之间找到真正的最佳平衡点。

[Background]
传统联机游戏的 Matchmaking (匹配系统) 靠人工定死规则，导致高峰期匹配烂，低峰期等人久。343 Industries 的 Josh Menke 分享了他如何用 Machine Learning (机器学习) 彻底解决这个痛点，特别适合负责多人游戏后端或数值设计的开发者。

[Recaps]
现在的 Matchmaking (匹配系统) 大多还是老一套，全靠开发手写规则，比如“允许的最大技能差是多少”。这有个大坑：早晚高峰玩家数量不一样，但规则不变。结果就是人多时为了凑局牺牲公平性，人少时傻等半天还凑不齐好局。更糟糕的是，这种静态规则没法区分不同地区的情况，英国玩家和美国玩家的网络环境需求本来就不一样。

演讲核心方案叫 TrueMatch，本质就是用 Machine Learning (机器学习) 代替人工调参。它分三步走：先算当前有多少玩家在排队，再用模型预测如果按现在规则匹配会有什么结果，最后找个最优解 (Optimizer)。关键是搞了个 Utility Function (效用函数)，把等待时间、公平性、延迟都换算成可比较的分数，比如“愿意多等 10 秒换 1 毫秒更好延迟”，让设计师直接量化权衡。

最骚的操作是把“技能值”改成“百分位”来匹配。普通方法是直接比分数，但高手区密度低，新手区密度高。用百分位的话，大家看到的可选池大小是相对公平的，不管人多人少，等待体验基本一致。实测 Halo 5 数据证明，这套方法能把平均等待时间砍掉 72%，虽然牺牲了一点点公平性，但这买卖绝对划算。最后还能给每个玩家单独预估排队时间，再也不怕玩家炸毛说匹配太慢。

## Online Game Technology Summit: Scaling to 10 Concurrent Users: Online Infrastructure as an Indie
- **Speaker:** Andrew Erridge (Gamebreaking Studios)
- **Duration:** 29 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1026625
- **Slide Page:** https://www.gdcvault.com/play/1026593
- **Custom ID:** 1026625

### Overview
After years building online games that serve 100 million players, Dru tells the story of how the technology that originally backed his (much smaller) university project evolved into a sprawling online platform through the game's 5 year development cycle and subsequent launch. In doing so, Dru tries to illuminate which of the AAA concepts he applied "scaled down" and which were illusions of grandeur. His talk dives into inescapable decisions like dedicated servers vs peer to peer, microservices vs monolith, and when to use the cloud, among others.

### Content Summary
[TLDR]
独立游戏做联机后台别盲目迷信微服务，选对技术栈保命，核心永远是按时把游戏做完上线。

[Background]
独立开发者想做联机功能，面对自建后端还是用第三方服务常犯难。这讲总结了从学生项目到商业化过程中的踩坑经验，适合小团队想省钱省时间搞定服务器架构的同学看。

[Recaps]
第一块是技术选型。当年大家都在比谁的语言新，最后定下来用了 Node.js 环境 (Node.js runtime)，搭配 Express 框架 (Express)。这东西异步 IO 能力强，单线程处理网络请求不卡顿，特别适合小团队快速迭代。后来还加了 TypeScript (TypeScript) 来保证代码质量。这建议现在听也不过时，只要不是超大型系统，这套组合拳绝对是独立开发者的利器。

第二块是通信协议。纯靠 HTTP 协议 (HyperText Transfer Protocol) 轮询效率太低，根本没法确认玩家是否在房间。得用能保持长连接的双向通道，比如 WebSocket (WebSocket) 或者 gRPC。哪怕是用底层的 TCP (Transmission Control Protocol) 也能解决会话问题，但千万别为了省事只写 HTTP，不然后期改接口全是坑，得让客户端和服务端真正“在线”对话。

第三块是架构设计。最忌讳的就是盲目跟风搞 微服务 (Microservices)。虽然听起来很高端，但独立团队搞一堆独立部署的服务，光是部署、监控、数据一致性就能拖死你。像创建个账号要跨好几个库调用，断一个环节就出鬼状态。除非你真的有几十万用户，否则单体架构 (Monolith) 加水平扩展才是性价比之王，别把时间浪费在造轮子上。

最后是心态。独立开发时间成本最高，别碰还没成熟到 1.0 的新框架。有些技术看着光鲜但其实是坑，别去当小白鼠。与其花时间研究怎么优雅地拆分服务，不如早点把游戏上线，让玩家玩到好东西。毕竟你的核心竞争力是玩法，不是服务器架构，省下来的每一分钟都得花在刀刃上。

## Free to Play Summit: Forget CPI: Dynamic Mobile Marketing
- **Speaker:** Heather Gainer (Kongregate)
- **Duration:** 20 分钟
- **Category:** Free to Play Summit
- **Video Page:** https://www.gdcvault.com/play/1026607
- **Slide Page:** https://www.gdcvault.com/play/1026682
- **Custom ID:** 1026607

### Overview
Cost per install (CPI) has traditionally been one of the most important metrics for mobile user acquisition. However, the industry is changing and if you are still focused on your CPI then you are already behind. In this talk we will discuss how the industry is changing the way we bid on users. We will cover why CPI is no longer as important and instead, what metrics we should be focusing on. Furthermore, we will discuss how we measure success. Finally, we will talk about how these new trends are impacting the marketplace and the challenges they present for performance-based marketing.

### Content Summary
[TLDR]
别死磕低价安装成本，动态出价和后端变现收益才是手游买量盈利的核心。

[Background]
很多团队盯着测试期的低成本，一上全球就崩心态，不懂为什么花大钱也能赚。这篇给买量操盘手和制作人看的避坑指南，教大家怎么算清账。

[Recaps]
以前做游戏买量，团队最怕看到数字高，觉得成本高就是亏。Heather 拿自家作品《Idle Frontier》举例，指出测试市场 (Soft Launch) 是为了测稳定性、收数据，用户越杂越好，风险越低；但正式发全球就是奔着赚钱去的，得找愿意充值的优质用户。这导致上线后 CPI 从测试期的$1.6 飙升到$6.2，开发商一度慌神，其实只要算好账，高成本也是合理的。

行业老规矩别太迷信“平均安装成本 (Cost Per Install, CPI)"，核心是看最终能不能回本。建议用“预估净玩家价值 (Estimated Net Player Value, ENPV)"替代模糊的“玩家终身价值 (Lifetime Value, LTV)"。重点关注前七天留存率和首日“应用内购买 (In-App Purchase, IAP)"占比，以及“投资回报率 (Return On Ad Spend, ROAS)"。只要七日 ROI 达标，哪怕单用户获取价贵十倍，只要后续产出够多，照样能盈利。

现在的广告网络都进化了，别再死守旧式固定出价。Facebook 的“价值优化 (Value Optimization, VO)"策略敢花$14 买个用户，但换来的是高消费能力的大佬；Google 接入 Firebase 后，机器学习更快，不用烧几十万冷启动；IronSource 还能把广告收入和 IAP 一起算进 ROAS 里，特别适合混合型变现游戏。Unity 甚至能做用户级定向。像 Maloco 这种通过实时竞价 (Real-Time Bidding, RTB) 的平台也有专人帮你盯盘。总之，让 AI 帮你找精准流量，只要最后利润是正的，别纠结单价高低。

## Online Game Technology Summit: Start-And-Discard: A Unified Workflow for Development and Live
- **Speaker:** Bjorn Tornqvist (Ubisoft Massive)
- **Duration:** 26 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1026718
- **Slide Page:** 
- **Custom ID:** 1026718

### Overview
Ubisoft Massive is unifying the production and live aspects of games development by focusing on a single unified workflow called Start-and-Discard. This enables the product and the workflow to be iterated upon in tandem during production and after release.nnThe Start-and-Discard workflow increases the quality-of-product by ensuring that every playtest is 100% relevant for the live game. Furthermore it increases quality-of-life by ensuring that the live workflow of deploying, debugging, and monitoring is practised and iterated upon at every single playtest. nnThis talk covers the Start-and-Discard workflow in detail, as well as the logical implications of it for production, qc, and live.

### Content Summary
[TLDR]
告别开发上线两张皮，拥抱云原生思维，通过代码定义一切让测试环境完全复刻上线状态。

[Background]
现代网游强依赖在线服务，存档和逻辑都在云端，这意味着永远不能离线。但随着项目迭代，测试环境越来越乱，容易导致上线即事故，急需一套统一的线上化研发流程来规避风险。

[Recaps]
Massive 的在线架构早就把 AI 和存档都扔到云端了，客户端只要负责画面和 UI，这样性能预算更足，还方便无缝联机。系统由超过 20 个微服务 (Microservices) 组成，但这有个代价：单机模式也得随时在线，稳定性就是生命线。以前为了图快，开发阶段大家各用各的测试桩 (Stub)，导致很多人以为测试环境没问题，结果一上线就挂，因为真正跑的代码根本没测过。

解决办法就是推行“启动和销毁 (Start and Discard)"策略，配合基础设施即代码 (Infrastructure as Code)。简单说就是把所有服务器配置都写成代码，想要什么样的测试环境，一键调用代码就能瞬间拉起来一个和线上完全一模一样的副本，随便折腾，用完直接销毁。这样无论是新人培训还是功能验证，所有人都活在同一个标准流程下，彻底消灭了“特殊案例”。

这套玩法不光保稳，还省钱。之前自建子系统太贵，换成谷歌云的按需服务后成本砍掉 90%。甚至能模拟全球不同地区的网络延迟，不用让人飞去澳洲测试，直接在云端把主服搬到那边跑一圈就知道感觉咋样了。大方向上，这就是要把整个工作室变成云原生 (Cloud Native) 的 2.0 版本，让开发环境本身就具备上线级的容错能力。

## Online Game Technology Summit: Is Your Game Cross-Platform Ready?
- **Speaker:** Raymond Arifianto (AccelByte)
- **Duration:** 30 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1026623
- **Slide Page:** 
- **Custom ID:** 1026623

### Overview
Everyone is buzzing around enabling cross platform features for their games. Making a Cross-Platform game is not for the faint of heart, so here are 9 things you need to know, before you make the big jump.

### Content Summary
[TLDR]
跨平台开发绝非简单加接口，需构建统一底层服务与账号体系，方能打通玩家体验与商业闭环。

[Background]
跨平台 (Cross-Platform) 已成趋势，但技术坑深不见底。本文作者结合多年在线服务经验，拆解从账号到部署的实战方案，专为计划开发多人联机游戏的开发者提供避坑指南与基建思路。

[Recaps]
老哥们都知道，现在玩家都爱在哪玩就在哪玩，不想被锁死在一个机器上。但想把这事儿做成，真不是说加个按钮就行。首先得把这行当的术语整明白，最核心的就是跨平台联机 (Cross-play)，也就是让大家在同一局里嗨；还有跨进度 (Cross-progression)，指存档互通；以及跨购买 (Cross-buy)，买了东西两边通用。还有个新词叫“买一次玩到处”(BOPA)，虽然目前还是画饼阶段，但这绝对是未来的大势所趋。

搞多人联机最怕的就是底层乱套。各家平台的 SDK 数据不兼容，像 Xbox Live 的数据跟 Steam 的对不上。所以咱们不能光靠原厂的东西，得自己搭一套中间层的服务来做连接。这里面最关键的是**账号关联 (Account Linking)**，得把所有不同平台的 ID 绑到你自己的系统里，这样才能认人。另外，网络同步也是个坑，别轻易尝试**点对点 (Peer-to-Peer)**，尤其是主机和 PC 混战时 NAT 限制很麻烦，建议老老实实用**专用服务器 (Dedicated Server)** 或者中继模式。至于帧率，模拟逻辑定死 30 帧，渲染随便拉，稳就完事了。

运营层面的事也得注意，比如商店管理，分**主商店 (Primary Store)**（平台收钱那块）和**游戏内商店 (Secondary Store)**（你自己控制的）。为了减少重复配置，建议尽量简化主商店流程，多用游戏内的虚拟货币。更新补丁也很折磨人，每个平台审核周期不一样，容易导致同步不了。这时候就用**服务端开关 (Server-side Toggle)**，把活动或数值改写在代码之外，随时改随时生效，不用重新发包审核。当然，跨平台认证有额外要求，比如界面要显示队友的平台信息，这点容易被驳回，记得给自己留足缓冲时间。

最后总结一下，跨平台开发这事儿，前期投入很大，得有长期运营的心态。别想着全靠自己造轮子，有些成熟的后台即服务 (Back-end as a Service) 方案能帮咱省不少力气。总之，未来的风向是平台退居二线，玩家体验才是中心。只要能把这九条路走通了，哪怕以后出新平台，也能轻松跟上趟，别让硬件限制成了玩家的拦路虎。

## Online Game Technology Summit: Real-Time Data Processing for Multiplayer Online Games
- **Speaker:** Xia Lei, Zechen Xu (Netease, NetEase)
- **Duration:** 20 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1026914
- **Slide Page:** 
- **Custom ID:** 1026914

### Overview
The data generated by MMO games is huge, and real-time data processing can maximize the value of data. Netease's Thunder Fire UX team has extensive experience in processing real-time large data in MMO games.Our talk will introduce the whole system structure of real-time data processing including data recording and collection, data transmission, and data storage.We will also introduce various open source tools of big data which are related to real-time computing, such as Logstash, Kafka, Flink, etc. Tools and processes constitute our real-time computing system.Meanwhile, we will demonstrate the real-time calculation of game data in the practical application of Netease games, which includes real-time monitoring of in-game currency flow, real-time detection of cheating players, real-time processing of chat data.Through this talk, the audience can understand the whole process of real-time processing of game data, be familiar with the big data technology we used, and apply real-time data processing of game data in their own games to improve the value of game data.

### Content Summary
[TLDR]
抛弃传统 T+1 报表，构建基于 Kafka 与 Flink 的实时数据流系统，实现秒级运营监控与风控响应。

[Background]
游戏发版后老板急需知晓今日流水、新用户增量及黑产盗号情况，传统离线处理 (Offline Data Processing) 的延迟会让决策失误。本次演讲适合后端开发、运维及数据分析师，揭秘如何搭建高性能实时数据分析架构来解决这一痛点。

[Recaps]
咱们首先面对一个尴尬场景：新游戏上线，老板急着要看今天的流水和新服人数，这时候你告诉他“明天早上给您”，估计得挨骂。所以核心诉求很明确，告别传统的离线处理 (Offline Data Processing)，拥抱实时数据加工 (Real-time Data Processing)。前者是 T+1 模式，得等半天甚至一天，后者能把延迟压到秒级甚至毫秒级，这才是现代网游运营需要的速度。

架构层面，这套方案的基石很清晰：Kafka 充当流量洪峰的中转站，负责削峰填谷；Flink 作为核心计算引擎 (Computing Engine)，负责在内存里跑批处理和流式计算；前端展示则依靠 Druid 数据库或者 MySQL。以前大家习惯用 ELK 系统 (ELK System) 做日志检索，但如果是复杂的指标统计，像 DAU、日活这种实时看板，光查日志不行，还得用 Flink 跑通全链路，或者直接导入 Druid 库，通过 SQL 就能秒查，省去了写复杂代码的麻烦。

落地实操时，网易团队分享了几个硬核案例。比如利用 Flink 的窗口功能 (Window Function) 统计金币获取量，一分钟滚一次就用固定时间窗口，一小时看累计就用滑动窗口。当然，稳定性才是生命线。分布式环境下的节点挂了怎么办？高可用性配置 (High Availability) 加 Checkpoint 检查点机制能保命。还有最关键的数据一致性问题，必须做好幂等操作 (Idempotent Operation)，防止网络抖动导致数据重复计算扣错玩家的钱。
