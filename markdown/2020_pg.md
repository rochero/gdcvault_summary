## Variable Rate Shading Tier 1 with DirectX12 from Theory to Practice (Presented by Intel)
- **Speaker:** John Gibson, Marissa du Bois, Kai Wang (Tripwire, Intel, Intel)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1026691
- **Custom ID:** 1026691

### Overview
10th Generation Intel Core Processor Architecture (codenamed Ice Lake) with Gen11 Graphics supports the DirectX12 Tier 1 Variable Rate Shading (VRS) capability. We'll walk you through an integration of Tier 1 VRS with a AAA game engine and it's forward and deferred rendering pipeline with examples of the performance and quality trade-offs. We'll also provide recommendations for the use of Tier 1 VRS based on our experience.

### Content Summary
[TLDR]
英特尔实战分享变量着色率技术：相比传统降级方案，它能更精细分配算力，在提升帧率同时保留画面边缘清晰度。

[Background]
现在的游戏对显卡要求越来越高，玩家想要高画质又想跑满帧很难。这场演讲专门聊怎么用变量着色率技术在不怎么掉画质的前提下提升性能，适合做图形优化的同行看。

[Recaps]
兄弟萌，这篇 GDC 干货主要讲的就是**变量着色率 (Variable Rate Shading)**，也就是大家常说的 VRS。这玩意儿的核心逻辑特简单，就是让 GPU 聪明点干活。以前咱们想省性能，最直接的办法就是把**渲染缩放 (Render Scale)** 调低，但这会导致整个画面都变糊。VRS 就不一样了，它走 **DirectX 12 API** 就能指定屏幕不同区域用不同精细度。远处的草丛或者没啥内容的背景，可以让 GPU 少算点 **像素着色器调用 (Pixel Shader Invocations)**，反正人眼也看不清；但关键的人物面部还是高清处理。最香的是它有**边缘保留 (Edge Preservation)** 功能，保证锐利的线条不被锯齿化，这点比单纯降分辨率强太多了。

关于落地实施，这次重点秀了 **虚幻引擎 4 (Unreal Engine 4)** 里的集成方案。开发者可以通过材质实例给不同物体单独设精度，甚至按**细节层次 (Level of Detail)** 自动切换。比如近处模型用 1x1，远景物体用 2x2 或 4x4。不过老哥们要注意避坑，如果着色器代码里写了某些特定指令（比如采样相关的关键词），系统可能会强制回退到 1x1，反而拖慢速度。所以尽量把能用的地方集中起来，避免频繁切换导致驱动层开销过大。

最后拿《Chivalry 2》的数据说了实话，这游戏优化后确实真香。对比纯降分辨率，VRS 在保住**边缘保留 (Edge Preservation)** 的情况下，帧率涨得更稳。特别是在结合基础绘制批次 (**Mesh Passes**) 和半透明通道后，性能释放很猛。总的来说，别傻傻地全局拉低分辨率了，试试这种分区优化的路子，既能稳住关键画面的清晰度，又能实实在在地给显卡减减负，这对追求高性能的单机和联机大作来说绝对是必学的。

## Tools Summit: Geometry in Milliseconds: Real-Time Constructive Solid Geometry
- **Speaker:** Sander van Rossen (Unity Technologies)
- **Duration:** 46 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1026755
- **Slide Page:** https://www.gdcvault.com/play/1026735
- **Custom ID:** 1026755

### Overview
Constructive Solid Geometry is a technique that has various use cases, ranging from quickly blocking out levels in a level editor to building generic 3d procedural geometry. Previous algorithms scale poorly and have reliability issues. This presentation will explain in detail how to implement a unique algorithm that allows you to perform hierarchical Constructive Solid Geometry in real-time on thousands of primitives.

### Content Summary
[TLDR]
利用分块缓存与动态路由表优化，彻底解决旧版 CSG 卡顿问题，实现可实时迭代的高性能布尔运算构建方案。

[Background]
很多开发者嫌弃传统的 CSG（构造实体几何）就是老旧的 BSP（二分空间分割树）那一套又卡又硬，干脆弃用。但这篇演讲想纠正一个误区：作为快速原型设计的神器，它能让关卡设计师像搭积木一样即时调整碰撞体和视线。演讲者用实战代码告诉大伙儿，现在的硬件完全跑得动新版算法，别轻易放弃这个利器。

[Recaps]
首先得说说为啥还值得折腾这老技术。虽然像 UE4 这种引擎还在吃 Tim Sweeney 当年的老代码，但现实是，CSG 能让设计师在几分钟内改出一版能通过玩的雏形。比如 Warframe 和 Apex Legends 里那些关卡，最早都是靠这种“加减笔刷（Brush）”的方式抠出来的。跟传统 3D 建模纠结于三角形网格不同，CSG 强迫你关注整体结构，比如玩家在哪能躲子弹、怎么走才顺，这才是游戏设计的本质，而不是一上来就画贴图。

其次，这演讲最核心的黑科技在于解决了“更新速度”问题。以前的做法是把所有面混在一起算，加个形状就要全盘重来，越积越慢。新方案把每根笔刷当成独立的计算单元，也就是“每笔刷计算（Per-Brush Computation）”。你想移动一堵墙？引擎只重算这堵墙和它触碰到的那几个局部，其他的直接用缓存。这就像修水管不用砸整个房子，哪里堵了通哪里，彻底避免了全量重新生成网格（Mesh）带来的性能爆炸，多核 CPU 也能并行干这活儿。

再者，针对复杂的层级结构，他发明了一套“路由表（Routing Table）”机制。想象一下 CSG 是个树状图，操作节点多了很容易指数级爆炸。这套表相当于把所有布尔运算（Boolean operations）的逻辑压缩成一张巨大的查表文件。当面对嵌套分支时，它会智能地合并重复路径，确保无论树有多深，查找分类的速度都不受影响。同时，他还特意为防止缝隙泄露做了浮点对齐处理，保证生成的实体永远不会出现无限薄的破洞，对物理引擎非常友好。

最后总结一下适用场景。这招肯定不是万能的，别拿它去捏花草或角色模型。但它绝对是建筑关卡、机械结构和物理碰撞体领域的黄金标准。只要你需要绝对的实心几何体，又不想受限于手动的网格拓扑，这套现代化的迭代方案能让你在保持创作自由的同时，跑得飞快，这才是真正的好工具。

## Intel® oneAPI Rendering Toolkit and its applicationin games
- **Speaker:** Sven Woop, Jeff Amstutz (Intel, Intel)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1026685
- **Custom ID:** 1026685

### Overview
Intel's oneAPI Rendering Toolkit presents a set of libraries for CPU, and soon to be GPU, optimizations of common ray tracing tasks from base ray tracing kernels, to denoisers, to volume rendering and full turn-key renderers. Several use cases and optimization strategies are presented in real-world applications including interactive path tracing in digital content creation tools, interactive rendering of movie production assets at large scales, interactive denoising of path traced lightmaps, and run-time uses of Embree in gaming engines.

### Content Summary
[TLDR]
Intel 推出 CPU 光追库，帮游戏在没显卡加持下也能玩光照和碰撞，省成本还高效。

[Background]
大家平时聊光追只盯着 NVIDIA 的 GPU，Intel 这篇演讲其实是强调 CPU 在图形计算上的巨大潜力。适合引擎开发者和图形程序员阅读，旨在解决渲染性能瓶颈，提供跨平台的高性价比解决方案。

[Recaps]
英特尔这次 GDC 的大招其实是想把“光线追踪”从只有高端显卡才能玩的圈子里解放出来。他们展示了一套基于 CPU 的计算工具包，虽然 **开放体积内核库 (Open Volume Kernel Library)** 和 **OSPRay** 偏向专业可视化，但对游戏开发更有启发的是那个叫 **开放图像降噪库 (Open Image Denoise)** 的组件。简单说，现在的 **光线追踪 (Ray Tracing)** 需要海量采样才能清晰，否则全是噪点，这库能用深度学习快速把噪点抹掉，预览和最终出图都能用，极大地节省了等待时间。

重头戏是 **Embree** 库，这是英特尔为了 **高性能可见性查询 (High-performance visibility queries)** 打造的开源库。它的核心逻辑不是硬拼算力，而是算法优化。通过构建高质量的 **包围盒层次结构 (Bounding Volume Hierarchy, BVH)**，再配合 CPU 自带的 **单指令多数据流 (SIMD)** 指令集，让光线在场景里找物体时跳过大部分空气，效率比以前高了 1.5 到 6 倍。这东西在电影圈已经是标配了，像《复仇者联盟》这些大片后期都在用，证明它足够稳定可靠。

对咱们做游戏的来说，关键是怎么落地。Intel 给了几个实操方向：第一是 **静态几何体 (Static Geometry)** 的 **光照烘焙 (Light Baking)**，提前把复杂光影算好压进 **光照贴图 (Light Maps)**，这样运行时不占性能，Activision 就在他们的引擎里集成了。第二是利用 **光线查询 (Ray Queries)** 做 **碰撞检测 (Collision Detection)**，子弹判定、角色走路撞墙，这些不需要 GPU 那么复杂的计算，用 CPU 算反而更快。第三个是《坦克世界》那个案例，展示了怎么在 CPU 上跑 **软件光栅化 (Software Rasterization)** 来生成高精度阴影，甚至支持 **运动模糊 (Motion Blur)** 和实例化内存节省，说明以后不一定要全靠 A 卡或 N 卡，服务器端或者 CPU 密集型的渲染也有很大空间。

## Tools Summit: From 0-1000: A Test Driven Approach to Tools Development
- **Speaker:** David Paris (Playground Games)
- **Duration:** 24 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1026631
- **Slide Page:** https://www.gdcvault.com/play/1026596
- **Custom ID:** 1026631

### Overview
The talk describes Playground Games' journey from 0-1000 automated tools tests during the development of Forza Horizon 4 expansion packs. It focuses on how and why they created a testing culture, what they learned from the experience and how they plan to continue cultivating and improving their investment. The talk demonstrates how teams can improve their tool stability and developer confidence and still deliver new features by adding automated tests.

### Content Summary
[TLDR]
建立测试驱动文化，让工具开发从被动修 Bug 转向主动保障稳定，大幅提升团队效率和信心。

[Background]
工具频繁崩溃导致创作受阻，传统人工测试效率低且漏检多。Playground Games 借此分享如何用自动化测试重构工具流程，适合所有受限于工具质量和团队协作的游戏研发团队参考。

[Recaps]
当初咱们做《极限竞速》扩展包时，工具维护简直是场灾难。每次发布前的人工测试就要拖上一周，修完这个 Bug 又冒出那个，开发者整天忙着填坑，根本没时间整新功能。这种“救火式”工作不仅让用户抓狂，连工具组自己都心态崩了。后来大伙儿琢磨明白了，光靠人力堆不出稳定性，必须得搞一套“测试驱动文化”（Test-Driven Culture）。这玩意儿不光适用于游戏运行时，对于工具软件同样管用，核心就是通过“自动化测试”（Automated Testing）来保证改动不会把原有功能搞挂。

那具体该怎么落地呢？千万别指望一夜之间全员转型，这跟做游戏迭代一样，得从小步快跑开始。他们没急着把所有旧系统都覆盖一遍，而是先挑个小的设置保存模块练手，哪怕面对一堆“遗留代码”（Legacy Code）也不怕。他们先写了些针对特定功能的“单元测试”（Unit Tests），从最简单的输入输出验证入手。定了规矩很重要，别整那些门槛高的框框，选了大家都熟的 MSTest 框架，接上“持续集成流水线”（Continuous Integration Pipeline）。代码一提交，后台自动跑测试，挂了就不给打包发行。这样既能保证发给美术的工具是靠谱的，又不用大家天天盯着屏幕傻等。

最直观的效果就是数据说话。在乐高主题扩展包里，有了自动化测试护航，工具开发花在修 Bug 上的时间砍了一大半，腾出的精力用来加新功能，整整多了一个月的工期。有个特生动的例子是积木搭建系统，以前 QA 反馈个错位问题得半天排查，现在直接对着测试用例就能定位是逻辑问题还是误操作，协作效率直线上升。甚至美术同事都开始信任咱们了，愿意配合尝试新特性，因为知道交出来的东西基本能直接用，不用折腾兼容性的坑。

当然，也不是说写了测试就高枕无忧。作者也敲了警钟，测试本身不是银弹，质量还得靠人，得防止出现“不稳定测试”导致大家不敢信。另外记得把测试时间算进排期里，不然会被优先砍掉。还有一个关键点是设计代码时得多想一步，把公开接口（Public APIs）定义清楚，底层逻辑换了不影响上层测试。对了，测试脚本跑得要快，跑一分钟的测试谁受得了，最好是几百次一天能跑完。长远来看，这套流程得持续迭代，哪怕刚开始只有一个人写测试，只要能看到好处，慢慢就能带动整个工作室，最后实现全流程的稳定可控。

## Tools Summit: Writing Tools Faster: Design Decisions to Accelerate Tool Development
- **Speaker:** Niklas Gray (Our Machinery)
- **Duration:** 59 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1026729
- **Slide Page:** https://www.gdcvault.com/play/1026597
- **Custom ID:** 1026729

### Overview
This session discusses the drastic design decisions we made in The Machinery to overcome the problems we had in previous engines (Bitsquid, Stingray) where writing tools became the primary development bottleneck.nnFirst, we minimized the the tech stack to put more control in the hands of the developers. Second, we moved the responsibility for things like undo, copy/paste, save, revert, etc into a shared central data model so that tools get it "for free". Third, we standardized the way in which data interacts with views, so that the same views can be reused for different purposes. nnThis talk will discuss the consequences, pros and cons of our approach and show how it works in a concrete example: implementing an animation state machine editor.

### Content Summary
[TLDR]
摒弃臃肿第三方框架，通过统一数据模型与自制即时模式 UI，实现工具链的高效自洽与快速迭代。

[Background]
针对传统引擎开发中工具构建耗时、维护困难且性能差的痛点，作者回顾了在 Bitsquid 和 Stingray 项目上的失败经历，分享了如何通过简化技术栈重构工具流程的经验。

[Recaps]
这哥们先掏了老底，讲了自己过去搞引擎工具时的惨痛教训。最开始以为让用户自己写工具就行，结果被现实打脸。后来用了窗口窗体 (WinForms) 快速凑合，界面虽丑但好写；转投 XAML 框架 (WPF) 后界面好看，但开发周期拉长，重写半个版本都没完成。最惨的是后期搞 Autodesk 收购后的产品，为了跨平台上了大量的网页技术 (Web Technologies)，C++、Lua、JS、Chromium 等组件层层叠加，这技术栈深不见底，不仅修 Bug 找不着北，性能也拉胯，简直是给开发者挖坑。

为了解决这些坑，他在 The Machinery 引擎里彻底推倒重来。核心是把“数据源”统一成“真理”数据模型 (The Truth)，所有编辑器状态都在这一个地方跑。这么做的好处是真香，撤销 (Undo)、复制粘贴、序列化甚至实时协作功能全部白嫖，不用单独写代码适配。数据读写采用了无锁编程 (Lock-free Programming)，靠原子指针交换 (Atomic Pointer Swap) 保证多线程安全。虽然这套模型中心性太高，改起来风险大，但对通用功能的覆盖确实做到了极致。

UI 交互方面，他果断放弃了流行的 保留模式 UI (Retained Mode UI)，选了更硬核的即时模式 UI (Immediate Mode UI)。配合自制的 Vulkan 渲染管线，整套界面只用一次绘图调用，性能和透明度吊打第三方库。虽然这意味着所有控件每帧重绘，逻辑上要适应“无对象”的思维（比如点击判定需延迟一帧），但调试极其直观。再配合“方面” (Aspects) 机制自动生成属性栏和预览窗，把开发时间压缩到极致，这才是做工具该走的路。

## Rendering Roblox: Vulkan Optimisations on Imagination PowerVR GPUs (Presented by Imagination Technologies)
- **Speaker:** Arseny Kapoulkine, David Hamill (Roblox, Imagination Technologies)
- **Duration:** 58 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1026753
- **Slide Page:** https://www.gdcvault.com/play/1026736
- **Custom ID:** 1026753

### Overview
Join us as we dive into the lighting and shadow systems of the latest Roblox engine. We'll be exploring the voxel lighting system, EVSM shadow mapping implementation, shader optimisations, and other recent features of the Roblox renderer optimised for PowerVR. We'll also take a look at the process of profiling and optimisation on mobile and investigate how to use asynchronous compute to improve performance on PowerVR.With the release of its new powerful GPU IP, Imagination Technologies has been working closely with Roblox to investigate low-level performance improvements that will give players the best gaming experience.

### Content Summary
[TLDR]
Roblox 结合体素光照与分块阴影方案，深度适配 PowerVR 移动端架构，实现了跨平台画质与性能的完美平衡。

[Background]
罗博乐普（Roblox）作为 UGC 平台，玩家设备跨度极大。演讲者旨在分享如何在不依赖人工调优的情况下，让复杂的光照系统在老旧低端机和现代高端机上都能流畅运行，特别是基于 Vulkan 的移动渲染优化经验。

[Recaps]
Roblox 遇到的最大痛点是硬件代差太大，没法像传统 PC 游戏那样让玩家手动切换画质选项。他们采用了一个统一的品质滑块，系统自动判断当前是否有余力提升画质或降低负载来保帧率。为了简化开发并保证一致性，团队坚持不做预烘焙 (Baking) 的全动态光照方案，这对性能提出了极高要求，必须精打细算每一帧的计算预算。

针对低端移动设备，核心策略是利用体素网格 (Voxel Grid) 将光照计算前置到 CPU 端。场景被划分成固定体积的小块，提前算好环境光、阳光和局部光源的影响，打包成纹理供 GPU 读取。为了进一步压缩带宽，使用了 RGBM 编码存储高光色值。这里还有一个黑科技叫时间节流 (Temporal Throttling)，允许光照更新延迟几帧进行，以此换取 CPU 运算空间的释放，哪怕会有轻微的光影滞后，但在低配机上换稳定帧率绝对划算。

对于需要精细阴影的场景，则启用了阴影贴图 (Shadow Maps) 技术。他们采用了分块 (Tiling) 技术的级联阴影映射 (Cascaded Shadow Maps)，传统方案中物体移动往往导致整张阴影图重绘，而分块后只需更新物体所在的局部瓦片，大幅减少了几何重绘成本。软阴影方面选用了 EVSM (Exponential Variance Shadow Maps)，这种方案便于滤波但容易产生漏光，团队通过压缩深度范围和使用深度夹紧 (Depth Clamp) 技术巧妙规避了这一常见问题。

在 PowerVR 架构的特化优化环节，演讲者展示了如何利用硬件特性省钱。比如直接用 MSAA 的多采样解析来替代昂贵的后处理模糊滤镜，这样既利用了片上缓存减少了显存读写，又达到了平滑阴影的效果。另外测试了将高斯模糊移到异步计算 (Asynchronous Compute) 处理，利用共享内存 (Shared Memory) 缓存数据。虽然这在高端芯片上通过双队列提交能提升任务并行度，但在低端机上因缓存单元缺失反而可能变慢。这说明底层技术必须根据目标硬件特性灵活取舍，没有银弹。

## Quad Mesh Simplification in Frostbite
- **Speaker:** Ashton Mason (Electronic Arts)
- **Duration:** 27 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1026752
- **Slide Page:** https://www.gdcvault.com/play/1026739

### Overview
In early 2014, the Frostbite team started developing an in-house LOD technology for quad-based Bioware character models. Today that tech powers tools used by studios across Electronic Arts, from Battlefield to Plants vs Zombies. Quad-based models are widely used in the industry, and artists devote much care to their topology and edge flow. While LODs are sometimes thought of as throwaway, maintaining good topology benefits subsequent hand-editing, lighting and animation. For that reason, Bioware historically spent days per model hand-authoring their character LODs. ### Content Summary
[TLDR]
EA 通过自研的四边面简化技术，解决了 LOD 生成后拓扑崩坏和不对称的问题，让自动减面模型在视觉和结构上都无限接近美术亲手雕刻。

[Background]
传统的游戏 LOD（Level of Detail）生成工具通常只认三角形，这会彻底破坏美术精心设计的四边面（Quad Mesh）布线。当角色进行复杂动作时，这种被拆乱的拓扑结构会导致皮肤变形穿模或出现诡异的褶皱。鉴于此需求，EA Frostbite 团队联合 BioWare 研发了这套新方案，旨在替代旧工具，减少美术后续人工修复模型的时间成本。

[Recaps]
这次技术的核心就在于怎么伺候好四边面网格（Quad Mesh）。以往的简化逻辑是先把四边面转成三角形（Triangle-based）再做削减，虽然几何形状对了，但原本用于控制变形的规则布线全没了。比如角色关节处的环状边线一旦被打散，跑起来肯定掉链子。所以他们的目标是直接在四边面上做减法，保证生成的 LOD 依然保持着像手工作坊一样的规律拓扑结构，这样既能省资源，又不会牺牲角色的动作表现力。

为了做到这一步，他们改良了底层的折叠算法。经典的方法是边缘折叠（Edge Collapse），简单说就是抽掉一根边把两个顶点合并。但为了适应四边面，他们引入了一个更猛的概念叫多边形链折叠（Polychord Collapse），也就是一下子处理一串相连的四边形。不过这还不够灵活，有时候只想把背部的链条压细，结果整条链连着耳朵和脸都要一起被砍掉。所以他们提出了子多边形链折叠（Subpolychord Collapse），允许只切断链条的一段。这让美术能通过优先级涂抹（Priority Painting）功能，告诉程序哪些部位（比如人脸）必须保留细节，哪些地方可以随便减，实现按需分配几何体预算。

此外，他们还特别照顾到了对称性（Symmetry）。大部分角色都是左右镜像的，如果程序瞎折腾导致左半边和右半边不一样，那就完蛋了。不过他们也留了余地，叫作软对称，不是死板规定必须完全一致，而是通过代价函数（Cost Metric）去极力倾向对称的处理方式。哪怕后期编辑搞乱了，算法还能自动识别出纠缠在一起的边群并尝试配对折叠。最后的效果测试非常能打，不仅比第三方工具 Simplygon 更干净，做出来的东西甚至连车辆道具这种非角色模型都能通用，妥妥的全能型选手。

到了运行时阶段，就不能光看跟玩家的距离了。引擎会根据屏幕分辨率、视场角 (Field of View) 以及当前的 GPU(图形处理器) 性能情况动态调整。特别是当 GPU 帧时间变长或者顶点处理 (Vertex Processing) 压力过大时，系统会自动降低等级细节 (Level of Detail) 级别来保流畅度。这种基于性能预算的动态 Bias 机制，让游戏在不同配置下都能自动寻找画质和帧数的最佳平衡点。

对于大地图模式如 Warzone，还有一套特殊的代理细节 (Proxy LOD) 方案。原本地图上成千上万的小物体渲染会压垮 CPU 和 GPU，产生大量无效的子像素三角形。新做法是把一片区域的静态物体重新合并成一个简化的代理模型。以前一个街区可能有几千个模型，现在直接变成几个低模代表。这样大大减少了绘制调用 (Draw Calls)，让百人大战也能顺畅运行，这才是真正的工业化级内容扩展能力。

### Content Summary
[TLDR]
别再用泰勒级数硬算，掌握范围缩减与极小极大概率逼近，结合硬件位思维能让数学函数又快又准。

[Background]
这是十年前的演讲更新，针对追求极致精度的开发者。随着 FPGA 普及和开源工具出现，传统的浮点运算思维已过时。重点解决如何让数学函数在硬件上跑得更猛、算得更准，特别是最后几位的精度问题。

[Recaps]
这次演讲核心就一个字：变。面对 FPGA 这种新玩具，传统的浮点运算思维早该扔了。你得学会按“门电路”思考，而不是盯着 CPU 指令集。比如求平方其实是乘法特例，有对称性可省电路；甚至在固定点数运算里，加减乘都可能被优化成纯导线连接。这里特别提到了“范围缩减 (Range Reduction)"，不管输入多大，先把它塞回一个小区间再算，能避开精度崩溃的边缘，毕竟在硬件上，wiring（布线）永远比 gate（门）更便宜。

接着聊数值逼近，这地方坑最多。别信那些教你用泰勒级数 (Taylor Series) 的教程，它在单点附近还行，拉宽范围误差就会爆炸。真正的行家都用“极小极大逼近” (Minimax Polynomial)，保证整个区间误差最小化。现在有了免费工具 Sollya，能直接算出最优系数，但别高兴太早，直接把神仙系数塞进 float 会丢精度。正确的姿势是做“机器系数优化”，把它们转成整数除以 2 的幂次，这样既保留了精度又方便硬件读取。

最后是实操干货。算倒数、开方这些函数，别死磕公式，试试分块查表加 Newton-Raphson 迭代，速度起飞。有个著名的 Quake 逆平方根魔数其实也能继续优化，多加一次迭代就能显著提升精度。对于 FPGA 玩家，还有“比特堆 (Bitheap)"技术，能把复杂的多项式拆解成并行的位堆积，最后用压缩树汇总，效率吊打传统方法。另外像 Flopoco 这样的工具能自动生成 VHDL 代码，连多分式查找表 (Multipartite Tables) 都能造出来。文末还讲了离散振荡器，利用矩阵形式算 sin/cos，配合“自动增益控制 (Automatic Gain Control / AGC)"防止振幅漂移。这对做音效合成或波形生成太有用了，比那种查表法省空间又稳定，简直是嵌入式开发的宝藏。

## Math In Game Development Summit: Improving an Iterative Physics Solver Using a Direct Method
- **Speaker:** Maciej Mizerski (Roblox)

### Overview
As the content on Roblox is user generated, the physics engine is required to handle much more variety of interactions than other engines. Roblox doesn't have the luxury of using standard methods of fixing physics engine failures by tweaking the simulated models, their masses, inertias, removing over-constraints or using gameplay tricks to hide the issues. The requirement is stability at all costs. This session will describe how to use a direct matrix solver based on LDL matrix decomposition in tandem with a PGS solver (a.k.a. ### Content Summary
[TLDR]
Roblox 推出的 LDL-PGS 混合求解器，彻底解决了复杂机械结构下的物理模拟爆炸和卡顿难题。

[Background]
Roblox 平台鼓励用户创作奇葩 3D 机械装置，但传统物理库在处理复杂约束和高质比物体时经常出 bug，演讲者分享如何定制高性能求解器来保障稳定性。

[Recaps]
这演讲主要是在聊怎么把 Roblox 的物理引擎调教得更结实。大家都知道，普通的 投影高斯塞德尔 (Projected Gauss Seidel) 求解器虽然常用，但在处理复杂的机械结构（比如升降机）或者质量差异巨大的物体时，很容易算着算着就炸了，出现穿模或者飞出去的事故。Roblox 团队开发了一种新的混合求解器，核心思想是利用稀疏矩阵技术处理 刚体 (Rigid Body) 约束，避免了传统方法在雅可比矩阵求导和反演时的不稳定性。

它的核心思路其实很巧妙，把复杂的 线性互补问题 (Linear Complementary Problem) 拆解成了两个阶段。一个是符号相，只需要对每个机制运行一次，用来分析拓扑结构并生成最优的计算顺序；另一个是数值相，每一帧物理更新都执行。在数值计算中，大部分时候还是靠传统的迭代法快速逼近，但在最后关键的一步，它会调用基于稀疏矩阵的 直接法 (Direct Method) 进行精确校正。更狠的是，这两步还能并行处理，不浪费 CPU 资源。这样既保证了精度又没牺牲多少性能。

为了榨干硬件性能，演讲还介绍了一些底层优化技巧。比如利用 图论 (Graph Theory) 中的节点消除算法来决定最佳计算顺序，避免不必要的内存填充。最精彩的是针对稠密矩阵提出的 刚体破碎 (Body Shattering) 技术，当某个 刚体 (Rigid Body) 挂载了太多约束导致计算量暴增时，就把这个刚体虚拟拆分成几个小块，通过 刚性关节 (Rigid Joint) 连起来。这样一来，原本立方级的计算复杂度直接变成了线性级，哪怕是坦克履带这种复杂结构也能在低端机上跑得丝滑。

这演讲其实就是聊咋样让游戏录像变成个“平行时空”。Wargaming 团队没选最省事的本地录屏，而是采用**服务端存储 (Server-side)** 存数据，确保所有人看到的信息一致。核心难点在于“时间管理”，不能一暂停就把游戏锁死，得弄个**分步更新路径 (Split update paths)**，把物理和渲染跟核心逻辑分开走，这样拖拽进度条才不会卡成幻灯片。

最后强调，这技术不光是给主播做集锦的，对内更是神器。利用回放能做**自动化测试 (Automated Testing)**，快速复现 BUG 甚至揪出外挂玩家。但这东西是个双刃剑，它会破坏引擎原有的很多假设，比如**LOD 级别 (Level of Detail)** 切换、雾气渲染这些老规矩都得重写，建议各位架构师在设计初期就把“可回放性”考虑进去，不然后期就是拆墙填坑累断腿。

动机这事儿在心理学上有个硬核框架叫自我决定理论 (Self-Determination Theory)，简单来说就是人玩游戏图个啥。主要是三块：自主性 (Autonomy)，觉得自己能掌控；胜任感 (Competence)，觉得技术长进了；还有归属感 (Relatedness)，跟游戏世界或别的玩家有连接。育碧为了量化这个，开发了育碧感知体验问卷 (Ubisoft Perceived Experience Questionnaire)，专门用来评估玩家的基本心理需求满足度。但这玩意儿只能小范围撒网，没法全服铺开，所以这次演讲的核心，就是把这玩意儿从“问卷”变成“行为分析”。

效果简直惊人。如果只用简单的分类模式预测，准确率也就一半多。但只要把具体的行为指标加上玩家的行为流派结合起来，非线性的预测模型能跑出 80% 以上的平均准确率。最猛的是“胜任感”维度，预测准度高达 94%。这说明啥？说明哪怕是个没填过问卷的玩家，只要看他玩了多少小时、怎么死的、怎么升级的，咱们就能知道他心里爽不爽。这对运营和数值来说太实用了，省得到处发调查问卷打扰人家玩游戏。

这套玩法还能接着用，不仅能测动机，还能顺便抓一抓有毒玩家、预测氪金潜力甚至找带新人的好苗子。现在的技术逻辑就是一样，纯粹靠游戏内表现来分析人性。这工作算是学术界和游戏界的一次深度联姻，既验证了理论又解决了实际痛点。对于做玩家体验和数值平衡的团队来说，这就是把枯燥的数据变成了洞察人心的望远镜，以后搞活动调平衡也能更有底气，不再是一拍脑袋定方案。

### Content Summary
[TLDR]
物理动画不仅是防穿模工具，通过灵活组合电机与约束，能在保留动画意图的同时赋予动作真实的流体反馈。

[Background]
很多开发者头疼传统动画容易出现模型穿模或动作死板的问题。这次 Respawn 的老哥分享了在《绝地》里如何改造物理系统，让角色既有动画精度又能和环境自然互动，对想做高级动作效果的同行很有参考价值。

至于咱们操控的主角，重点不是硬碰硬，而是要动作看着“丝滑”。光靠电机有时候太死板，遇到滑墙或者抓钩这种高速变向，角色会晃得像喝高了。后来他们采用了混合方案，比如滑动动作混合 50% 的物理姿态，走路转身时手臂加一点物理惯性，让动作带点延迟感。最绝的是为了稳住重心，他们给腰部单独上了一个速度驱动（Velocity Drive），或者给手腕加了个距离限制的约束，让手臂能根据环境微调位置，看起来就像真在应付地面的起伏一样自然。

最后那个跟屁虫小机器人是最难搞的，毕竟一直挂在主角身上。为了防止它脑袋钻进主角身体里，他们搞了个动态距离约束（Dynamic Constraint），主角跑得越快，给机器人头的活动空间就越小，极限情况下直接锁死。另外为了避免计算冲突，他们专门为这个小机器人开了个独立的物理场景（Physics Scene），固定在特定帧率下运算，确保不管游戏帧数怎么跳，小机器人的摆荡都稳如老狗。总之这活儿不能硬做，得清楚你到底是要它抗撞击还是要它看着软弹，参数之间互相牵制，改好了回头看看之前的案例可能又崩了，得多轮试错。

具体到游戏圈，这玩意儿应用场景多得很。比如在《坦克世界》里，他们用这个在 CPU 上构建复杂的阴影结构，再丢给 GPU 显存，比传统阴影映射细节多太多了。平时做关卡设计师的话，可以用它做光照贴图 (Light Maps) 烘焙，或者在游戏里算子弹弹道、角色落地判定这种简单射线查询，动静结合特别灵活。

最后还提到了未来计划，正在集成 SYCL (统一异构计算标准)，到时候 C++ 代码能同时在 CPU 和 GPU 上跑，不用折腾两套语言。总之就是利用多核 CPU 的强大算力，配合 GPU 图形管线，把原本属于高端特效的计算压力分摊开，性价比很高。

[Background]
光追效果虽好，但性能开销巨大，开发者常遇卡顿或画面噪点问题。此次 NVIDIA 资深工程师结合实战案例，分享了如何在保证视觉质量的前提下，优化光追管线性能并解决常见坑点。

[Recaps]
要想光追跑得动，底层优化是地基。首先关于**加速结构 (Acceleration Structure)**，构建工作应尽量扔到**异步计算 (Async Compute)** 队列里，别阻塞主渲染线程。内存分配是个大坑，无论是 **BLAS (底部加速结构)** 还是 **TLAS (顶部加速结构)** 都要极力避免碎片化，静态物体建议压缩显存，但动态物体频繁更新会导致 BVH 结构松散，最佳策略是偶尔全量重建。几何体排列也很有讲究，AABB 包围盒重叠或空隙太大会导致大量无效光线，尽量合并静态模型，还要避免长条细碎的三角形，这样才能减少不必要的**相交测试 (Intersection Test)**。

最后聊聊画质与后期处理。光线采样时，要根据距离动态调整**纹理细节等级 (Texture Level of Detail)**，推荐使用射线圆锥法，比盲目贴高清贴图更省资源且画质更好。在处理反射和间接光照时，若场景**一致性 (Coherency)** 较差（如粗糙表面），光线方向发散严重，不如在算法上做一点模糊处理，兼顾性能与观感。至于**去噪 (Denoising)** 环节，必须尽早介入，流程通常包含信号预处理、**时间累积 (Temporal Accumulation)** 以及空间滤波。务必将漫反射与镜面反射分离处理，并充分利用现有成熟方案如 SVGF，毕竟纯实时计算成本太高，混合烘焙才是王道。

效果怎么样？实打实地干下来，CPU 渲染耗时能砍掉三分之二，比 OpenGL 快两三倍。这说明现在 Vulkan 驱动效率高，倒逼咱们代码必须写得精，以前那些藏在驱动开销下的小毛病现在全暴露出来了。建议大伙儿去 ARM 的 GitHub 仓库下点示例代码，对着看性能计数器实测一下，这才是最稳的经验。

那怎么知道这玩意儿好不好训练呢？这就得靠柯尔莫哥洛夫复杂度 (Kolmogorov Complexity) 的概念了，听着玄乎其实就是衡量这段数据到底多难编成代码。实际干活儿的时候，我们直接用 PCA(主成分分析) 来量化物理系统的复杂程度。比如一块布，如果能用很少几个变形模式 (Modes) 就能还原大部分动作，说明它不复杂，神经网络就能学得飞快；要是乱七八糟的全是细节，那就得加大算力。说白了，就是先降维，再训练，这样模型才吃得消。

实操中最坑的一点不是训练，而是稳定。刚开始大家习惯一帧一帧地教，结果模型稍微有点误差积累，下一秒布料直接炸穿屏幕，状态彻底崩坏。后来改成预测几帧作为一个窗口，让它不断自我修正轨迹，而不是每一帧都从头纠偏，系统立马就稳如老狗。最后实测下来，CPU 成本跟顶点数无关了，只看用了多少个模式，从每秒半帧直接拉满到三千帧，这效率简直是降维打击。

最后还得给大伙提个醒，别一开始就把那些计算量大但效果好的“暴力解法”给毙了。虽然它跑不动，但它生成的“真实基准” (Ground Truth) 是最宝贵的训练数据。另外别光看损失率低了就觉得质量好了，稳定性才是用户体验的关键。这套玩法特别适合那些物理规律明显、不想搞随机混沌的系统，比如软体形变 (Soft Body Deformation) 或者布料，算是给咱们未来的物理特效开发指了条新路。

LevelX 团队专门研发医疗手术模拟游戏，既要保证医学真实性，还得照顾手机那点可怜的显存。这次演讲作者掏底牌分享了四套经手验证过的技术栈，教大家在移动平台上怎么用最少的资源做出最骚的视觉特效。

[Recaps]
LevelX 团队主要解决移动端资源少但效果要求高的问题。他们用了一套动态生成遮罩 (Mask) 的方案，直接把低分辨率纹理画进模型的 UV 空间。考虑到 UV 展平带来的接缝问题，他们特意加了一步膨胀 (Dilation) 处理，相当于把像素往边缘多推一点，完美掩盖瑕疵。配合 Unity 的命令缓冲区 (Command Buffers)，玩家就能在屏幕上实时“作画”而不卡死手机。

有了遮罩基础，他们做出了流血和积水效果。利用双缓冲 (Ping-Pong) 技术，两个渲染纹理轮流读写，每一帧把颜色值乘个小数实现淡化，或者乘以大于 1 的数实现淤血堆积。再挂上几个简单的刚体物理组件，液体流动就活了。想要洗掉血渍，把混合模式改成减法就行了，这种逻辑简单粗暴，却比硬算流体模拟要省性能多了。

软组织变形这块，作者没用笨重的骨骼绑定，而是改了顶点着色器 (Vertex Shader)，用世界空间衰减函数直接操控网格点。为了光照不穿帮，还得顺带重算法线。遇到旋转形变时，把位移、缩放和旋转拆开单独处理，彻底消除了常见的拉伸褶皱，比传统蒙皮灵活多了。

最后的压轴戏是“体积鼻屎”，靠有向距离函数 (Signed Distance Function) 和球面光线追踪构建。配合模糊折射和弹簧物理，不仅看着真实，还能玩物理互动。整个演讲的核心思想很明显：别硬算物理，多用 Shader 和数学技巧去骗过眼睛，让低端机能跑起看似高端的效果。

[Recaps]

再看篮球 3v3 项目，难点变成了团队配合。 offense 这边设了个“教练”角色，负责指挥战术跑位，球员只负责执行；defense 那边用了分层多智能体强化学习（Hierarchical Multi-agent Reinforcement Learning），高层决策盯谁，底层负责具体动作。结果证明，这种架构比普通强化学习效果猛多了。目前这些 AI 已经上线服务，峰值 TPS 过万，连服务器压力都成了问题，玩家评价更是“这不像人机”，顺便还用来测试新职业的技能平衡，妥妥的实用主义黑科技。

## 'Witcher 3' on the Nintendo Switch: CPU & Memory Optimization (Presented by NVIDIA)
- **Speaker:** Roman Lebedev (Saber Interactive Inc.)
- **Duration:** 21 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1026635
- **Slide Page:** 
- **Custom ID:** 1026635

### Overview
A lot of old and new games are ported to Nintendo Switch; this talk will show that Switch is a capable platform that can run even the most demanding today's games with little loss in fidelity. We describe in detail CPU, Memory and Build size optimizations and tradeoffs we made during the development of Switch version of Witcher 3: The Wild Hunt.

### Content Summary
[TLDR]
通过重构线程模型与内存布局优化，硬是把 46G 的巫师 3 压成 28G 并在 Switch 上跑通了。

[Background]
面对媒体质疑及机能差异巨大的硬件，演讲者分享了将原版高优化主机游戏移植到低端掌机的经验，重点解决性能卡顿与存储超限问题，适合关注跨平台优化的开发者。

[Recaps]
咱们先说 CPU。Switch 这玩意儿核心就那么点，跟当年 PS4 比差远了。以前那些自旋锁 (Spinlock) 和忙等待 (Busywait) 的代码，在这上面就是灾难，线程互相等结果直接卡死。我们直接把同步机制全砍了，换成条件变量 (Condition Variable) 这种高效的，甚至搞了个锁栈 (Lock Stack)，保证每个核心都有活干，不再有空档期。物理模拟太吃资源，只能降低频率或用 GPU 通用计算 (CUDA) 做加速，虽然提升有限，但动态切换能救急。

再看内存，这是最容易忽视的坑。有时候你以为性能瓶颈在算力，其实是在 CPU 缓存跟不上，也就是常说的缓存未命中 (Cache Miss)。我们拿工具分析热路径，把经常调用的结构体成员挪到一起，让它们在同一块内存区域。编译的时候又上了链接时优化 (LTO) 和配置导向优化 (PGO)，把代码指令排序得更符合流水线。哪怕是简单的解压操作，换个内存缓存类型，速度都能翻好几倍。

最后就是怎么塞进那个 SD 卡槽里。音效能耗大，长声音走 Opus (Opus) 高压缩，短音效用 DPCM (DPCM) 快解码。文本编码从 Unicode (UTF-16) 切到 UTF-8 (UTF-8)，字符串瞬间省一半。贴图格式换了 ASTC (ASTC)，必要的时候哪怕牺牲一点 LOD (Level of Detail) 也在所不惜。最绝的一招是取消流式缓存，Switch 的闪存读写本来就快，没必要多此一举。这套组合拳下来，46G 的大文件被硬生生压到了 28G。
