## Go With the Flow! Fluid and Particle Physics in PixelJunk Shooter
- **Speaker:** Jaymin Kessler (Q-Games)
- **Duration:** 59 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012358
- **Slide Page:** https://www.gdcvault.com/play/1012447
- **Custom ID:** 1012358

### Overview
The presentation will focus on the technical aspects of PixelJunk 1-4 (PixelJunk Shooter) for the PlayStation 3. The game makes use of a fluid system that is generated using the PS3 SPU and the presentation will cover this in some detail, as well as the stage editor and the character animation system.

### Content Summary
[TLDR]
揭秘 PS3 独占神作如何通过 SPU 集群与粒子算法优化，突破硬件限制实现丝滑流体特效。

[Background]
针对 PS3 特殊架构下的性能瓶颈，演讲者分享了如何用专用处理器处理高复杂度实时物理模拟，为同类项目提供硬核参考。

[Recaps]
这场演讲主要分享了 Q-Games 如何用 PS3 独特的硬件架构做出了惊艳的流体效果。主角《PixelJunk Shooter》的设计核心就是元素融合，比如岩浆遇到水会变石头或蒸汽。物理层面上，开发者没有直接套用学术界的**平滑粒子流体动力学 (Smooth Particle Hydrodynamics)**，因为那个太吃性能。他们选择了更适合实时的**并行粒子模拟 (Parallel Particle Sim)**，并用**维尔莱积分 (Verlet Integration)** 代替常规方法，确保每秒 60 帧下能稳定驱动三万多个粒子，即便牺牲了一点灵活性换取了更高的帧率稳定性。

说到性能榨取，不得不提索尼 PS3 特有的**协同处理单元 (Synergistic Processing Unit)**。团队设计了精细的**任务链 (Job Chain)**，将复杂的物理计算拆解为碰撞检测、合力统一、位置更新等步骤，分派给多个 SPU 并行干活。为了让流体摸起来像真的，他们引入了粒子间的斥力逻辑，强行维持间距防止“液体”压缩变形，还加入了热量传递机制让水火反应更有质感。另外，用原子 DMA (**Atomic DMA**) 技术在内存块间高速搬运数据，避免了主频瓶颈导致的卡顿，整个流程就像精密的流水线作业。

图形渲染和碰撞检测上也充满了“土办法”。既然粒子画出来是一堆点，那就用低分辨率缓存加模糊滤镜，掩盖颗粒感，制造出液体表面的连贯性幻觉。碰撞判定更是玩起了**距离场 (Distance Field)**，预先算出整个关卡里每个点到墙壁的距离，一旦角色进入区域就查表判断是否撞墙，比传统算法快得多。演讲最后还提到编辑器功能，以及为什么这类重度依赖 SPU 计算的玩法很难移植到 Xbox 360 上，强调了架构选择对游戏设计的决定性影响。

## Graphics Programming for Multi-GPU and Multi-Monitor Games
- **Speaker:** Thomas Fortier (AMD)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1012663
- **Custom ID:** 1012663

### Overview
AMD's Radeon 5000 family of GPUs enables games to display graphics across multiple displays from single card, offering panoramic views and a more immersive gaming experience to end users, while simultaneously leveraging multiple GPUs for maximum performance. This session discusses how game developers can take advantage of this new multi-monitor technology for innovative gameplay scenarios, as well as how to ensure optimal graphics performance when multiple GPUs work in parallel for rendering operations.

### Content Summary
[TLDR]
想让玩家在多屏多卡上玩得爽，得避开资源同步坑并正确计算视野，否则帧数不涨反跌。

[Background]
现在的玩家爱折腾三屏看风景和双卡刷帧数，但开发者如果代码写得烂，不仅体验差还可能导致性能缩水。AMD 大佬这篇演讲就是来教大家怎么给多显卡和多屏幕做优化，别把高端硬件当摆设。

[Recaps]
首先说多屏幕这事儿，AMD 旗下的 ATI Eyefinity 多屏拼接技术 (Eyefinity Technology) 让一张显卡能同时推三块甚至六块屏，分辨率叠加起来非常大。开发者绝对不能把代码写死在特定分辨率上，否则玩家根本没法在宽屏选项里选。最关键的是要把视场角 (Field of View) 根据实际显示比例自动调整，别让角色在巨幕中间看起来像被压扁的怪物，还有那些过场动画和 HUD 界面也得挪挪位置，别被物理分屏切断视线。官方认证分了 Ready 和 Validated 两种，前者只是勉强能跑，后者才是在 UI 布局上真正做到了兼容好，想拿贴纸宣传最好冲后者。

然后是双显卡或多显卡协同工作的交火技术 (Crossfire)，虽然大家都指望加张卡帧数就能翻倍，但如果处理不好反而可能比单卡还卡。这里最大的坑在于交替帧渲染 (Alternate Frame Rendering) 带来的帧间依赖，比如上一帧生成的资源这一帧还没准备好就被另一张卡用了，这时候就得给每个 GPU 复制一份资源来避免打架。另外，CPU 跟 GPU 之间别瞎搞同步，尤其是别等着查询 (Query) 结果返回再干活，这样会把图形流水线 (Pipeline) 彻底堵死，内存映射的时候也别锁住静态缓冲，不然多卡性能反而不如单卡。

最后总结几个实战避坑指南，别把显卡数量写死在逻辑里，测试时记得强制单卡模式对比基准线，还要查查有没有不必要的纹理依赖。如果想跑满性能，必须确保游戏是显卡瓶颈而不是卡在 CPU 调度或者驱动锁里。AMD 也提供了专门的 SDK 样本可以参考，兄弟们在做适配的时候多测几台真机，别光看自己那台高性能机器能跑就行，毕竟硬件生态千奇百怪，稳妥点总没错，免得上线后被玩家喷优化做得太烂。

## Zero to Millions: Building an XLSP for Gears of War 2
- **Speaker:** Dan Schoenblum (Epic Games)
- **Duration:** 45 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012329
- **Slide Page:** https://www.gdcvault.com/play/1012456
- **Custom ID:** 1012329

### Overview
This lecture will dissect how Epic Games built a robust and massively scalable backend platform for Gears of War 2 with less than a year to build, test, and deploy it - starting from scratch. The system had to collect stats from hundreds of thousands of game sessions per day, monitor hardware information and player settings, and deliver daily content to every user. Attendees will learn how the system was built, problems overcome during its development, and what can be expected when trying to build a similar system.

### Content Summary
[TLDR]
Epic 自建 MCP 架构突破主机限制，靠异步处理与 OLAP 方案轻松驾驭海量玩家数据。

[Background]
Epic 团队为了给《战争机器 2》添加超越 Xbox Live 的功能，由极小团队在有限时间内从零搭建高性能后端，适合对服务器架构和运营数据分析感兴趣的开发者。

[Recaps]
兄弟们在玩主机游戏时可能感觉不到，但为了搞出比官方平台更牛的功能，Epic 团队决定自己建一套后端系统。这套架构的核心是用 web 服务器 (Web Server) 对接 SQL 数据库 (SQL Database)，并通过 XLSP (Xbox Live Server Platform) 技术通道保证安全性。系统主要分两种模式：一种是你要啥我回啥的双向服务，另一种是只管收不管回的异步服务 (Asynchronous Service)。为了防止大量数据把网络堵死，他们会先把异步请求扔进本地队列 (Queue) 里慢慢处理，这样客户端就不用傻等了。

这套系统的性能优化全是实战里摸出来的坑。当初想用 xml 传数据，发现太占资源，最后换成了二进制格式。还有个挺容易忽略的 bug，关于玩家账号 ID 的缓存逻辑，因为事务回滚处理不当导致缓存出错，后来才记住“事务提交后再更新缓存”的原则。当数据积累到几十亿行时，普通 SQL 查询就卡成 PPT 了，这时候必须上 OLAP (Online Analytical Processing) 方案，它能把数据预聚合，瞬间就能跑出玩家行为报告，这对于游戏平衡调整和运营活动规划简直是大杀器。

上线前的日子更是惊心动魄。他们搞了一套压力测试 (Stress Test) 来模拟流量，还意外发现了多线程下的死锁问题。最刺激的是一次发布前 117 秒才发现外网端口没配好，全靠运气才保住发布日期。他们还做了个网页版的后台管理界面，方便随时调度节日活动，比如什么“情人节双倍经验”。运维方面则依靠 SCOM (System Center Operations Manager) 工具实时监控，还得防着误报警报吓死人。虽然后期也遇到服务器宕机之类的小插曲，但这套架构确实让 Gears 系列能长期稳定运行，还能支持像“双倍经验周”这种复杂的活动策划，真心给想自研后端的同行省了不少心。

## The Next Generation of Fighting Games: Physics & Animation in UFC 2009 Undisputed
- **Speaker:** Hiroki Ueno (Yukes Co., Ltd)
- **Duration:** 47 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012304
- **Slide Page:** https://www.gdcvault.com/play/1012454
- **Custom ID:** 1012304

### Overview
UFC 2009 Undisputed is a fighting game first to employ a variety of newly developed game techniques, among these being full-scale physics simulation. This session will provide a detailed description of the most useful character animation techniques used in UFC 2009 Undisputed, focusing mainly on Physics and Character Animation Blending, while also introducing Full-body IK Targeting and Character Navigation. Additionally, this session will explain these concepts without delving too deeply into difficult numerical formulas, thus allowing all types of game designers and artists to be welcome listen.

### Content Summary
[TLDR]
融合物理引擎与动画，破解穿模与控制矛盾，树立格斗游戏新标准。

[Background]
格斗游戏画质虽进化，但核心交互依旧僵硬。团队欲在《UFC 2009》突破极限，解决物理稳定性与操作反馈的难题。

[Recaps]
以前玩格斗游戏，画面是高清了，但打人还是像撞墙，甚至能看到衣服穿模。开发组立了三个 Flag：动作要逼真（Realistic Animation）、别穿模（Collision）、操作必须跟手（Constant Control）。为了搞定这些，他们没选纯物理控制，而是选了基于 Havok (HAVOK) 物理引擎的混合方案：先播动画，再用物理参数把角色模型推着走。这种玩法既能保留动画的演出效果，又能让碰到墙壁时产生自然的晃动反应，比死板的脚本灵活多了。

但这事儿做起来全是坑。物理太不稳定，经常抖得像癫痫，手脚还会卡进肉里。解决之道在于精细调教：第一，初始设置别把关节限位开太大，否则人一放松就会扭成麻花；第二，动态计算关节活动范围，只允许必要的幅度运动。遇到穿模或抖动（Jitter）时，直接用反向运动学（Inverse Kinematics / IK）瞬间修正姿态，比如拳头埋进对手身体里时，强制把骨头拉出来，或者临时关闭部分碰撞判定，给个“瞬移”缓冲，让玩家看不出来 BUG。

移动和打击更是核心难点。移动时没用传统的硬切方向，而是用了动画混合（Animation Blending），配合八种基础步态，根据摇杆力度平滑过渡，走路才有呼吸感。为了防止脚底打滑，他们锁定了落地的那只脚。至于出拳踢腿，开发组自己写了一套全身上肢 IK 求解器，不用做几百种瞄准动画。系统会自动算手臂该伸多长、转多大角度才能打到目标，还能根据敌人跑动实时微调。这套黑科技不仅省了动画资源，还让角色看起来真的在“瞄准”敌人，最后销量破 350 万，算是把物理拟真和手感平衡做到了极致。

## Texture compression in real-time, using the GPU
- **Speaker:** Jason Tranchida (Volition Inc. (THQ))
- **Duration:** 23 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012254
- **Slide Page:** https://www.gdcvault.com/play/1012554
- **Custom ID:** 1012254

### Overview
This session covers how to use the GPU on current consoles and DirectX 10.1 video cards in order to perform DXT texture compression. It presents a method that does not rely on GPU computation APIs or the presence of bit-wise math operations. Implementation details & optimizations per-platform will be discussed.

### Content Summary
[TLDR]
别再让 CPU 压纹理了，直接用 GPU 实时跑 DXT1，把延迟干到几毫秒，动态素材做出来再也不卡脖子。

[Background]
以前做动态纹理（Texture），CPU 压缩太慢，得等好几帧数据才能给回去，体验极差。演讲者为了支持无缝地形混合等玩法，决定用 GPU 加速。

[Recaps]
先说说为啥要把这个苦活累活丢给 GPU。这哥们当年做《红风暴：游击队》的时候发现，CPU（中央处理器）压纹理虽然稳，但太慢，有时候从生成好图到能拿去显示，中间得等个三四个帧，玩家看着画面加载会懵圈。换上 GPU（图形处理器）跑 DXT1（纹理压缩格式）后，压一个 1K 纹理只要零点几毫秒，基本做到实时响应，这对那些要无限叠加材质层的地图系统简直是救星，否则没法处理无缝地形混合的需求。

具体咋搞呢？简单说就是把大图渲染到一个分辨率缩小的缓冲里，每个小像素负责代表原始大图的十六个像素块。核心逻辑全在 Shader（着色器）里跑，别整那些复杂的位运算，靠加减乘除凑合出颜色端点和索引值最快。最简单的算法是取颜色的最大值和最小值当端点，虽然遇到纯色或者强对比色可能会有瑕疵，但速度真的快。最后通过平台特有的 API 把结果存回显存，比如 X360 可以用内存导出省流程，PS3 因为格式限制就惨了点，得靠交替写入的代码绕弯路。

还得注意几个性能优化的细节。编译器虽然智能但不一定对味儿，同一份代码加上循环展开的标记，执行效率直接翻了四倍，这差距太大了。不同的贴图类型最好用专门写的 Shader，比如法线贴图（Normal Maps）单独处理就能并行计算两个像素。画质方面大家不用慌，肉眼几乎看不出区别，除非你拿软件放大看差异图。虽然有些极端颜色组合下会出现噪点条，但总体来说这波技术升级性价比极高，动态生成的世界就是这么搞定的，想做的赶紧抄作业。

## Streaming Massive Environments from 0 to 200 MPH
- **Speaker:** Chris Tector (Turn 10 Studios)
- **Duration:** 60 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012335
- **Slide Page:** https://www.gdcvault.com/play/1012656
- **Custom ID:** 1012335

### Overview
Come to this session and learn about the processes used to produce and render the massive track environments in Forza Motorsport 3. Walking the pipeline from art to game the attendee will learn some of the key components of rendering massive detailed models at 60 frames per second with specific stops along the way discussing the details of Turn 10's strategies and practices to provide photo quality detail at racing speeds.

### Content Summary
[TLDR]
想要在大地图里狂飙 60 帧？Turn 10 教你把优化全搬到离线阶段，用硬件极限换极致体验。

[Background]
Turn 10 工作室为了在 Xbox 360 有限的存储和算力下实现超大规模赛道无缝加载且保持高画质，分享了一套极致的流式加载管线经验，供同行参考。

[Recaps]
核心痛点很简单：赛道长达十几英里，资产几十万，但主机内存就这点，还得跑满特效、UI 和 AI (Artificial Intelligence) 保证 60 帧。他们的解法是把大部分优化工作放在离线预处理 (Offline Processing)，绝不占用运行时性能。整个数据流遵循存储层级：从硬盘到压缩缓存 (Cache) 再到解压缩堆 (Heap) 内存。利用块读取 (Block Read) 技术隐藏硬盘寻道时间，通过 LZX 格式压缩减少磁盘占用，核心就是为了降低对随机读取的依赖。

最硬核的是离线可见性系统。他们在预制作阶段就用深度缓冲渲染和遮挡查询 (Occlusion Query) 来计算视野，甚至包括贡献剔除和 LOD (Level of Detail) 选择。这保证了运行时不需要再算这些逻辑。纹理管理是另一大难点，他们把纹理分成顶层 MIP、MIP 链 (MIP Chain) 和小图三个视图，根据屏幕贡献率动态裁剪内存占用，优先删纹理保模型不被抠掉出现穿帮。

运行时策略同样重要。为了让数据读取更顺畅，他们会对 ZIP 里的文件按赛道顺序排序，减少磁头跳动。内存分配上采用批处理模式，先释放再统一申请，避免碎片化。Pipeline 中的优化分三波：先用像素阈值剔除 trivial 数据，再按内存容量切分纹理，最后根据驾驶速度和带宽限制调整下载量。这套经过三代产品打磨的系统，能在几小时内构建完一个赛道，并让游戏在高速流动中保持画面稳定，几乎没有卡顿感。

## R-Trees -- Adapting out-of-core techniques to modern memory architectures
- **Speaker:** Sebastian Sylvan (Rare Ltd.)
- **Duration:** 23 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012255
- **Slide Page:** https://www.gdcvault.com/play/1012452
- **Custom ID:** 1012255

### Overview
Code running on modern in-order CPUs pay a hefty cost for cache misses. This leads to major performance problem for pointer-heavy data structures, such as spatial hierarchies. This problem is similar to the problems encountered by people doing out-of-core processing for the last several decades. They needed to minimize disk seeks, we need to minimize memory fetches. An R-tree is a BV-hierarchy based on large fixed-size blocks, commonly used in disk based spatial processing. This talk shows how to adapt them for in-memory use, reaping major benefits with respect to cache behaviour, as well as SIMD processing, and more!

### Content Summary
[TLDR]
别把内存访问当免费午餐，借鉴数据库“外存算法”思想搞块存储 R 树 (R-Tree) 加预取，能治掉主机架构里的缓存缺失焦虑。

[Background]
主机架构里二级缓存 (L2 Cache) 丢失一次代价太大，传统指针结构太容易崩盘。这讲是教开发者在设计初期就别想着“内存访问很便宜”，而是像管硬盘一样管内存，专门救那些空间索引的性能急病。

[Recaps]
老哥们先扒一扒现在的痛，主机上的二级缓存 (L2 Cache) 缺块得罚几百个时钟周期，传统的指针遍历简直就是给 CPU 喂屎。演讲者强调一个核心心态：别总以为内存调用不花钱，得把它当成读硬盘那么小心，提前把路铺好。手里最好的工具就是 `DCBT (Data Cache Block Touch)` 指令，要么主动搞预取 (Prefetch) 让数据等人，要么一把拉一大块数据来平摊单次访问的巨额罚款。

具体的数据结构方案就是 R 树 (R-Tree)，你可以理解成一种经过改造的 AABB 树 (AABB Tree)。它不走常规二分法，而是一个节点里塞满几十个子节点，而且把子节点自己的包围盒也直接写在父节点的数组里。这么做就是为了让你遍历的时候少解引用几次指针，直接在一整块连续内存里横扫过去，大大降低了随机访存的开销。这种“按块存取”的设计天生就是为高速缓存设计的，不用后期瞎折腾优化。

至于动态操作和怎么建，R 树支持物体动起来也不用重排拓扑，只要更新边界框就行。节点分裂的时候，普通的切法不行，得用改进的 K-means 聚类 (K-means Clustering) 算法来解决斜向聚集的坏情况，顺便还能时不时跑个增量修复程序，把树的质量拉回到最佳状态。查询遍历千万别用深度优先堆栈，要用广度优先搜索 (Breadth-First Search) 加队列，这样能配合预取流水线，不让数据流断档。

根据实测，分支因子也别贪大，硬件限制导致超过 32 就没用了，卡在 20 上下最划算。最后给个通用套路：以后内存访问慢了别光顾着调编译器参数，多看看数据库那帮人是怎么处理磁盘 IO 的，把他们的算法借过来套用到内存上，往往能省下大把研发时间，这就是典型的偷师学艺。

[Background]
做物理模拟的都头疼怎么快速算距离，特别是 CPU 资源紧缺的时候。暴雪大佬分享了这套 2D 凸多边形求距方案，适合写底层物理或碰撞检测的同学，全是实战干货。

[Recaps]
要想搞定物理碰撞，第一步得会算点到几何体的距离。演讲先从最简单的线段、三角形讲起，引出了 `Voronoi regions (沃罗诺伊区域)` 和 `重心坐标 (Barycentric coordinates)` 这两个核心工具。简单说，前者帮你判断点是靠近哪个顶点还是边，后者则是算点在三角形内部权重的神器，能把面积比例化成计算用的系数。搞懂这些基础，再算点到复杂的 `凸多边形 (Convex polygons)` 就水到渠成，能精准定位 `最近点 (Closest points)` 在哪。

接下来登场的是绝对的核心 `GJK distance algorithm (GJK 距离算法)`。这招比硬算快得多，它是通过不断“进化”一个简单的形状叫 `Simplex (单纯形)` 来逼近目标点。初始随便选个顶点，算出当前面的最近点，然后顺着误差方向找一个更远的支持点 `Support point` 加进来，直到形状不再变化或者包住目标点。这种迭代方式效率极高，而且逻辑严密，几乎不用考虑复杂的解析解，是业界通用的标准打法。

最后，如果要用在两个物体之间呢？这就得用到 `Minkowski difference (闵可夫斯基差)`，把求两个物体的距离转换成求新生成的虚拟物体和点的距离。大佬特意强调了数值精度的坑，单精度浮点数容易让搜索方向搞错，甚至死循环。解决办法是用叉积直接求垂直向量代替除法，并设置严格的终止条件，防止因微小误差卡壳。这套逻辑后来直接成了 Box2D 物理引擎的基础代码，非常值得抄作业。

## Physics for Programmers: Contact Generation
- **Speaker:** Erwin Coumans (Sony Computer Entertainment)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1012528
- **Custom ID:** 1012528

### Overview
As the complexity of games has increased, so has the knowledge needed to create them.  Creating the latest code for graphics, animation, physical simulation, even some extent artificial intelligence, requires greater knowledge of the necessary engineering and mathematical underpinnings than ever before.  And of the fields described above, one that has grown increasingly important is physical simulation, as shown by the latest games such as Little Big Planet and Crayon Physics. Creating such a simulation may appear to be a daunting task, but it is possible with the right background.

### Content Summary
[TLDR]
物理引擎别硬算所有接触点，学会用持久接触缓存加动态 AABB 树，碰撞稳定性和运行性能直接拉满。

[Background]
搞游戏开发的兄弟都知道，物理一旦算不对，就是穿模、物体乱飞或者服务器卡顿。索尼大神 Erwin Coumans 分享的这份干货，专门给那些深究 Bullet 引擎或底层碰撞算法的小伙伴，教咱们怎么处理碰撞生成里的各种奇葩 bug，让模拟更稳更省资源。

[Recaps]
做物理碰撞最忌讳一股脑全量计算，得讲究个流水线作业。整个流程分三层：先是用 `宽相检测 (Broadphase)` 的粗筛机制，利用 `轴对齐包围盒 (AABB)` 快速剔掉绝对碰不到的物体对；接着进 `窄相检测 (Narrowphase)` 找具体碰撞细节；最后才是生成 `接触流形 (Contact Manifold)`。最简单的做法是直接算单个 `接触点 (Contact Point)`，但这玩意儿在物体高速运动或旋转时特别不稳定。所以行家里手通常都会启用 `持久接触缓存 (Persistent Manifold)`，直接把上一帧算好的多个接触点留到下一帧复用，只根据位移更新距离，这样能大幅减少 `碰撞检测 (Collision Detection)` 的开销，还能避免物体在地面上无故抖动。

遇到凸体这种形状，光靠一个点不够，得用 `扰动法 (Perturbation)` 绕着法线方向转几圈多采几个样点，但这招用在圆球形物体上会有副作用，容易导致物体自己产生自转。所以实际操作中要严格控制扰动角度，或者加阻尼抑制。对于像建筑墙体这种复杂的 `凹形网格 (Concave Mesh)`，直接用 `GJK 算法 (GJK Algorithm)` 会挂，得拆成一个个小三角形面片单独处理。这时候性能瓶颈就在搜索上了，必须上 `动态 AABB 树 (Dynamic AABB Tree)`。它不像静态树那样死了就要重造，支持增量式添加或删除节点，比如插入新节点时会自动寻找曼哈顿距离最近的叶子节点合并，能有效应对物体移动带来的拓扑变化，连光线投射和视锥剔除都能顺手做了。

最后还得防着那种“地台跌落”的诡异 bug，也就是当物体撞到两个三角形拼接的 `内部边缘 (Internal Edges)` 时，接触法线容易乱跳，导致物体被莫名其妙地弹飞或卡在墙里。这时候不能盲目统一法线，得引入 `沃罗诺伊区域 (Voronoi Region)` 的逻辑来判断物体到底处于哪个区域的邻域内，只有当接触发生在边缘之外时才进行法线修正。把这些底层的数学陷阱填平，无论你是魔改 Bullet 引擎还是从头撸代码，都能少走很多弯路，毕竟代码跑得流畅，玩家体验才算到位。

[Background]

## Per-Pixel Linked Lists with Direct3D 11
- **Speaker:** Nicolas Thibieroz (AMD)

### Content Summary
[TLDR]

[Background]
做游戏的老哥都知道，一堆半透明玻璃打架时的颜色混合是老大难问题，搞不好就糊得一塌糊涂。这演讲就是拿来解决这个痛点的，专门教引擎开发人员如何在 DirectX 11 环境下实现高性能的“无顺序透明”渲染。

[Recaps]
这事儿的核心其实就是“像素级链表 (Per-Pixel Linked Lists)"。以前显卡 API 限制太多，想做个链表管理每个屏幕位置的碎片太难了。但到了 DX11 这里，硬件允许我们高效创建和解析链表。简单来说，就是屏幕上每一个坐标点都挂了一个小尾巴，把重叠在这一块的像素碎片全串起来，这样后面处理起来就方便多了，想怎么排就怎么排。

具体的实现过程分两步走，首先得把这些碎片存进去。这时候得用像素着色器 (Pixel Shader) 5.0 配合 原子操作 (Atomic Operations)，通过两个 无序访问视图 (Unordered Access View) 的缓存区来抢地盘。这就像大家在银行窗口办业务，必须用“中断交换 (InterlockedExchange)"这种互斥锁操作，保证每个人都能准确地把数据填进对应的小格子，不会撞车。写入完再根据 起始偏移量 (Start Offset Buffer) 找到链表的头。

最后一步是把存好的东西拿出来渲染。这时候可以把真实的硬件混合模式关了，自己在着色器里按 深度测试 (Depth Test) 结果把碎片从远到近拉出来，手动算混合颜色。为了省显存，作者还搞了个骚操作，用 早深度剔除 (Early Depth Stencil) 把看不见的碎片直接扔一边，颜色深度数据全部压缩打包。就连支持 多重采样抗锯齿 (Multisample Anti-Aliasing) 都不怕，只要多塞几个比特位记录覆盖率就行，既保了质量又不吃满内存。

## Direct3D 11 Indirect Illumination
- **Speaker:** Holger Gruen (AMD)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:**

### Overview
Brought to you with the collaboration of the industry's leading hardware and software vendors, this day-long tutorial provides an in-depth look at the Direct3D technologies in DirectX 10, 10.1 and 11, and how they can be applied to cutting-edge game graphics.

### Content Summary
[TLDR]
AMD 大神用 DX11 和光追技术实现了实时间接光照和阴影，解决了动态场景的全局光照性能瓶颈。

[Background]
实时全局光照一直是图形编程的硬骨头，传统算法要么画质差要么太卡顿。这场演讲针对动态场景，拆解了一套结合反射阴影贴图与射线追踪的实战方案，适合想提升画面光影质量的图形程序员参考。

[Recaps]
首先解决怎么算出柔和的间接光照但不带阴影的问题。核心思路是用反射阴影贴图 (Reflective Shadow Map, RSM)，把场景里所有能发光的表面都存进一张图，当成虚拟点光源 (Virtual Point Light, VPL)。计算光照贡献时，别傻乎乎地一个个算，而是利用数学技巧对周围四个 VPL 做双线性插值混合。同时配合双边上采样 (Bilateral upsampling) 技术，先把低分辨率的光照数据算完，再通过高斯滤波边缘检测平滑到全屏。这招在老旧显卡上也能跑得动，关键是把那种死板的色块感变成了像真实环境里的漫反射光晕。

接着就是最难搞的间接阴影环节。既然有光，肯定会有东西挡光线产生阴影。演讲者提出用直接渲染线程 (Compute Shader, CS) 把遮挡物（比如墙壁、角色）扔进一个三维网格列表里，相当于给空间建了个哈希表。然后从光源位置发射射线去扫这个网格，看看哪些 VPL 发出的光被前面的三角形挡住了。把这些“挡光”导致的亮度损失从总光照里减掉，就能得到准确的间接阴影。这种方法比纯物理模拟快得多，适合游戏里实时演算。

最后是性能和未来的优化方向。实测数据很猛，在双卡 HD5970 上开满特效能跑到 280FPS，加上间接阴影也有 70FPS，不过射线检测确实吃 CPU/GPU，占了约 9ms。演讲者也承认还有坑可以填，比如把间接光照分辨率压得更低，或者改进数据结构去掉原子操作 (Atomic Operations) 这种同步开销。如果能搞定这些，这套技术甚至能往更早的硬件上移植。总的来说，就是从 DX9 兼容模式过渡到 DX11 高端玩法，给开发者提供了一条可落地的实时全局光照实现路径。

### Content Summary
[TLDR]
DX11 DirectCompute 性能优化核心：吃透硬件差异，避开存储库冲突与频繁同步，线程组大小必须达标。

[Background]
两位行业大佬基于 AMD 和 NVIDIA 的显卡架构，详解了 DX11 DirectCompute 的性能陷阱与技巧。适合负责 PC 端图形引擎、算子优化的程序员，特别是想提升 GPU 利用率并解决卡顿问题的开发者。

[Recaps]
这篇内容其实就是在教大家怎么正确喂饱 GPU 这个大胃王。GPU 本质上是吞吐量导向的处理器，就像流水线工厂，必须不断塞给它足够的任务才能运转。所以代码里要找细粒度并行（Fine-grained parallelism），比如一个线程处理一个像素或粒子，这样效率最高。另外 DirectCompute (DirectCompute) 虽然能搞定通用编程 (General-purpose programming) 和后处理操作 (Post-process operations)，但不代表它永远胜过传统的像素着色器 (Pixel Shader)，只有在显存或计算密集型任务时才有优势，平时平衡好的传统管线很难被 CS 击败。

硬件细节差别很大，NVIDIA 的卡偏向标量 (Scalar) 架构，写代码不用刻意向量化，而 AMD 的卡是向量 (Vector) 架构，必须利用向量化指令否则性能崩盘。推荐优先使用 Shader 5.0 版本的 Compute Shader，因为线程数、共享内存和原子操作 (Atomic Operations) 的支持更全面。声明线程组时非常关键，总线程数必须大于硬件的波前大小 (Wavefront Size)，A 卡最大 64，N 卡最大 32，千万别写成 numthreads(1,1,1)，否则就是浪费算力。

内存管理也是个雷区。无序访问视图 (Unordered Access View, UAV) 如果被随机散乱读写，会引发缓存失效，应尽量批量写入。如果要做计数器功能，直接用带 Counter 标记的 Buffer，比手写原子操作更高效。线程组共享内存 (Thread Group Shared Memory, TGSM) 虽然快但有 32 个存储库 (Banks)，多个线程同时访问同组地址会触发存储库冲突 (Bank Conflicts)。解决办法是增加数组 Padding 或者按特定顺序访问，避免撞车。最后，尽量减少 Compute 和 光栅化 (Rasterization) 之间的切换次数，这对性能伤害很大。不同的显卡对占用率 (Occupancy) 的敏感度不同，不要盲目照搬官方示例，自己多调参数才是硬道理。

[Recaps]

### Overview
In Braid the player can rewind time at will - the scene plays backward at an accelerated pace, like you might see on a VCR. Rewinding is heavily used, and higher-level gameplay concepts are built on top of it, so it was important for rewinding to be robust, exactly reproducing the game scene at each given time. Furthermore, the game design required the player to be able to rewind a large amount of gameplay (30 to 60 minutes) and the memory of this gameplay had to fit into a small space (40 megabytes on consoles). [TLDR]

[Recaps]
做《时空幻境》时，这位开发者为了搞不定无限回溯 (Rewind) 的需求，试了很多种路子最后都没行。像录操作指令重放、做可逆物理模拟这些常见套路，要么维护成本高，稍微改个版本就挂，要么逻辑太复杂全是坑。他最后拍板，核心原则就是“稳健大于炫技”。与其绞尽脑汁去抠那 5% 的性能提升，不如干脆点，直接用内存换稳定，保证代码能跨版本跑通，毕竟能把游戏做出来发货才是真本事。

- **Speaker:** Ron Fosner (Intel)

### Overview
Threading a game can be hard work when you have lots of heterogeneous tasks to balance. In this session, you'll learn how to take a simple single-threaded series of semi-independent tasks, break them up, and solve them (with dependencies). ### Content Summary
[TLDR]
别死磕底层线程，搞个任务架构交给系统调度，这才是让游戏吃满未来多核核心的正道。

[Background]
现在电脑全是多核，很多开发者还在手动调线程，既累又不高效，还跟不上未来硬件。Intel 工程师 Ron 想告诉大家，别纠结线程细节，转向任务架构，让系统自动分配，才是让游戏引擎适配各种 CPU 的良方。

[Recaps]
演讲的核心就是劝大家忘掉“写线程”，改练“写任务”。现在的趋势是多核普及，单纯把渲染塞进一个线程、逻辑塞进另一个线程那种老套做法已经过时了。正确的姿势是利用**任务架构 (Task-based Architecture)**，把大工作拆解成无状态的**任务 (Task)**，扔进系统的**工作队列 (Work Queue)**里。具体的调度工作全甩给操作系统的**线程池 (Thread Pool)**，程序员只管把活儿切碎了投进去，不用操心哪个物理核心去干活。这样一来，无论是现在的六核还是未来的三十二核，代码都不用大改，实现真正的**可扩展性 (Scalability)**。

在处理这些任务时，最坑的是总想着复用数据和过早优化。讲者分享了个解迷宫的 Demo，一开始试图沿袭单线程的递归回溯写法，结果发现根本没法并行。后来他狠心放弃节省内存的念头，改为每个分叉路口直接复制一份上下文派生出新任务，哪怕有些路会重复走也没事，反正最后能收敛。这种“笨办法”反而消除了复杂的锁竞争。只要处理好任务之间的**依赖 (Dependencies)**，比如通过计数器知道某个任务等谁完成，就能在不阻塞主线程的前提下让多核并行起来。

最后还得提一嘴，多核化是为了让用户在任何硬件上都有好体验，而不是为了让游戏变得更快到离谱。讲者吐槽了个老游戏《Wing Commander》，在新电脑上因为没加帧率限制，三十分钟的关卡几秒就通关，导致玩家还没看清敌舰就死了。所以设计时要预留调节空间，别为了追求极致效率牺牲了可玩性。另外别光猜性能好坏，一定要拿工具实测，像 Intel 的图形性能分析器这类工具能帮你看到真实的任务执行情况，只有当你能意识到 L2 缓存争用这类问题时，才说明你真的把 CPU 榨干了。

做社交游戏，最头疼的是服务器得跟着玩家情绪走，流量波动太大。Zynga 老罗建议别死磕单机大服务，首选“横向扩展 (Horizontal Scaling)"。也就是多用小机器代替少数大机器，因为网上资源扩容比买新硬件快多了。但这就逼着你要改架构，不能像单机游戏那样依赖单一强服务器，得搞“数据库分片 (Database Sharding)"，把玩家 ID 算个模运算扔不同机器上，这样扩容的时候直接加节点就行，不用迁移大量数据，简单粗暴好维护。如果是读写冲突太多，可以在应用层自己协调，别指望数据库自带的事务机制，这样能减少跨机器开销。

关于架构选型，纯网页逻辑适合用 LAMP 栈 (LAMP Stack)，处理请求响应很快但没法做“服务器主动推送 (Server Push)"。如果要做 MMORPG 那种实时互动，就得混合架构，一部分走网页栈做社交功能，另一部分用长连接的 MMO 服务器维持状态。不管是哪种，核心是把复杂逻辑从数据库里抽出来，放到“应用层 (Application Layer)"。比如频繁读取的玩家状态，直接塞进“内存缓存 (Memcache)"里，别让数据库累死，只有最终结果才落盘。对于持久化连接，部署时要小心版本兼容，通常采取新老服务器并行，慢慢把旧流量切走的方式。

运维和落地细节也不能马虎。流量进来先过一层“负载均衡 (Load Balancing)"代理，像 HAProxy 这种，保护后端并防止单点故障。媒体文件（如 Flash 资源）别跟数据一起发，丢给 CDN 加速去。监控方面，用 Munin 画图看历史趋势，结合 Nagios 设报警阈值，一旦业务数据跌了就立马知道。最后老罗透露，虽然 NoSQL 很火，但目前 MySQL 生态更稳，只要逻辑做到位，普通 MySQL 照样能玩出花，不用迷信高端商业数据库，毕竟社区支持才是硬通货。另外别为了省事让客户端直接连数据库，一定要包个中间层，方便以后换库或者加缓存都不慌。

## Don't Dread Threads
- **Speaker:** Orion Granatir, Omar A Rodriguez (Intel, Intel Corporation)
- **Duration:** 51 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012189
- **Slide Page:** 
- **Custom ID:** 1012189

### Overview
Parallel code unleashes the full computing power potential for all major gaming platforms. You'll learn 4 easy steps to run in parallel: data decomposition, task definition, threading (API), and validation. We will share an introduction to these threading concepts and build up to apply these concepts to a game-based workload. Learn the legendary four point multi-core threading technique and take your place as a threading master!

### Content Summary
[TLDR]
GHz 瓶颈已过，靠堆主频没戏，得靠数据切分加任务调度，才是榨干多核 CPU 的正道。

[Background]
CPU 频率涨不动了，全是拼核心数。不少开发者一听说多线程就头疼，怕死锁卡顿。Intel 这回拿出内部实战经验，教怎么简单高效地把游戏跑在多核上，适合想优化性能又怕掉坑的老司机们看。

[Recaps]
开场先秀了个“萤火虫”Demo，20 万只 AI 同时动。串行的时候只有 33 帧，上了多线程直接 104 帧，差距巨大。这说明以前那种按功能分线程的做法（功能分解 (Functional Decomposition)）不行，比如单独一个音频线程、一个渲染线程，多了核心也没啥用，还容易打架。简单的把模块拆分并不是最优解，尤其是在核心变多的时候，很容易导致某些核心闲置。

真正好用的办法是数据分解 (Data Decomposition)。别管模块是什么，直接把一大坨数据拆开，谁有空谁干一份。像那些 AI 虫子，每只虫子互不影响，就能切成小块丢给不同核心算。关键是要少用锁 (Locks)，别让一块内存被多个线程抢着写，不然性能全浪费在等待上。只要数据块独立，逻辑就简单，并行效果立竿见影。

进阶一点要用任务系统 (Tasking)。把计算单元打包成“任务”，扔进线程池 (Thread Pool)，系统自动分配。这招能避免超负载 (Oversubscription)，也就是线程比核心还多导致的空转浪费。配合英特尔线程构建工具 (Intel Threading Building Blocks)，不仅能适配现在的 6 核，以后 32 核也能无缝运行，相当于提前防老了。任务机制让代码自适应硬件，不用为了新 CPU 重写逻辑。

最后别闭门造车，善用工具。平行工作室 (Parallel Studio) 能找到性能热点 (Hotspot)，还能抓死锁 (Deadlocks)。还有显卡性能分析仪 (Graphics Performance Analyzer) 能直接看每一帧 CPU 和 GPU 在干嘛，甚至能看到具体任务在哪条线上跑。工具好用，优化才能快，别自己瞎琢磨写错代码，有了这些辅助手段，多线程开发其实没那么吓人。

## Animation Warping for Responsiveness in FIFA Soccer
- **Speaker:** Paul McComas, Jason Sanmiya (Electronic Arts, Electronic Arts)
- **Duration:** 60 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012342
- **Slide Page:** 
- **Custom ID:** 1012342

### Overview
This session presents methods used in FIFA Soccer to improve the responsiveness and flexibility of motion captured animations. It describes when and how turn animations can be procedurally altered, and how this warping is done on-the-fly. Also, it details how this warping can be expanded to any animation that must reach a specific point at a specific time. The session concludes with some general observations on the benefits of warping method over more traditional techniques such as blending.

### Content Summary
[TLDR]
别死磕混合动画（Animation Blending），用变形（Warping）技术改动作，让 FIFA 角色又稳又快又跟手。

[Background]
做体育游戏最怕动捕太死板，一操作就滑步或者反应慢半拍。EA 这帮人为了模拟真实物理手感，憋出了这套变形方案，适合做高交互动作游戏的人看看。

[Recaps]
先说痛点，以前搞体育游戏要么纯程序化转圈像机器人，要么切动画脚底板溜冰，还很难中途改主意。EA 这帮老哥搞了个变形（Warping）系统，简单说就是把动捕好的素材拿过来当底图，按需求拉长压扁。特别是急转弯，他们把动作拆成减速、下蹲蓄力、加速三段，大部分旋转量都塞到下蹲那会儿，既省计算量又能保证脚不滑地，这就得配合反向运动学 (Inverse Kinematics) 锁住脚掌。

到了踢球头球这种互动环节，纯反向运动学 (Inverse Kinematics) 容易把人胳膊腿扭断，覆盖范围也有限。这时候就得上变形术，位置不够就往外拽点，高度不够就加层缓冲，甚至还能调整播放速率（Playback Rate）来匹配球的飞行速度。关键是要保持动量的连贯性，别让角色突然刹车或者浮空感太强，看着别扭，甚至为了匹配球速，他们还会微调播放速率，只要不突兀就行，毕竟玩家更在意动作细节是否自然。

最后再提几个实战坑。最忌讳盲目混合两个差距大的动作，就像混血基因突变，看着恐怖，这叫 Brangelina 问题，不如直接变形一个素材来得自然。还有方向调整时，优先保移动角度（Movement Angle）而不是脸朝哪里，因为身体转向比脸转头耗能量多，强行转身体会穿模。核心就一点：可预测性 (Predictability)，得提前算准角色到底停哪儿，不然 AI 规划全废，走路画圈圈谁爱看啊。其实连艺术家都要自己调反向运动学 (Inverse Kinematics) 限制，自动算不准，工具给足权限才好用。

## Animation and Player Control in Uncharted: Drake's Fortune and Uncharted II: Among Thieves
- **Speaker:** Travis McIntosh (Naughty Dog Inc.)
- **Duration:** 55 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1012300
- **Slide Page:** 
- **Custom ID:** 1012300

### Overview
A look at the techniques used by Uncharted: Drake's fortune and Uncharted 2: Among Thieves for implementing the player character's animation and control. Partial and additive animations, layering, remapping, flipping, performance and memory considerations are all examined in depth, as well as particular focus on the the player's core movement implementation. This is a look at what worked, and what didn't work, how we did what we did, how we're going to improve it in the future, and what non-standard animation features proved particularly valuable for the player's look and feel in the Uncharted series.

### Content Summary
[TLDR]
核心在于解决操控的即时响应与动画物理动量的冲突，通过分层、增量等黑科技省下巨大内存并保住好手感。

[Background]
这讲是 Naugthy Dog 的大神 Travis 掏心窝子分享《神秘海域》开发里的痛点和干货。主要解决了当玩家手柄输入要绝对跟手，但角色动作又要符合物理惯性的两难问题。特别适合对动作状态机、内存优化以及程序与美术协作流程感兴趣的同行，里面全是实打实的工业界解决方案。

[Recaps]
这事儿的核心矛盾就是“控制要快”和“动画要真”打架。按键跳转需要瞬间响应，而好的动作得带起节奏感，不能像机器一样瞬移。Naughty Dog 的解法是搞了一个强大的 分层系统 (Layering)，角色身上能叠个几十层动画，底层负责跑路，上层负责换枪或者滚翻，甚至脸部和手指都单独分层。这样一边在翻滚，一边还能接着换弹夹，互不影响。他们还用了细粒度的 部分覆盖集 (Partial Sets)，不用全身体重做，只替换手臂或脊椎骨骼就能出新动作，极大地灵活度了组合空间。

内存这块更是命根子，动画能占到关卡数据的三四成。为了省空间，他们出了不少骚操作。比如用 增量动画 (Additive Animations)，给角色加点抖动、摇头这种细碎的偏差，基础模型没变，但看起来就有几十种不同的站位，省去了大量全量动作数据。还有 镜像翻转 (Flipping)，左右对称的动作只做一半，运行时自动镜像。最狠的是直接把很多非关键动画采样率砍到 10 赫兹，只要配合高帧率回放，肉眼基本看不出来，硬生生把可用空间翻倍。

为了让手脚别穿模，得靠 反向运动学 (IK) 来救场。手抓枪口时要准，脚踩地形要对，哪怕下面是一坨复杂的网格碰撞体，他们也会用射线检测地面位置，动态修正脚踝高度。最后强调了工作流，别搞大厚设计文档，先拿冻结姿势做原型，好用再迭代。特别是 重映射 (Remapping) 技术，把动作参数交给动画师配，不用改代码就能调整跑速或转身幅度，这才是真正解放生产力的法子。
