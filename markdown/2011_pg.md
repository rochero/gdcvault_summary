## Physics for Game Programmers: Numberical Integration
- **Speaker:** Erin Catto, Erwin Coumans, Squirrel Eiserloh, Glenn Fiedler, Takahiro Harada, Gino van den Bergen, Kees van Kooten, Jim Van Verth (Blizzard Entertainment, Sony SCEA US R&D, TrueThought, Sony Santa Monica, AMD, DTECTA, Virtual Proteins, Insomniac Games)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1014280
- **Custom ID:** 1014280

### Overview


### Content Summary
[TLDR]
游戏物理里，辛欧拉法 (Symplectic Euler) 比欧拉法稳，比 RK4 快，是处理物理模拟的性价比之王。

[Background]
很多物理开发者都遇到过物体模拟“乱飞”或者能量守恒崩溃的毛病。这篇 GDC 演讲专门教大家怎么从底层选对 数值积分 (Numerical Integration) 算法，帮你避开那些会导致模拟发散的坑，适合想做动作或射击游戏底层逻辑的同学。

[Recaps]
咱们先说核心痛点：怎么预测物体下一秒在哪？最简单粗暴的 **欧拉法 (Euler's method)** 就是拿着当前速度乘时间，但这有个大雷，一旦遇到弹簧、轨道这种反复震荡的系统，算法会给环境不断注入虚假能量，最后物体就像疯了一样螺旋向外飞出，根本没法控制。

为了修正这个，有人可能会想到 **四阶龙格 - 库塔法 (Runge-Kutta 4, RK4)**，这玩意儿精度高还稳定，不会乱跑，但它太吃算力了，每个步骤得算四次导数，放在实时渲染的游戏里容易卡顿。还有一种 **隐式方法 (Implicit methods)**，虽然稳住了不发散，但有个副作用是会消耗能量，导致东西慢慢停摆，也不符合真实物理。至于 **韦勒特积分 (Verlet integration)**，虽然便宜又稳，但它主要是靠位置反推速度，碰到那种需要瞬间改变速度的碰撞冲量时，处理起来比较麻烦，还得额外改代码。

最后给出的最优解是 **辛欧拉法 (Symplectic Euler)**，有时候也叫半隐式欧拉。这招的核心逻辑就是：先用加速度算出新速度，再用新速度去算出新位置。这么一来，既保住了速度的准确度，方便处理碰撞检测，又不会因为累积误差而丢失能量。虽然精度不如 RK4，但在绝大多数游戏物理场景下，它足够稳定且省资源，绝对是物理引擎优化的首选方案。

## Physics for Game Programmers: Soft Constraints
- **Speaker:** Erin Catto, Erwin Coumans, Squirrel Eiserloh, Glenn Fiedler, Takahiro Harada, Gino van den Bergen, Kees van Kooten, Jim Van Verth (Blizzard Entertainment, Sony SCEA US R&D, TrueThought, Sony Santa Monica, AMD, DTECTA, Virtual Proteins, Insomniac Games)

- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1014283
- **Custom ID:** 1014283

### Overview


### Content Summary
[TLDR]
告别传统弹簧带来的数值爆炸与玄学调参，利用软约束技术实现稳定且直观的物理效果调控。

[Background]
演讲者 Erin Catto 曾负责《古墓丽影》及《暗黑破坏神 3》物理引擎开发。针对传统弹簧易导致模拟崩溃、调试全靠蒙的痛点，他分享了如何通过“软约束”技术，在保证数值稳定的前提下，让物理效果更易于设计与维护，适合对物理系统头秃的同学阅读。

[Recaps]
老哥们在做物理模拟时，最常遇到的坑就是弹簧系统。以前咱们习惯直接用简谐振荡器 (Harmonic Oscillator) 来建模，但这玩意儿太敏感。特别是用显式欧拉积分法 (Explicit Euler Integrator) 计算时，稍微参数不对，数值不稳定性立马爆发，直接把模拟推到外太空去。就算换成半隐式欧拉积分法 (Semi-implicit Euler Integrator) 这种主流方案，一旦弹簧刚度调得太高，照样容易崩，而且调参全靠蒙，因为刚体 (Rigid Body) 的质量往往在运行时才确定。

这时候就得请出主角——软约束 (Soft Constraint)。Erin Catto 把这玩意儿戏称为“布达哈弹簧”。它本质上不是施加力的弹簧，而是修改后的刚体约束方程，通过加入两个魔法参数 beta 和 gamma，实现了类似弹簧的效果却无比稳定。这其实解开了 Open Dynamics Engine 里的谜团：beta 对应的是 ERP (Error Reduction Parameter)，gamma 则是 CFM (Constraint Force Mixing)。利用这些公式，我们能保证在任何时间步长下都稳如泰山，彻底告别爆表风险。

最后的大招是引入有效质量 (Effective Mass) 概念。别再让设计师瞎填刚度 k 和阻尼 c 这种反人类的单位了。我们只需要让他们设定期望的频率和阻尼状态，引擎会自动算出对应的软约束参数。这就好比给设计师提供了个直观的遥控器，前端控制体验好，后端计算还稳定。总结来说，这就是用数学上的隐式稳定性换取人工操作的便捷性，绝对是物理程序员的福音。

### Content Summary
[TLDR]
Maya 2011 底层全面移植 Qt 框架，给美术工具和脚本开发者提供了类似搭积木般的高效界面定制方案。

[Background]
咱们做 Maya 插件或脚本的都知道，以前界面丑且难改是通病，尤其是跨平台各种坑。这次 Autodesk 直接把底层的 UI 引擎换成了行业标准，专门跟搞开发的兄弟们聊聊怎么少写代码也能搞定高大上的工具界面，适合刚入门的工具开发者以及想要提升效率的老手阅读。

[Recaps]
首先得知道，从 Maya 2011 版本开始，它的底层界面系统彻底换成了 Qt 应用框架 (Qt Application Framework)。这玩意儿最大的好处就是跨平台兼容性极强，还能做出高性能的程序，让咱们把精力花在创新功能上，而不是去死磕那些重复造轮子的基础代码。对于咱们普通玩家来说，这意味着以后做出来的小工具能更紧凑、更灵活，不像以前那样受限于老旧的 UI 架构，真正实现自定义操作界面。

具体咋玩呢？演讲里主要给了四条路。最简单的是利用 Qt Designer 拖拽设计出对话框和布局，然后调用新的 `loadUI` 命令加载到 Maya 环境里，就像拼乐高一样简单。如果你更喜欢硬核一点，可以直接通过 Maya API 里的 MQtUtil 类来操作控件指针，或者直接套用 PyQt (Python Qt Bindings) 这个 Python 与 Qt 的绑定库，毕竟你本来就在用 Python，学习成本几乎为零。不管走哪条线，核心都是为了让你能随心所欲地定义窗口和控制按钮，甚至能把原本只能靠 MEL (MAYA 嵌入式语言) 硬写的东西，变成可视化的动态属性。

最后得特别提个醒，安全第一条。虽然 Qt 功能强大，但官方警告说千万别闲着没事去修改 Maya 自带的原生界面元素，容易引发崩溃或不稳定。建议的做法是新建自己的浮动窗口来进行控制。另外，想编译自己做的插件，别指望依赖 Visual Studio，直接用官方给的 Makefile.qt 文件生成就行。总之，这套更新就是为了让大家做内部工具时更方便，不用为了一个按钮布局熬夜调试，算是给开发圈送了一波福利。

## Mega Meshes - Modeling, Rendering and Lighting a World Made of 100 Billion Polygons
- **Speaker:** Michal Iwanicki, Ben Sugden (Lionhead Studios, Lionhead Studios)
- **Duration:** 60 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1014349
- **Slide Page:** https://www.gdcvault.com/play/1014350
- **Custom ID:** 1014349

### Overview


### Content Summary
[TLDR]
依靠分层雕刻和虚拟流式传输，配合球谐光照，让老硬件也能跑出细腻的手绘大世界。

[Background]
线头工作室在做《Milo and Kate》时，被要求既要手绘雕塑感又要写实光影，还得卡在旧主机性能极限内，不得不自己造轮子来解决美术和性能之间的矛盾。

[Recaps]
传统的建模流程是把模型分两步走：先在软件里搭骨架，再跑去画图板画皮肤，这导致模型看起来像贴了图的三角形盒子，边缘生硬。他们不想这样，决定直接把雕刻工具用在场景制作上，但常规软件撑不住几十亿的三角面。于是开发了 Mega Mesh 工具，把大场景拆成小块集群，用增量层 (Delta Layer) 来管理细节。这意味着艺术家可以直接在三维空间里画细节，而不需要去烦人的 UV 展开，而且修改底层形状时，高层的细节会自动跟随变化，不用重做一遍。

纹理数据量太大是另一个头疼事，存不下也读不进。他们参考了 Sean Barrett 的方案，搞了一套虚拟纹理 (Virtual Texture) 系统，就像操作系统的虚拟内存一样。把一张巨大的贴图切成千百个小方块，玩家看哪块就加载哪块，避免内存爆炸。为了省内存带宽，普通的 DXT 压缩格式效果不好，他们就自研了 PTC 编码器 (PTC Codec)，还把颜色通道做了特殊处理，最终把原本几 GB 的数据压到了能放进主机内存的大小，还保证了画质不崩。

光照方面为了追求皮克斯电影那种柔和质感，常规的漫反射显然不够，他们需要实时的全局光照 (Global Illumination)。方案核心是用球谐函数 (Spherical Harmonics) 来描述光的传播方向。预计算阶段把场景里的光源和物体关系算好存在查表里，运行时只需要把直接光照的结果投射进去叠加一下就行。这让灯光能随时间动态变化，哪怕是移动灯具或者改变材质颜色，画面依然能保持正确的阴影和反光，不需要死板的静态烘焙。

- **Duration:** 53 分钟

### Overview


### Content Summary
[TLDR]
索尼圣莫尼卡揭秘《战神》相机系统，核心是用分层混合与优先分框算法实现电影级流畅运镜。

[Background]
这篇演讲是老将 Phil 的迭代版，讲的是开放动作游戏里镜头怎么同时兼顾 Cinematics 和 Gameplay。他们放弃笨重的碰撞检测，改用数据驱动，特别适合想做镜头系统的同行避坑参考。

[Recaps]
整个相机架构分四大块：选择 (Selection)、混合 (Blending)、动态 (Dynamics) 和目标 (Targeting)。系统会从一堆候选相机里按优先级过滤，再通过混合树 (Blend Tree) 把旧镜头淡出、新镜头淡入。为了镜头转动不生硬，存储朝向时用了欧拉角 (Euler Angles) 而非复数，避免了奇怪的翻滚效果。遇到万向节锁 (Gimbal Lock) 这种尴尬情况，他们干脆把航向角转成 2D 向量计算，防止视角突然翻转。

镜头生成分三种主力。动画相机直接读 Keyframe，用于过场。动态相机负责大世界探索，靠“推杆” (Dolly) 和“摇臂” (Boom) 模型配合约束求解，确保角色始终待在安全框 (Safe Zone) 内。战斗相机则用同步关节 (Sync Joints) 绑定敌我，虽然不做环境碰撞检测，但靠覆盖场景相机的视场角 (FOV) 实现特写。

最硬核的改进是多目标焦点。早期加权平均法导致单人对战视野太远，后来上了优先分框算法。它能保证高优先级目标永远在画幅内，再兼顾其他人，直接在球面空间算范围。针对怪物绕后或瞬移导致的画面抖动，系统会把逻辑焦点强粘在镜头前平面上，彻底根治了闪烁。这套思路后来甚至延伸到了控制景深 (Depth of Field)。

## Physics for Game Programmers: Contacts (PDF Version)
- **Speaker:** Erin Catto, Erwin Coumans, Squirrel Eiserloh, Glenn Fiedler, Takahiro Harada, Gino van den Bergen, Kees van Kooten, Jim Van Verth (Blizzard Entertainment, Sony SCEA US R&D, TrueThought, Sony Santa Monica, AMD, DTECTA, Virtual Proteins, Insomniac Games)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1014281
- **Custom ID:** 1014281

### Overview


### Content Summary
[TLDR]
物理模拟别死磕数学完美，迭代求解接触约束，稳住别穿模才是核心。

[Background]
做物理的总被穿模和抖动折磨，这篇演讲就是给程序员的避坑指南。针对复杂的接触求解和碰撞检测痛点，分享如何用工程手段搞定数值稳定性，适合刚入坑物理编程的老哥。

[Recaps]
兄弟们，做物理最烦的就是接触求解。简单来说，物体接触时的力分两拨：垂直面的正压力和切向的摩擦力。摩擦力是有上限的，叫“摩擦锥 (Friction Cone)"，超过这个范围就会打滑。求解的时候别整什么复杂矩阵，直接用“高斯 - 赛德尔迭代法 (Gauss-Seidel Method)"，虽然偶尔不准，但算得快还总能给个解，特别适合游戏这种实时场景。

遇到物体穿插（Jitter）怎么办？千万别一帧就把穿透修回来，那样物体会像弹簧一样抖。这里有个大招叫“投影高斯 - 赛德尔 (Projected Gauss-Seidel)"，把算出来的力掐在摩擦锥范围内。修正穿透建议用“后稳定化 (Post-Stabilization)”，相当于每帧给个零头的“幽灵动量”去推回原位，比那种加弹簧的“邦加特稳定化 (Baumgarte Stabilization)"要省心得多，不会导致数值爆炸。

碰撞检测这块，核心思想是把找两物体的距离变成找个点到原点的距离，这就引入了“构型空间 (Configuration Space)"的概念。工具包里有大神推荐的"GJK 算法 (GJK Algorithm)"，不仅能算最近点，配合射线还能做“连续碰撞检测 (Continuous Collision Detection)"，防止子弹穿墙。要是碰到网格模型边缘太糙的问题，就用插值法平滑下法线，效果跟光照处理类似，整体体验丝滑不少。

### Overview


### Content Summary
[TLDR]
别只盯着标准 Lua，用 Havok Script 替换虚拟机能让脚本更稳更快，Debug 和 Profiling 直接起飞。

[Background]
很多开发者爱用 Lua 做脚本，但它跑起来性能瓶颈难找，内存泄漏像黑盒。这演讲教大伙怎么给 Lua 换个“高性能引擎”，让修改逻辑不卡顿，还能轻松定位代码问题。

[Recaps]
各位老哥都知道，现在的游戏项目都喜欢用 Lua 这种脚本 (Scripting) 来做逻辑控制，为啥？因为迭代快啊！不用每次都重新编译整个游戏，部署的时候还能在线修脚本，这对策划特别友好，门槛低了以后依赖也少了。它属于一种解释型语言 (Interpreted Language)，不直接变机器码，而是靠虚拟机 (Virtual Machine) 在真机上跑，所以灵活性极高，不管是做 DLC 还是开放给用户造 mod，只要开了沙箱 (Sandboxing) 模式，安全性完全不用担心。

先说痛点，老版《MK 对战 DC》用的 DLMalloc 其实是个老古董，没怎么考虑多核场景。它有个**全局锁 (Global Lock)**，只要有一个大操作在进行，比如 realloc 复制数据，其他线程想申请小内存也得排队干等，导致一帧画面里光等内存分配就占了 16%，这谁受得了？再加上之前的游戏侧内存管理器用的是**固定后备存储 (Fixed Backstore)** 机制，内存碎片多了直接导致大块分配失败，太浪费资源。

具体哪些活儿适合 `CPU (Central Processing Unit)` 呢？像 `HDR (High Dynamic Range)` 这种后处理流程，还有静态几何体的阴影图生成，以及 `粒子系统 (Particle System)` 和 `UI (User Interface)` 界面。因为这些东西对显卡专用的光栅化或纹理过滤器需求不高，反而更需要 `CPU (Central Processing Unit)` 灵活的数据处理和分支判断能力。实验数据显示，`CPU (Central Processing Unit)` 跑粒子甚至能到一毫秒十万个，相当惊人。当然，`API (Application Programming Interface)` 本身不是为这种混合架构设计的，数据拷贝是个大坑，不过好在硬件融合后有望改善。

要想玩转这套方案，还得有点技术含量。首先是利用 `Tasking (任务)` 系统来管理线程依赖，避免锁开销；其次是 `Tiling (分块)` 策略，把屏幕切分成小块分配给不同核心并行计算；最后是榨干 `SIMD (单指令多数据流)` 潜力，用上 `SSE (Streaming SIMD Extensions)` 和 `AVX (Advanced Vector Extensions)` 指令集批量处理像素数据。虽然目前主要挑战是数据传输延迟，但这个思路绝对是未来的突破口，鼓励大家别墨守成规，亲自上手试试把渲染任务卸载到 `CPU (Central Processing Unit)` 上。

### Content Summary

[Background]
InView 做虚拟社交起家，用户多了 HTTP 长轮询扛不住，现有中间件太笨重或没法横向扩展。为支撑实时互动与海量在线，必须搞一套轻量化、内存优先的实时通讯方案，解决传统架构的性能瓶颈。

[Recaps]
兄弟们都懂，以前做社交网页主要靠 HTTP 长轮询 (HTTP Long Polling)，也就是那种不断请求拿数据的蠢办法。虽然能用，但到了一定规模服务器就废了，延迟也高。我们当时的目标是要做到端到端 100 毫秒内，还得能抗住几十倍的用户增长。市面上那些企业级的排队软件，要么太看重数据持久化，浪费资源，要么根本不支持动态扩缩容，像 XMPP 这种协议跨服务器扩展也是坑爹。没办法，只能自己造轮子，核心选型定在了 Erlang 语言 (Erlang) 上。这货当年是爱立信搞电话交换机的，天生就是为了不死机和高并发设计的，简直是为我们这种场景量身定做。

架构设计上，我们把系统拆成了网关 (Gateway) 和 队列服务器 (Queue Server)。用户先连网关，网关只管握手验证。具体的聊天和状态广播交给后面的队列处理。为了解决多台机器之间的流量分配问题，我们上了一套一致性哈希 (Consistent Hashing)。简单来说就是把所有队列的 ID 算成哈希值，根据这个值找对应的机器。机器多了，只需要把一部分哈希桶搬家过去，不用重启服务就能扩容，非常丝滑。队列内部还分了挂载点 (Mount)，比如一个是纯聊天文本流，另一个是排行榜状态流，互不干扰，想改规则随时改。

技术细节上，Erlang 最大的好处是不用像 Java 那样到处抢锁。它用的是进程模型 (Process Model)，每个任务是个独立的进程，通过发送消息交流，内存不共享，所以完全不用担心数据竞态条件 (Race Condition)。而且它的垃圾回收机制 (Garbage Collection) 很聪明，进程挂了就重启进程，不影响别人。运维这块我们也搞得很灵活，支持连续部署 (Continuous Deployment)，因为 Erlang 原生热升级太慢，我们模拟了 Apache 的优雅重载，新版本慢慢顶上，老用户无感知切换。至于网络层，为了让防火墙和代理别瞎管，我们用 443 端口跑二进制协议缓冲区 (Protocol Buffers)，伪装成 HTTPS 流量，成功率极高。就算某个节点宕机，客户端重连一下，丢一点缓存数据而已，整体系统稳如老狗，堪称游戏后端架构的实战范本。

[Background]
Volition 团队开发《红色派系：末日》面临全场景可破坏的难题，传统静态光照失效。此分享旨在讲解如何构建既能应对高频动态变化，又能平衡画质与性能的全新动态光照架构。

[Recaps]
首先，这款游戏的设定非常硬核，几乎万物皆可被摧毁和修复。这意味着传统的预计算光照贴图彻底罢工，必须采用全动态的光照系统。为了应对火星地表及地下各种复杂环境，工程师们在成熟的延迟光照 (Deferred Lighting) 基础之上，开发了一套名为推测光照 (Inferred Lighting) 的方案。整个流程分为三个关键步骤：首先是几何通道 (Geometry Pass)，把可见物体的深度、法线等信息打包进 G 缓冲区 (G-buffers)；接着是光照通道 (Lighting Pass)，计算每盏灯的影响并存入 L 缓冲区 (L-buffer)；最后是材质通道 (Material Pass)，将这些数据与物体贴图混合输出。为了节省显存并提升速度，团队甚至把多种数据强行塞进同一个 32 位纹理中，实测帧率提升了近两成。

核心亮点在于如何解决低分辨率渲染带来的画面瑕疵。传统做法是把光影图放大，结果边缘容易漏光或模糊。这里作者祭出了杀手锏“不连续敏感过滤” (Discontinuity Sensitive Filtering, DSF)。简单来说，就是给每个像素打上“身份证”标签，记录它是哪个物体、属于哪个材质部分。当需要还原高分辨率画面时，如果周围采样点的标签和当前像素对不上，算法就会自动忽略这些错误数据。这不仅解决了低分率光照的上采样伪影问题，还顺带完美支持了多重采样抗锯齿 (MSAA)，不需要额外写代码就能兼容各种反锯齿效果。

当然，这套系统也不是银弹，存在不少局限性。最头疼的是半透明物体 (Translucent Objects) 的光照处理，系统虽然允许最多四层重叠，但会牺牲有效分辨率，且无法支持大量粒子特效，所以游戏里粒子都要单独计算。至于头发渲染，因为现有光照模型会导致发丝像塑料头盔，所以《红色派系：末日》的主角被迫成了光头。相比之下，同厂的新作《黑道圣徒 3》针对 DSF 做了不同配置，允许了更复杂的头发表现。总的来说，这是一套高度灵活的方案，开发者可以根据机器性能动态调整光照分辨率和是否开启 DSF，在画质和流畅度之间随时找平衡。

David Aldridge 上来就抛干货，核心架构是“半可靠 (Semi-reliable) 传输”。传统的全可靠模型会导致延迟爆炸，没法承载大规模作战。他们将网络通信视为一种“复制 (Replication)"过程，而非绝对同步。数据主要分三类：负责最终一致性的状态数据 (State Data)，负责描述因果的事件 (Events)，以及用于预判的控制数据 (Control Data)。只要保证最终状态能对上，中间过程丢了也不影响大局，从而避免了积压“延迟债务 (Latency Debt)"。

关键是优先级 (Priority) 调度。网络资源不能平均分配，必须像切蛋糕一样按需分配。离你越近、对你威胁越大的物体，网络更新频率越高。哪怕是掉在地上的枪，因为关注度低，更新频率也能压得很低。这套逻辑解决了所谓的 N 平方级带宽难题，确保关键时刻不掉链子。

遇到延迟别硬抗，该改玩法就改。比如护甲锁定的激活时机，为了抵消服务器确认的延时，直接把护盾生效帧提前，玩家感知不到差异，但逻辑世界依然同步。又如刺杀动作，进动画前物理引擎强制拉回主机位置，视觉层面再做个平滑过渡。此外，客户端侧的“预测 (Prediction)"技术也至关重要，比如扔手雷时先本地播放动画，等服务器确认后再修正结果。这种策略证明了，有时候改变游戏性设计是隐藏网络延迟的最佳手段。

最后强调工具和迭代的重要性。光有理论没用，得实测。他们开发了深度分析工具，甚至能让玩家在游戏里按按钮标记“卡顿”，将主观感受转化为客观数据。很多带宽节省其实是通过改玩法实现的，比如简化布娃娃系统的物理模拟。记住，不要盲目优化代码，先问设计师能不能动规则，这才是最高效的优化路径。

拒绝手动调分辨率！推荐集成动态分辨率与时间抗锯齿，自动平衡画质与性能，让游戏在任何硬件上流畅运行。

[Background]
Intel 工程师针对 PC 硬件差异大、UI 需高清的问题，提出一套动态切换渲染方案，旨在解决帧数卡顿与画质损耗的矛盾，适合图形程序及引擎开发者学习。

[Recaps]
这位来自 Intel 的 Doug Binks 老哥开门见山，直接劝大家别让用户进游戏还要手动选分辨率了。现在硬件太乱，有的电脑能跑 4K，有的只能凑合 720P。核心思路很直白：把游戏里的 3D 场景交给**视口大小 (Viewport Size)**动态控制，性能不够就降级渲染，性能好就拉满，但把操作界面（UI）始终锁在屏幕原生分辨率上，保证字清图锐，不会糊眼。

技术上主要靠改变**渲染目标 (Render Target)**的大小来做**动态分辨率 (Dynamic Resolution)**。比如降分辨率后放大，或者升分辨率后缩小。演示里试了几个滤镜，像**双线性过滤 (Bilinear Filter)**虽快但边缘虚，**双立方滤波 (Bicubic Filtering)**效果好但耗资源。最值得玩味的是利用**运动模糊 (Motion Blur)**，人眼在快速转视角时对细节不敏感，这时候大幅降低分辨率几乎看不出差别，既保住了帧数还省了笔记本电量。

重头戏是强烈推荐的**时间抗锯齿 (Temporal Anti-Aliasing)**，简称 TAA。这招通过奇偶帧微偏移半像素，叠加上下两帧信息，就算你只渲染一半像素，也能达到接近全高清的效果。哪怕是用核显的笔记本，这招也能帮你做续航和画质的灵活取舍。要是硬件够猛，还可以搞**超采样 (Supersampling)**，直接把渲染比例调得比显示器还高，抗锯齿效果吊打普通 FSX。

最后给点实操建议，别光测 CPU 帧率，要用 GPU 事件计时器看真实渲染耗时；注意贴图的边界处理，防止漏色带；阴影图和**Level of Detail (LOD)**也要跟着分辨率动态变。特别是**Z 缓冲区 (Z Buffer)**的清除要规范，支持分层 Z 测试。总之，除非你是极端强迫症，否则这套方案能让你的游戏在任何机器上都能跑得更稳更流畅。

咱们玩游戏的都知道，传统游戏里靠“混合权重 (Blend Weights)"来控制动画其实是玄学。改数字你不知道角色会咋动，特别是在“混合树 (Blend Trees)"里，经常会出现奇怪的卡顿或者动作不连贯。Crytek 工程师 Ivo 就说了，这玩意儿在精准导航和瞄准上简直是噩梦，尤其是在需要精确控制角色朝向和速度的时候。

技术核心在于网格简化 (Mesh Simplification)。直接甩给 DX 工具效果不行，他们先搞了个体素化 (Voxelization)，从六个视角拍深度图再滤波，把多余内部面和杂乱细分全清理干净，让拓扑更规矩。材质方面不依赖源码，而是渲染特定光照把漫反射和反光特性“吸”进贴图，合并成单材质，发布版还能把采集代码剔除，实现零性能损耗。

除了静态物件，动态角色的骨骼权重也被“瘦身”，每点只保一个主骨骼，减轻顶点着色器负担。环境物体（如树石）直接烘焙光照信息，同批批量绘制，效率狂飙 50 到 100 倍。虽然透明或极薄几何体会翻车，但整体让动态物体帧率翻倍，内存反而更少，最后建议未来加美术自定义接口来兜底，毕竟机器算的总有不如人意的地方。

## Approximating Translucency for a Fast, Cheap and Convincing Subsurface Scattering Look
- **Speaker:** Colin Barre-Brisebois (Electronic Arts Montreal)
- **Duration:** 30 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1014536
- **Slide Page:** 
- **Custom ID:** 1014536

### Overview


### Content Summary
[TLDR]
EA 利用反向环境光遮蔽生成厚度贴图，以极低算力消耗实现了视觉上逼真的实时透光效果。

[Background]
游戏界一直在权衡画质与性能，真正的物理级透光算起来太烧显卡了。这帮 EA 老哥分享了一套折中方案，适合想在 Frostbite 引擎上快速提升画面质感又怕掉帧的开发团队。

[Recaps]
传统的**双向反射分布函数 (BRDF)**只能表现物体表面的反光，无法模拟光进入物体内部的效果。想要呈现**次表面散射 (Subsurface Scattering)**这种真实的**透光性 (Translucency)**，通常得用计算量巨大的**双向扫描反射分布函数 (BSSRDF)**。这对游戏引擎来说是灾难，现有的方案要么不够快，要么只能处理薄平面。这次演讲的核心就是找条中间路：既要像《Crysis》处理树叶那样轻量，又要能处理类似大理石雕像那样的厚体积物体。

解决思路非常巧妙，避开了昂贵的光线跟踪。核心在于用“偷梁换柱”的办法算出物体的局部厚度。常规方法依赖动态深度图，他们直接利用离线烘焙好的**环境光遮蔽 (Ambient Occlusion)**，把模型法线翻转后重新计算一次 AO。这个预处理过程生成的贴图其实就代表了厚度分布，甚至还能存储颜色值来模拟光穿过后变色的效果。这样既不用在线搞重头戏，又能让光线在穿过物体时表现出厚薄差异带来的自然衰减和偏移。

最后说说落地细节，这套算法特别抠门，指令数极低，连旧时代的 SM 2.0 硬件都能跑。利用**延迟渲染 (Deferred Shading)**管线，把额外的透光参数塞进**G 缓冲数据 (G-buffer)**的空余通道里，甚至还能靠材质 ID 做筛选优化。虽然对凹面或非变形物体支持有限，但作为视觉欺骗手段，它能在保证性能的前提下让场景瞬间立体起来，绝对是美术与技术结合的优秀案例。

- **Speaker:** Dmitry Andreev (LucasArts)
- **Duration:** 22 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1014549

### Overview


### Content Summary
[TLDR]
针对主机平台，通过检测边缘方向并针对性模糊，以低成本实现稳定的画面抗锯齿效果。

[Background]
卢卡斯艺术工程师分享在《Force Unleashed 2》项目中遇到的困境：传统多采样抗锯齿太贵且不支持动态分辨率调整，形态学抗锯齿又容易闪烁。本文适合想了解如何在主机低配下搞定稳定抗锯齿的开发者看。

[Recaps]
咱们都知道，现在的游戏为了画面好看，特效堆得猛，传统的**多采样抗锯齿 (Multi-Sample Anti-Aliasing)**虽然稳，但在主机上开销太大，特别是配合了动态分辨率调整 (Dynamic Resolution Adjustment) 后，老办法根本跑不动。之前试过 Intel 搞的**形态学抗锯齿 (Morphological Anti-Aliasing)**，虽然静态看着还行，但一动起来就有鬼影闪烁，而且 CPU 占用太高，没法用。于是团队就在纠结怎么解决锯齿，发现核心问题在于动态场景下很难兼顾性能和质量，必须找个新路子。

这招到底是怎么玩的？其实核心就一句话：顺着边缘的方向把它抹平，而不是随便乱糊。具体实现上，先别急着写代码，作者说是拿 Photoshop 试出了灵感。系统会用高通滤波器把长边和短边分开，短边直接按标准处理，长边再加大模糊半径，避免画面糊成一团。最关键的是颜色渗漏，解决思路很简单，就是不让模糊后的颜色乱跑，而是从附近找一个亮度相近的原生像素来替换，这样既保住了边缘柔和，又不会串色，效果非常惊艳。

真刀真枪上机子的时候，才是真的见功夫。Xbox 360 那边做了不少奇技淫巧，比如翻转深度缓冲 (Depth Buffer) 测试逻辑，复用内存，减少显存读写。PS3 更变态，直接把算法塞进五个 SPU 里跑，还得手动向量化、流水线平衡，甚至能不用浮点运算就用字节操作省时间。最终这套方案每帧只要花大概 2 毫秒，比老方法省了一半力气，而且不管分辨率怎么跳变，画面都特别稳，艺术家都觉得更有电影感，这就是典型的“用最简单的算法拉最满的格”。

## Adaptive Order Independent Transparency: A Fast and Practical Approach to Rendering Transparent Geometry
- **Speaker:** Marco Salvi (Intel Corporation)
- **Duration:** 63 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1014547
- **Slide Page:** 
- **Custom ID:** 1014547

### Overview


### Content Summary
[TLDR]
英特尔提出一种基于近似可见性函数的实时 OIT 方案，不再依赖昂贵的像素排序，实现了画质与性能的双赢。

[Background]
过去游戏里的透明物体常被排序问题坑爹，老式 OIT 算法太卡还占内存。这次分享的是英特尔新搞出的招数，让透明渲染既稳又快，再也不用靠 hacks 凑合了。

[Recaps]
讲者开篇就吐槽，传统的 Alpha 混合 (Alpha Blending) 在处理重叠透明物体时容易穿帮，比如树叶该在前却在后。而以往主流的 A-buffer (A 缓冲区) 算法虽然理论上全能，但因为需要每像素对碎片排序，导致性能极不稳定，换一下镜头角度帧率就崩，显存也容易爆，开发者根本没法在商业项目里放心用。这也正是大家急需更好的顺序无关透明度 (Order Independent Transparency / OIT) 方案的原因。

所以核心解法是不再纠结严格的深度排序，转而构建每个像素的可见性函数 (Visibility Function)。简单说，就是动态记录光线穿过一层层透明物体时被吸收的程度（即透射率 Transmittance）。为了省显存带宽，他们没把曲线记死，而是用固定大小的数组存关键点。如果数组满了，算法会自动删掉对整体视觉形状影响最小的节点进行压缩，这样既保留了数学逻辑，又极大降低了开销，相当于边渲染边自动无损压缩。

实测表现非常硬气，相比之前 AMD 在 DX11 (DirectX 11) 架构下的实现，速度提升了不止一倍，而且无论怎么看场景，帧率都稳如老狗。虽然受限于 DX11 API 没法完全原地更新数据，需要分两遍渲染（先建列表再合成），但在前向渲染 (Forward Rendering) 模式下集成很容易。遇到显存不够的情况，可以采用分块渲染 (Tiling) 的策略来解决。对于绝大多数场景，用 8 到 16 个压缩节点就能达到肉眼难辨的效果，即便有轻微的闪烁也不会像传统方法那样明显，是目前最实用的 OIT 方案之一。
