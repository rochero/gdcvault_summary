## Ray Tracing in Snowdrop: Scene Representation and Custom BVH
- **Speaker:** Oleksandr Koshlo (Massive Entertainment - A Ubisoft Studio)
- **Duration:** 47 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034277
- **Slide Page:** https://www.gdcvault.com/play/1034404
- **Custom ID:** 1034277

### Overview
How do you achieve high fidelity lighting with ray tracing, while maintaining high performance target in an expansive world such as the world of Avatar: Frontiers of Pandora? It requires a good implementation of ray tracing pipeline at multiple levels. This session describes BVH and material management part. The talk shows in detail two different acceleration structure implementations: a custom one used on consoles, and a DXR-based one for PC platforms. It highlights advantages and tradeoffs available with a custom approach, and tackles both common and unique challenges of each implementation, and a range of possible optimizations. The second part talks about "average" material representation, and how Snowdrop handles calculating the average for artist-authored materials, often dependent on runtime inputs.

### Content Summary
[TLDR]
依靠自定义 BVH 架构与材质简化策略，在 Snowdrop 引擎中实现了兼顾性能与画质的硬件中立光追方案。

[Background]
面对光追性能开销大且部分主机不支持的问题，Massive 工作室分享如何通过优化场景表示和加速结构，在《阿凡达》这种大场景下落地光追技术，适合想啃硬骨的渲染开发者阅读。

[Recaps]
这次讲的是光线追踪 (Ray Tracing) 在 Snowdrop 引擎里的硬仗。团队没盲目迷信纯硬件支持，而是搞了个混合方案，结合屏幕空间 (Screen Space) 与世界空间的补漏。最核心的是针对主机做了定制版边界体积层次结构 (Bounding Volume Hierarchy)，俗称 BVH，因为标准 DXR API 太占内存。他们用 CPU 实时构建顶盒，底盒则离线烘焙，动态物体再特殊处理。有个叫多根优化 (Multi-root) 的技巧特别实用，把物体拆分得细一点进树，减少重叠框，实测能省 5% 到 10% 的性能。

遍历过程也很有意思，光追路径因为射线相干性高，用了共享栈代替普通堆栈，能大幅降低局部数据存储器 (Local Data Store/LDS) 压力。材质这边更是脑洞大开，为了解决植被透明度的性能坑，干脆放弃了昂贵的 Alpha 测试 (Alpha Testing)，改用蓝噪点抖动 (Blue Noise Dithering) 来模拟透光，效果看着跟真的一样。还有那个平均材质 (Average Material) 机制，配合元数据着色器 (Metadata Shader)，把复杂的 Shader 图转成简单的数值运算，避免每次光追都重新算一遍材质，虽然牺牲了点精度，但在间接光照里根本看不出来。

最后他们还处理了一些坑爹的小细节，比如发光小物体如果只算屏幕空间会乱套，就得额外判断一下光追世界里有没有对应物体。总的来说就是工程化思维至上，该偷懒的地方偷，该硬核的地方硬，这套经验对于想在次世代主机上塞入光追的团队绝对是本开源教科书，毕竟现在的光追不仅要画质好，还得跑得动才是王道。

## Scaling Git Workflows for Game Development
- **Speaker:** Vikram Saran (Independent)
- **Duration:** 59 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034365
- **Slide Page:** https://www.gdcvault.com/play/1034326
- **Custom ID:** 1034365

### Overview
Game development studios often face a dilemma when choosing version control systemsspecific requirements like exclusive file locking can limit options, while common solutions remain financially out of reach for up-and-coming studios. Surprisingly, even with widely used solutions, many projects struggle to adhere to the 'not rocket science' rule of software engineering: maintaining a code repository that consistently passes all tests. Join Vikram in this session as he delves into the challenges of version control in game development and explores how modern git tooling, coupled with strategic workflow adjustments, can pave the way for a cost-effective solution. Discover practical insights to start utilising modern DevOps practices with your projects.

### Content Summary
[TLDR]
小团队别盲目跟风买贵软件，掌握 Git 的高级用法配合自动化流程，能用小成本搞定接近大厂的版本管理体验。

[Background]
小工作室发展到三四十人时，传统的手工协作容易乱套。想达到大厂那种稳定高效的流水线（CI/CD）又不想付 Perforce 的天价授权费，这篇实战分享提供了高性价比的解决方案。

[Recaps]
很多中小游戏工作室刚起步还行，人一多就乱套，特别是多人编辑资产容易互相覆盖，或者发布全靠手动点按钮，版本控制（Version Control）简直就是灾难现场。演讲者虚构了一个叫“小乌龟”的团队，他们面临典型的扩张瓶颈：分支管理混乱、持续集成（Continuous Integration）不健全。想要解决这个问题，核心思路就是不要为了省钱就凑合，而是要用对的 Git 配置替代昂贵的商业方案，把流程标准化。

技术上最关键的几个点是先配好 Git LFS (Large File Storage)。别以为只有大公司才用得上这个，它能把大文件存到服务器上，本地只留指针，不然仓库几 T 大了谁受得了？更重要的是开启 Git File Locking (文件锁定)。以前大家习惯自由合并，现在针对美术资源要像大厂那样加锁，谁占用了别人就不能动。但这有个副作用，锁住了就不能随意合并，所以必须转用变基（Rebase）的工作流，强制大家在合入前先同步最新代码，保证历史干净，不会炸链。

工作流程上要彻底放弃旧式的复杂分支模型，全面采用主干开发（Trunk Based Development）。别再搞那种长达数周的功能分支了，所有人都切短分支，一天一个任务那种。提交上去后，如果有测试通过，直接用合并机器人（Merge Bot）自动合进主线，没人需要在那儿傻等。对于特别巨大的改动，比如新功能，别靠分支隔离，直接甩上功能开关（Feature Flags），代码全在主线上，只是默认关闭，方便随时灰度发布或回滚。这样能确保主干永远是可运行的版本，极大降低线上故障率。

最后是落地执行的事，光有工具没用，还得有人教。推行新流程初期肯定有阻力，美术策划可能觉得麻烦，这时候就得准备详细的可视化文档，甚至让人人都当技术支持，快速响应求助。演讲者算了一笔账，对于几十人的团队，自己搭这套 Git 自动化体系的成本和人工成本，往往比给大厂买 Perforce 授权费还便宜。虽然还有诸如稀疏检出（Sparse Checkout）等新功能没完全普及，但只要把这些基础打牢，就算没有专业运维团队，小团队也能跑出大厂级别的工程质量。

## Open World Rendering Techniques in 'Hogwarts Legacy'
- **Speaker:** Rob Hall (Avalanche Software)
- **Duration:** 59 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034600
- **Slide Page:** https://www.gdcvault.com/play/1034811
- **Custom ID:** 1034600

### Overview
Rendering a game as complex as Hogwarts Legacy required a focus on adapting the Unreal engine for an open world game. This included handling the massive scale of the Hogwarts castle and scaling rendering systems for a seamless indoor and outdoor experience. This talk will expound on the technical aspects of this work. Topics will include how to render with hundreds of shadow casting light sources, rendering multi-layered cloth at a reduced cost, and how to batch light probes, reflections, and foliage. Hogwarts Legacy also contains several other techniques that make it an immersive experience. This will involve topics like Dynamic time of day, camera exposure, seasons, and weather. Lastly, we will discuss how to render animated paintings without the typical way of rendering to a render target.

### Content Summary
[TLDR]
靠无绑定资源 (Bindless Resources) 与自动化测试，把 9 平方公里的魔法世界塞进全平台还能丝滑运行。

[Background]
《霍格沃茨之遗》是 Avalanche 首个开放世界 (Open World) RPG，刚迁移到 Unreal Engine 4.27 引擎。要在 Switch 等全平台跑满城堡与小镇的超高复杂度，画质与性能平衡是最大痛点。

[Recaps]
面对 9 平方公里的开放世界 (Open World) 加上拥有 200 间房的霍格沃茨城堡，性能优化是最大拦路虎。UE4 默认的渲染线程 (Render Threads) 瓶颈限制了每帧只能处理约 1 万个绘制调用 (Draw Calls)。他们先搞了个“能实例化就实例化”的原则，看不见的东西直接剔除，利用无绑定资源 (Bindless Resources) 绕过传统绑定上限，让 Shader 能一次性读取海量纹理和灯光数据。此外，他们还通过层级流式加载 (Level of Detail Streaming)，确保远山近树的精度切换无缝不卡顿。

光影部分更是黑科技。用了分块延迟渲染 (Tile Deferred Rendering) 处理重叠光源，大幅降低开销。最绝的是针对 48 分钟真实昼夜循环的阴影缓存方案。因为光照方向改变会失效缓存，他们锁定了短时窗口并平滑过渡，保证了日夜更替不掉帧。对于复杂的布料材质，原本要算 16 层，他们通过预烘焙改成每像素只算 1-2 层，兼顾了物理效果与性能。城堡里高塔还用了特殊的圆柱形光照体积 (Cylinder Probe Volumes) 来贴合建筑结构。

最后还得提一下工业化流程。没用自动化工具根本管不住全图性能，他们搞了个每天运行几百次的自动化测试系统 (Automation Tests)，盯着 GPU 耗时看有没有超标，最终让 95% 的测试用例达标。再加上昼夜四季的真实感、动态壁画（把 3D 压扁渲染）、体积云 (Volumetric Clouds) 这些视觉加分项，这套组合拳硬是在低配上也保住了画质，给行业打了个好样板。

## Real-Time World Editing Technology in Northlight
- **Speaker:** Sebastian Eriksson (Remedy Entertainment)
- **Duration:** 59 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034236
- **Slide Page:** https://www.gdcvault.com/play/1034300
- **Custom ID:** 1034236

### Overview
Requirements for game worlds are ever-increasing, being more realistic, more interactive, and larger than ever before. This means that there is a ton of content to be authored, but also large amounts of data to pass through pipelines and workflows to the engine runtime. Remedy has been working on a new data pipeline and technology stack for the Northlight engine that allows us to optimize entity data for authoring at edit time, and performance at runtime, while keeping near-instant iteration times for world editing workflows. The fundamental parts of this technology are OpenUSD for authoring, and Northlight's transformative live-edit pipeline that enables entity modifications to be applied to a running game process on the fly. In this presentation, Sebastian shares how we keep the editor and runtime data representations separated, how the data is transformed, and how the real-time editing between the editor and runtime works in practice.

### Content Summary
[TLDR]
Remedy 基于通用场景描述 (USD) 构建实时管线，联动编辑与运行时，改关卡无需重启，迭代效率大增。

[Background]
做完《Alan Wake 2》后，Remedy 发现迭代慢成了大坑。这次分享如何搭建新管线，让内容策划能直接进游戏里改关卡，实时生效，专治各种“改完得重起”的毛病。

[Recaps]
Remedy 这次的核心就是搞了一套实时修改管线。以前旧技术在处理大型关卡时，迭代循环太长，严重拖慢进度。他们把重心从底层运行时转到了工具链，构建了包含编辑插件、编辑器层 (Editor Layer) 和游戏运行时 (Runtime) 的新架构。这三层通过 gRPC 通信，实现了双向数据同步，彻底打破了工具与游戏的隔阂。

数据结构的设计相当硬核，采用了三套格式流转：创作端用通用场景描述 (USD)，存储端用二进制格式，运行时则转为实体组件系统 (Entity Component System)。最骚的操作是不缓存，每次加载或改动都强制重新导出。虽然看起来笨重，但这消除了维护缓存一致性的复杂度，配合依赖图 (Dependency Graph) 确保改哪里就只更新哪块数据，不会误伤其他地方。

实测效果非常硬核。单个物体修改延迟仅 40 多毫秒，复杂批量操作也能瞬间完成。他们甚至允许通过命令行或外部差异包 (Diff) 发送指令来同步状态，这意味着未来可以接 Maya 或者实现跨机协同编辑。简单来说，就是让你边玩边调，完全不需要反复保存或重启流程，真正做到了所见即所得的实时开发体验。

## Obstacle Traversal in the Organic World of Pandora
- **Speaker:** Joel Nilsson (Massive Entertainment - A Ubisoft Studio)
- **Duration:** 52 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034231
- **Slide Page:** https://www.gdcvault.com/play/1034304
- **Custom ID:** 1034231

### Overview
Stepups and mantles are an established part of the game character's repertoire, yet with increasingly complex game worlds traditional markup solutions have become increasingly cumbersome. In Avatar: Frontiers of Pandora we wanted to portray the full dense, organic beauty of Pandora while making the motion feel as flowing and unobstructed as you would expect from a Na'vi. In order to deal with these challenges we created a highly generic and (almost) markup-free system for stepups and mantling relying on a minimum of assumptions while trying to maximize freedom of movement. This talk presents the basic philosophy, concepts, and implementation of this solution. The focus is on providing a solid starting point for those just starting out with this problem and some useful tools for anyone working with it.

### Content Summary
[TLDR]
用简化的球体投射和评分机制，以极简逻辑解决复杂丛林障碍穿越，让玩家获得自信流畅的移动体验。

[Background]
《阿凡达》的丛林环境太密太乱，传统地图标记法根本扛不住。这场演讲适合想优化角色移动或处理非结构化地形的开发者，分享如何在保持开发效率的同时，模拟出真实的攀爬手感。

[Recaps]
这帮人做东西的思路很正，核心原则就是“简单方案解决复杂问题”。他们没搞一堆特例代码，而是一个系统通吃攀爬和翻越。关键点不在于动作多帅，而是让玩家从上手那一刻起就觉得自己“天生就会这招”，比起花里胡哨的动作设计，优先保证移动的连贯性，这就是障碍穿越 (Obstacle Traversal) 的终极目标。

技术上主要靠胶囊体 (Capsule) 配合球体投射 (Sphere Casts) 来干活。把复杂的 3D 地形切成分剖面分析，利用球面上不同区域对应的法线来区分哪些坡能走哪些不能。找障碍有四套方法轮流上阵：看连续采样的高度角差、检查不可走环是否被击中、故意偏移坐标猜角落、最后还有兜底的陡坡检测，基本能把各种奇葩地形都扫到。

找到障碍后还得打分决定走哪条路，会先自问三个核心问题：有没有障碍物？能不能站稳？是不是现在的最佳时机？评分项包括路径长度、切入几何体的程度、到达时的坡度平整度等。为了手感更好，系统还支持边爬边转弯，遇到坑洞能当平地过，甚至允许中途打断平滑过渡。

最后聊聊避坑指南。调试绘图 (Debug Drawing) 绝对是神技，能在跑图时实时看到轨迹和状态，修 bug 快得多。还有个教训是系统太智能也是麻烦，设计师需要用“禁行标签”拦住那些不该爬的高墙小缝，不然玩家会钻进禁区卡死。性能方面虽然开销低，但也得注意多线程处理，毕竟算得太散对缓存不友好。

## Next Level of Mobile Graphics: Ray Tracing in 'Arena Breakout' (Presented by Tencent Games)
- **Speaker:** Junhong Wang (Tencent Games)
- **Duration:** 36 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1034690
- **Slide Page:** https://www.gdcvault.com/play/1034829
- **Custom ID:** 1034690

### Overview
"Arena Breakout" is a next-gen immersive tactical FPS powered by Unreal Engine 4.26 on mobile devices.The game integrates Vulkan Ray Query-based reflection, ambient occlusion and soft shadow, all optimized to run seamlessly on the latest Android platform. In this session, Junhong Wang, Lead Mobile Programmer of Arena Breakout, will introduce the implementation and optimization of the Vulkan Ray Query in 'Arena Breakout', including its ability to maintain a stunning 60 FPS within the expansive open world map.

### Content Summary
[TLDR]
手游光追不是玄学，靠精细化管理资源和混合渲染管线，移动端也能实现稳定 60 帧的高质量光照。

[Background]
移动端做光线追踪常被性能劝退，易发热掉帧。本讲由《暗区突围》主程分享，揭秘如何在有限算力下平衡画质与帧率，提供实战方案。

[Recaps]
这场演讲主要讲的是怎么在手机里搞光追。《暗区突围》这款大地图 FPS 游戏要在移动端实现逼真画质，光追是个必经之路。但手机端算力有限，光加载一个场景的数据就能把内存撑爆。团队的核心思路就是“按需加载”：针对光影射线追踪 (Ray Tracing) 用的底层加速结构 (BLAS) 和顶层加速结构 (TLAS)，只根据相机距离动态生成和销毁，而不是全盘端上去。这招“空间换时间”极其有效，直接把相关内存占用砍掉了 75%，从 4.4G 降到 1.1G，这是能跑动的基础保障。

接下来是渲染管线的大坑。很多大佬习惯用延迟渲染 (Deferred Rendering)，但作者实测后放弃了，因为移动端显存带宽不够，搞出来太费电。他们选择了前向渲染 (Forward Rendering) 的老路子，然后针对光追反射设计了一套混合管线流程。先发射光线找位置，再算材质颜色，最后加个双边滤波 (Joint Bilateral Filter) 平滑瑕疵。连阴影和环境光遮蔽 (AO) 都尽量复用同一套光线逻辑，配合时序去噪，不仅画面好，还能在天玑 9200 这种芯片上稳住 60 帧。

现场问答环节也很实在。有人问帧率预测怎么做，他们透露用了重构静态网格顶点的办法，比单纯依赖速度缓冲区省带宽得多。不过也承认，开光追后功耗会上涨大概 1000mW，省电和画质得两头兼顾。总的来说，这不是什么黑科技，而是靠对资源管理的极致抠门和对管线设计的深度定制，才让手机端光追从概念变成了实际上线的产品。

## UIPainter: Tile-Based UI Rendering in One Draw Call

- **Slide Page:** https://www.gdcvault.com/play/1034768

### Overview
Every game editor needs a user interface. It is how we allow developers to create content for the game in a visual way. A good UI renderer has clear-cut constraints, like drawing nicely anti-aliased primitives, yet programmers have vastly different approaches to rendering game editor UI.In this session, Wessel Mast, Tools Programmer at Guerrilla, will tell you about how Guerrilla's editor 'Decima' renders UI: how it uses a tile-based renderer, commonly used in light culling, SSAO, depth of field and more, for drawing complex UI in an efficient manner and how it manages to draw thousands of primitives like rectangles, lines and curves in a single draw call using signed distance fields.

### Content Summary
[TLDR]
十年磨一剑，用单一绘制调用加瓦片渲染搞定了编辑器里又快又美还稳定的 UI。

[Background]

[Recaps]
讲道理好工具得像调好音的吉他，让人想玩。Guerilla 十年前开始搞这个 UI 框架时，目标就很明确：要支持多分辨率，边缘平滑，还得简单易懂能让非 UI 组的人也能写功能，最后必须快，一帧得在 16 毫秒搞定。这框架现在叫 UI Painter，十年来一直用在他们的编辑器里，成了项目基石。

具体怎么实现呢？核心逻辑是用 C++ 写一堆绘制命令 (Draw Command)，记录要画啥，像矩形或线条。关键是用 有符号距离场 (Signed Distance Fields) 来算像素位置，这样不用多层混合就能自动抗锯齿，边缘丝滑。所有的东西最终只用一个绘制调用 (Single Draw Call) 丢给显卡处理，省了很多麻烦。文字和图片则打包成缓存纹理，避免频繁切换材质。底层的逻辑全靠 着色器 (Shader) 统一处理，不用反复读写显存。

现在这套系统跑了十年，配合《地平线》系列游戏都发货了。核心就是简单实用，不追求花哨，只要稳。以后就算要把瓦片分配也移到显卡上，大方向估计也不会大变，毕竟好东西经得起时间考验，这才是工业级工具该有的样子。

### Overview
This talk covers the evolution of REDengine 4's thread-based job system: its API, internal implementation details, and our overall efforts to achieve greater parallelism. The final design was the result of many iterations and stages of feedback while the game was under development. The final approach chosen resulted in nearly all engine and gameplay systems taking advantage of multiple cores, which helped toward reaching our performance goals. Particular topics include solutions for a thread-based approach using counters for interjob dependencies, debugging and profiling, practical philosophy towards CPU resource sharing, integration with other systems, and overall approaches to the composability of jobs.

### Content Summary
[TLDR]
任务系统设计得越简单，开发者越爱用，性能优化才能真正落地。

[Background]
CDPR 在过往项目中吃过亏，发现再强大的框架若难用就会被弃用。本次分享旨在说明如何降低 `任务系统 (Job System)` 门槛，让开发团队真正用起来，避免并发带来的优先级混乱和调试困难。

[Recaps]
首先，CDPR 的核心哲学是“易用性大于一切”。他们摒弃了复杂的优先级争吵，将工作划分为`关键路径 (Critical Path)`、`潜伏路径 (Latent Path)`等简单类别。前者必须在一帧内完成以保证画面流畅，后者则像加载资源一样可延后。这种分类避免了开发者互相争夺算力，确保核心逻辑优先。同时，API 设计极其直观，直接在系统更新函数中就能接入，无需在代码海洋里找接口，强迫症都得投降。

其次，技术实现上最大的亮点是引入了 `任务计数器 (Job Counter)` 而非直接绑定任务依赖。你可以把计数器想象成排队叫号，一个任务开始排队就 +1，做完 -1，其他任务只需等数字归零即可执行。这巧妙的解决了“断裂的依赖链”问题。传统做法下，若中间任务因条件跳过，后续任务可能提前运行导致崩溃。而计数器机制下，即使中间空过，只要前序任务未完成计数，后续仍会安全等待。此外，计数器自带引用计数机制，无需开发者手动销毁，从源头上杜绝了野指针引发的崩溃风险。配合 `任务构建器 (Job Builder)`，开发者像搭积木一样串行或并行分发任务，无需手动管理底层线程同步细节，极大降低了出错概率。

最后，针对多线程环境下的锁和数据安全问题，演讲者分享了实战技巧。例如减少 `锁 (Lock)` 的使用时间，采用“锁与交换 (Lock & Swap)"策略快速隔离数据；或是用 `性能分析器 (Profiler)` 标记父级任务名，避免陷入几百个子任务的日志泥潭。特别是 `并行循环 (Parallel For)` 模式，能自动将大数据集分配给多个 `工作线程 (Worker Thread)` 处理。这里有个坑，如果数据量为零，仍需保留一个空任务占位，维持依赖顺序，防止逻辑错乱。同时善用自定义分析工具，将分散的子任务聚合在同一个父标记下，否则面对成千上万个微任务，排查性能瓶颈就像大海捞针，很难准确判断某项系统在整个帧周期中的真实开销，这也是动画和物理系统高性能的关键所在。

[Background]
Nanite (纳米粒子系统) 刚出来时虽然能跑亿级模型，但材质系统像个半残废，连个简单的 `WPO (World Position Offset)` 动画或透明效果都搞不定。而且随着场景里唯一材质变多，传统的 `像素着色器 (Pixel Shader)` 管线反而成了瓶颈，效率大幅下滑。这次 Epic 工程师把压箱底的技术公开，主要是给那些被传统渲染管线卡脖子的开发者指条明路，看看大厂是怎么把 `GPU (图形处理器)` 资源压榨到极致的。

[TLDR]
艾伦·韦克 2 用 GPU 计算提前搞定骨骼动画，配合顶点压缩和光追优化，让海量森林植被既能动又准确。

[Background]
为了在续作里实现比前作更逼真的森林生态，开发组想摆脱简单的顶点抖动，改用真实骨骼动画。但传统方法太吃资源，这篇分享详细拆解了 Remedy 如何用新技术平衡画质与性能。

[Recaps]
Remedy 这次主要解决了一个大难题：怎么在《控制》的基础上，把森林做得更大、更多，而且还得是真实的骨骼动画，不能靠简单的顶点抖动凑合。之前的管线对光照计算有要求，导致每帧要把模型算两次（蒙皮 (Skinning) 两次），一次画图，一次给光线追踪 (Ray Tracing) 用的包围盒层次结构 (BVH)。到了《艾伦·韦克 2》，这开销太大了，他们干脆搞了个“预蒙皮”流程，用计算着色器 (Compute Shader) 先算好所有骨骼变形后的顶点数据，存进缓存，后面渲染和光追直接拿去用，省了一次昂贵的运算。

关于光线追踪部分，为了保证低角度阳光下的阴影准确，必须把所有植被都放进 BVH 里面，不能像以前那样只看镜头近处。但全部实时重建会拖慢 CPU。所以开发者用了分级构建策略，离镜头远的树，重绘频率就低点，近的就高点，还在调试参数时处理了闪烁问题。最终 PS5 上花了 1.5 毫秒左右就能搞定这么多模型的动效，Series X/S 上稍微降点密度也能稳住 30 帧，算是把次世代性能压榨干了。

## FP16 Shaders in Frostbite
- **Speaker:** Alexis Griffin-Lira (Electronic Arts)
- **Duration:** 54 分钟

### Overview
This talk describes how Frostbite implemented multi platform 16 bit type (FP16) support for shaders in order to increase shader performance, especially on mobile. 16 bit shader types like half and short have advantages over 32 bit types, like occupancy and ALU performance. However, converting shaders to take advantage of half precision types is often not a straightforward process, in particular when accounting for platform and driver quirks. nnThis talk will cover the process of creating Frostbite's FP16 API, which enables shader programmers to write FP16 shaders while the tools bridge the platform gaps under the hood. ### Content Summary
[TLDR]
Frostbite 团队通过定制半精度浮点方案实现跨平台渲染优化，移动端收益显著，但需谨慎处理精度与驱动兼容性。

[Background]
为应对低功耗设备散热与能效挑战，Frostbite 引擎团队分享了在多平台上统一集成半精度浮点渲染的实战经验与踩坑记录。

[Recaps]
讲真，这演讲就是 Frostbite 如何把**半精度浮点数 (FP16)** 塞进引擎的血泪史。初衷很简单，为了手机和掌机这种低功耗设备省点电、少发点热，避免**图形处理器 (GPU)** 过热导致**热节流 (Thermal Throttling)**。核心逻辑是**半精度浮点数 (FP16)** 在**着色器 (Shader)** 中占用内存只有**32 位浮点 (Float32)** 一半，能减少**寄存器 (Register)** 压力，提高**图形处理器 (GPU)** 同时运行的线程数，也就是**占用率 (Occupancy)**。理论上代码跑得更快，指令更少，但这事儿没想象中简单。

为了不让程序员写一堆乱七八糟的条件编译，他们搞了套自定义类型系统和模板化的**C++**结构，配合**高级着色语言 (HLSL)** 实现跨平台统一。目标是一次性写代码，到处都能跑，而且不想让**驱动程序 (Driver)** 的差异搞崩体验。结果发现，桌面端驱动经常对**半精度浮点数 (FP16)** 支持得各种飘忽不定，甚至直接不支持，导致不得不强制转换回 32 位，反而拖累了性能。这就属于典型的“想省力反被累”。

最大的坑在于精度丢失带来的**量化伪影 (Quantization Artifacts)**，比如画面出现不自然的**色带效应 (Banding)** 或者光影错误的**裁剪 (Clipping)**。有些原本用 32 位计算深度偏置的地方，转成 16 位后精度不够，阴影全是马赛克。他们靠大量的回归测试来对比 16 位和 32 位的截图找茬。优化方面，关键是要减少**转换 (Conversion)** 成本，尽量让数据全程保持**半精度浮点数 (FP16)**，还要鼓励向量化编写以提升**算术逻辑单元 (ALU)** 效率。

最后实测结果是：移动端简直是“真香”，性能起飞；主机端主要是增加了并行度，实际帧数提升不明显甚至偶尔更慢；PC 端因为驱动问题目前主要用的是映射模式。总之，**半精度浮点数 (FP16)** 渲染是好东西，但别指望自动优化，得手动调教，尤其要注意画质的取舍，毕竟没人愿意玩着游戏看着画面掉渣。

[Recaps]
兄弟们，先把编译时间和帧率预算对比一下，60 毫秒能干多少事，我们花几个小时就在等编译，这太疯狂了。解决思路得从底层开始堆料，比如高速固态硬盘 (SSD)、大内存和关闭杀毒软件扫描 (Antivirus)，有服务器条件就上分布式构建 (Distributed Builds)。但这些只是锦上添花，核心痛点还是在代码和编译器层面。大多数时间被编译器前端 (Front End) 消耗在了理解代码和解析依赖上，而不是生成机器码的后端 (Back End)，这意味着我们有更大的操作空间来优化。

既然不能瞎猜，那就得量化，测不准就别想改进。Clang 和 MSVC 虽然自带追踪功能，但一个是生成 JSON 文件，一个是系统级事件，数据太散。主讲人自己写了个 Compile Score (Compile Score) 工具，把两边数据统一成一套标准，还能做成 VS 插件实时显示。打开这个黑盒，你会发现所谓的编译慢，90% 都是因为在处理嵌套的头文件 (Header Files)，像什么万能头文件之类的东西，简直就是性能杀手。

## Building the Fully Connected Multiverse in 'Suicide Squad'
- **Speaker:** Ingimar Gumundsson (Rocksteady Studios Ltd.)
- **Duration:** 30 分钟

- **Video Page:** https://www.gdcvault.com/play/1034617

### Overview
This talk presents a method of how to support an environment design in a streaming open world that changes greatly over time within the game. The design allows for navigation data to be built, such that a predictable minimum set of offline data is readily available to complement the changing nature of the environment. Within this framework the talk will detail how to build connected navigation data that spans all surfaces, allowing agents to traverse walls, fly and reach the player at any location, quickly. ### Content Summary
[TLDR]
用分层分块加动态导航技术，搞定超大开放世界剧情变动后的全域可达与高机动性设计。

[Background]
做开放世界最怕地图一大变 AI 就瞎了。本作主角是超级反派，得能在城市里随便飞跳，还得跟着主线剧情把地图改得面目全非，这怎么搞？讲者分享了咋保证动态世界里 AI 还能满处跑。

[Recaps]
核心难点在于既要让城市变得面目全非，又要保证 AI 和玩家随时能去任何地方。解决办法是把整个城市场景切分成一个个“分块”（Chunk）。每个分块内部又分为两类层：一类叫“不变量层”，负责固定的建筑结构和跨分块衔接的几何体，保证邻居之间不脱节；另一类叫“变量层”，负责根据剧情变化的内容，比如外星人入侵带来的新元素。因为变量层的几何体严格限制在自己分块的边界内，换装时不需要重新处理周围的数据，这让地图的大规模变更变得可行且高效。为了支持这种结构，所有的关键数据都经过了“预烘焙”（Baked Data），确保流式加载时数据永远有效。

为了让角色能在高楼大厦间任意穿梭，传统的水平导航不够用，所以做了个骚操作：把地面的“导航网格（Navigation Mesh）”旋转起来贴在墙面上。Unreal Engine 自带生成地面网格的工具，团队通过旋转坐标系，把墙面当成地面来算，甚至处理了天花板。考虑到精度问题导致角度过大的墙面没覆盖到，他们放宽了坡度判定阈值，并加了多边形减法处理，保证了墙壁、屋顶这些垂直表面也能被计算进“导航网格”里。所有分块的导航数据也按网格细分，不同分块加载时会自动拼接边缘的多边形，形成一张无缝的全局通网。

至于那些实时生成的爆炸物或者 Boss 掉下来的触手怪怎么办？方案是分两步走。对于可破坏物体，直接标记网格 ID 快速切换状态，炸了就变通行区。对于像 Brainiac 触手这种实时生成的新几何体，系统会识别它们是“动态层”资产，触发局部重算导航数据。虽然这听起来很耗资源，但因为利用了现有的分块约束和空间查询技术，实际上做到了毫秒级响应。这套机制不仅解决了静态地图的可通达性问题，还保证了动态环境下 AI 依然能做出高机动性的复杂移动，给玩家带来足够的压迫感和爽快感。

针对玩家和开发者最关心的 CPU 瓶颈问题，CDPR 工程师掏心窝子复盘了《赛博朋克 2077：往日之影》的优化历程。旨在解决旧作性能捉襟见肘的痛点，分享如何在多核心架构下实现稳定的高帧率表现。

[Background]
手机玩高画质游戏容易发烫、耗电还卡？《Arena Breakout》团队分享了如何用自研帧预测技术解决高刷模式下的功耗和延迟难题，适合移动端渲染开发者参考如何提升体验。

[Recaps]
以前大家总想着用深度学习 (Deep Learning) 或者帧插值 (Frame Interpolation) 来提升画质流畅度，但这俩路子都有坑：前者得专用芯片，后者会拖慢操作跟手性，对于硬核射击游戏简直是自杀。这老哥直接提出搞一套纯软件层的**帧预测 (Frame Prediction)** 技术。核心逻辑特简单：既然相邻两帧静态场景变化不大，那就直接用上一帧的像素信息复用过来，没必要每一帧都死磕着重画一遍，这样既省功耗又能保证 144 赫兹的丝滑跟手感。

[Background]
现在的 AI 模型越做越臃肿，直接塞进手机里不仅占存储、吃流量还费电。把模型放云端虽然有路走，但延迟和隐私又是新问题。Unity 联合 ARM 团队分享了这个主题，就是告诉大伙儿怎么把大模型“瘦身”并在本地高效运行，适合所有想在移动端落地 AI 功能的开发者。

[Recaps]
核心痛点其实就一个：模型太胖跑不动。数据图显示，新出来的 AI 模型参数量指数级暴涨，这意味着存储成本、数据传输带宽和计算算力都要翻三倍。对于手机这种资源受限的设备，频繁在内存和不同计算单元间搬数据特别耗电，游戏优化再好也容易被发热的用户骂。与其搞云端推理，不如在本地想办法优化，Unity Sense 这个神经网络推理引擎最近就在推量化技术来解决这个问题。

最直接的解法是权重量化 (Quantization)。接下来发布的版本支持把原本的 FP32 权重换成 FP16 或者 INT8。简单来说，FP16 能把模型体积砍掉一半，而且几乎看不出差别；INT8 更猛，能省下 75% 的空间，虽然会有轻微误差，但在生成分类这类任务上大部分情况是可接受的。好处是这属于后处理，开发者不用拿回原始数据重新训练，把模型丢进编辑器就能压，非常省心。

更进阶的做法叫算子量化，也就是直接在计算时用整数运算。比如把卷积层换成 8 位整型，推理速度能提升 54%，这对实时性要求高的场景非常有用。不过这玩意儿还没正式量产，主要是为了演示上限能到哪。因为它不是所有数学操作都能转成整数，遇到像 Sigmoid 这种没法量化的层，还得加一堆额外的节点做数据转换，逻辑复杂度会提高一些。

最后给大家提个醒，量化好不好用得看具体活儿。如果是图像分类这种死板的任务，INT8 可能会因为偏差导致全错；但如果是写故事这种生成式模型，有点偏差反而不影响体验。Q&A 环节确认了，这套方案不需要专用的 NPU 芯片，普通的 CPU 或 GPU 都能跑，大家拿到 Unity 更新包直接测，看看移动端到底能跑出什么花样。

### Content Summary
[TLDR]
拒绝碎片化布尔值，用依赖节点图接管游戏状态，实现自动查错与存档兼容，彻底治愈开发痛点。

[Background]
前作因为全凭全局布尔值管状态，导致存档容易坏、调试像在猜谜，还出过著名的玩家卡死 Bug。为了拯救续作品牌口碑，技术负责人决定彻底重构底层逻辑，把这些血泪经验分享给同领域开发者避坑。

[Recaps]
咱们先聊聊前作为啥头大。以前管理游戏进度全靠全局布尔标志位 (Global Boolean Flags) 和散落在各个物件里的私有状态，光是开关就有上千个。这玩意儿一旦加了新内容，旧存档就极易冲突，甚至导致玩家进不去房间被锁死在地图里。最要命的是，想调某个阶段剧情，还得靠策划手搓脚本模拟玩家之前的行为，稍微有点变动整个流程就得崩盘。这种分散管理让后期维护变成了修不完的漏勺，测试人员更是苦不堪言。

为了解决这烂摊子，新系统的核心思路是把所有状态变成一张有向图 (Directed Graph)。每个状态是个节点 (Node)，箭头代表依赖关系，必须前面的事做完，后面才能解锁。这就好比家族树，你得先有爷爷才能有孙子。系统会自动检查每个节点的前置条件，一旦发现玩家跳过了步骤直接点后续节点，立马就会报错并生成一个补丁级修复。这种集中式的管理不仅让存档跨版本加载变得很皮实，就算加了新门，也能自动根据你到达的位置推断出门的状态，再也不怕玩家卡在密室里出不来。

工具方面，这套系统做得特别贴心，支持分层的子图 (Subgraph)，方便不同团队分工编辑。编辑器里能直观看到哪个任务可做了，还能通过关卡标签 (Level Tag) 平滑迁移旧逻辑，不用一次性推翻重来。更有趣的是它内置了一个安全网，万一触发严重错误弹窗，会提示玩家选择回档还是尝试修复，甚至自动补全缺失的步骤。虽然早期弹窗设计得太简陋让人误解是崩溃，但经过几次迭代优化后，现在成了保护玩家体验的最后一道防线。

### Overview

### Content Summary
[TLDR]
掌握 Compositor Layers 和 Application Space Warp 两大核心工具，能在保证画质的前提下突破 Meta Quest 的硬件性能瓶颈。

[Background]
很多开发者拿 PC 或主机那套思路硬搬 VR，结果在电池受限的 Quest 上各种卡顿且文字糊成狗。Meta 老哥今天掏心窝子讲如何绕过硬件坑爹的物理架构，专门教怎么用官方工具让画面更清、帧数更稳，避免大家在优化路上走弯路。

[Recaps]
首先要懂个死理儿：Quest 是干电池供电，算力天花板摆在那，而且 CPU 和 GPU 是零和博弈，想提一个就得砍另一个。最贵的功能还是透视模式（Pass Through），因为系统要把摄像头画面歪到和你眼睛对齐，这关系到你的**本体感觉 (Proprioception)**，搞不好手会穿模让你犯恶心。而且透视画面不能给你读像素，安全原因。这一切都靠一个叫**合成器 (Compositor)** 的系统来管，它负责把你做的游戏、透视画面、UI 叠在一起，最后扭曲了塞进屏幕里。

这就引出了一个大坑：为啥你在游戏里显示的汉字越看越糊？这是因为屏幕镜头有**桶形畸变 (Barrel Distortion)**，再加上每次渲染都要经过**双线性过滤 (Bilinear Filtering)**，滤镜一层压一层，清晰度就崩了。解决办法很简单，叫**合成层 (Compositor Layers)**。别在游戏引擎里画好字再让系统去折，直接把资源给系统，让它一次性把纹理映射到屏幕上并矫正畸变。实测下来，用这招哪怕字号小一半，看着都比不用的清楚，特别适合做 UI 或者放高清视频。

至于帧数不够咋整？别光盯着 CPU 跑分，Mobile 端用的是**瓦片渲染 (Tiled Rendering)**，多开几个特效通道成本比主机高多了。这时候神器来了，叫**应用空间变位 (Application Space Warp)**。简单说是你每两帧自己只算一帧，OS 帮你补中间那个画面，这样你就有了双倍计算时间。但这玩意儿不是万能药：你得额外算**运动矢量 (Motion Vector)** 给系统用，透明度物体容易闪烁，快速甩动作会有残影，而且按键操作延迟会变长。所以得权衡，特别是动作游戏要慎重。

最后送几样趁手的家伙事儿。不想插线测试就用 Meta XR Simulator，引擎里就能模拟透视和手柄震动；音效反馈别瞎猜，用 Haptic Studio 自动生成对应设备的手感文件；查卡点别只会看日志，下载 RenderDoc 看 GPU 着色，用 ProfettoO 抓 CPU 耗时；还有上线前记得用 Meta 商店后台开 Beta 渠道，方便玩家直接反馈问题，省得你自己满世界找测试账号。

最后给大家深扒了下底层原理。安卓其实就是个带用户空间的 Linux，驱动信息都在 `/dev/input` 目录下。你通过 Shell 命令 `getevent` 能看到设备上报的原始信号。这些数据经过系统的 `Input Manager Service (输入管理服务)` 分发，最终传到游戏里主要有两条路：旧点的 `NativeActivity` 能让你直接拿 `AInputQueue (输入队列)` 指针，零延迟但兼容性差；新出的 `GameActivity` 继承自 `AppCompatActivity`，跟现代库更亲，虽然有点内存拷贝开销，但更稳。API 33 以上还开放了 Java 层面的直接访问，想冲性能的赶紧换架构。

[Background]

工具链方面，调试神器 PIX 也升级了。以前玩图形编程怕漏单，现在 PIX 支持直接捕捉工作图的运行状态，还能调试光线追踪 (Ray Tracing) 的命中和未命中着色器。另外，Shader Model 6.6/6.7/6.8 也带了些小更新，比如波束尺寸范围属性，让兼容性更好。虽然有些新功能如 GPU 上传堆需要新版 Windows Insider 版本才能跑，但整体方向就是让显卡更智能，别再卡 CPU 脖子。

总的来说，这波操作就是告诉开发者：别再用老办法硬抗了，赶紧上手试试新的工作图和 Direct SR，配合最新的驱动包，你的引擎性能上限可能直接翻倍。

- **Speaker:** Jesper Tingvall (Microsoft)

### Content Summary
[TLDR]
用自动化工具把远处的复杂模型打包成“替身”，既能省性能又能保画质，这才是现代引擎该有的做法。

[Background]
面对开放世界巨大的性能压力，尤其是 UE5 时代显存和三角面数爆炸的问题，开发者急需一套能自动化解决远景优化的方案。这个微软系工具分享了怎么用“取巧”的方式换回高帧率，适合所有做 3A 和开放世界的团队。

[Recaps]
首先，讲者来自微软旗下的 Simplygon (原文听作 Simon/Simplon)，这家公司做了 18 年中间件优化。他们核心的玩意儿就是帮美术和开发者把模型优化好，不用人工手调。重点在于处理那些离得远的物体，也就是所谓的 **层次细节 (Level of Detail/Lod)**。简单来说，人眼在远处看不出细节，这时候就别浪费算力了，直接找个更省钱的模型顶替上去。

接着是具体的优化手段。以前常用 **三角形削减 (Triangle Reduction)**，但这会有问题，比如挖空的窗户、断开的树枝会被砍掉一部分变成实心，或者留下奇怪的孔洞。所以 Simplygon 提倡用 **重网格化 (Re-meshing)**，就像给模型包一层保鲜膜，强行生成一个低面的封闭外壳。这样既能保留外形，又能大幅减少面数，特别适合那种复杂的建筑或松散结构的物体。

在虚幻 5 引擎里，他们做了个实机对比，用了著名的矩阵城市演示。结果很惊人：开启他们的代理 **聚合 LOD (Aggregate LOD)** 后，切换视距可以从 750 米提前到 100 米，不仅画面没崩，性能还上去了。因为现在的 **纳米几何体 (Nanite)** 不怕三角形多，但怕内存占用大，这种聚合后的代理能省不少显存。

最后是植被优化，这是个大坑。树要是简化太多就只剩杆子，树林看着光秃秃。他们的办法是用 **广告牌 (Billboard)** 技术，把树叶纹理烤到平面上，而且去掉了透明通道，这对带透明效果的 Nanite 性能至关重要。另外，他们的 Unity 插件也更新了，支持原生集成，以后不用走中间格式，夏天就能出新版本，总之就是想让大伙儿不管跑哪张硬件都能跑得爽。

[Background]
老牌工作室雷迪米因旧编辑器陈旧、迭代慢且不支持外包协作，决定从头搭建基于 Open USD 的新工具链来解决规模化生产痛点。

[Recaps]
咱们今天聊的干货是雷迪米的程序 Wea Park 分享咋拿 Pixar 的通用场景描述 (Open USD) 来造游戏编辑器。老雷以前那个 Wet 编辑器虽然用了十几年，但面对现在多项目并行和外包合作，早就显出疲态了，迭代慢还不灵活。这次他们彻底推翻重来，核心诉求就三点：迭代要飞快、资源能反复复用、还得方便跟外部伙伴协同。这新框架目前已经在《Control》续作和《Max Remix》等项目里跑通了日常开发。

技术上他们把游戏里的东西硬套进 USD 模型里。比如关卡整体就是一个根节点，角色和物体对应带特定标记的原语 (Prim)，技能或物理效果这些组件 (Component) 则挂载在应用 API 模式 (Applied AP Schemas) 上。最硬核的操作是把旧的老婆 (FBX) 资产通过插件强行转换成层 (Layer) 数据，这样不用动资产管线就能直接在引擎里用新工具编辑，实现了真正的实时修改，不用来回倒腾文件。

复用这套玩法的核心在于引用 (Reference) 和变体 (Variant)。他们把类似预制件 (Prefab) 的功能封装成自己的"Bundles"，支持多层级子层 (Sub-layer) 叠加。简单说就是一棵树的模型做成一个文件，引过来后能通过变体一键换颜色、换大小，甚至不同人可以在各自的层里单独调参数，最后由系统按优先级合并。这种机制完美契合了 Git 类的版本管理思路，避免了多人改同一个文件导致的“代码打架”事故。

不过专家也直言这玩意儿不是万能的，最大的坑在于意见栈 (Opinion Stack) 太复杂，稍微不注意就会因为优先级问题导致修改不生效，比如删了个颜色反而没反应。而且改名操作很容易断掉引用关系。所以结论很明确，光有底层技术不行，必须配备顶级的 UI/UX 设计师把复杂的底层逻辑可视化成直观的界面，否则这工具就是给程序员造的孽，美术和策划根本没法用。

咱们做开发的最怕的就是新老引擎混战。这次 EA 大神 Jason Bright 揭秘了 Frostbite 引擎怎么从老旧的 DirectX11 过渡到 DX12、Vulkan 和 Metal 这些新架构。核心策略是建立一个独立的渲染抽象层，他们称之为渲染上下文 (Render Context / RC2)。这玩意儿独立于主引擎，想适配新平台就能单开一条线，不会把老代码搞得乱七八糟。最关键的一点是，他们明确不搞什么“移动专属引擎”，而是直接把 Frostbite 搬过去，给工具让开发者自己取舍画质和性能。

为了平衡速度和质量，他们没有强求一次性全重写，而是造了一个“桥梁”组件。这个桥能模拟旧有的即时模式 (Immediate Mode) 行为，底层却对接新的 RC2。这样做避免了大量废弃代码的堆积，让 Switch 和 Stadia 这类新项目能立刻跑起来。虽然中间多了一层开销，但换来了并行开发的自由，等 RC2 稳定后再逐步剥离桥梁，回归纯原生支持。

着色器这边也是统一战线的做法。坚持用高阶着色器语言 (High-Level Shading Language / HLSL) 作为唯一源码，中间转成标准二进制着色器中间表示 (SPIR-V) 格式分发。遇到不同平台驱动对描述符集 (Descriptor Sets) 支持的差异，他们写了自动修补脚本，在编译后阶段动态修正。最后针对移动端特有的瓦片缓存机制，优化了帧图系统 (Frame Graph)，减少不必要的显存拷贝，为后续的 FP16 精度优化铺平了道路。

[Background]
随着图形处理器 (GPU) 任务加重，传统截图测试太慢且难定位 Bug。演讲者分享了 Rare 如何建立自动化着色器单元测试体系，解决开发效率与稳定性痛点。

[Recaps]
咱们平时总觉得图形程序员只管画面，其实着色器代码 (Shader Code) 和普通逻辑没区别，都得测。以前 Rare 团队主要靠截图测试 (Screenshot Testing)，这属于测试金字塔顶层的“端到端”测试，虽然能看画面对不对，但跑一次得两秒，一旦出点小颜色或者纹理问题，根本不知道是哪行代码导致的排查成本高，而且容易受环境干扰产生误报。

为了解决这个坑，他们自己搓了一套基于 HLSL (着色器语言) 的单元测试 (Unit Tests) 框架。这套方案把测试下沉到最底层，不测渲染出来的图，直接测着色器的计算逻辑。比如测试水花生成算法是不是按预期算数。因为不用跑整个游戏场景，速度从每轮两秒优化到了几十毫秒，效率提升了几个数量级。测试通过与否就是简单的红绿框，没有模棱两可的百分比差异，让质检同事也不用天天去人工校验那些该死的自动结果。

在实现上，框架核心是靠共享缓冲区和原子操作 (Atomic Operations) 来统计测试结果，配合虚幻引擎 (Unreal Engine) 自带的测试框架。遇到 Bug 时，可以用 DirectX 的性能调试工具 PIX (DirectX 调试工具) 抓取现场，像断点调试 C++ 一样单步追踪着色器里的变量变化，能快速定位是循环写错了还是公式算错了。

总结一下，截图测试并没有完全被抛弃，对于云朵、雾气这种整体视觉效果的回归检查它依然有用。但对于具体算法逻辑，一定要坚持写单元测试，并且尽量编写无全局状态、方便依赖注入 (Dependency Injection) 的代码。这样既能保证开发进度，又能减少加班熬夜，毕竟测试不是为了折磨人，是为了早点下班。
