- **Slide Page:** https://www.gdcvault.com/play/1028839
- **Custom ID:** 1029260

### Overview


### Content Summary
[TLDR]
针对物理沙盒游戏的高延迟痛点，通过相对预测与层级绑定技术，实现了更流畅的多玩家实体同步方案。

[Background]
作为《Space Engineers》的技术负责人，面对海量动态实体与复杂交互，传统的 FPS 同步逻辑会导致严重的延迟和不同步，本次分享旨在拆解其独特的解决方案，给做同类游戏的开发者避坑参考。

[Recaps]
聊起基础网络架构，大家肯定都懂那种权威服务器 (Authoritative Server) 模式，客户端只管发指令，服务器算完再回传。但在《Space Engineers》这种动辄百人联机、成千上万个网格 (Grids) 的游戏里，直接用简单的UDP 流式传输加插值 (Interpolation) 和外推 (Extrapolation) 是不行的。因为网络波动大，包会乱序甚至丢包，所以服务器端加了个四包的播放延迟缓冲 (Playout delay buffer)，哪怕包迟到一点也要按顺序排好再进模拟，免得角色动来动去像抽搐一样。但这套下来，从你按键到屏幕反应，理想状况也得两百多毫秒，卫星网直接奔着半秒去了，这对任何游戏来说都是灾难，尤其是当你在开船或者建基地的时候，这手感简直没法忍。

为了解决这个“手慢无”的问题，团队上了客户端预测 (Client Prediction)。简单说就是客户端先自己算一遍，等服务器反馈回来对一下账，如果有偏差再修正历史轨迹。这在《Counter-Strike》或《Fortnite》这种地图固定的环境里挺好使，但在太空沙盒里就出大问题了。因为服务器的世界状态比你手里拿着的状态要“新”一个 Ping 周期，这就造成了时间悖论 (Time Paradox)。比如你飞着靠近一艘飞船，你以为能钻门进去了，结果服务器那边判断你撞到墙了，最后还得把你弹回来，这种穿模和瞬移体验极差，根本没法用纯绝对坐标来预测。

核心大招是相对预测 (Relative Prediction)，其实就是把实体搞成父子层级关系。就像角色骨骼动画一样，你在飞船上走，你的位置不是绝对坐标，而是相对于飞船原点的偏移量。只要飞船动，你就跟着动，服务器只通知你“上车”这件事，之后怎么飞全靠本地算。对于物理部分，没被控制的物体在客户端全是静态刚体 (Static Rigid Body) 用来占位，只有你操控的角色才是动态的。遇到复杂的机械结构（比如很多连杆组成的长腿），误差积累太大会炸，就直接关闭预测转成动画播放；碰到离心力差异太大时，也及时切回动画以防不同步。这套路虽然听着绕，但实测下来确实大幅减少了卡顿和瞬移，让这艘老破船跑起来终于顺溜了。

- **Speaker:** Ispanji Pratama (AccelByte)
- **Duration:** 1539 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1029255
- **Slide Page:** https://www.gdcvault.com/play/1028747
- **Custom ID:** 1029255

### Overview


### Content Summary
[TLDR]
搭建 UGC 系统核心是灵活架构加真实压测，少存大字段在数据库，多靠外部存储兜底。

[Background]
分享《黑道圣徒》角色定制系统开发经验，解决 UGC 高并发下的性能瓶颈和内容审核难题，适合想做社交功能的后端同学避坑。

[Recaps]
这次讲的是《黑道圣徒》的 Boss 工厂系统，本质上就是个让玩家捏脸、改装备还能直接分享的 用户生成内容 (User Generated Content) 平台。架构上用了 微服务 (Microservices)，后端全跑的 AWS，数据库选了灵活的 NoSQL 数据库 (NoSQL Database)，文件放 S3 上。为啥选 Mongo 呢？因为游戏迭代快，数据结构变来变去，处理无结构数据 (Unstructured Data) 不用像传统数据库那么麻烦，这点特别适合敏捷开发。认证部分用的是 身份与访问管理 (Identity and Access Management) 服务，确保用户身份准确。登录这块不整太复杂，游戏里直连主机账号，网页端用个中转账号（Pros Account）通过 开放标识连接 (OpenID Connect) 把两边串起来，保证你在哪玩都能找到以前的角色。

内容审核其实是重头戏。为了少挨骂，官方不让玩家随便打文字描述，全是管理员预设的 标签 (Tag) 和包 (Pack)。这样既省了脏字过滤的成本，又减少了运营压力。审核机制很简单：玩家一键举报，报告攒够 5 条自动下架，不用客服 24 小时盯着。这算是入门级的风控方案，但胜在省心。跨平台体验也做得挺溜，不管你是用哪个主机或网页，身份能对应上，存档和作品能互通。

最值钱的还是后面几个血泪教训。第一，千万别把大图塞进数据库，测试时有人直接把图片转编码存在库里，结果一查就卡死，后来全移到 对象存储 (Object Storage) 了，查询速度飞起。第二，S3 分片有限制，之前几十万文件挤在一个包里，每秒请求数 (QPS) 不够，后来按上传时间切分了，才扛住流量。第三，索引不是越多越好，有些全局标记（比如隐藏所有 Epic 区内容）加了 数据库索引 (Database Index) 反而慢，得根据实际在线数据调整。总之，真实环境下的压测绝对比跑分数据重要，别等开服炸了再修。

## Online Game Technology Summit: XPR Model: Building a Truly Scalable Virtual World
- **Speaker:** Richard Li (LIGHTSPEED STUDIOS)
- **Duration:** 1935 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1029262
- **Slide Page:** 
- **Custom ID:** 1029262

### Overview


### Content Summary
[TLDR]
利用量子力学原理重构游戏模拟模型，通过时空叠加与退相干机制，解决大规模联机世界的性能扩展难题。

[Background]
传统游戏服务器分区因维护数据一致性需大量重叠区域，造成算力浪费，难以支撑未来的超大规模在线世界。此分享适合对底层架构、高性能计算及 MMO 扩展性感兴趣的资深开发者参考。

[Recaps]
大佬们看这篇干货，核心痛点是现在的在线游戏虽然画面大了，但逻辑还是老古董。为了多人同步，服务器得不断重叠模拟区域（Overlap Area），就像做遮挡剔除反过来了，越分越浪费算力。作者团队来自腾讯 Light Speed Studios，也就是《PUBG Mobile》背后的工作室，他们决定不修修补补，而是直接借用**量子力学 (Quantum Mechanics)** 的思路来搞个大工程。传统的牛顿力学世界观太死板，全局时间空间限制了上限，而量子模型更灵活，允许在未被观测时并行处理，只有当玩家“观测”（交互）时才坍缩成现实。

具体怎么落地呢？作者提出了个叫 XPR 的处理管线。核心单位叫**时空气泡 (Space-Time Bubbles, ST)**，相当于一个个独立的小宇宙。在这个模型里，实体可以处于**叠加态 (Superposition)**，意味着一个物体可以同时存在于多个地方而不冲突，直到发生**纠缠 (Entanglement)** 或交互。这时候需要触发**退相干 (Decoherence)**，把多个状态合并成一个确定的结果，合并用的算法是简单的**归约算子 (Reduced Operators)**，比如取平均或插值，千万别把复杂的非线性逻辑塞进去。信息传递也有光速限制，通过改进的**蝴蝶网络 (Butterfly Network)** 结构来实现高效的远距离通信，保证延迟可接受。

如果遇到冲突怎么办？这就得靠**历史回滚 (History Rewinding)**。系统会记录事件帧号，发现不一致就倒带重算，但这要求固定帧率且需要向量时间戳来判断因果关系的先后顺序。这招虽然稳，但代价大，所以建议尽量把复杂逻辑移出归约阶段。整体来说，这套方案能把游戏模拟的天花板掀翻，支持超长距离交互和海量实体，但缺点也很明显：你得重构大部分代码，特别是物理引擎部分。最后作者还透露未来想用深度学习自动优化这些算子，看来大厂的技术栈是真卷啊。

[Background]
针对印度市场用户多但分散、获客成本极高（CPI）的行业痛点，WinZO 团队分享了如何用技术驱动分发替代传统广告，为中小开发者提供了一条高性价比的出海与商业化路径。

[Recaps]
印度游戏市场虽然下载量大，但大部分来自四五线城市，英语普及率低，直接投谷歌或 Facebook 广告效果极差且 CPA（单次行动成本）居高不下。WinZO 意识到不能单纯拼资金，而是得拼产品逻辑。他们做了一个类似“游戏版 Netflix"的聚合平台，核心打法不是买量，而是发动了 7 万个长尾网红来做推广。这种去中心化的分发模式，让网红能把粉丝导流到应用内直接变现，解决了传统渠道触达不到的下沉用户问题。

为了管理这庞大的网红网络，仅靠 4 个人的团队根本不可能，全靠数据中台。所有点击、转化和行为数据都汇聚到 Kafka（消息中间件）管道，通过机器学习 (Machine Learning) 模型进行离线分析和在线推理。比如系统会自动识别像 Lokesh Gamer 这样的潜力网红，根据表现动态调整奖励，防止用户流失；一旦发现有设备农场刷单骗佣金的欺诈行为，实时反作弊引擎能在毫秒级内切断异常流量，保护了平台经济的安全。

商业变现上，WinZO 没有选择传统的展示广告，而是推行了 微交易 (Micro Transaction) 的付费模式，玩家每局游戏都要押注少量资金，平台从中抽成，这种方式比广告费高出几十倍。游戏内容上，他们不仅接第三方游戏，还会把糖果传奇 (Candy_Crush) 这种单机游戏强行改成 多人游戏 (Multiplayer) 的对战模式，增加社交粘性。同时，他们向开发者开放高达 20-30% 的收入分成，并建立了专门的基金扶持内容创作，真正实现了多方共赢，这也是为什么他们能用极简配置支撑起亿级日活和数亿美元营收的关键。

## Online Game Technology Summit: Optimizing Live Gameservers with Continuous Profiling
- **Speaker:** Jordan Schidlowsky (Winterpixel Games Inc)
- **Duration:** 2732 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1029259
- **Slide Page:** 
- **Custom ID:** 1029259

### Overview


### Content Summary
[TLDR]
利用 eBPF 实现在线服务器零侵入的持续性能剖析，精准定位 CPU 热点从而大幅削减云成本。

[Background]
云游戏服务器按资源付费，但传统性能剖析往往需要独立构建版本，无法实时反映线上真实负载。此方案适合负责多人联机游戏服务端优化、关心云成本的开发者和运维人员。

[Recaps]
各位老铁都懂传统**性能剖析 (Profiling)**，比如用 Unity Profiler 追帧率卡顿，但这通常只能在开发期搞，因为要在代码里埋一堆监控钩子，放到正式环境（Release Build）会增加负担。但在**云游戏服务器 (Cloud Gameservers)** 上，咱们是按 CPU 和内存时长掏钱的，最怕白忙活浪费资源。所以演讲者提倡**持续剖析 (Continuous Profiling)**，就是把监控系统常年挂在生产环境，随时盯着。

怎么挂还不卡死机器？秘诀是**eBPF (extended Berkeley Packet Filter)**。这玩意儿能在 Linux 内核里跑微型程序，用**调用栈采样 (Call-stack sampling)** 的方式收集数据，几乎不占用游戏进程资源，**开销 (Overhead)** 控制在 1% 以内。作者用的是 Pyroscope（现在归 Grafana 管），配合 Kubernetes 几行命令就能搞定，瞬间生成直观的**火焰图 (Flame-graphs)**，哪块函数占用了 CPU 时间一目了然。

效果有多猛？讲个案例：《Rocket Bot Royale》游戏刚开服时发现大量 CPU 时间在压缩数据包，查了半天发现默认用的 gzip 太慢。改成 Zstandard 算法后，性能提升七八倍，光这一个操作就把云成本砍了一半。不过有两个雷区别踩：一是编译必须保留**帧指针 (Frame pointers)** (-fno-omit-frame-pointer)，否则内核找不到堆栈起点；二是得有对应的**调试符号 (Debug Symbols)** 才能把地址翻译回源代码。有了这些数据，不仅能修 Bug，还能对比新旧版本的性能差异，防止更新变卡，绝对是云服务器的省钱秘籍。

## Online Game Technology Summit: How to Design an Expressive and Efficient Matchmaking System
- **Speaker:** Chris Molozian (Heroic Labs)
- **Duration:** 1510 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1029258
- **Slide Page:** 
- **Custom ID:** 1029258

### Overview


### Content Summary
[TLDR]
匹配系统别光盯着完美算法，别让设计改配置卡脖子，降低等待时间比强行优化体验更重要。

[Background]
很多团队自建匹配服务时容易陷入数据库索引瓶颈，或者让设计师没法灵活调参。这篇干货适合准备搭多人联机系统的开发者避坑参考。

[Recaps]
说到底，匹配系统 (Matchmaking System) 就是要把玩家凑一锅饭吃，但这活儿有三大坑：是直接打 PVP，还是支持随时加入退出 (Drop-in and dropout)，亦或是像 MMO 那样选大区。核心矛盾永远摆在台面上：匹配条件越严，玩家等越久。老手都知道，宁可让玩家进去随便玩个不完美局，也不能让人家排十分钟队最后还掉线，毕竟“有得玩”比“完美匹配”更重要。

打法通常分两大流派。以前大家喜欢搞算法式方法 (Algorithmic Approach)，比如微软那个独占的 TrueSkill 算法，靠概率分布给玩家打分，适合主机游戏那种复杂的队伍配合。但现在趋势变了，更多用搜索式方法 (Search-Based Approach)，简单理解就是把玩家变成文档，像查百度一样按标签搜。这招最爽的地方在于灵活，设计师想看数据效果，直接改查询语句就行，不用求着程序员去改底层代码做 A/B 测试。

真刀真枪上生产环境，千万别把所有数据硬塞进关系型数据库里搞索引，那玩意儿一旦量大就会触发写放大 (Write Amplification)，性能瞬间爆炸。Best Practice 是把匹配逻辑剥离出来，搞成内存驻留 (In-Memory) 的分布式系统，用像 Bluge 这样的开源库来扛。数据分散在不同节点，请求来了就走分发与聚合 (Scatter/Gather) 模式。最后千万记得搞监控，盯着查询延迟别让它飙升，还有，人少的时候得备点机器人或者限制模式当 fallback，别让大家对着空荡荡的房间干瞪眼。

## Online Game Technology Summit: Hallucinations: Baiting Cheaters Into Self-Identifying by Reversing Detection
- **Speaker:** David Durst, Carly Taylor (Stanford University, Activision Publishing, Inc.)
- **Duration:** 1929 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1029256
- **Slide Page:** 
- **Custom ID:** 1029256

### Overview


### Content Summary
[TLDR]
别让反作弊成无底洞，而是搞套“钓鱼执法”，造出只有外挂能看见的假人逼对方暴露。

[Background]
Activision 的 Ricochet 团队受够了传统反作弊 (Anti-cheat)“补丁打不完”的被动局面。今天分享个新路子：不再死磕检测代码，转而给外挂玩家下套，让他们自己露马脚。适合关心服务端安全、网络同步和反作弊对抗的同学，尤其想了解如何从成本角度思考攻防战的老哥。

[Recaps]
大家都知道反作弊本质是个循环的猫鼠游戏 (Cat and Mouse Game)。以前我们是猫，抓一只修一只，但外挂开发者是老鼠，总会变异出新招数。这种不对称的消耗让我们很累，因为防御方被迫不断缩小外挂的可用特征空间 (Feature Space)，试图把他们逼回正常玩家模式。但这太费人力了，所以卡莉决定换个姿势：既然当老鼠（躲着跑）比当猫（抓人）便宜，不如让外挂玩家误以为他们在追捕“人类”。

于是核心大招来了——“幻觉 (Hallucination)"。简单说就是服务端造几个看起来像真人的假玩家，但只让外挂看得见。正常人看不见，外挂却会当成真人去瞄准或透视。以前有些静态伪装失败，因为外挂学会了无视特定区域。这次我们不仅要伪造数据，还要动态调整位置。关键点在于怎么藏？不能改游戏逻辑怕出 Bug，也不能动客户端防止被扫内存。最终锁定在修改发送给客户端的游戏状态快照 (Snapshot) 上，复制一份真人数据进去，再利用几何遮挡技术隐藏渲染结果，确保渲染器 (Renderer) 不画出来，但外挂读取内存时依然能看到实体。

落地策略分步升级：现在的做法是把假人塞到敌人视线死角或身后，未来的目标是生成更像真人的运动轨迹，甚至混在其他玩家模型里。这样做目的不是绝对防住，而是增加对方的防御成本。一旦外挂程序开始尝试过滤这些假人，就等于承认了自己的存在。为了防止误伤好人，我们强调需要观察到持续的行为模式才判定，不会一枪定生死。这套方案配合潜在的可见集 (Potentially Visible Set) 技术来管理可视范围，既能保护普通玩家体验，又能作为最后确认封禁的有力证据，把攻防节奏主动权抢回来。

[Background]
这位前黑客现身说法，揭露虚拟资产背后的黑色产业链。专为游戏开发者和安全人员准备，告诉大家为什么看似安全的网络交易总能被轻易突破。

[Recaps]
讲者老阿德从早年开始就喜欢研究游戏代码，发现只要游戏里存在玩家交互的**经济系统 (Economy)**，就必然产生巨大的灰色市场需求。很多时候影子市场里的流水甚至超过官方收入好几倍，这就是黑客们源源不断找漏洞搞钱的动力，毕竟这可是实打实的真金白银，像当年把虚拟城堡卖三千刀这种事也不是没有过。

想找漏洞，首选不是去硬刚机房，而是盯着**客户端 (Client)** 和**服务器 (Server)** 之间发的**数据包 (Packet)**。哪怕你有再强的**防火墙 (Firewall)**，如果 API 层面上的命令写得烂，黑客照样能刷金币或瞬移。老阿德用的工具很经典，像 Cheat Engine 加 Wireshark 抓包就能搞定大部分通信分析，毕竟一个大型网游可能有四五百种命令接口，随便哪个环节出错都能让人上天。

这三类最常见漏洞分别是**整数问题 (Integer Issues)**、**授权绕过 (Authorization Bypass)** 和**数据竞态条件 (Data Race Conditions)**。比如发负数个物品让库存变正数，拿别人账号 ID 开别人银行，或者利用多线程时间差一件东西卖两次。这些纯底层逻辑没写严实的锅，光靠**UI 界面 (User Interface)** 限制根本没意义，得靠**线程锁 (Mutex)** 和**运行时检查 (Runtime Analysis)** 来防守。老阿德还讲了个段子，以前有个项目因为数字计算错误，花四亿美元造了颗会自爆的火箭，这也提醒咱们编译器警告别忽略。

最后他还提了个新威胁，是用摄像头看屏幕再通过硬件模拟输入做辅助，这种 AI 外挂很难查。现在行业里连统一的安全标准都没有，他自己在制定规则，但大家得趁早意识到，虚拟资产价值越高，安全越得重视。他在 2018 年就停止为了赚钱而破解游戏了，毕竟跟厂商抢生意太危险，现在的重心更多是帮大厂做安全顾问。
