## Visual Effects Bootcamp: Rapid Talks
- **Speaker:** Alim Chaarani, Nadab Goksu, Sarah Grissom, Fred Hooper, Andy Lomerson, Matt Radford (Blizzard Entertainment, EA DICE, FXVille, NVIDIA, Vicarious Visions, Beyond-FX)
- **Duration:** 60 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024299
- **Slide Page:** https://www.gdcvault.com/play/1024704
- **Custom ID:** 1024299

### Overview


### Content Summary
[TLDR]
用全局工具管发光统一性，靠流程规划保手感，配合性能优化，实现高画质与高效率并存的特效工作流。

[Background]
多位 GDC 一线专家分享如何规避特效制作中的“撞车”与“返工”，涵盖从色彩管理到动效逻辑的全套工业级方案，适合追求量产质量的制作人学习。

[Recaps]
EA 暴雪那些大佬最先抛出了个硬问题：以前做特效，每个人调的颜色亮度都不一样，晚上亮得刺眼，白天又淡成灰。这次分享的《战地 1》方案是给所有**发光表面 (Emissive Surfaces)**装了个全局控制器，不管是粒子**粒子系统 (Particle System)** 还是**网格着色器 (Mesh Shader)**，都听一个总指挥的参数。这样美术只管设计素材，不用反复微调，场景一亮一暗画面依然和谐，连电影镜头都能直接复用这套数值，彻底解决了以前特效风格割裂的毛病。

搞爆炸最头疼的是啥？看着爽玩家却没感觉。NVIDIA 的老师傅建议别闷头画，先找策划对需求，明确这爆炸到底能不能把人震飞。参考现实视频定好**缩放 (Scale)**和冲击波范围，跟声音部门也要提前串台，避免画面跟音效不同步。这种规划虽然前期多花时间，但能少后期无数次改图的麻烦，毕竟特效是为玩法服务的，不是纯为了好看，否则游戏里就会显得空洞。

Blizzard 那边则是给**制作管线 (Production Pipeline)**做了拆解，分概念、功能、风格、打磨、优化五步走。像《风暴英雄》这种角色技能多的项目，前期就用简单的方块把技能机制跑通，确认打击感没问题了再加花哨的**粒子特效 (Particle Effects)**。最后还得考虑硬件配置，低端机直接开简化模式，保证多人对战不卡顿，毕竟技术再好不能带不动显卡啊。

分享环节里还提到了一堆实用小技巧，比如用**偏移 (Offset)**处理贴图接缝，或者手搓**法线贴图 (Normal Map)** 省插件时间。有个关于移动火焰的干货特别值得学，关键是得根据速度改变**粒子寿命 (Particle Lifetime)**，速度快火苗就短，慢了才能飘起来。还有那种不用复杂计算的远景地图扩展，直接用圆柱加贴图画出来，利用**视差效果 (Parallax Effect)**模拟无限延伸，既不费**渲染 (Render)** 算力又好改，简直是美术生的福音。

## Visual Effects Bootcamp: Artistic Principles of VFX
- **Speaker:** Hadidjah Chamberlain, Jason Keyser (Blizzard Entertainment, Riot Games)
- **Duration:** 60 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1023943
- **Slide Page:** https://www.gdcvault.com/play/1024439
- **Custom ID:** 1023943

### Overview


### Content Summary
[TLDR]
特效别光图好看，得让玩法清晰易懂，用视觉语言帮玩家快速读懂战场局势才是硬道理。

[Background]
来自拳头和暴雪的大佬联手分享实战经验。主要针对做特效的同行，解决“特效太花哨看不清啥”或者“为了好看牺牲了功能性”的痛点，强调做游戏开发者而不是纯艺术家。

[Recaps]
这两位业界大牛开麦的核心观点特别实在：做游戏视觉特效 (VFX) 首先要认怂，因为游戏玩法 (Gameplay) 才是老大。别把自己当纯艺术大师，要先把功能做好。设计师知道玩法目标在哪，特效得配合这个目标。比如 Tristana 火箭跳跃，一开始做得挺花，结果范围效果 (Area of Effect) 不清楚，导致玩家觉得自己被阴了。改版之后虽然没那么炸裂，但玩家一眼就能看懂伤害圈，这才是合格的视觉反馈。所以平时得多跟策划唠唠，搞清楚技能到底想传达啥信息，是爽感还是提示危险。在做之前最好先过一遍工作管线 (Pipeline)，确保做出来的东西不会喧宾夺主。

再来聊聊怎么让玩家一眼抓到重点。形状这东西最直观，尖尖的通常意味着危险，圆滑的可能就是个装饰。对于范围，千万别搞虚头巴脑，必须把边界给玩家留清楚。还有明暗对比 (Value Contrast)，这可是抢注意力的神器，但不能全屏幕都是高亮，那样就没重点了。像元素法师 Lux 的火球，只要球头够亮，尾巴暗点，玩家就知道该躲前面了。有个很实用的建议，就是把整个场景切到灰阶 (Grayscale) 看看亮度层次，这样最容易发现视觉噪音太多，看不清主次。

最后是节奏和颜色的门道。颜色不只是调色盘，那是身份的代名词，不同派系得有固定色调，避免玩家混淆，比如水变绿容易被误判成毒。而节奏才是决定“威胁等级”的关键。同样的特效，改改随时间变化的强度 (Intensity over Time)，就能从回血变成大招爆发。这里涉及几个动画原则，比如预备动作 (Anticipation)，爆炸前先缩一下，打击感立马翻倍；还有次要动作 (Secondary Action)，主伤害过后的小点缀能增加华丽感。记住，好的特效是让对手还没反应过来就输了，而且输得心服口服，知道为啥死的，这才是最高境界。

## Visual Effects Bootcamp: Like a Mace to the Face: Leaving the Battlefield to Go It Alone
- **Speaker:** Andreas Glad (Partikel)
- **Duration:** 48 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024295
- **Slide Page:** https://www.gdcvault.com/play/1024468
- **Custom ID:** 1024295

### Overview
In this talk, Andreas will share some of the techniques and methodology used to create blockbuster effects in 'Battlefield 1'. He will also walk through how Houdini can be leveraged when creating assets for Realtime VFX without the need for expert knowledge. There are many ways it can be used to improve or replace existing workflows by simply allowing realtime previews instead of relying on one-off scripts. As a final topic, Andreas will present a comparison between creating effects for one of the largest games of the year, and running a one man studio, working remotely with teams all across the globe.

### Content Summary
[TLDR]
揭秘如何在 60 帧高负载下实现电影感特效，并聊聊从大厂螺丝钉转型独立工作室的真实生存体验与行业反思。

[Background]
来自前 DICE 核心 VFX 专家。针对玩家关心“大作怎么还不卡”以及从业者纠结“要不要单干”的痛点。不仅讲技术优化，更给职业心态上了一课。

[Recaps]
先把硬核技术部分撸明白。想在《战地 1》这种级别的游戏里跑出高帧率 (FPS)，每个特效只剩两毫秒预算。别整那些复杂的法线贴图粒子 (Normal Map Particle) 了，费资源还没啥提升，全换成纹理序列贴图。为了不让爆炸多了卡成 PPT，得用实例数量限制器 (Instance Count Limiter) 掐住发射器头数，谁也别想乱刷。远景里的士兵和飞机直接用低模 (LOD) 精灵图 (Sprites) 贴地形上，既省算力又骗过眼睛，这就叫优化得当。火焰要是没东西依托就会飘在空中很假，记得加点附着结构让火光粘在箱子上，配合 PBR (Physically Based Rendering) 材质瞬间就有燃烧感了。远景贴地形还能减少过度绘制 (Overdraw)，这就是所谓的该省省该花花。

接着是 Houdini (Houdini) 软件的几招必杀技。做泥水血迹别手搓，把流体模拟直接转成网格 (Mesh)，重拓扑几次导出就行，程序化生成 (Procedural Generation) 的好处是一变参数就全变。还有那个经典的循环体积 (Looping Volume)，别只盯着 2D 序列，3D 模型做出来的烟雾后期换灯、换天气能直接调密度，省得回去重新合成。批量渲染可以用 Wedge 节点 (Wedge Node) 一键出多个切片或代理模型 (Imposters)，比如把角色转成一堆图片做无限军团，虽然看着简单但能节省大量资源。最重要的是学会“够用就好” (Good Enough)，快速原型验证 (Pre-visualization) 比追求完美更重要，先把数据存好再看能不能省掉一帧，这比瞎折腾强多了。

最后聊聊身份转换的心路历程。在 AAA (AAA) 大厂虽然人多势众、福利好，但出了事容易互相甩锅，团队氛围既是保护伞也是压力源。一旦跳出来自己干，虽然时间地点自由，但所有烂摊子都得自己扛，还得时刻面对冒充者综合征 (Imposter Syndrome)。这时候不能光顾着写代码，营销自己和心态建设更是关键。听反馈时别觉得自己被否定了，那是让你进步。行业现状也不容忽视，咱们特效组还是在用旧技术，太封闭，得提倡通用工具，少点保密多交流，毕竟大家都是搞游戏的，抱团取暖才能少踩坑，大家一起努力把这行的门槛降低才是正道。

#Battlefield_1 #Battlefield_4 #Doom

## The Great Divide: Unique Visuals and Deterministic Gameplay in 'Deserts of Kharak'
- **Speaker:** Yossarian King (Blackbird Interactive Inc.)
- **Duration:** 59 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024242
- **Slide Page:** https://www.gdcvault.com/play/1024571
- **Custom ID:** 1024242

### Overview
'Homeworld: Deserts of Kharak' is a classic RTS game with hundreds of heavily armed vehicles battling it out across a hostile landscape. The presentation layer uses Unity graphics and input, but is fully decoupled from the game simulation, which runs on a separate C# thread. Deterministic simulation keeps multiplayer synchronized, as game state changes only in response to low bandwidth command inputs that are shared across the network. Audiovisual presentation reacts to events and state changes output by the simulation. Vehicles are simulated in 2D using fixed point math and augmented with "aesthetic physics" in the 3D presentation layer. Large desert environments are authored as sculpted meshes painted with a multi-layered deferred decal system. Off-the-shelf and custom particle systems, shaders, post-effects and lighting are combined to achieve uniquely stylized visuals. Performance was optimized with a cache-friendly entity system, robust LOD techniques, and various extreme measures to avoid C# garbage collection.

### Content Summary
[TLDR]
多人 RTS 核心在于隔离模拟与表现层，用定点数消除分歧，C# 优化重在严控内存分配而非单纯加速。

[Background]
很多老哥觉得 Unity 搞不了重负载联机 RTS，怕性能崩、同步乱。主讲人黑鸟互动 CTO 分享实战经验，展示如何用这套架构在 Unity+C# 环境下做出流畅的大规模战斗体验。

[Recaps]
主讲的核心思想是“大分割”，把游戏逻辑（模拟层 (Simulation)）和画面表现（表现层 (Presentation)）彻底剥离开。模拟层就是纯 C#代码，不依赖任何 Unity 引擎接口，只负责计算状态；表现层全靠 Unity 搞定渲染、音效和特效。两边通过命令层连接，就像 MVC 模式那样，模拟更新内部数据，推送给表现层去显示像素和声音。这样不仅逻辑干净，还方便跨平台调试，避免互相牵制。

画面方面，为了在大沙漠地图里省资源又好看，团队用了延迟贴花 (Deferred Decals) 技术。底层的网格高度图其实很粗糙，全靠画上去的“贴纸”来增加沙丘起伏、岩层纹理等细节。这比堆多边形省钱多了，而且还能动态生成爆炸痕迹或弹孔，让画面更生动。同时车辆运动虽然底层是 2D 坐标移动，但物理表现层会加上车轮动画和悬浮效果，实现所谓的“美学物理”，保证手感丰富但不影响底层算法规则。

联机同步是 RTS 的重灾区，为了解决带宽和同步问题，他们采用了确定性的锁步模式。所有电脑运行同样的程序，分发同样的操作指令，就能得到相同的结果。最头疼的是浮点数 (Floating Point Numbers) 在不同 CPU 架构下运算结果可能微差导致不同步，所以他们把所有数学运算都换成了定点数 (Fixed Point Numbers)。另外，为了避免网络卡顿，他们还设计了自适应调度机制，只要最终能跟上节奏就行，不用死板地对齐每一帧。

最后是 C# 的性能优化，重点不在算法快慢，而在内存分配。Unity 自带的垃圾回收机制 (Garbage Collection) 一旦触发就会卡顿，所以要尽量避免新创建对象。他们大量使用了对象池 (Object Pools) 来复用物体，提前分配好列表容量，甚至自己写定制的数据结构来替换标准集合类。还要特别注意装箱和拆箱 (Boxing/Unboxing)，尽量用结构体而不是类，减少不必要的内存拷贝和堆内存压力，这样才能在低端机上稳住帧数。

## The Illusion of Motion: Making Magic with Textures in the Vertex Shader
- **Speaker:** Mario Palmero (Tequila Works)
- **Duration:** 31 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024032
- **Slide Page:** https://www.gdcvault.com/play/1024616
- **Custom ID:** 1024032

### Overview
Not much is being done with textures in the vertex shader. The usage so far has been limited and purely experimental. There are some use cases in video games but Mario believes there should be a bigger place for it in this medium. He will present usage of textures in vertex shader as cheaper alternative solutions to established methods. He will also present a new technique in the animation pipeline that bypasses the CPU and enables him to increase the bone count dramatically.

### Content Summary
[TLDR]
利用顶点着色器采样纹理做数据容器，GPU 直算模拟与动画，摆脱 CPU 瓶颈与繁琐管线。

[Background]
面对海量粒子或物理运算，CPU 容易过载，Alembic 又太重。作者分享了 Vertex Shader (顶点着色器) 读纹理的骚操作，适合想深挖 GPU 潜力、优化工作流的技术团队。

[Recaps]
核心思想其实挺简单，Vertex Shader (顶点着色器) 不只是用来改顶点位置的，它还能便宜地直接读取纹理数据。以前艺术家布置关卡时，得一个个模型去贴合地形，非常累。现在直接用 Height Map (高度图)，程序一查就知道偏移量，雨水滴落碰到港口会自动重置，地面凹凸不平能让资产完美贴合。这招最大的好处就是省去了 CPU 创建缓冲区、跟 GPU 通信的麻烦，纯纹理驱动，效率极高。

进阶玩法就是把动画本身烤到纹理里。像是手部动作或烟雾扩散，直接把 XYZ 坐标转成 RGB 存进像素点，烟雾上升时按顺序读取上一帧的数据就能做出动态效果。粒子系统更绝，纹理的一行代表一帧，一列代表一个粒子，配合 Bilinear Filtering (双线性过滤) 做插值，哪怕删掉一半帧数也不容易察觉。如果是刚性物体，千万别暴力存所有顶点，用 Pivot Points (支点) 分组，只记录支点的位置和旋转，比用 Vertex Cache (顶点缓存) 存储单个顶点要省空间得多。

终极方案是把 Bone Transformation (骨骼变换) 也做成纹理。把骨骼的位置、旋转存进两张图里，权重信息放 Extra UV Channels，索引放 Vertex Color。这样 CPU 完全不需要感知 GPU 里的细节，数据还是标准的图片格式，方便分享和传输。但这玩意儿有坑，首先是精度丢失严重，其次是调试难度地狱级，必须自己造工具链。跟 Alembic 不冲突，前者是文件交换格式，这是运行时数据，灵感来源于 John Carmack 提到的硬件压缩缺失问题，适合作为特定项目的优化手段，别盲目照搬。

## Technical Artist Bootcamp: Tech Art for Educators
- **Speaker:** William Crosbie, Mary Denman, Barak Moshe, Matt Oztalay, Chris Roda (Raritan Valley Community College, EA Tiburon, Lucasfilm, Certain Affinity, Florida Interactive Entertainment Academy)
- **Duration:** 61 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024283
- **Slide Page:** https://www.gdcvault.com/play/1024615
- **Custom ID:** 1024283

### Overview


### Content Summary
[TLDR]
解决业界招不到年轻技术美术的痛点，强调教育应重跨学科协作与原理，而非死扣特定软件工具。

[Background]
许多高校不懂咋培养技术美术，导致企业招人难。这次 GDC 座谈由 EA、卢卡斯影业等行业前辈分享经验，告诉老师们如何识别和培养这类稀缺人才。

[Recaps]
首先，大家得搞清楚技术美术 (Technical Artist) 到底是干啥的。简单说，这帮人是项目的“胶水”，负责打通美术、程序和制作之间的隔阂，专门解决没人愿意管或者没人能管的硬骨头。找这种人不用看简历，要看谁眼里有活，爱主动帮同学修 Bug 或优化流程，而且对啥都好奇，不怵未知领域。

在学校咋教也是个关键。单纯上课行不通，得搞项目制学习 (Project-based Learning)。把学艺术的、写代码的和做管理的拉到一组，真刀真枪地跑个完整的生产周期。教的时候别死盯着某个具体软件，因为工具几年就换代了，得教底层逻辑和数学基础，比如着色器 (Shaders) 背后的算法，让学生学会“举一反三”。同时要注重管线 (Pipeline) 的搭建，让学生理解资产从创建到引擎落地的全过程，而不是孤立地做任务。

最后，毕业生能不能被公司看上，全看作品集 (Portfolio) 怎么秀。别光放成品图，得多记录你解决问题的过程，比如写博客吐槽调试经历。学校最好请业界大佬来给学生做点评，毕竟外人的反馈比老师更狠也更真实，能直接看到演示影片 (Demo Reel) 的问题。另外提醒一句，现在还得留意机器学习 (Machine Learning) 等新技能，别掉队，特别是针对计算机视觉 (Computer Vision) 这块需求正在增长。

程序化创作并非取巧捷径，而是通过节点与非破坏性管线将重复劳动自动化，最终实现团队生产力与内容规模的质变。

### Content Summary
[TLDR]
别把模拟当炫技工具，它是用算力换人力的工业化捷径，能把复杂资产批量生产出来。

[Background]

[Recaps]
现在的游戏开发别总想着纯手工硬啃，得学会用**离线模拟 (Offline Simulations)** 这种算法来生成内容。核心就是算力换人力，硬件配置要看类型：粒子流体这种并行计算多的就上**图形处理器 (GPU)**，物理碎块这种线性计算强的得上**中央处理器 (CPU)**。大团队建议直接租**渲染农场 (Render Farm)** 分摊压力，小团队本地也得配好网带，否则传几个 G 的数据能把你卡死。

数据管线是重灾区，模拟结果只是中间数据，得保存多个迭代版本，推荐用**阿勒姆 (Alembic)** 来存取几何数据，支持单帧快速读取，避免每次改个颜色全量加载。**开放曝光 (OpenEXR)** 适合存 HDR 数据，别用损压缩格式的图。千万警惕**管线腐烂 (Pipeline Rot)**，场景节点命名要规范，不然后期维护像拆盲盒。

[TLDR]

最后强调几个坑爹的经验：别盲目照搬现实物理，记得降低骨骼质量比例；测试时多扔来扔去看看有没有穿模；最主要是得有耐心调参。物理不是魔法，稳定帧率是前提，同步数据还得靠预测算法兜底。总之，这套流程虽然开发周期长点，但能让玩家在互动中感受到那种真实的重量感和反应，比死板的关键帧强太多了。

到了玩法层面，程序 Son 把腿和胳膊当作独立的网格 (Mesh) 挂载上去，而非死板的骨骼延伸。利用射线检测地面高度来混合跑步动画，跑得快了就滑步，伸手抓物体则依靠动态的瞄准点 (Aim Points) 自动吸附，不需要每个手指都单独编程。打击反馈也很到位，落地和抓取时会向物理核心注入冲击波，让玩家真切感受到这坨肉球的重量感。

视觉效果由 Mikkel 把关，为防看起来像塑料肥皂，他采用了特殊的法线贴图 (Normal Mapping) 融合方案，关节处软边、指尖硬边。光照上用了伪高光技术配合鸡皮纹理，还加了简单的次表面散射 (Subsurface Scattering) 模拟肉质透光感。至于受伤后的淤青血渍，则是 CPU 统计刚体撞击数据后，通过着色器 (Shader) 实时绘制掩码生成的，彻底摆脱了繁琐的手动贴图。

## GPU-Based Run-Time Procedural Placement in 'Horizon: Zero Dawn'
- **Speaker:** Jaap van Muijden (Guerrilla Games)
- **Duration:** 47 分钟

### Overview
Jaap van Muijden from Guerrilla Games will describe the GPU based procedural placement system that dynamically creates the world of 'Horizon: Zero Dawn' around the player. Not limited to just rocks and trees, the procedural system assembles fully-fledged environments while the player walks through them, complete with sounds, effects, wildlife and game-play elements. ### Content Summary
[TLDR]
Guerrilla 用 GPU 实时密度计算技术，实现了美术可控的高品质大规模自然场景生成，平衡了效率与质量。

[Background]
《杀戮地带》系列靠手工打磨环境，品质高但费时。转到《地平线》这种开放大世界后，传统手工不行，旧式程序化又太呆板，离线烘焙效率低。为了保持高美术标准还能快速迭代，Guerrilla 决定把整套生成逻辑搬到 GPU 上实时跑，解决性能和质量的矛盾。

[Recaps]
大伙儿都知道以前的过程化放置 (Procedural Placement) 要么看着假，要么改起来麻烦。这团队直接推翻了传统做法，没选离线烘焙 (Offline Baking)，而是搞了个实时系统 (Real-time System)。核心思路是用基于密度的系统 (Density-based System) 替代直接摆放，美术不用盯着每个点位，只负责产出一张密度图 (Density Map)，后台算法自动根据这张图把植物岩石离散化 (Discretization) 成物体。这样做不仅省了磁盘空间，还能像流媒体一样随玩家移动动态更新，大大降低了带宽压力。

美术的工作流特别灵活，核心概念叫生态位 (Ecotope)，简单理解就是不同环境的规则包。基础数据靠世界数据贴图 (World Data Maps) 存储，包括高度、道路、水流这些信息。最关键的是，所有逻辑都能在 GPU 管线 (GPU Pipeline) 里跑，美术在游戏内直接拿笔刷涂色，比如想砍出一片空地或把森林改成草原，改完贴图游戏里立马变样，根本不用重启工具。逻辑层也是节点化的，技术美术写好通用模块，普通美术照着配就行，完全保留了人工创作的感觉。

技术实现上最骚的操作是用了顺序抖动 (Order Dithering) 来做物体分布。这东西本来是图像处理的，被他们拿来把密度图转成具体的坐标点，既快又能避免排列过于整齐。为了防止玩家看出规律，他们还加了随机抖动 (Jitter) 算法打破秩序感。至于防碰撞，也没搞复杂的回读逻辑，而是规定相同占地面积的物体层叠加积，利用数值互补自然互斥。这套方案实测 GPU 占用也就 250 微秒左右，能扛住十万级的实时渲染量，对于只有几个人做资源的团队来说简直稳得一批。

- **Speaker:** Alex Fry (Electronic Arts)
- **Duration:** 55 分钟

### Overview
This talk presents the approach Frostbite took to add support for HDR displays. It will summarize Frostbite's previous post processing pipeline and what the issues were. Attendees will learn the decisions made to fix these issues, improve the color grading workflow and support high quality HDR and SDR output. This session will detail the display mapping used to implement the"grade once, output many" approach to targeting any display and why an ad-hoc approach as opposed to filmic tone mapping was chosen. ### Content Summary
[TLDR]
别靠色调映射 (Tone Mapping) 改色，最后统一做显示映射 (Display Mapping)，以宽色域为主兼容 SDR。

[Background]
Frostbite 工程组总结 HDR 落地经验。旧管线色调映射 (Tone Mapping) 会导致偏色且工作流割裂，难以适配新型显示器。本次分享如何在新架构下实现可控的色彩管理和高性能输出。

[Recaps]
老哥们都知道，以前的游戏渲染管线为了迁就老旧屏幕，经常早早就把高亮部分压进有限的亮度里，这叫色调映射 (Tone Mapping)。但这招有个致命伤，红绿蓝通道分别计算时，一旦某个通道先撞墙截断，整体颜色比例就乱了，导致高光处物体颜色乱飘，比如橙光变黄、蓝天发青。为了解决这个痛点，Frostbite 这次干脆重写代码，把核心的色彩处理留到最后一步，叫作显示映射 (Display Mapping)。

这一整套新流程的核心思想就是“全程宽体”。从渲染开始直到出图前，全部在 高动态范围 (HDR) 和 宽色域 (Color Gamut) 空间里干活，避免数据被压缩。美术在专业的调色软件里修好的图，通过查找表 (LUT) 直接喂给引擎，最后在扫描输出那一瞬间，引擎才根据你接的是什么屏幕，决定是压缩还是保留。这样一来，不仅解决了颜色失真，还实现了真正的 WYSIWYG（所见即所得），美术不需要为了适配电视反复折腾。

不过技术再好也不能牺牲性能，毕竟 60 帧是底线。Alex 提到他们在扫描着色器里做了大量优化，比如利用 AMD 显卡的 CMASK 元数据，只处理有内容的像素块，把 UI 合成开销压到了 0.5 毫秒以内。虽然新方案消除了早期的伪色效果，导致一些火球特效看起来太素，但他们后来加入了可配置的 色移 (Hue Shift) 开关，让艺术家能根据需要选择追求真实物理还是艺术风格。

最后总结一下避坑指南，千万别指望后期滤镜拯救贴图质量，真颜色必须提前埋在资源里。关于行业标准，虽然大家都在推 杜比视界 (Dolby_Vision) 或 HDR10，但别忘了绝大多数用户还在用普通 SDR 电视。最佳策略是以 HDR 作为母版输出，再针对性生成一份高质量的 SDR 副本，或者考虑接入电影工业编码系统 (ACES) 来统一管理多平台规范。

[TLDR]
别让“评审”变“人身攻击”，用共情搭建跨部门桥梁，把冲突变成加固团队关系的契机。

[Background]
游戏公司里，策划、美术、程序经常鸡同鸭讲，好点子卡在沟通这关直接流失了。作者用十年教学经验结合大厂经历，分享如何用心理技巧消除隔阂，适合所有想提升协作效率的制作人和团队成员看。

[Recaps]
咱们搞开发的都遇到过这种情况，领导或同事一句话下来，你觉得是在针对你个人。演讲者开场就区分了两个概念：**批评 (Criticize)** 其实是表面化的主观评判，而真正的 **评审 (Critique)** 应该是像解剖一样客观分析作品的运作机制。这两者最大的区别在于心态，前者往往为了发泄情绪，后者才是为了解决问题。作者强调，沟通的核心是 **共情 (Empathy)**，但这不代表单纯的同情，而是真的能站在对方立场上想象他的视角。比如很多时候程序员被视为“扫兴的人”，是因为我们只看到他们砍功能，却没理解他们是用系统思维帮你在避坑。承认这种认知偏差，是开启有效对话的第一步。

在正式开会之前，准备工作做得够细，后面就能省一半力气。千万别一上来就扔素材，最好有 Kickoff 会议明确分工，避免扯皮。作者分享了一个非常实用的“三步走”评审法：先客观描述这东西长啥样（比如那个水瓶有多高），再说你的主观感受（看着渴不渴），最后分析创作者的目标是否达成。另外，别光靠嘴聊，做一个 **灰盒 (Gray box)** 或者简单的 **原型 (Prototype)**，甚至画个纸面草图，能让跨部门沟通清晰很多。平时也要多维护关系，在非工作场合多给肯定，哪怕只是句简单的“做得不错”，等到真需要提尖锐意见时，地基打牢了对方才听得进去。

到了实际讨论环节，每个人都可以自带“主持人”属性来掌控节奏。面对 **跨学科沟通 (Communicating Across Disciplines)** 时的语言障碍，别急着反驳，先问几个“为什么”。比如那个机器人 HUD 的设计，先问问需求背后的具体限制是什么，往往能发现之前的理解全是错的。如果你听到了反对意见，试着复述对方的观点，确认自己没理解错，这叫“反思式沟通”。如果遇到根本性的分歧，不要陷入无休止的争吵，公司应该有个预设的流程来处理。就像受伤愈合的地方会更结实一样，经历过建设性争吵的团队，信任度反而会更高。

- **Speaker:** Matt Nava (Giant Squid Studios)

### Overview
In this talk, the creative director of 'ABZU', Matt Nava, will give insight into the unique art style of the game, and the processes that he and the team at Giant Squid developed to create it. ### Content Summary
[TLDR]

[Background]
水下场景计算量巨大，鱼群一多就卡顿，传统骨骼绑定太吃性能，且地形编辑迭代困难。这篇干货适合想要提升渲染效率或面临人手不足的开发组参考，提供了一套高性价比的工业落地方案。

[Recaps]
讲真，水下题材看着美，做起来简直是硬件杀手。Nava 大神分享了他怎么用 10 个人的小团队搞定《Abzu》这种大作级别的画面。核心思路就是：能偷懒绝不硬刚，能用软件算绝不让 CPU 跪着求饶。

海底植被和地形也是难点。海带叶片有三十多万片，同样靠实例化挂上简易绳索模拟水流动感。地形这块更骚，彻底抛弃传统的挖坑涂抹法，改用预制好的地形高度补丁 (Terrain Height Patches) 拼凑。就像搭积木一样，哪里不满意就旋转缩放哪个地块，还能顺便把岩石对齐带上，迭代速度快到飞起。

最后是氛围营造。本来想做复杂的光线追踪 (Ray Tracing) 或体积光，最后砍掉了。改用带可调节衰减曲线的线性雾，配合“剪影范围”暗化远景灯光，营造水深浑浊感。最绝的是用门户卡 (Portal Cards) 来引导玩家，本质是个深度渐变平面，既能提亮关键区域又不占用太多算力。整场下来全是实打实的优化技巧，值得大家回去抄作业。

最后是团队协作和产出管理。因为规则复杂，外包团队经常做错，厚厚的手册没人看得懂。团队直接把文档换成了一堆可视化图片文件夹，配上统一的笔刷预设，告诉人家照着做就行，不用理解背后的原理。同时他们联手灯光组定了一套关键色板，把环境色控制在一个特定范围内，保证角色能跳脱出来。James 最后吐槽，千万别把自己关在封闭的领域里，遇到难题多去问问隔壁组的专家，哪怕问出蠢问题，往往也是解决问题的捷径。

最后总结的经验就是，别指望机器能全包圆，得给程序化工具设好界碑。早期测试时发现生成的杂物经常挡路，或者光效太亮盖过了服药后的真实感，这都是反复调试出来的教训。现在的优化方向是通过设定不同街区规则（比如商业区多层密集，住宅区矮层带花园）来制造宏观差异，再用拱门和植被遮挡视线来强行拉回构图。这证明哪怕没有复杂的地形起伏，只要美术规则定得死死的，程序化也能做出很有味的复古世界。

最后还得提硬件坑。未来的战场不在分辨率而在 HDR，也就是 高动态范围显示 (High Dynamic Range Display/HDR)，它能呈现真正的明暗对比，比单纯堆像素值重要多了。至于 虚拟现实 (Virtual Reality/VR)，除了晕眩感问题，还得考虑人眼视野边缘不需要高精度，得配合 foveated rendering 优化性能。总之，不管怎么变，核心就是怎么把技术藏起来，让人看见的都是艺术表现力。

### Content Summary
[TLDR]
用数学公式忽悠眼睛，不用动引擎底层就能搞定衣服、水纹和冰块的逼真质感。

[Background]
演讲者 BioWare 资深技术美术认为，写 Shader 是把枯燥算式变成艺术的过程，比修工具更有成就感。本期重点分享怎么用节点编辑器快速上手进阶技法，适合不想深挖图形学底层但想提升画面表现的技术人员。

[Recaps]
老哥先定个调子，说 Shader (着色器) 就是拿算数造艺术品，虽然有时候还要处理 Bug 被喷，但效果好起来确实拉风。这次延续了去年的基础课，复习了三个经典思路：Distortion Shader 是通过滚动纹理的 UV 坐标 (UV Coordinates) 来模拟扭曲效果；Atlas Walk 是利用 Floor 函数让动画帧像爬楼梯一样一格格跳，避免平滑滚动时的穿帮；Projection Blend 则是利用世界空间方向直接投影材质，比如岩石上面自动长苔藓，省去了大量手动制作资产的活。

重点讲的是三种新材质，核心都是“以假乱真”。第一个是布料效果，难点在于布料边缘和面向摄像机时的高光不一样。这里引入了 Fresnel (菲涅尔) 概念，其实就是计算视线和表面法线的夹角关系。通过反向并调整指数，能让边缘更亮或中心更亮，配合噪点图就能模拟棉布或丝绸，比硬算 BRDF (双向反射分布函数) 快多了。第二个是水纹涟漪，之前如果用动画图存太多帧太占显存，现在改用数学生成的正弦波叠加掩膜。关键是会打包数据，把梯度、法线和时间偏移塞进 RGB 和 Alpha 通道里，一次性算出多圈波纹，还能加动态遮挡避免穿模。第三个是体积感冰块，既然模型没体积，那就骗过眼睛。利用光线穿过物体产生的 Transmission Vector (传输向量)，反向计算 Reflection Vector (反射向量)，再根据这个偏移 UV 坐标，看起来就像里面还有东西在晃动，加上噪点深度变化简直绝了。

最后还顺嘴提了下开发体验。虽然公司都在用类似 Frostbite 这种节点编辑器，但大神还是推荐大家看 HLSL 代码原理，毕竟节点只是代码的可视化。另外做特效时注意除以零的问题，有些平台可能当成 1 某些当 0，加个小量保底就行。想入门就去找书看或者研究下《CG Tutorial》，多动手撸码才是硬道理。

- **Speaker:** Mary Cassin (Google)
- **Duration:** 32 分钟
- **Category:** Visual Arts
- **Video Page:** https://www.gdcvault.com/play/1024280

### Content Summary

做 VR 开发千万别光盯着画质，把舒适度、帧率稳定性和用户体验放在第一位，才能做出让人不晕还上头的作品。

[Background]
VR 开发者常面临眩晕劝退和性能跑不动的瓶颈，尤其是移动端限制更严。作为谷歌 Daydream 团队的技术美术，作者总结了如何平衡生理舒适与硬件性能的高效工作流和避坑经验。

[Recaps]
咱得先把硬件底数摸清楚。现在市面上的头戴式显示器 (Head-mounted displays) 基本分两拨：一类是得连台式机的主机版，支持六自由度 (six degrees of freedom)，这玩意儿能让你在房间里随便走、蹲起、转身，沉浸感没得说，但被线拴着也限制了场景；另一类是手机塞进去就能跑的三自由度 (three degrees of freedom)，像 Cardboard 这种，虽然只能转头不能走路，但胜在随时随地能掏出来玩，不过手机性能有限，发热和渲染都得小心伺候。

做虚拟体验最大的痛点就是别让玩家难受呕吐。视觉上要注意会聚 (convergence)，别让视线总盯着太近的物体，核心的交互区建议放在正前方 30 度视场角 (Field of view) 范围内，这样最安全，周围装饰东西可以放宽到 70 度。移动方式要稳，尽量线性匀速前进，别搞随机晃动，地平线得保持平稳，不然大脑判断不了状态。性能方面帧率 (frame rate) 是底线，手机至少 60 帧，PC 端尽量奔着 90 帧去，一旦画面更新跟不上头动，那感觉就像在吐之前还要吐一样。

心理安全感这块容易被忽略，新手容易犯错误。别把人悬空扔在大白墙中间，或者站在悬崖边上吓唬人家，除非你是想做恐怖游戏。得给脚下留个“地”，弄点地标参考物，不然用户会觉得自己在飘或者迷路，完全没法专注你的交互。工作流上别死磕静态效果图，直接拿方块和球体搭个体积布局 (volumetric layout) 进引擎测试，赶紧拉人来体验，听着他们的吐槽迭代，这种“暴力测试”比闷头憋大招效率高得多。

最后是硬核优化技巧。手机端环境别用复杂实时渲染，可以用全向立体图像 (Omnidirectional Stereo Image / ODS)，本质是把 360 全景照片拆成左右眼立体图贴在球面上，既省算力又逼真，但要注意物体比例不能乱调，否则会像微缩玩具。UI 设计记得在 VR 里亲手量距离，字体要够清晰，着色器 (Shader) 尽量简单，别整花哨特效，把算力留给核心内容。记住，技术美术 (Technical Artist) 不是只会画图，而是解决性能与体验的平衡问题，这套思路放在 AR 或者其他项目上也通用。

[Background]
面对海量植被和动态物体，传统骨骼绑定开销太大。Naughty Dog 开发者分享他们在《神秘海域 4》中如何把顶点着色器 (Vertex Shader) 当成通用工具，用数据存算替代物理模拟，大幅降低性能消耗，让环境更有生命力。

[Recaps]
这次演讲的核心其实就一个字：变废为宝。大家通常认为顶点着色器只是用来变换模型的，但在《神秘海域 4》里，他们把它当成了数据容器。最典型的例子就是植被风动系统，他们没搞复杂的骨骼 hierarchy，而是直接把叶子的“旋转中心点”位置数据填入**顶点颜色 (Vertex Color)** 里，Shader 读取坐标直接控制弯曲。这样做的好处是几万个植物实例不需要额外的骨骼开销，性能几乎可以忽略不计。不过要注意，叶子动了，光照反射也得跟着动，所以务必同步更新**法线 (Normal)**，否则高光不跟着转，看着特别假。

为了增强环境互动性，Shader 还得解决“没记忆”的痛点。因为 Shader 每一帧都是独立的，踩过的草如果没留下状态，一转眼就恢复原状了。他们的解法是一张动态跟随主角的**渲染目标 (Render Target)**，相当于给地面盖了一层隐形的记录布。玩家或 NPC 走过时，粒子在这层上写字，草就被压低了；车子压过时也能刷层印记。头发和衣物逻辑类似，因为角色**蒙皮 (Skinning)** 后局部空间会乱，无法直接使用固定的旋转点，他们改用**顶点颜色 (Vertex Color)** 存储方向矢量和**父级顶点 ID**，成功实现了风吹乱发的效果。甚至连衣服褶皱受风变平这种细节，也可以通过 Shader 里的**变形目标 (Morph Target)** 混合来实现。

这套技术的上限比想象中高。比如车身撞击凹陷，他们把受损后的几何形状数据拆解，一部分方向信息存一组颜色通道，幅度存另一组，配合撞击时的粒子反馈，实现低成本的车损表现。性能方面确实惊艳，一万多实例的动态模型只占 1ms GPU 时间。但也有限制，比如每次 Pass（阴影、光照）都要重算，累积成本会变高，且 Shader 本身不支持持久化状态。对于开发者来说，遇到动画问题别总往骨骼或复杂物理上想，有时候换个思维，利用顶点处理这种骚操作，能以极小的代价换取巨大的视觉回报，尤其是在移动端或主机优化受限的场景下，这种“骗眼球”的方案简直太香了。

这么干最大的红利就是省预算。以前为了覆盖不同角度和大小，可能需要做几十个甚至上百套类似的动作，还得靠动画混合 (Animation Blending) 来过渡，累死人还不一定自然。现在只用几套基础动画配合扭曲点，运行时 (Runtime) 下动态修正，连 AI 小怪那种到处乱跳的行为也能搞定。而且程序同事还发现，因为不需要同时评估好几个混合动作，性能反而更好了。不仅资产少了，还能把省下来的人力去做更帅的风格化表现，这才是真正的四两拨千斤。

当然最大的坑在于 Coverage（覆盖度），也就是场景够不够多。如果每次都要新拍一套动作，成本太高。所以系统给了不少大招来节省素材。比如有可选 Slot（Optional Slots），有些动作缺个人也不影响演；还有延迟加入（Late Join），中途跑过来的人也能顺手参与；甚至支持镜像翻转（Mirroring），左右对称的动作复制一份就能用。另外还能自动微调角色站位（Alignment），哪怕位置差一点点，系统会推你一把让你接上招。这些功能结合起来，能让有限的动作库撑起更多情况，大大降低了开发成本。

[Recaps]

技术实现上，图层 (Layer) 系统必须用好，大动作归一层，细微的抖动归另一层，修改手感不伤筋骨。面部口型同步 (Lip Sync) 别死磕每一个音素，用几个标准形态组合摆动就行。遇到导入游戏的 BUG，先别找程序吵架，自己查查是不是骨骼节点 (Bone Node) 或地面节点 (Ground Node) 冲突了。最后一定要进引擎实测，多问自己一句：这手感舒服吗？这才是检验动画好坏的唯一标准。

这演讲其实就是个定心丸，告诉大家别把第一人称动画 (First-person animation) 当苦力活干。核心就一条：玩法优先 (Gameplay first)。玩家拿着枪怼着脸呢，动画再花哨也不能挡住视线或者干扰操作。得给足反馈，让玩家觉得拳拳到肉，但又不能太复杂。因为用的是锁定相机 (Locked-off camera)，这其实是福利，不用像 TPS 那样担心全身协调，但责任更重，毕竟全是你的戏份。

最后就是怎么整出角色味儿。跟第三人称搭档定好“黄金姿势”，比如寡妇师的枪长啥样才看着顺眼。为了省事儿，看不见的地方随便搓，比如天使的法杖握姿直接平移骨头就行。瞄准动作用弹簧物理 (Spring-based) 模拟性格，麦克雷紧绷，路霸松垮。打击感全靠夸张拉伸和瞬回，比如开火瞬间枪管拉长再秒缩，这种极端帧虽然不写实但爽。总之，只要能藏住漏洞，你就放开了整。

这招他在几部大作里都验证过了。从《黑道圣徒 2》开始他就意识到，如果只按日常方式演，做出来的效果会很假。到了《混乱特工》这种需要扮演多个不同体型的角色时，这套理论特别好用。哪怕你是矮个子演巨人，只要找到了那个结构性的发力点，就能假装自己有三百磅重。甚至有一次让他一个人演完战斗场面，对手全是自己的分身，他全靠调整身体基座来实现无缝衔接，不用替身也能打出大片感。

除了技术硬实力，沟通也是重头戏。他建议导演们别太含蓄，直接告诉演员想要什么，别指望对方猜谜。同时演员自己也得多做功课，拿着概念图和声音参考来找角色灵魂。最重要的是别过度思考 (Overthinking)，一旦你发现自己技术在刻意控制，那就假了。只有把技术练成下意识反应，才能在镜头前“活”过来，这才是行业顶尖玩家该有的水平。

### Overview


### Content Summary
[TLDR]
动画师别被“游戏”或“电影”标签框住，核心是练好手艺，根据项目流程灵活适应才是王道。

[Background]
演讲人混迹影视和游界多年，发现太多学校和学生把动画师割裂开。其实不管在哪行当，表演的本质没区别，区别在于流程和约束。这篇总结适合想理清职业方向的新人，或者在跨行业时迷茫的老手参考。

[Recaps]
核心观点特简单：动画这门手艺本身真不分三六九等，不管是做 **Feature Animation（传统电影动画）** 还是做 **Game Animation（游戏动画）**，底层逻辑都是表演。现在太多学院派把动画师割裂成“游戏动画师”或“电影动画师”，其实换个环境也就是个新流程的学习成本。你得先把自己当成最普通的动画师，活儿练到极致了，再去适应不同平台的坑。比如从特效公司跳槽去电影厂，或者反过来，**爬坡期 (Ramp-up Time)** 其实都差不多，关键是看你怎么适配那个项目的需求，而不是死守着某个标签。

影视制作里的坑多且深，特别是特效这块。比如在《猩球崛起》里，因为现场实拍时的失误，导致特效团队得在无物理依据的情况下强行让猩猩扔人，还得处理演员被单根吊索拉飞的旋转，简直噩梦。这说明了前期规划的重要性。再看 **Feature Animation（传统电影动画）**，虽然给了自由度高些的空间，能改镜头长度来配合表演，但也容易翻车。像《驯龙高手》里，动画师想突出眼神戏，结果后期 **特效部门 (Effects Department)** 把船移走导致焦点没了，或者把动效删减过度，导致节奏全崩。这行特别讲究跟后期人员磨嘴皮子，不然你的意图全会被覆盖。

到了游戏行业，规矩就完全变了，主要受限于 Technical Design（技术设计）。这里没有现成的 **实景底片 (Live-action Plate)** 给你借，全是技术文档定死的参数，比如动作多少帧、预瞄多久、收招要停几秒。你得保证动作从玩家视角的各个角度看着都顺溜，不能像电影那样靠固定机位或剪辑掩饰破绽。而且得跟 **骨骼绑定 (Rigging)** 搞好关系，游戏迭代快，经常拿着半成品架子干活，甚至要为了演示提前修好只露半边的模型。最后就是复用性，做得好一个动作能在宣传片和实机里通用，这才是游戏动画的大忌与大爱，一切为了 **Gameplay（游戏玩法）** 服务。

[Background]
《茶杯头》主创揭秘项目耗时两年的深层原因，主张全手绘与实景配乐是核心壁垒。适合追求复古美学与独特交互体验的独立游戏开发者参考，学习如何平衡效率与艺术质量。

[Recaps]
老铁们听好了，这游戏最核心的竞争力就是它的美术路子。设计组死磕 1930 年代的“橡皮管风格 (Rubber Hose)”，简单来说就是那时候的卡通人物肢体像管子一样软，随便拉扯都行，不用搞那些复杂的肌肉纹理。但这规矩看着简单，实操起来特挑人，你得保证角色无论怎么转动都能看，不能像现在有些游戏那样侧面好看正面崩。所以做概念的时候就得提前算好账，别整那些花里胡哨的细节，比如给角色戴个船身帽子，转起来就容易穿模，不然动起画来全是坑，还得重画，累死人。

再看动画怎么整，既然选择了纸笔这条路，前期规划就得够狠。讲个实例，做海妖女角色的“待机动画 (Idle)”循环，作者先拿蓝铅笔画“缩略草图 (Thumbnail)”，甚至自己上手表演一下找节奏，确认动态逻辑通顺了才往正片上推。这里面有个门道叫“预备动作 (Antic)"，就像敌人砸下来前先缩回去，这一下不仅是为了帅，更是为了让玩家看清哪里该躲。等草图定住后，才进入精细描线和上色，这流程虽然费纸费眼，但做出来的东西确实是有魂儿的，比冷冰冰的 CGI 更有味道。

最后说说为啥非得走这条弯路。有人可能会问，为啥不直接数字化？其实这是为了卡住游戏的灵魂。卡通逻辑不守物理法则，主角能从肚皮里喷虫子也能顶天立地，这种自由度在现代引擎里很难做出来。而且现场爵士乐、真水彩背景加上纯手工动画，这种味儿是用 MIDI 合成器和 PS 滤镜调不出来的。团队觉得就算做得慢点，也得保住这份手作的“体温”，这样才能让玩家真正回到那个疯狂的年代去玩耍，这也是他们不愿妥协的根本原因。

小团队做游戏最怕什么？怕的就是活多钱少人还缺。Phoenix Labs 这帮老兄弟本来都在大厂商混过，出来单干做《达姆》，就一个硬指标：人少还得把活儿干漂亮。核心思路就是不跟传统流程硬刚，而是换个玩法。比如动作捕捉 (Motion Capture)，别总指望外包或昂贵的大棚，他们干脆自费买了套 OptiTrack 设备。这玩意儿虽是一次性投入，但迭代起来是真香，一天能拍几轮新招式，比等外传省钱省时，算下来几个月就回本了。

真正的痛点还是那些大家伙“巨兽”(Behemoth) 的动作。人形动捕直接套在四足生物身上根本行不通，Simon 琢磨出一套“质心”方案。简单讲就是把人的动捕数据拆解成一堆位置点，而不是死板的关节连线，重新映射到怪物的骨骼上。哪怕解剖结构不一样，只要重心和大致的节奏对了，后续微调就快得多。再加上“类属”(Genus) 系统设计，一套骨骼套用不同模型，改改配色材质就能出新怪，动画资源复用率直接拉满，大大减少重复劳动。

技术细节上还有几招狠的。地形适应全靠引擎里的 Ikinema 反向运动学 (Inverse Kinematics) 插件，一脚踩上去自动调整脚爪贴合坡面，不用存几十种跑步姿态；尾巴这种麻烦东西，直接在 Maya 里进行物理模拟 (Physics Simulation) 再烘焙回骨架，省掉了大量逐帧手调时间。外包也没当冤大头，找的是合作伙伴而非供应商，像内部同事一样实时沟通。最后强调一点，动捕不是只为了写实，把它当成可编辑的数据曲线，配合分层修改，小团队也能跑出 AAA 级的流畅度。

## A New Dimension to 'Below': Personal Discovery and Adaptation
- **Speaker:** Dan Cox (Capybara Games)
- **Duration:** 29 分钟
- **Category:** Visual Arts

### Overview
Translating great art from 2D to 3D can be a difficult, combine that with a complex pipeline and ingrained notions of how content should be made and that work becomes even more challenging. In this talk Dan Cox of Capybara Games covers the techniques they used to bring 'Below' to form a mostly 2D game into the realm of 3D and how to adapt and change to find happiness and success.

### Content Summary
[TLDR]
小团队把 3D 硬塞进手绘 2D 世界，通过拥抱混乱流程和定制工具，让美术风格独树一帜。

[Background]
主讲人丹·约翰·考克斯分享了小团队如何在没有成熟编辑器支持下，将 3D 角色融入手绘 2D 背景的实战经验。重点解决无编辑器的痛点和风格统一问题，适合关注美术管线优化的同行。

[Recaps]
先把画风讲清楚。这游戏主打就是 2D 背景加 3D 人物，背景全是手绘画出来的光影，也就是“绘画法线 (Hand-painted Normals)"。最绝的是视角，参考了塞尔达那种顶视跟侧视混合的“斜向透视 (Skew)"，人物得对着镜头偏一点，否则容易穿模卡死，但这数学计算挺变态，还得防止物体互相遮挡。背景虽然是平面的，为了光照效果还得手动抠出明暗关系，工作量极大，但这正是他们想要的独特感觉。

再聊聊工作流程有多头大。刚进去的时候根本没实时编辑器 (In-game Editor)，改个模型得去 Maya 建好，批处理编译，写 Lua 代码，再跑进游戏测试，一步错全得重来。而且 Maya 里的视图跟游戏里不一样，改着改着就找不到北了，连阴影都对不上，这种折磨谁懂啊。而且程序化生成 (Procedurally Generated) 的地牢有时候结构不合理，只能人工去手雕大块区域来修正，效率低但效果好。

怎么破局呢？一是自己造轮子，搞出了 In-game 编辑器能直接挪东西、调灯光，省了好多编译时间。二是省点纹理资源，不用搞复杂的纹理图集 (Texture Atlas)，直接用顶点颜色 (Vertex Colors) 加渐变模拟手绘效果，墙面上随便给点 NGON (N-gons) 只要不旋转看着也平整。三是盯着像素看，毕竟角色在屏幕上就那么大点，太细的细节开启抗锯齿 (Anti-aliasing) 后还是会闪烁，干脆简化造型变成"3D 像素画”。

最后心态得摆正。小团队虽然穷，但是乐观。别觉得自己是个打杂的建模，有时候顺手帮策划做做设计甚至搞搞 Excel 表，反而更有成就感。演讲者还提到，偶尔的挫败感其实能促进创造力，别把自己框死，有时候“蠢办法”加上一点点光，反而能做出独特的东西。他还给新来的同事录视频教流程，减少沟通成本，确保大家都能快速上手资产 (Assets)。

### Overview
'Bound' is a game that features a contemporary dancer in a procedural world inspired by demoscene and modern art movements. It is also an emotional game that deeply resonates within the players that share similar life experiences as the main character.

### Content Summary
[TLDR]
核心是用数学算法构建视觉世界，结合专业舞蹈动作捕捉来传递家庭议题的情感共鸣。

[Background]
波兰小厂 Plastik 从 Demo 圈起家，这次想跳出纯炫技，参考《Journey》做一个有家庭温情和故事深度的游戏。主要分享他们如何平衡技术实现与情感表达，以及怎么通过“玩命”测试来打磨情绪体验。

[Recaps]
这帮波兰老哥有个怪癖，每个项目都重新搓一套 `自定义引擎 (Custom Engine)`。为了把画面做得既有几何美感又流畅，他们没上物理模拟，而是直接用 `数学算法 (Mathematics)` 控制方块消隐和位移。视觉上受 `至上主义 (Suprematism)` 影响，甚至直接把蒙德里安的色块和美术馆结构搬进游戏里。为了让那些漂浮的碎片更丰富，他们还搞了个 `程序化贴花 (Procedural Decals)` 系统，把艺术品投影在移动的碎块上，既省资源又有艺术感。

动作方面更是折腾得厉害。起初是手动 `关键帧动画 (Keyframe Animation)`，结果被反馈“像个没感情的机器人”。后来老大直接去学芭蕾、体操和花样滑冰，最后请了专业编舞师来做 `动作捕捉 (Motion Capture)`。整个游戏的跑跳甚至过场全替换成了动捕数据，连手写的动画系统都尽量简化，就是为了保证动作看起来既丝滑又充满人的情感张力。

设计上他们踩过不少坑，早期照搬 Demo 圈习惯不做 `游戏测试 (Play Testing)`，结果发现观众根本看不懂情绪。后来彻底改变，找单独的房间给玩家，避免现场干扰破坏沉浸感。虽然导致了玩家两极分化，但也筛选出了真正能共情的受众。在 `虚拟现实 (Virtual Reality)` 模式下，摄像机离角色极近，这种身临其境的“在场感”让玩家觉得像是在看一场私人演出，甚至产生了某种宗教般的沉浸体验，证明了好内容确实能跨越硬件限制。
