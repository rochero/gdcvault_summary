## Online Game Technology Summit: Quasar, Brightest in the Galaxy: Expanding 'EVE Online's' Server Potential with gRPC
- **Speaker:** Nicholas Herring (CCP Games)
- **Duration:** 50 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027755
- **Slide Page:** https://www.gdcvault.com/play/1027663
- **Custom ID:** 1027755

### Overview
After 18 years of live service development, CCP Games is utilizing new technology to improve its legendary spaceship MMO, EVE Online. By implementing gRPC architecture called "Quasar," CCP is creating in-game systems that operate separately from EVE's main server. These systems free up space on the game's main server to perform additional operations, allowing players to better interact with each other and their surroundings.nnThis session explores why CCP is using gRPC as a solution to enhance EVE Online's massive player battles, how gRPC works within EVE's server architecture, and the opportunities this independent domain service structure provides for server stability and maintenance.

### Content Summary
[TLDR]
EVE Online 通过 Quasar 项目完成架构重构，利用现代云技术攻克 20 年老项目的扩展瓶颈与开发效率难题。

[Background]
老牌宇宙 MMO《EVE Online》跑了 20 年，单服架构虽强但代码老化严重，改个功能都要停机维护。这次分享讲解如何用现代方案给老引擎换血，解决高并发和团队协同难题。

[Recaps]
EVE Online 是个硬核的**单服沙盒 (Single Shard)**，所有人都在一个大世界里玩，最大活动有 6000 多人同时开打。但维持这 20 年的老系统全是**Stackless Python (堆栈式 Python)** 和单体架构，最大的痛点就是**全局解释器锁 (Global Interpreter Lock)**，导致 Python 只能干一件活，性能上不去；而且数据库耦合太重，小改动可能导致全网瘫痪，开发团队还得凑齐了一起等每晚停机维护才能更新，效率极其低下。

为了解决这些问题，项目组启动了 Quasar 重构计划。他们没有直接重写老代码，而是先通过接口隔离，建立了**消息总线 (Message Bus)** 来消化老旧系统的流量。随后引入 **Kubernetes (K8s)** 进行容器化管理，将庞大系统拆解为独立的**领域服务 (Domain Services)**。在通信协议上，强制统一使用**Protobuf (协议缓冲区)** 定义数据结构，配合 **gRPC (远程过程调用框架)** 实现服务间的高效调用，这样既规范了接口，又避免了不同团队代码互相污染，让系统变得灵活可控。

除了架构拆分，他们还做了底层优化来绕过 Python 的性能瓶颈。比如在客户端传输大量战斗数据时，核心逻辑依然用 C++ 处理序列化，只传递结果给 Python 层，大幅减少了 CPU 占用。比技术更难的是文化转型，以前大家习惯了“能跑就行”，现在要求按标准流程开发、写测试。现在的核心经验是“别造轮子”，能用现成的开源方案就别自己发明，让 API 成为团队的边界，这样哪怕明天要改核心功能，也能在不停机的情况下安全迭代。

## Online Game Technology Summit: 10 Ways To Crash Your Server on Launch Day
- **Speaker:** Chris Cobb (Pragma Platform, Inc.)
- **Duration:** 58 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027752
- **Slide Page:** https://www.gdcvault.com/play/1027549
- **Custom ID:** 1027752

### Overview
We've all experienced launch days with crowds of angry players upset they are unable to play the game due to server crashes. This talk will provide practical guidance on what steps you can take to ensure a failed launch day.nnChris Cobb from Pragma will go through ten easy steps that cover everything from failed login queues to common microservice mistakes, to storing massive amounts of mostly useless data. He'll share stories from his experience at multiple game studios that demonstrate the importance of each of these techniques.

### Content Summary
[TLDR]
上线崩盘多半是作出来的？核心就是早点备队列、狂搞数据库分片，千万别拿新手上线去赌新鲜技术。

[Background]
很多开发者以为上线就完事了，结果首日体验差得能劝退 70% 的玩家。Chris Cobb 作为 Pragma 的 CTO，带着做过《英雄联盟》和《命运 2》的经验，专门来讲讲怎么避免把自己玩死，给大伙排排雷，全是实打实的血泪教训。

[Recaps]
想稳住上线第一天，准备工作必须提前。后台架构不是补丁，不能等最后几个月才塞进去，得多核心开发并行。关键是要建立真实的遥测 (telemetry) 监控体系，光看论坛抱怨太晚了，得有运营数据和玩家行为数据支撑。另外别单打独斗，找个踩过坑的老鸟帮忙，毕竟实战经验最值钱。

流量进来怎么接是个大问题。上线那天流量可能是平时十倍，所以一定要有登录队列 (login queue) 来排队。但队列做错了也是白搭，比如别先查账号库再进队，会直接连累主库崩溃。一定要加限流 (rate limiting) 和并发限制 (CCU limit)。压力测试 (load-test) 环境得跟生产环境一模一样，别偷懒配错参数，还得用代码管理基础设施 (infrastructure as code)，还要模拟真实玩家操作路径，别光跑个空接口就觉得自己行了。

架构设计上，数据库分片 (database sharding) 绝对是性价比最高的扩容方案，把数据拆细放多个库里，别用一个大号 Blob。微服务 (microservices) 也别贪多，几十个服务容易变成“分布式单体”，更难受。网络通信尽量别用轮询 (polling)，改用长连接 (long-lived socket) 推送消息。技术选型保守点，老的稳定技术比新花样靠谱。最后牢记不要重复自己 (DRY)，逻辑精简了才能少出 Bug，别让过度优化把架构搞得没法维护。

## Online Game Technology Summit: Observing Changes: Time-Dependent Social Network Visualization and Community Behavior Pattern Analysis
- **Speaker:** Yiheng Zhou (LeoCool Games)
- **Duration:** 29 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027944
- **Slide Page:** https://www.gdcvault.com/play/1027655
- **Custom ID:** 1027944

### Overview
The visualization of social network data has always faced the problem of being too complicated and lack of readability. This problem becomes even more acute when it comes to observing and analyzing how social networks evolve. The group explores visualization schemes and corresponding analysis methods for temporal social networks and analyzes the patterns of social behaviors of different players and groups in games. By distinguishing the different information densities of temporal social networks at the levels of groups and individuals, accordingly, they create highly readable visualization and analysis methods and analyze the actual data of a typical newly opened online game.

### Content Summary
[TLDR]
利用图模型与时间序列聚类技术，将动态社交关系数据化，帮助运营精准识别核心玩家并防范社群流失风险。

[Background]
很多做线上游戏的哥们都知道，光有玩法不够，还得有人聚堆儿玩。但传统数据分析像拍照片，只能看静态，没法看社交关系怎么随时间变。这篇演讲就是教大伙怎么用数学模型和算法，把这种“流动的”社交关系给量化出来，方便运营抓核心用户和防流失。

[Recaps]
首先得把游戏社交结构建模，最基础的就是把玩家或公会看成**节点 (Node)**，他们之间的互动关系就是**边 (Edge)**。这玩意儿分两种，两边平等的叫**无向图 (Undirected Graph)**，像并肩作战；一方邀请另一方就是有向的。关键是要加上**权重 (Weight)**，比如两人组队次数或交易金额，以此区分关系的亲疏远近。

再说具体的游戏类型。一类是大世界类，像**MMORPG(大型多人在线角色扮演游戏)**，地图大相遇随机，公会 (Guild) 绑定强，数据杂但归属感高。另一类是即时对战类，像**MOBA(多人在线战术竞技游戏)**，没大地图直接匹配，数据简单但群体归属模糊，通常是一盘散的，很难界定稳定的社会单元。

分析的时候得有套指标体系。比如**社交率 (Social Rate)**看活跃度，**聚类系数 (Clustering Coefficient)**看抱团程度，还有测贫富差距的**基尼系数 (Gini Coefficient)**，毕竟头部玩家一旦跑了，整个服务器生态就崩了。除了静态指标，还得用**动态社区发现 (Dynamic Community Discovery)** 算法，才能看清小团体是怎么生长或消亡的。

最后怎么展示这些变化？别搞成死板的报表。要把玩家行为按时间分类，不同颜色的点代表不同倾向：有的刚来就走，有的是新晋大佬，有的是万年核心。节点大小代表投资度，线条粗细代表互动强度。这么一画，谁在掉队、谁在维持生态一目了然，这才是给运营真正的大杀器。

## Online Game Technology Summit: 'Sky's' Journey to 1MM CCU: A Cloud Native Approach To Scaling
- **Speaker:** Kunal Lanjewar (thatgamecompany)
- **Duration:** 44 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027847
- **Slide Page:** https://www.gdcvault.com/play/1027676
- **Custom ID:** 1027847

### Overview
Sky: Children of the Light is a cross-platform free-to-play multiplayer social game from Thatgamecompany (Journey's Developer) that originally launched in 2019 on iOS Platform. Prior to launching on Android in 2020, developers were concerned with Sky's potential to exponentially scale overnight so they started to aggressively prioritize the scaling efforts.nnThis session dives deeper into scaling challenges and new backend architectural adoptions made by Sky's small online services team allowing Sky to reach its goals of 100MM+ downloads and 1MM CCU at peak.

### Content Summary
[TLDR]
小厂硬刚百万并发：TGC 如何用云原生架构把 Sky 单体后端拆成微服务稳住大服务器。
[Background]
《Sky》iOS 成功后安卓上线面临百万 CCU 挑战，单体架构和老旧代码难以支撑扩展，小团队如何在有限资源下完成后端彻底重构的技术实战总结。
[Recaps]
当初小团队接手《Sky》后，发现单体应用 (Monolithic application) 全是 Erlang (Erlang) 写的，业务逻辑塞进 PostgreSQL (PostgreSQL 数据库) 函数里，单机数据库一扛高负载就炸。特别是自研 C++ (C++) 游戏引擎太硬核，不支持分块传输，内存容易爆。再加上 CI/CD (持续集成与部署) 混乱，发布得跟游戏发版绑定，动不动就有人请假导致卡住。

于是他们决定搞云原生 (Cloud-native)，全面转向微服务 (Microservices)。用 Terraform (Terraform) 管理基础设施，环境隔离做到每一套都有独立 VPC (VPC 虚拟私有云)，代码通过 GitOps (Git 运维流程) 自动部署。核心逻辑转 Go (Golang) 语言，跑在 Kubernetes (Kubernetes 容器编排) 集群上，中间加个 Linkerd 做服务网格 (Service Mesh)。

数据一致性是大坑。他们用 CQRS (CQRS 模式) 模式，写入强一致，读取走只读副本接受最终一致性。跨库事务不用两阶段提交，改用基于 Kafka (Kafka) 事件的 Saga (Saga 模式) 模式，强调事件幂等性，保证最终成功。非关系型数据库 (NoSQL) MongoDB 用来分担压力。

最后为了可观测性，引入了 Prometheus (Prometheus) 抓指标，OpenTelemetry (OpenTelemetry) 做链路追踪。本地开发直接用 Telepresence 把电脑进程串进云端。虽然踩过事务回绕 (Transaction wraparound) 的雷，但这波架构升级让迭代速度起飞，稳稳抗住了 1M CCU (并发用户数) 的峰值流量。

## Online Game Technology Summit: Real-Time Anomaly Monitoring in Multiplayer Online Games
- **Speaker:** Lei Xia (Thunderfire UX)
- **Duration:** 52 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027938
- **Slide Page:** https://www.gdcvault.com/play/1027664
- **Custom ID:** 1027938

### Overview
Big data systems are increasingly pursuing real-time, as well as in the game field. The more real-time the data is, the more timely the decisions we can make. However, this also poses a higher challenge to our data accuracy. When there are abnormal data fluctuations, we need to immediately judge whether it is the abnormal behavior in the game or the abnormality in the data pipeline. In the development practice of ThunderFire UX, we have established a complete data exception monitoring system to monitor every aspect that may go wrong, whether it is the problem of the real-time system itself or the exception of the game service. Through our system, we can quickly troubleshoot the abnormal stage, so as to quickly evaluate the time taken for the system to return to normal. In this speech, in addition to showing the audience how to build this system, we will also show the audience how this system finds various exceptions in practice, such as exceptions in network transmission, exceptions in the task scheduling systems, and exceptions in-game service itself. By listening to this speech, both data engineers, data analysts, QA, SA, and game programmers can quickly apply the ideas of this system to their own game projects and quickly troubleshoot the problems in the game.

### Content Summary
[TLDR]
利用消息队列核心指标结合联机分析处理架构，快速区分游戏服务崩溃与数据记录错误，将异常定界从小时级缩短至分钟级。

[Background]
网易雷火 UX 团队痛陈游戏数据分析往往“马后炮”的痛点。本演讲为数据和运维同事提供实战指南，教大家如何利用消息队列指标，快速定位问题是服务器宕机还是数据记录异常，最大限度减少业务损失。

[Recaps]
首先得弄明白什么是异常。就像网易雷火之前在监测《永劫无间》时发现退款数据暴增，光看数字不行，还得结合活跃玩家曲线去比对。真正的异常是指偏离了常态的 时间序列数据 (Time Series Data)。我们不仅要知道出了事，更要搞清楚是啥原因。比如服务器维护会导致在线人数归零，这是正常的；但如果维护时数据还是一条直线，那反而可能是活动搞砸了。所以核心在于通过数据形态来反推基础设施或业务逻辑的问题。

接下来是核心大招，利用中间的 消息队列 (Message Queue) 来充当“交警”排查问题。我们重点关注三个指标： 主题延迟 (Topic Lag)、 消费速率 (Consumer Rate) 和 生产速率 (Producer Rate)。如果这三个指标显示生产和消费都接近零，那大概率是上游游戏服务挂掉了；如果是生产正常但消费降了，那就是下游处理卡住了。这就好比快递中转站，只要核对发货和收货的速度差，就能一眼看出是哪边堵车，彻底避免了扯皮。

当然也有更隐蔽的情况，就是队列指标全绿，但大屏数据就是不对劲。这时候就得动用高级货了，利用 联机分析处理 (OLAP) 数据库比如 Apache Kudu 和 Apache Impala 直接查原始日志。作者举过例子，如果登录数和在线数能对不上，那就是数据记录本身写错了。最后这套方法还能实战用在对比同品类游戏的实时留存率，或者盯着不同客户端版本的 FPS 帧率表现，一旦发现新版本导致卡顿比例飙升，立马就能通知开发修 bug，不用等用户投诉炸锅再行动。

## Online Game Technology Summit: From Development to Production: Building Game Servers for the Cloud
- **Speaker:** Harry Stevenson, Ben Burghaus (Electronic Arts, Electronic Arts)
- **Duration:** 51 分钟
- **Category:** Online Game Technology Summit
- **Video Page:** https://www.gdcvault.com/play/1027941
- **Slide Page:** 
- **Custom ID:** 1027941

### Overview
Exclusively running and testing game servers on developer's local machines during a game's development cycle can result in multiple issues when the time comes to deploy to production. This presentation explores how EA's Game Server Hosting Platform packages and deploys multiplayer game servers to cloud platforms earlier in the development cycle, through a set of tooling built to reduce risk. With features such as auto-containerization, configuration management, and deployment pools, studios who adopt this pipeline benefit from more rapid deployment iterations, faster defect discovery, and wider playtest availability before launching a production title.

### Content Summary
[TLDR]
EA 自建了一套云端托管平台，通过标准化和容器化技术，把游戏服务器部署全流程提前，实现开发与生产环境无缝衔接。

[Background]
EA 内部多个工作室使用不同引擎，导致服务器环境五花八门，配置管理混乱且部署效率低。分享方旨在通过统一云平台，解决跨团队协作难点，提升迭代速度并确保上线稳定性。

[Recaps]
这帮老哥的核心思路就是“先标准化，再自动化”。以前各家工作室的服务器简直是乱炖，日志格式、操作系统信号响应全都不一样，没法统一管。所以 EA 搞了套行业标准规范，还给 Frostbite (Frostbite) 和 Unreal Engine (Unreal Engine) 这两个主流引擎写了插件，强制新项目遵守规则。最关键的是他们搞了个通用包系统 (Universal Package Systems / UPS)，开发人员只要把编译好的二进制包扔上去，系统自动帮你们处理依赖、打包成容器镜像，彻底消除了环境不一致带来的脏活累活。

部署这块主要靠 Kubernetes (Kubernetes) 集群，但他们没直接裸奔，而是加了一层名叫 Watcher 的守护进程当“中间人”。这玩意儿负责读配置、拉环境变量、盯着进程死活，一旦服务器崩了或者数据异常，立马上传日志和崩溃文件到云端存储，并推送到 Slack (Slack) 群里报警。这设计挺鸡贼，根本不用改游戏本身的代码，哪怕是那种老旧项目也能无缝适配新架构，要是将来底层基础设施换了，只动 Watcher 那层逻辑就够了。

测试环节还有个骚操作叫部署池 (Deployment Pools)，简单讲就是个带容量限制的黑洞队列，旧的自动踢出去，新人完全不用操心清理资源的事儿。配合自动伸缩 (Auto Scaling) 机制，不管是根据缓冲区被动扩容，还是根据历史数据主动预测流量，都能灵活应对。现场演示用命令行工具 (CLI) 几秒钟就能拉起一个完整的遊戲集群，还能远程连进去测试网络，最后设置定时任务自动回收实例，这流程确实丝滑，避免了资源浪费。

最后的落脚点就是“零摩擦上线”。因为开发和测试阶段实际上都是在类似的生产环境里跑，等到正式发布那天基本上没啥 surprises。虽然现在主要给自家工作室提供“白手套”式的深度服务，但也留了 API 接口，未来还支持本地机直接构建部署，甚至按需自动创建区域集群，真想把游戏服务器当成云原生应用来养。
