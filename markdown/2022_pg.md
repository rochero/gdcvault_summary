## An Overview of the 'Diablo II: Resurrected' Renderer
- **Speaker:** Kevin Todisco (Blizzard Entertainment)
- **Duration:** 3300 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1028027
- **Slide Page:** https://www.gdcvault.com/play/1027558
- **Custom ID:** 1028027

### Overview
Building a new 3D renderer seems seldom heard of these days, with powerful engines like Unreal and Unity available to the public and indie scene. AAA developers typically rely upon pre-existing proprietary technology to drive their products forward, iterating on this technology to slowly adapt it to new industry trends and techniques. In this talk, Kevin will explain why the Diablo II Resurrected team chose to build a custom 3D renderer from the ground up and shed light on some of the key aspects of it, such as lighting, skin rendering, HDR color grading, and order-independent transparency. Come learn what went into giving Sanctuary a new look.

### Content Summary
[TLDR]
在老旧引擎上硬搓新渲染器，靠固定视角优势和拿来主义，在工期极限下实现画质与性能最佳平衡。

[Background]
为了保留原汁原味手感，暴雪决定在 20 年前原版引擎上硬搭新渲染管线，类似白手起家。面临工期紧、工具缺失及兼容 Switch 的压力，这篇分享对想做老 IP 重制或被迫造轮子的开发者很有参考价值。

[Recaps]
这次重制为了保住老玩家的感觉，干脆在 20 年前的原版引擎上硬造了个新渲染管线。为了赶工期，团队第一条铁律就是“快”，美术资源支持“实时热更新 (Live Updating)"。技术上选用了“前向 + 渲染器 (Forward Plus Renderer)"，这样写材质 Shader 特灵活，不用像延迟渲染那样受限。最狠的是完全没做“光照烘焙 (Light Baking)"，因为暗黑是程序化生成的关图，还有满屏法术特效需要动态发光。虽然听起来很疯，但配合固定机位，阴影系统反而简单得多了。

画面表现上，他们把色调处理 (Color Grading) 参考了《使命召唤》的思路，分两步走，保证艺术家看到的跟游戏里一模一样。为了处理满屏飘过的半透明技能，用了“顺序无关透明度 (Order-Independent Transparency)"而不是传统的排序，虽然后期折腾了不少优化带宽，但视觉效果确实到位。另外得益于固定视角和有限的视野范围，他们甚至能用预计算的光照辐射图来模拟大范围动态光效，省掉了复杂的级联阴影贴图开销。

最后总结几个血泪经验：千万别低估底层基础设施的价值，比如线程池和“作业系统 (Job System)"，没做好后期加进去就是灾难；做技术选型得贴合项目背景，别为了炫技乱上高深技术；还有就是要懂得利用既有优势，像这种固定视角就是个巨大的免费红利。如果再来一次，肯定一开始就上“多线程架构 (Multi-threaded Architecture)"和异步加载，别等到卡脖子了再动刀子，风险太大了。

## Architecting Jolt Physics for 'Horizon Forbidden West'
- **Speaker:** Jorrit Rouwe (Guerrilla Games)
- **Duration:** 3574 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1027891
- **Slide Page:** https://www.gdcvault.com/play/1027560
- **Custom ID:** 1027891

### Overview
For Horizon Forbidden West, Guerrilla Games switched from a commercial physics engine to Jolt Physics, an open-source physics engine that was born as a personal hobby project. By switching to this new engine, we saved memory, executable size and were able to double our simulation frequency while using less CPU time. This talk describes how we use a physics engine at Guerrilla, how our previous physics engine caused bottlenecks while streaming in data and while interacting with the multi-threaded game object update. Jolt was architected specifically to help solve these two problems and the talk explains two of the systems that made this possible.

### Content Summary
[TLDR]
通过无锁化设计重构物理引擎，消除锁竞争，将模拟频率稳定在 60Hz 并显著降低内存与卡顿风险。

[Background]
演讲者来自 Guerrilla Games，在为《地平线》开发时遭遇旧物理引擎的全局锁瓶颈，多线程下严重制约 CPU 性能，尤其是开放世界加载和背景任务交互时，被迫自研物理引擎以根治性能顽疾。

[Recaps]
先吐槽一下老毛病，以前做多线程游戏时，物理引擎这种全局系统通常得用 **互斥锁 (Mutex)** 保护，一旦多个线程同时访问，就会发生 **锁竞争 (Lock Contention)**。大家排着队等别人释放资源，导致开图、AI 寻路或者物体生成时经常卡顿，甚至影响整个 CPU 的并行效率。GDC 这位大神为了治这个病，自己从头造了一个物理引擎 Jolt。

核心解法主要靠两样神器。一是把 **粗检测 (Broad Phase)** 改造成了基于 **四叉树 (Quad Tree)** 的结构，利用 **SIMD (单指令多数据流)** 友好性动态调整边界框，避免修改时阻塞其他线程。二是针对 **岛屿构建 (Island Building)** 这种以前必须串行做的事，他们采用了带 **路径压缩 (Path Compression)** 的并查集算法，在 **细检测 (Narrow Phase)** 碰撞时就顺便把逻辑关系连好，彻底实现了无锁化。

这一套下来，收益非常直接。物理模拟频率从 30Hz 提升到了 60Hz，这意味着同样的帧时间里能算两次物理或算得更精确。实际测试显示内存消耗降了 25%，最关键的是帧率稳得像石头一样，之前那个容易抖动的巨型 BOSS 蛇形怪现在也丝滑流畅了。这技术不仅自己好用，现在已经开源让大家一起白嫖了。

## Adventures with Deferred Texturing in 'Horizon Forbidden West'
- **Speaker:** James McLaren (Guerrilla)
- **Duration:** 3273 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1028035
- **Slide Page:** https://www.gdcvault.com/play/1027553
- **Custom ID:** 1028035

### Overview
To accelerate its foliage and alpha tested geometry Horizon Forbidden West implements a novel loosely tiled deferred texturing system. A visibility buffer is drawn as a pre-pass followed by analysis and shading steps which run entirely in compute shaders. The use of compute shaders also provides extra flexibility that allows for the implementation of a software variable rate shading solution. Due to being able to run on the compute pipes on PS4 and PS5 it is able to overlap both the G-Buffer rendering and the rendering of cascaded shadow maps meaning that analysis and shading typically have very little overhead. This presentation will describe details of the system, and the optimizations and design choices made to integrate it into the Decima engine.

### Content Summary
[TLDR]
别硬啃植被渲染了！Guerrilla 揭秘如何用延迟纹理化把计算负载塞进阴影空隙提帧。

[Background]
《地平线：西之绝境》面临植被密度提升与跨世代兼容的双重压力，此讲深入剖析了如何利用新渲染管线解决高过绘制痛点，适合图形程序开发者参考。

[Recaps]
以前的方案太费油，传统深度预通行法得算两遍顶点，而且因为 Alpha 测试容易导致隐藏的像素也被处理，俗称四边形过绘制 (Quad Overdraw)。这次《地平线：西之绝境》的方案变了，核心是用可见性缓冲区 (Visibility Buffer) 先把能看到啥记清楚，再决定怎么画，这玩意儿叫延迟纹理化 (Deferred Texturing)。

具体的难点在于如何避免显存读写成为瓶颈。他们在分类阶段做了三步走：先标记哪些批次在哪些区块有用，再用前缀和统计偏移量，最后才生成真正的绘制指令。这种设计保证了即使在大场景下，内存访问也是局部的，不会导致显存带宽爆掉。此外，CPU 端会把大量植被合并成“微批次”，防止单个批次太大撑爆环形缓冲 (Ring Buffer)，整个流程环环相扣，稳定性拉满。

他们主要靠计算着色器 (Compute Shader) 配合“松散平铺”策略，既按区域分块照顾缓存命中，又能灵活把同一材质的像素凑一波，避免线程分歧。顶点变换不傻等，直接丢进环形缓冲里并行干，彻底告别重复劳动。最后还能再压榨点性能，上了变量着色率 (Variable Rate Shading/VRS)，根据距离和角色移动速度自动偷懒降低采样精度。结果很香：把本该卡在几何 Pass 里的活，硬塞进阴影计算的间隙里，PS4 直接省出 2.5 毫秒，PS5 也有 1.4 毫秒。简单来说就是画质没变，引擎现在跑得更快更稳，这招图形学同行赶紧抄作业。

## Virtual Sync: Terabytes on Demand
- **Speaker:** Brandon Moro (Bungie, Inc.)
- **Duration:** 3742 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1028081
- **Slide Page:** https://www.gdcvault.com/play/1027699
- **Custom ID:** 1028081

### Overview
For decades, the basic way we work on games has remained mostly unchanged - we sync the game's source data from something like Perforce, we change a few things, we validate locally, and we submit our changes. With AAA game source data exceeding 10 TB, and content creators needing to work across multiple branches, it has become steadily less practical to require these volumes of data transfer. When the Covid-19 pandemic sent all of our employees to work from their homes, our development process ran into the limitations of multi-day network data transfers and we were faced with the need to physically transport hard drives back and forth. VirtualSync is our answer: a virtual file system that seamlessly fetches assets on-demand as-needed, allowing us to shrink up-front syncs by 98% or more. We show how this simple idea requires a number of complex engineering challenges to be solved. We will present numerous problems encountered and the solutions we developed to solve performance issues, operating system limitations, service monitoring at scale and more.

### Content Summary
[TLDR]
Bungie 利用投影文件系统重构开发环境，实现海量素材按需加载，大幅降低同步时间和本地存储压力。

[Background]
《命运 2》作为大型 MMO，资产积累过 PB 级，单分支就有 TB 级数据。旧版同步方式不仅耗时长，远程办公期间更是让人崩溃，急需一种能减负的高效方案。

[Recaps]
Bungie 面对的核心痛点是版本管理系统 (Perforce) 里的资产太巨大且分支繁多，导致开发人员机械硬盘 (HDD) 爆满、同步极慢，甚至远程办公期间更是让人崩溃。为了解决这个问题，他们放弃了自研底层驱动，转而采用了微软成熟的投影文件系统 (ProjFS)。这套名为虚拟同步系统 (Virtual Sync) 的方案核心在于“按需加载”，用户看到的仓库可能有几 TB，但实际下载到本地的只有几 GB，极大缓解了网络和存储压力。

在实现细节上，系统通过拦截文件 API 调用，将文件状态分为虚拟、占位符、已水化等多种形式。为了不让工具因扫描整个仓库而卡顿，他们引入了内存缓存机制来处理元数据枚举，并针对文本文件格式差异做了特殊兼容处理。此外，他们还开发了专门的诊断网页，支持通过远程排查网络共享协议 (SMB) 上的状态问题，这让原本复杂的维护工作变得简单可控，支持成本几乎降为零。

实施过程中也遇到了不少坑，比如文件通知机制会误触发工具刷新，以及长期累积的缓存会导致硬盘空间慢慢膨胀。Bungie 通过清理旧缓存、定制内容监视器 (ContentWatcher) 接口等方式逐一攻克。最终效果立竿见影，新分支同步从几天压缩到几分钟，且允许用户使用更快的 NVMe 协议存储。这套经验对于面临类似资产爆炸和远程协作难题的团队来说，极具参考价值，强烈建议大伙研究一下这种虚拟化方案的可行性。

## Tools Summit: Immutable Data for Editors for 'EVE Echoes'
- **Speaker:** Kai Zhang (Netease Games)
- **Duration:** 2760 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1027947
- **Slide Page:** https://www.gdcvault.com/play/1027628
- **Custom ID:** 1027947

### Overview
This session presents the technical details of EVE Echoes immutable data based editor framework. During this presentation, you will see how a small team developed a large number of editors. Several solutions are compared alongside, and we discuss why immutable data best suited our tools. You will see how to use immutable data to decouple the UI update, why it can significantly decrease the complexity of editor development, and how it offers a simple, reusable, and feature-rich undo/redo solution. You will also see how the framework can greatly improve the reusability of UI logic when combined with component-based UI.

### Content Summary
[TLDR]
小团队通过不可变数据架构，彻底解决编辑器维护难、撤销逻辑复杂及自动化测试缺位的痛点。

[Background]
网易《EVE Echoes》工具组人手极少，传统基于事件的编辑器导致 UI 同步错乱且撤销逻辑难以扩展，急需一套能降低维护成本的通用框架。

[Recaps]
老牌开发者常受困于传统 Model View Controller (MVC) 模式下的编辑器维护难题。旧方案依赖事件驱动，UI 状态容易和真实数据对不上号，而且每次修改都得手动编写撤销命令，也就是命令模式 (Command Pattern)。一旦功能多了，撤销逻辑就像滚雪球一样难处理，稍有不慎整个历史记录就废了，这对只有少数几个人的小团队简直是灾难。

为此演讲者引入了不可变数据结构 (Immutable Data Structure) 方案。核心思路是修改前先拷贝副本，原始数据永远不变。利用结构共享 (Structural Sharing) 技术，系统只需复制少量节点就能生成新版本，效率极高。这使得“撤销”操作变得极其简单，不需要倒推命令，直接在历史栈 (History Stack) 里移动指针就能回到过去或重做，完全透明不费脑。

在框架实现上，UI 更新不再靠通知，而是由数据驱动。类似于组件化的 View Tree (视图树)，每一帧都会比对新旧数据的差异来刷新界面。这种机制天然支持异步操作，比如 3D 模型加载未完成时，系统会暂时跳过 UI 刷新，等数据就绪后再统一校准，避免了缓存逻辑带来的崩溃风险。配合录制数据快照回放的能力，他们甚至不需要专职的 QA 就能实现全自动化的视图测试，极大降低了日常迭代的成本。

### Overview

And some designers are not familiar with data-driven decision making. The speakers suggest a solution: Design a tool to help designerfetch and analyze data directly without knowledge of coding. ### Content Summary
[TLDR]
拒绝低效沟通！用 5W 模型自建在线透视表工具，让策划自助查数，30 分钟搞定数据需求。

[Background]
策划查数总得求着数据工程师，排期慢还容易沟通误解，严重拖慢迭代节奏。网易团队分享如何自研低门槛在线工具，把“查数据”的权利还给策划，实现自助式分析。

[Recaps]
以前咱们组要想拿数据，设计师只能乖乖等着数据工程师派活。不管是搞实时监控还是跑 BI 平台，起码得拉上好几个人协调，沟通扯皮能浪费半天时间。为了解决这个痛点，我们决定搞个在线工具，目标就是一个设计师自己在 30 分钟内搞定全流程，不再占用资深开发的时间，让他们腾出手去优化游戏里的数值体系。这其实就是想真正落地 数据驱动决策 (Data-driven Decision Making)，别让数据卡在部门墙后面。

考虑到很多策划并不懂代码，强制学写 SQL 是不现实的。所以我们设计了套 5W 模型的问答系统，把人怎么查数据的思路拆成 Who、Whom、What、When、Where 五个问题填进去。后台直接把人的自然语言请求转换成 SQL 代码 (SQL Code) 去库里捞数。这就跟搜东西一样，告诉它你要啥时间段、啥服务器的什么活动日志，系统自动给你整理好，省去了大量解释需求的过程，准确率也高了。

技术选型上，前端用的 React 框架，后端跑 Python Django，库是 MySQL。之前试过几套开源的现成方案，发现要么收费太狠，要么功能太死板，像能不能固定行列、自定义编号这些细节都改不了。最后没办法，只能自己手写核心模块，做出了支持冻结功能的 透视表 (Pivot Table)。总的来说就是两点：先想办法让大家养成看数据的习惯，再用便宜好用的工具帮他们省力，这才是工具开发的正道。

## Tools Summit: Efficiently Shuffling Loads of Data from Place to Place
- **Speaker:** Adrian Astley (Activision)
- **Duration:** 3182 分钟
- **Category:** Tools Summit
- **Video Page:** https://www.gdcvault.com/play/1027948
- **Slide Page:** https://www.gdcvault.com/play/1027588
- **Custom ID:** 1027948

### Overview
Games and tools are big and only getting bigger. Games are expanding to be developed by multiple studios in potentially distant physical locations. In addition, the game data and assets are also growing. Thus, using a network file server to transfer data for both Continuous Testing servers as well as individual developers is no longer viable. This talk is a postmortem of a tool we created to manage data transfers in order to optimize for speed, space, and bandwidth. The talk will discuss the reasons for needing this tool, the architecture we ended up with, an analysis of how well it's working, and finally a discussion of all the issues / pitfalls we ran into while developing the tool and running it at scale.

### Content Summary
[TLDR]
Indy 利用内容寻址存储 (Content Addressable Storage) 和分块去重，彻底解决了跨国协作中海量构建数据的传输难题。

[Background]
针对动视跨多地工作室协同开发的痛点，传统文件服务器延迟高、带宽贵且去重 (Deduplication) 差，导致持续集成 (CI) 效率低。适合负责 CI/CD 架构、大型项目管线优化的同行参考。

[Recaps]
动视那边遇到的最大麻烦就是人多地散。以前游戏开发都在一个大楼里跑局域网，现在好了，工作室遍布加州、澳洲甚至中国，再加上各地的测试团队。这时候再用传统的文件共享 (File Share) 比如 SMB 或者 NFS，一旦跨越国界，物理延迟 (Latency) 就会让网速直接变龟速。最要命的是构建数据太巨大了，光地图烘焙一次就几十个 GB，哪怕只改一张贴图，旧方案也得全量传输，带宽 (Bandwidth) 根本吃不消。而且单台服务器挂了就是全线崩盘，数据去重 (Deduplication) 做得也很傻，容易陷入死循环。

所以动视搞了个叫 Indy 的工具来解决。核心思路是把所有内容都变成可寻址的，也就是所谓的对象存储 (Object Store) 模式。具体来说，这属于内容寻址存储 (Content Addressable Storage)，每个文件和数据块都用唯一的哈希值 (Hash) 当名字，只要内容不变，名字就不变。大家不再直接复制大文件，而是像快递拼单一样，先比对服务器上缺哪些“零件”（数据块），只上传缺失的部分。这样几 TB 的数据传输也能实现类似秒传的效果，省下的带宽 (Bandwidth) 简直就是白送。

这套系统还自带“自动清洁工”功能。通过标签 (Label) 指向具体的镜像，设置过期时间后，系统会自动执行垃圾回收 (Garbage Collection)，精准删掉没人用的镜像和孤立的数据块。为了解决不同文件格式导致的去重失效问题，他们还引入了内容定义分块 (Content Defined Chunking)。这玩意儿能根据文件内部的天然边界自动切分，避免了因为一个小改动导致后面整个文件哈希都变了。加上配合每地部署的边缘缓存节点，下载请求优先走本地，再不上云，流量省了一半以上。

最后分享几个血泪经验。第一是规模诅咒，并发量一大，百万次操作里的微小概率 Bug 必现，所以必须随时进行数据校验 (Data Verification) 确保不损坏。第二是 Windows 文件系统的问题，rename 操作在不同系统下不一定保证原子性，多线程写同一文件名容易坏，得自己加锁保护。第三是防火墙别只看标称带宽，开启分类策略后速度可能直接腰斩，得提前跟 IT 部门沟通做流量限制。总之，这工具已经跑了四年，效果非常稳，想学大规模数据管线的同行可以参考一下。

### Content Summary
[TLDR]

[Background]
RTS 游戏要拉高单位数量全靠暴力堆显卡和 CPU，单线程跑不动就必须搞多线程（Parallelization）。但这容易让不同玩家的电脑运算顺序不同，导致联机时画面对不上（Desync），这是行业老大难问题。

[Recaps]
想要《帝国时代 4》支持上千单位同屏打架，得把引擎吃满到并行化（Parallelization）模式。可 RTS 传统模式靠的是确定性网络（Deterministic Networking），要求大家每一步操作结果都必须一模一样。如果线程乱序跑，或者两个线程抢着改同一个数据，就会破坏规则，导致服务器和客户端状态不一致。这时候要是加互斥锁（Mutex）保数据安全，又怕拖累太多帧数没法玩，所以必须找到更聪明的办法。

这工具的集成成本极低，只要给特定对象打上几个宏（Macros）标记就行，默认编译掉的代码完全不消耗性能，只有开启跟踪的部分才累一点。它最狠的地方在于反馈机制，报错时会带着完整的调用栈（Call Stack），甚至能直接定位到具体的脚本代码行，设计师一看就知道是谁改乱了数据。最后这套系统只增加了约 20% 的开销，却能让整个项目放心大胆地并行化，简直是给大乱斗游戏做同步优化的一剂猛药。

## Pathing in 'Age of Empires IV': Flow Fields and Steering Behaviors
- **Speaker:** Frank Cheng (Microsoft, World's Edge)
- **Duration:** 1789 分钟
- **Category:** Programming
- **Video Page:** https://www.gdcvault.com/play/1028036
- **Slide Page:** https://www.gdcvault.com/play/1027659
- **Custom ID:** 1028036

### Overview
Creating a real-time strategy game with hundreds of units moving across an ever-changing battlefield, as opponents construct and destroy buildings and walls, requires a robust and efficient pathfinding system. This presentation walks through how Age of Empires IV combined flow fields, hierarchical A*, and steering behaviors to deliver fluid and cohered unit movement across a dynamic world. Going into details on dealing with different terrain types and unit sizes, the optimization strategy and new features that were developed for each of these base systems, and the implementation nuances and gotchas the team encountered.

### Content Summary
[TLDR]
《帝国时代 4》用流动场 (Flow Fields) 解决海量单位协同，配合层级分块与分段生成，兼顾流畅度与帧率稳定。

[Background]
RTS 游戏面临上千单位同屏，传统 A*算法太慢且动态避障难处理。本分享揭示了如何构建高性能的移动系统，适合做 MMO 或大规模战斗 AI 的开发者参考。

[Recaps]
传统的 A*算法在单位多的时候根本算不过来，而且加上**转向行为 (Steering Behavior)** 后容易跑偏，导致单位明明绕开了障碍却再也找不到回去的路。为了解决这个痛点，开发组直接引入了**流动场 (Flow Fields)** 技术。简单说，它不是一张点列表，而是整个地图的距离梯度图，无论单位怎么避让，脚下永远是最短路径的方向指引，彻底避免了卡死和绕远路。为了算得更准，他们没用基础扩散，而是用了**快速行进法 (Fast Marching Method)**，让距离变化的形状像水滴一样圆润，不再出现那种生硬的折线拐弯。

光有流动场还不够，全图 1024 格的大地图全算一遍太耗资源，玩家电脑要冒烟。所以团队搞了个分层策略，把地图切成小格子，通过连接**传送门节点 (Portals)** 抽象成路网。这里有个大坑叫“完美流动场”，虽然准但串行计算太慢；后来改成“单一格子流动场”，速度快但转弯怪异。最终方案是**分段流动场 (Segmented Flow)**，每次只往前看一格，既保留了预测能力，又能保证实时响应，还能缓存复用。再加上**视线整合 (Line-of-Sight Integration)**，看不见目标的地方直接跳过计算，性能直接砍掉大半开销。

实际游戏里情况更杂，比如大象和步兵混编。如果只算步兵的路，大象就走不过去。他们用**通行间隙 (Clearance Value)** 标记地形宽度，先算大号单位的路，再让小号单位以该路径为目标重跑一次，确保编队不散乱。陆战和海战地图本来是不通的，他们就画出一块**接驳区域 (Lendable Zones)**，拼成一个统一图，实现无缝登陆。编队时采用虚拟队长机制，一旦队员被障碍物挡住看不见队友标记，立马切换回流动场引导归位，保证了团战时的整齐划一。

最后数据很硬核，单位数量翻倍，流动场耗时几乎没怎么涨，说明这种共享计算的模式非常适合大规模战争场面。总结下来就是：别死磕 A*，对于群体移动，流动场加层级优化才是正道，既能保帧数又能保体验，这设计思路对咱们做大世界游戏的也很有参考价值，值得拿去细品。

[TLDR]
Halo Infinite 抛弃固定 60 帧魔咒，靠可变帧率模拟 + 通用作业系统实现跨平台高帧率与低维护成本。

[Background]
以前的《光环》引擎太死板，Xbox One 时代为了稳 60 帧把逻辑锁死在固定节奏里。如今要上 PC 和次世代主机，还得支持 120 帧，旧有的线程调度像给八核 CPU 贴条子，换个芯片就崩，代码维护更是坑爹，不改不行，改了更难懂。

[Recaps]
以前的《光环 5》引擎是个典型的**固定帧率 (Fixed Framerate)** 产物，游戏逻辑被锁死在 16.67 毫秒一组的**游戏刻 (Game Tick)** 里。这招在单平台上还行，一旦掉帧，系统只能靠“多倍速模拟”赶进度，结果就是输入延迟忽高忽低，手感发飘。更致命的是，为了榨干 Xbox One 的核心，美术组被迫采用手动的“俄罗斯方块式调度”，每个任务都死死绑在特定线程上，换成 PC 或主机新世代，这套硬编码的线程亲和机制直接水土不服，代码维护难度更是呈指数级上升。

这方案虽然成功，但也有坑。因为作业系统只负责执行顺序不负责数据访问，开发初期经常爆各种竞态条件，后来只能加额外的依赖补丁。作者建议下一代必须原生支持数据依赖，同时想把主线程也作业化，彻底摆脱历史包袱。总之，这套架构让《光环无限》能在各种离谱配置下跑分稳定，算是把跨平台仿真工程做进了行业教材级别。

各位老铁，今天给大伙聊聊 FunPlus 特效大佬 Abel 带来的硬核干货。他说咱们干 VFX 的，说白了就是把数学可视化。现场演示他用 **流体模拟 (Fluid Simulation)** 工具 **FluidNinja**，几分钟就能生成火、烟等特效，根本不用一帧帧手绘，效率直接拉满。但这只是第一步，真正的难点在于手机性能限制。

移动端游戏资源预算卡得死，贴图太大了显卡扛不住。以前做火焰 **翻页动画 (Flipbook)**，为了时长够长，贴图尺寸就得巨大，否则几十帧就不够放一秒。这时候 **数学知识** 就成了救命稻草。核心技巧是用一张 **流场映射图 (Flow-Map)**，简单讲就是用图像的红绿通道数据去控制目标图的像素坐标移动。红通道控制左右，绿通道控制上下，黑白色块代表方向与速度，相当于你在 PS 里直接“画”出运动轨迹。

为了解决手机性能瓶颈，他们进一步对 **着色器 (Shader)** 进行了深度优化。原版工具生成的节点太复杂，不适合移动端，于是他们将其简化，利用时间函数和插值算法把 A、B 两部分动作无缝拼接。这样一来，原本只有 16 帧的小贴图，经过 Shader 计算能跑出 256 帧甚至更长的平滑效果，内存占用几乎没变。最后提到的音乐驱动模型跳舞的例子也挺有意思，说明声音也是数字，也能转变成特效参数。

总之，这堂课就给咱们提了个醒：别看到数学就头大。在游戏行业，数字就是画面，画面就是数字。掌握这些原理，用对工具，像 Abel 一样把复杂的逻辑简化，才能做出既惊艳又跑得动的高质量手游特效。别再迷信纯靠画了，搞懂背后的逻辑，你就是半个图形学程序员。

[TLDR]

[Background]

## Math In Game Development Summit: Practical Automation: A Guide to Random Game Content Generation
- **Speaker:** Yiheng Zhou, Shuai Xu (LeoCool Games, LeoCool Game)

### Overview
Random generation is always a very important technology in the game industry. The typical Rogue Like game formally uses it to create extensive and profound randomness as well as the explorable depth. In this lecture, we will start from the mathematical principles of random game content generation technology, with a few simple demos, and gradually deepen, discuss and study a series of technical and game experience problems that random game content generation faces in the practical application. ### Content Summary
[TLDR]
利用大规模自动模拟结合统计学模型，将地图公平性与稳定性量化，从而自动化筛选高质量随机关卡内容。

[Background]
随机地图常因资源不均、出生点烂被玩家吐槽，人工测试难量化。本文分享用仿真模拟和数学统计把“好不好玩”变数据指标，适合需要搞程序化内容生成 (Procedural Content Generation) 的团队参考。

[Recaps]
这俩哥们儿上来就戳痛点：现在不少游戏的 `随机游戏内容生成 (Random Game Content Generation)` 地图，玩家总抱怨出生点烂、资源分得不均。他们基于自研的《Cast of Wanders》做了大量实验，核心逻辑别靠玄学，得跑数据。为了排除玩家技术差异的干扰，他们专门盯着游戏开局阶段做测试。这时候两个阵营（红蓝方）去挖矿，谁拿到的金子多，基本就看地图分配公不公平。

怎么量化“好不好”？他们定义了两个关键指标：**公平性 (Fairness)** 看的是分数差的 `期望值 (Expectation)`，**稳定性 (Stability)** 看的是 `方差 (Variance)`。简单讲，期望值接近零说明两边运气差不多，标准差小说明每次测结果都很稳。通过几千次模拟发现，地图面积越大、资源总量越多，反而越不稳定。想调平难度，除了改图大小，还能调整双方人数。另外，角色移动依赖的路径算法得做好 `路径寻找 (Pathfinding)`，不能傻到一直撞墙或者绕远路。

最后到底用啥算法画地形？他们对比了三款主流方案：`均匀随机选择 (Uniform Random Selection)`、`柏林噪声 (Perlin Noise)` 和 `分形噪声 (Fractal Noise)`。数据统计显示，`均匀随机选择` 在生成障碍物时最稳，而另外两种虽像自然纹理，但容易造成极端不平衡。总结出一套自动化流程：先定好各项指标的上限，选个合适的生成器，注意 `随机种子 (Random Seed)` 的选择也很重要，批量造图后扔进模拟器跑几千局，直接筛掉不达标的，剩下的就是能用的高质量随机地图。

## 'Knockout City's' Parallel, Deterministic, and Rewindable Entity System
- **Speaker:** Chris McEvoy (Velan Studios)
- **Duration:** 3618 分钟

### Overview
We present a general-purpose game entity system that supports deterministic, parallel computation and the ability to rewind world state within a time window. Such a system can be used to support robust client-side prediction in a networked game, world state scrubbing at development time, and effective utilization of processing power on multi-core hardware. ### Content Summary
[TLDR]
为了兼顾联机公平与流畅，Velan 团队开发了一套带脚本的确定性实体系统，实现了高性能并行与可靠回滚。

[Background]
竞技联机最怕延迟高又不公平。服务器要权威，客户端得预测，两边状态还得分秒不差。这篇就是实战经验，教怎么搭一套既能跑多线程又能随时倒带重来的脚本化 ECS 架构。

[Recaps]
为了在《Knockout City》里实现既公平又流畅的联机体验，Velan 搞了套自定义的**实体组件系统 (Entity Component System)**。核心是把所有游戏逻辑拆成脚本，数据按时间切成一份份**快照 (Snapshot)**。简单说，服务器拥有绝对控制权，但客户端为了减少卡顿得自己先预测动作。这就逼得系统必须具备三个特性：能并行加速运算，结果必须确定一致，而且随时能倒带回滚。只有做到这些，服务器确认后才发现错了才能无缝修正，不影响玩家手感。

搞并行最怕遇到**数据竞争 (Data Race)**，比如两个脚本同时读写同一个部件肯定出 bug。他们没走传统的互斥锁老路，而是玩了套花活：读到别人数据时自动插入等待，写到别人数据时先存进队列稍后统一提交 (**Deferred Write**)，读取时还能顺手查一下自己待办列表防尴尬。要是遇到俩脚本互相等导致的**死锁 (Deadlock)**，他们的**作业系统 (Job System)** 会用特殊算法强行解开，哪怕循环依赖也能保证程序不崩，确保流程稳定。

跑通之后发现效率还不够，主要是因为任务切换太频繁。于是做了不少骚操作来提效：比如给不同功能的组件排个优先级 **Wait Order**，让逻辑关联的尽量挨着跑；像粒子特效这种简单的直接堆在一起批量执行 (**Batching**)；复杂的摄像机逻辑改成单点指挥模式。内存方面也很抠门，不是所有时刻都存快照，只猜可能用到的时间点，节省空间。这些优化能让同样的硬件跑出更高的帧数，减少网络抖动带来的影响。

最后他们还给这套系统配了不少调试神器，比如自动跑两次比对**哈希校验 (Hash Comparison)**，只要状态不一致立马报错。还有个实体查看器能直接改数值测试。开发者事后复盘说，早点把性能优化做进去很重要，不然后期重构很痛苦。有些时候其实没必要强求实时最新数据，读上一帧的旧数据可能性价比更高。总之，用脚本控制底层架构是个双刃剑，但用好它能极大提升开发效率和游戏质量。

核心技术这块儿挺硬核，主要是利用摄像机的微小抖动 (Jitter) 采集子像素信息，再结合运动矢量 (Motion Vectors) 把上一帧的数据映射回来。为了防止“鬼影”现象，AMD 搞了几个骚操作：一是深度对比检测视差遮挡 (Disocclusion)，发现不该重合的地方就强制刷新历史记录；二是用亮度限幅 (Luminance Clamping) 修正颜色差异，防止光照变化导致残影；三是针对树木、栅栏这种细线，用了锁定机制，确保它们不会在采样过程中突然消失。这些手段加起来，让画质在保持稳定的同时没有那种模糊的糊墙感。

性能方面也没得黑，官方实测显示在高端卡上光跑一遍 FSR 2 耗时不到 1 毫秒，对帧数影响微乎其微。它还能完美适配动态分辨率缩放 (Dynamic Resolution Scaling)，比如战斗特效多的时候自动降渲染分辨率救场，打完怪再恢复，最终输出全是高清。最后强调了一下集成建议，最好直接把原有的时间性抗锯齿 (TAA) 通杀替换掉，注意提供反色深度图和 FP16 精度的运动矢量，记得给 Cinematic 切换场景时调用重置接口，这样就能把最顶级的画质拉满，还能照顾到老架构显卡，绝对是良心技术。

[Background]
材质点法（Material Point Method）是处理流体和固体变形的核心物理算法，但在显卡上跑得慢是个老难题。这场演讲专门针对现有单卡和双卡方案的痛点，分享了一整套硬核优化实战，给想搞高性能特效的游戏程序员和图形研究者指点迷津。

[Recaps]
这次分享的核心就是怎么让材质点法在现代 GPU 上飞起来。这玩意儿本质是用粒子带属性，再投射到背景网格上去算力，最后再把结果传回粒子。最大的麻烦在于粒子动了之后，怎么快速知道它该找哪个网格节点。以前每帧都得重新建一次映射关系，太费时间。他们搞了个“哈希表”直接把空间地址存好，还提出了“自由区域”的概念——只要粒子没跑出这个圈，就不用每次都重建映射，省了不少力气。

单卡优化的秘诀主要体现在两个方面：一是尽量把小的计算内核（Kernels）合并成大任务，减少读写全局内存（Global Memory）的次数；二是避开那些没有硬件原生支持的指令，比如别在非必要的共享内存（Shared Memory）里用复杂的原子操作（Atomic Operations），直接写全局内存反而限制更少、速度更快。还有个小技巧，不用全量排序，只在小范围内排个序就能解决大部分冲突，进一步减少开销。

到了多卡场景，挑战就变成了显卡之间的聊天延迟太高。解决方案是把活儿按粒子切分，而不是按空间切分，这样大部分计算可以并行互不干扰。关键步骤是利用 PCIe 或 NVLINK 做的对等传输（Peer-to-Peer），让不同显卡直接读写对方显存数据。同步这块，他们放弃了传统的 CPU 端等待方式，改用了一种纯 GPU 端的自旋锁机制，不仅省了 CPU 资源，还能大幅提升并行效率。最终实测，单卡最快提速 8.6 倍，四卡并发能冲到 14 倍以上，实打实的性能怪兽。

[Background]
针对开发者想把 DLSS (Deep Learning Super Sampling) 塞进自家项目却总遇到鬼图的痛点，这篇 GDC 实录毫无保留地分享了从原理到落地的全流程经验，特别是常见 Bug 的排查方法，特别适合图形组主程阅读。

[Recaps]
DLSS (Deep Learning Super Sampling) 本质是靠 RT 卡上的张量核心 (Tensor Cores) 跑神经网络，用低分辨率渲染出高分辨率画面。相比传统的空间超采样器 (Spatial Upscaler) 容易模糊或闪烁，DLSS 能通过收集运动向量 (Motion Vectors)、深度 (Depth) 等多帧时序数据，像“脑补”一样重建画面细节。除了性能模式，还支持纯画质的 DLAA (Deep Learning Anti-Aliasing)，让开发者在高负载下依然能保持原生水准。

想要顺利集成，引擎得满足几个硬性条件：视口必须支持小幅度的视口抖动 (Jittering)，运动向量指向要符合左上角为零的规则，后处理链得兼容非整数倍缩放。最佳实践是把 DLSS 放在后处理的第一环。最常见的翻车场景包括贴图变模糊，这是因为 LOD 层级没对缩放比例做纹理偏置 (Bias)；或者是物体莫名消失，这是遮挡剔除逻辑没算上显示密度的变化；还有景深、色差等特效如果没考虑渲染与显示的分辨率差异，会导致画面撕裂。

排错的时候别慌，直接用软件开发商提供开发工具包 (SDK) 自带的调试覆盖层 (Overlay)，能实时看到抖动范围是否合规、运动向量有没有漏算。Unity 和虚幻都有现成插件，自研引擎直接调 SDK 就行。记住一点，DLSS (Deep Learning Super Sampling) 的目标是几乎无感，发现问题就要死磕到底，调通了那就是帧率画质双丰收。

## Math In Game Development Summit: Deep Dive: Quaternion Springs
- **Speaker:** John Austin (Pontoco)

### Overview
It seems like a rather simple challenge: apply a spring to a quaternion so that it smoothly rotates between different orientations. However, most simple approaches will fail, creating oddly curved trajectories or failing under large forces. This is a common behavior that many games might need for targeting, animation, and physics. Why is this so challenging?nnIn this talk, we will do a deep dive into the creation of a mathematically accurate quaternion spring. ### Content Summary
[TLDR]
揭秘如何用摆扭分解和指数映射造出零损耗的旋转弹簧，告别诡异运动轨迹。

[Background]
游戏物理里线性弹簧很简单，但想让物体旋转时像弹簧一样回弹，直接用四元数减法会漏能、轨迹还怪。这演讲专门给想搞高级旋转物理的程序员解惑。

[Recaps]
咱们都知道线性弹簧 (Linear Springs) 好使，代码少几行就能让东西有点物理感。但想在旋转空间也这么干就不行了，直接把两个四元数 (Quaternion) 拿来相减，虽然看着像回事，实际上是在犯数学错误。最要命的是这会凭空损失能量，而且旋转路径不是最短弧，而是诡异的 C 形大弯，没法正常回弹。

为了解释这个，演讲者从二维复数 (Complex Numbers) 聊起，其实就是加了个虚数单位，让数字乘法变成旋转动作。三维空间也一样，为了避开欧拉角 (Euler Angles) 的死穴万向节锁 (Gimbal Lock)，我们得用更高级的轴角 (Axis-Angle) 配合四元数，它们住在四维单位球面上，虽然多了一层维度，但能精准表达任意旋转。

核心大招是别瞎加减，用力矩 (Torque) 驱动。关键是做摆扭分解 (Swing-Twist Decomposition)，把旋转硬生生切成两半，一部分负责把主轴往目标拉直（摆），一部分负责绕轴拧麻花（扭）。这种分法能让你灵活调整材料属性，比如让它不怕弯只怕扭，或者反过来。最后结合单位球上的角速度 (Angular Velocity) 更新公式，就能保证能量在旋转中不流失，回到原点只是震荡不停。

最后问答环节确认了这东西挺皮实，哪怕目标姿势在动也能平滑跟进，很适合用来做信号平滑或者物体跟随。虽然还有个小技巧是用近似公式直接加角速度，但那属于小角度的特例，想要严谨点的物理反馈还是按这套流程来最稳。

[Recaps]
现在的高清屏加上光线追踪 (Ray Tracing)，原生渲染根本跑不动。大家常听说的空间超采样 (Spatial Upscaling) 虽然能算得快，但放大倍数一大画面就糊成马赛克，质量下降严重。英特尔这次推的 XeSS 核心思路是用 AI 来做时域上采样 (Temporal Super Sampling)。它不是单靠一帧图猜细节，而是像看连续帧视频一样，利用前几帧的信息结合运动矢量 (Motion Vector) 来修补画面。这就好比拼图，光看一块很难拼对，但多参考上下几块的位置就能把缺角补得更准。

集成方面也很简单，UE4/5 有插件，基本是复制粘贴加个开关就行。引擎需要喂给它一些输入，比如抖动偏移 (Jitter Offset)、颜色缓冲 (Color Buffer)。在硬件支持上，如果是英特尔特定的 Arc 显卡，会用专门的 XMX 矩阵扩展单元加速；没这功能的其他 GPU，也能用 DP4a 指令兼容运行。实测显示，开了 XeSS 后，哪怕开着光线追踪跑 60 帧也不是梦，像演示中的《Dolmen》之类的项目就能明显看到性能提升而不损失画质细节。

[Recaps]
这次主要讲的是《暗黑破坏神 2：重制版》的毛发渲染技术。核心思路是用物理基础着色（Physically Based Shading）模型，把头发纤维当成半透明圆柱体处理。光线进去后会发生反射、折射和散射，团队用了高斯散射（Gaussian Scattering）来模拟光在发丝内部的漫反射效果。为了效率，他们做了烘焙（Baking），把复杂的计算提前算好存成 BCSDF 纹理（BCSDF Texture）。为了表现发束的体积感，他们还搞了层级 MIP 映射（MIP Mapping）来处理“毛发丛”的散射，简单说就是单层一层层叠加，让头发看起来不那么像纸片，远看近看都有质感。

不过技术不是万能的，最大的槽点其实是美术资产管线的配合问题。给外包团队的需求文档没写清楚，导致拿回来的法线贴图（Normal Map）、切线贴图（Tangent Map）格式五花八门，甚至出现了黑色作为无效切线方向的 BUG。最麻烦的是预乘 Alpha 通道的问题，因为修图软件默认带锐化，去预乘的时候边缘全是噪点，团队只能搞个膨胀算法硬补救。结果发现美术调参数特别慢，Maya 里改半天着色器（Shader）都不实时，逼得他们只能靠颜色贴图定色，浪费了很多物理渲染带来的真实感细节。

性能方面，这套方案大概占了渲染预算（Rendering Budget）的 5% 到 10%，不算太便宜，尤其是查 3D 贴图（3D Texture）和维持 LOD(Level of Detail) 细节。演讲者承认如果重来一次，可能不需要这么硬核的物理仿真，毕竟游戏风格偏暗黑奇幻，简单的模型也能达到差不多效果。最后提醒大伙儿，做次世代渲染前，一定要跟外包把技术规范咬死，别等模型做好了再改需求，不然后期修复成本比写代码还高。

首先来解决画面好不好看的问题。传统做法是直接把辐照度 (Irradiance) 存死，但这无法表现高光细节。这演讲引入了时序累积 (Temporal Accumulation)，每帧只保留一部分旧数据，根据材质的双向反射分布函数 (BSDF) 调整权重，这就是指数滤波 (Exponential Filtering)。简单说就是光滑表面更新要快，磨砂表面可以存久点，直接在世界坐标干这事儿，根本不需要那种容易出错的屏幕空间重投影 (Reprojection)。最后为了去除噪点和方块感，还会配合屏幕空间空间滤波 (Screen Space Spatial Filtering)，靠法线和距离判断，既能磨皮又不会把边缘糊掉。

其次是内存这块硬骨头。空间哈希最忌讳邻居节点在内存里八竿子打不着，CPU 缓存全废了，也就是内存一致性 (Memory Coherence) 很差。他们搞了个“松散聚类” (Loose Clustering) 的技巧，允许集群之间有点重叠，利用哈希冲突处理机制，既保证局部数据就近读取，又不浪费多余的空间。实测这种操作能让分配速度提高 40%，整帧效率直接拉满 20%，对于大地图场景来说这绝对是真香定律。

最后是画面锯齿和采样效率的平衡。网格对齐几何体会导致严重的闪烁锯齿 (Aliasing/Fighting)，作者没用抖动的笨办法，而是用正弦波扭曲坐标，让单元格的边界永远对不上模型的棱角，从根上杜绝了虚假伪影。在光照采样时，遇到室内遮挡多的场景，普通的重要性采样 (Importance Sampling) 会瞎射光线。他们改进了一种基于累积分布函数 (Cumulative Distribution Function) 的全局自适应方案，比如窗户亮的地方自动增加射线权重，收敛非常快，而且完全没有鬼影拖尾。整个流程跑在 RTX 3090 上能扛住 3 亿面数，细节依然锐利。

### Overview


### Content Summary
[TLDR]
光追开放世界开发中，利用系统内存缓存加速结构并优化构建策略，是解决显存压力和性能瓶颈的关键。

[Background]
随着光线追踪 (Ray Tracing) 成为标配，开放世界游戏面临巨大的显存与算力挑战。英伟达工程师分享如何在复杂场景中高效管理资源，解决构建延迟与内存爆炸的痛点，适合希望落地光追效果的程序与主程参考。

[Recaps]
想搞懂 光线追踪 (Ray Tracing) 为啥在开放世界里会掉帧，先得明白它的底层逻辑。游戏场景不能裸跑，需要用 加速结构 (Acceleration Structure) 来帮射线找交点，这里面最核心的算法叫 边界体层次 (Bounded Volume Hierarchy / BVH)。通常我们会建立两层结构，顶层管全局调度，叫 顶部级加速结构 (Top Level Acceleration Structure / TLAS)，底层管具体物体，叫 底部级加速结构 (Bottom Level Acceleration Structure / BLAS)。这玩意儿虽香但费钱，经过 压缩 (Compaction) 处理后，每个三角形还得再占约 33 字节，意味着开了光追，你的显存占用直接翻倍，老哥们手里没大显存真不敢随便动。

接下来说说为什么性能会崩。很多人以为构建越快越好，其实构建时间跟三角形数量是线性增长，建一个大的总比建一千个小的快得多。而射线遍历却是对数增长，查得越快。如果为了节省画面细节，每帧都把那些小模型单独重建成 BLAS，显卡立马累死。所以在开放世界里，千万别按材质切分模型，要把相邻的小物体合并成一个大 BLAS，同时避免 顶部级加速结构 (TLAS) 里有大量空隙，否则不仅内存浪费，构建效率也会暴跌。最后别忘了利用 顶部级加速结构 (TLAS) 里的实例机制，别让同个模型占多份显存。

最后的杀手锏其实是“缓存大法”。以前旧模型出框就销毁，新模型进来就重算，效率太低。现在的最佳实践是把已经建好的 底部级加速结构 (Bottom Level Acceleration Structure) 先拷一份到系统内存里存着，哪怕它现在看不见也没事。等地图滚动需要再次展示这块区域时，直接从系统内存拷贝回显存就行，省去了构建和压缩的巨大开销。配合官方的 RTXMU SDK 做的内存碎片整理，这套组合拳下来，即使是海量地形流式加载，也能做到流畅丝滑，这才是真正的硬核玩法。

[Background]
光追游戏普及后，图形引擎常面临性能瓶颈。Intel 此次拆解 Arc 显卡底层逻辑，专门解决多线程并行计算时的资源浪费问题，适合想做图形优化的程序员看。

[Recaps]
Intel Arc 最牛的地方在于有一套全硬件加速的流水线，连**绑定体积层次结构 (Bounding Volume Hierarchy)** 的遍历和求交都是硬解，完全不靠 CPU 干预。以前的老架构最怕**单指令多数据流 (SIMD)** 里有的线程快有的慢，导致大家一起排队干等。Arc 用的是异步打法，射线发射后线程就能去干别的，等后台把结果攒够了再统一调度执行。这在处理那些光线满天飞、路径各异的复杂场景时优势巨大，彻底告别“短板效应”。

为了实现高效的异步处理，Arc 引入了“桶状线程分发”机制。打个比方，如果一批线程打中的物体材质都一样，硬件就会把他们打包成一个小组，确保这一波指令走得完全一致。这种机制专门对付**命中着色器 (Hit Shaders)** 多样化的情况，避免了串行执行的巨大开销。演示数据也实锤了这一点：当场景里不同材质的着色器数量飙升时，Arc 的帧率表现依然稳定，远强于那些强行串行的竞品方案。

最后给大伙总结几个避坑指南：千万别迷信**射线查询 (Ray Queries)**，那玩意儿本质是阻塞的，一旦发出查询整个线程组就得停下，严重影响并发效率；编写**管道状态对象 (Pipeline State Object)** 时越精简越好，别整太复杂的递归；尽量把**局部根参数 (Local Root Arguments)** 设成全局一致的，防止同一波次的线程访问不同数据源。另外，构建加速结构时多用索引几何体，命令列表里少插屏障，方便驱动批量合并任务，把 GPU 利用率拉满。

[Recaps]
最硬核的操作就是把渲染管线从传统的**前向渲染 (Forward Rendering)** 直接换成了**延迟渲染 (Deferred Rendering)**。这招虽然看着挺耗显存，但好处是真香，毕竟有了**延迟渲染 (Deferred Rendering)** 的法线数据，后面搞**光线追踪 (Ray Tracing)** 才不费劲。另外团队也狠心砍掉了多平台支持，只留 PS5 和 PC 的 DX12 架构，这样调试起来少踩很多坑，大家也能更专心地优化。

在画面细节上也是各种较真。比如**粒子特效**的分辨率单独开一套，不然一屏幕爆炸直接把主画面分辨率压得没法看。针对复杂的**贴花 (Decals)** 叠加，尤其是那种雪地盖在墙上的情况，他们用**模板测试 (Stencil Test)** 给每个像素打了个标签，告诉引擎哪层是静态的、哪层是动态的，这样雪就不会挡住不该挡的爆炸痕迹，也不会出现材质穿模的尴尬。

性能方面，AMD 的专家给了几个独门秘籍。首先是用好**异步计算 (Async Compute)**，然后减少 GPU **屏障 (Barriers)** 的使用，在计算蒙皮那段代码里手动优化状态切换，一处就提了 60% 的性能。然后是读写数据的时候别偷懒，**统一写入目标 (UAV Target)** 必须一次写满 256 字节的块，不然压缩时还得解压保存，费事又费力。最后这游戏还是首批用上 **FidelityFX Super Resolution 2.0 (FSR 2.0)** 的作品，靠着**运动矢量 (Motion Vectors)** 帮忙插帧，画质没丢多少，帧数却涨了一大截，这波操作属实稳。
