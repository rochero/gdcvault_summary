## Building a Million Particle System
- **Speaker:** Cheryl Jackson ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022856
- **Custom ID:** 1022856

### Overview


### Content Summary
[TLDR]
通过全 GPU 化粒子物理模拟，彻底摆脱 CPU 与显卡的数据传输瓶颈，实现百万级粒子效果的实时渲染。

[Background]
传统游戏开发里粒子特效一到几百上千粒子就开始卡顿，主要是 CPU 往显卡传数据太慢，加上画质高了显存又不够，根本跑不动。这篇干货专门给特效程序看的，教你怎么把计算也扔给显卡，搞定爆炸烟雾这种需要大量小粒子的场面，避免后期优化抓狂。

[Recaps]
咱们先说痛点，以前的粒子系统大多是 CPU 负责算位置和速度，算完再发给显卡画图。这就有个大毛病，CPU 和显卡之间那条路太窄，一次性能传的数据有限，通常撑死也就 1 万个左右，再多的话带宽直接爆了。而且以前为了省带宽，粒子不得不做得比较大，导致填充率 (Fill Rate) 不够用。这次作者 Lutz Latta 决定硬刚，直接把整个粒子系统的模拟和渲染都丢到 GPU 上去干，也就是所谓的 GPGPU，让显卡自己算物理自己画，中间不需要反复回传数据。

核心玩法是建一套有状态粒子系统 (State-preserving Particle System)。传统的“无状态粒子系统 (Stateless Particle System)"只能按固定公式算，没法跟场景互动。新方法则是把粒子的速度和位置存在纹理 (Texture) 里，利用双缓冲技术，每一帧都用像素着色器 (Pixel Shader) 去读上一帧的数据算新数据，这样就能实时响应重力、风力或者地形碰撞。对于复杂的物理交互，比如粒子撞到地形或者障碍物，可以利用高度场 (Height Field) 来快速计算反弹角度，不用每次都去查复杂的网格模型，效率极高。

最麻烦的是半透明渲染，如果前面的粒子不挡住后面的，透明效果就会穿帮。为了解决这个问题，作者在 GPU 上搞了一个“奇偶合并排序 (Odd-even merge sort)"，按距离摄像机的远近把粒子排个序。这个算法完全并行，虽然一帧算不完可以分摊到几十帧里完成，但能保证 Alpha 混合渲染时顺序是对的。最后画图时，尽量用点精灵 (Point Sprites)，少生点多边形，减少显卡负担。

整体来看，这套方案对当时的硬件要求挺高，得是支持浮点运算的可编程显卡才行。不过逻辑非常清晰，就是把耗时的计算从串行转成并行，把数据传输从频繁变低频。这对于现在的开发者依然很有启发，尤其是看到后来很多高级特效都离不开类似的 GPGPU 思路，这算是当年的行业顶尖技术分享。

## AI and Design: How AI Enables Designers
- **Speaker:** Rishi Bhattacharya ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022851
- **Custom ID:** 1022851

### Overview


### Content Summary
[TLDR]
AI 并非代码附属品，应与设计同步开发，用 AI 驱动交互、性格与内容生成，提升游戏可玩性。

[Background]
传统开发常把 AI 当后期补丁，导致玩法割裂。Brian 老哥用实战案例告诉大家，AI 应该在设计初期就介入，用来驱动交互和增加内容密度，非常适合策划和独立开发者避坑参考。

[Recaps]
核心逻辑很简单：游戏设计 (Game Design) 和人工智能 (Artificial Intelligence) 不能各玩各的。如果加了个新功能却忘了教 AI 怎么玩，那测试出来的反馈肯定是假的。Brian 强调要在设计文档 (Design Doc) 完善前就上手改 AI，哪怕只是个随机的烂代码也行，关键是尽早让 AI 去挑战玩家，这样能反推设计是否好玩。早期甚至不需要处理路径寻找 (Path Finding) 这种底层逻辑，先让 AI 学会下棋或宣战，远比完美的寻路更重要。

拿《文明》系列开刀最典型。早期版本里 AI 根本不懂领土概念，看见你就冲，后来引入了国家边界系统，AI 才会计算谁的地盘，进而逼出了“边境施压”这种新策略。这种联动证明，好的机制会倒逼 AI 进化，而 AI 的行为又能启发新机制。想要有深度的电脑对手，就别想搞什么复杂的心理模型，用几个简单的角色性格 (Personality) 标签（比如暴兵还是稳健）往往效果更炸裂。

至于地图生成和内容生成 (Content Generation)，别迷信纯随机。像 CRC (循环冗余校验) 这种算法能让资源分布看起来杂乱但有逻辑，避免模式太明显。分形算法 (Fractals) 适合制造不对称的地图地形。总之记住几条铁律：别怕代码丑，别等文档齐，利用 AI 去探索玩家的可能性，而不是限制玩家的体验，这样才能保证游戏的重玩性 (Replayability)。

## Beyond Finite State Machines: Managing Complex,   Intermixing Behavior Hierarchies
- **Speaker:** Joseph W. Popinski III ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022854
- **Custom ID:** 1022854

### Overview


### Content Summary
[TLDR]
别再用死板的脚本管 NPC 了，利用分层行为系统实现即兴表演与多角色协同，这才是造真人的终极解法。

[Background]
很多开发者头疼 NPC 假，像复读机一样只会按固定套路走。这篇来自《Façade》项目的演讲就是为了解决这个坑，教你们怎么让角色既有剧情感又能灵活配合，非常适合做游戏 AI 和关卡设计的老哥参考。

[Recaps]
咱们聊到 NPC 智能，以前最常用的办法是有限状态机 (Finite State Machine)，但这东西太僵硬，换个场景就崩。演讲者直接从《Façade》项目的经验出发，提出了一套新的思路。他们没用传统的 C++ 或 Java 这种命令式语言 (Imperative Languages) 来写逻辑，而是发明了一种专门的行为语言 (Behavioral Language)，代号 ABL。简单说，就是把角色从“只会走路的机器”升级成“脑子里有目标的活人”。每个角色都有一堆目标 (Goal) 和行为 (Behavior)，它们可以组合出复杂的层级结构，而且支持并行执行。这意味着角色可以同时在做一件事的同时，心里还惦记着另一件事，不像以前只能在一个状态里打转。

这套系统的核武器在于“反应速度”。在传统设定里，NPC 经常卡顿，因为这货还在等上一句台词说完。而在新的架构里，行为被拆成了更细的原子步 (Atomic Behavior)，比如等待、物理动作 (Physical Act)、心理动作 (Mental Act)。每个步骤都有成功测试和上下文条件 (Context Conditions) 监控。一旦世界发生变化，比如玩家突然开枪了，NPC 能毫秒级识别并中断当前动作去处理新状况，根本不需要重新加载整个脚本。这种实时监测机制保证了角色在面对突发事件时，永远显得像是在“下意识”反应。

最硬核的部分是处理“多角色协作”。以前的 AI 很难让两个 NPC 默契地聊天或者打架，容易穿帮。这里引入了一套“联合目标 (Joint Goal)"机制。当两个角色要合作时，他们的意图会在各自的决策树里产生连接。如果发生冲突，系统会通过谈判机制来解决优先级，比如一方急着开门，另一方在说话，系统会自动调整谁先动，甚至冻结冲突的子树 (Subtree) 部分，直到问题解决。再加上“元行为 (Meta-Behavior)"的设计，NPC 可以在运行时动态修改自己的行为流，哪怕剧情主线被玩家带偏了，角色也能顺着玩家的骚操作调整后续表演，实现了所谓的“可塑性强”的戏剧体验。

## Advanced Real-Time Reflectance
- **Speaker:** Thomas Peltier ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022850
- **Custom ID:** 1022850

### Overview


### Content Summary
[TLDR]
搞定实时渲染里的材质真实感，核心得靠理解双向反射分布函数 (BRDF) 和微表面理论，别再靠经验瞎调参数了。

[Background]
游戏画面想逼真，光照、阴影和材质缺一不可。这篇主要是微软和顽皮狗的大佬们，分享如何把复杂的物理光学原理应用到实时渲染中，帮美术和技术解决材质看起来很假的问题。

[Recaps]
想把 3D 物体做得跟真的一样，最难的就是算清楚光打在东西上怎么反光。以前的简单做法往往忽略了真实世界的复杂性，现在有了更好的数学工具。首先是光的物理测量，比如辐射亮度 (Radiance) 和辐照度 (Irradiance)，这些量决定了光有多强、往哪射，这是计算的基础。而核心工具就是双向反射分布函数 (BRDF)，它就是个数学公式，告诉你光线从哪个方向来、从哪个方向看，会呈现出什么样的反光效果。

这个函数有两种类型，一种是各向同性 (Isotropic)，各个方向看过去差不多；另一种是各向异性 (Anisotropic)，像拉丝金属或头发，换个角度光泽就不一样。为了保证画面不过曝也不丢失细节，BRDF 必须遵守能量守恒 (Energy Conservation)，反射的能量不能大于照射进来的能量，否则物理上就说不通了。同时还要注意互易性 (Reciprocity)，反正光路可逆，这对算法效率很重要。

那怎么模拟粗糙表面的反光呢？这时候微面片理论 (Micro-facet theory) 登场了。把表面想象成无数个小镜子拼成的，每个小镜子的朝向随机分布，这就产生了所谓的法线分布函数 (Normal Distribution Function)。加上菲涅尔 (Fresnel) 效应，就是人眼看镜面侧面的时候比正面更亮，以及遮挡关系，整个模型的质感一下子就出来了。

最后聊聊实现细节。现在显卡都支持可编程着色器 (Shader)，把这些公式写进去就行了。但要注意远处屏幕上的像素太小容易锯齿，这叫走样 (Aliasing)，需要做预处理。另外，单纯算直射光太生硬，还得加环境贴图 (Environment Map) 或者预烘焙的光照来模拟漫反射。虽然追求完美的物理模型最好，但在游戏里性能优先，有时候为了流畅度还得稍微妥协一下，把参数交给美术手动调整也是常见操作。

## Using Verlet Integration and Constraints in a Six Degree of Freedom Rigid Body Physics Simulation
- **Speaker:**  ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022904
- **Custom ID:** 1022904

### Overview


### Content Summary
[TLDR]
抛弃昂贵雅可比矩阵，通过扩展 Verlet 积分实现 6 自由度，用半隐式算法在旧主机上换取性能与稳定。

[Background]
早期物理引擎要么太虚（显式易穿模），要么太重（隐式算不动）。为了解决《极限摩托》里的车辆碰撞和人物跌倒，团队决定改造成人版 Verlet，既能抗揍又跑得飞快。

[Recaps]
咱们先聊背景，早年间想做个刚体物理，大家挺头疼。用显式积分吧，稍微有点劲儿系统就崩了；用隐式积分呢，得算那个雅可比矩阵 (Jacobian Matrix)，在当年那种机能上简直是灾难，尤其还得处理轮胎这种非线性力模型。于是作者参考了 Jakobson 的 Verlet 积分，但这玩意儿有个大坑：它只管位置不管旋转，想模拟个完整刚体得凑一堆粒子，又重又不准。所以他们下了血本，把这个积分法升级成了 6 自由度 (Six Degree of Freedom)，引入了旋转状态，这时候就得用到四元数 (Quaternion) 来表示方向，这就省去了大量粒子开销。

接着是具体的落地技术，怎么算碰撞？作者没死磕复杂的接触力计算，而是分情况：要是静止或者慢速，就用惩罚法 (Penalty Method) 加弹簧阻力把它推回来，这样就不会像以前那样在桌面上弹来弹去；要是高速撞击，就直接给个冲量 (Impulse Method) 瞬移速度。关节方面，最实用的就是销钉约束 (Pin Constraint) 和角度约束 (Angle Constraint)，以前想做 Ragdoll 布娃娃系统得拼无数根线，现在直接锁两个点的距离和角度就行。不过作者也提醒，为了保留速度信息，有些方程会变复杂一点，这是个性能和精度的平衡选择。

最后是实战成果，这套系统全用在《MX Unleashed》里了。游戏里的人偶有 18 个身体部件，全靠这些约束连起来，还能在各种地形上摔得逼真。作者贴了对比表，PS2 和 XBox 上跑起来每帧耗时都不高，证明这套方案在当时就是最懂硬件的菜鸡互啄策略。结论也很直白：别迷信纯数学的完美，能跑起来还不卡才是王道，随着 CPU 变强以后或许能回去用隐式，但现在这种半路出家改出来的方案才是正解。

## The Making of the Official
- **Speaker:** Michael Booth (Valve)
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022878
- **Custom ID:** 1022878

### Overview
This lecture addresses the technical and design issues critical to the success of the official Counter- Strike bot, the most advanced FPS tactical multiplayer AI to date. The official Counter-Strike bot has received an enthusiastic reception from both newbies and veterans of the Counter-Strike community, largely due to the fact that it plays the game in a very believable, human-like fashion. The bots put on a "performance" that results in players feeling they are fighting against (and with) "worthwhile" opponents. Achieving this level of suspension of disbelief requires more than technical AI coding ability. It requires a thorough understanding of the game, insight into human limitations such as reaction times and attention prioritization, and a holistic sense of how to create a fun and believable "performance" from these disparate parts.

### Content Summary
[TLDR]
真正的游戏 AI 核心不在于算法多强，而是模拟人的行为瑕疵与战术思维，营造公平博弈的真实感。

[Background]
当年 CS 缺乏单机内容，Valve 想用 Bot 填补，但旧版太假。此演讲拆解了构建高智能、类人行为的 Bot 全流程，重点解决寻路、决策与人设问题，适合对游戏 AI 感兴趣的技术人员学习。

[Recaps]
老哥主要讲了怎么让 Bot 看起来像个真人。第一关是认路，以前用的 路径点 (Waypoint) 只能画直线，没法处理跳跃和复杂地形。后来改用 导航网格 (Navigation Meshes)，把地图划分成可通行的二维区域块，这样机器人才能灵活地跳台阶、爬梯子。移动逻辑还分了层级，从 寻路 (Pathfinding) 到跟随，再到 动态躲避障碍 (Reactive Obstacle Avoidance)，万一卡住还能随机晃动挣脱，避免死循环。

第二关是做决定。Bot 不光看目标，还得评估风险。系统里有个 代价函数 (Cost Function)，队友倒下会让周围区域危险值飙升，Bot 就会选更安全的路。还有个 士气 (Morale) 机制，打得顺就冲锋，输了就猥琐。战斗时也不能无脑爆头，通过 瞄准偏移 (Aim Offset) 来模拟人类反应误差，还得懂枪械特性，远距离切手枪，近身切狙击镜，甚至连换枪时机都模拟得很细致。

最后是细节打磨和架构。为了更像人，Bot 的反应时间、说话频率都会限制，还会叫玩家“指挥官”，甚至偶尔恭维你的击杀。技术上强调性能优先，用 状态机 (State Machine) 组织代码，保证逻辑清晰不崩盘。地图加载也做了自动化，新图丢进去几分钟就能自动生成导航数据，方便玩家用社区地图。总之就是：别整虚的，让玩家沉浸在“公平对决”的幻觉里才是成功。

## The Collection and Applications of Metrics in an MMP   Game: Lessons Learned from
- **Speaker:** Larry Mellon ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022859
- **Custom ID:** 1022859

### Overview


### Content Summary
[TLDR]
网游开发运营别靠拍脑袋，要用轻量级自动化系统抓核心数据，早布局才能稳住性能和体验。

[Background]
2004 年 MMO 刚兴起，服务器压力巨大，全靠猜不行。这位大佬分享怎么通过一套“度量系统”监控性能和经济，适合当时搞网游开发和运营的同行避坑。

[Recaps]
老哥们，做网游最忌讳靠拍脑袋。这篇 GDC 干货的核心思想就一个：数据是强大的仆人，但也可能是危险的主人。Lord Kelvin 曾说要量化才能懂，Mark Twain 却警告统计数字会骗人。所以制定度量指标 (Metrics) 时要极其小心，测什么就得想清楚是为了优化什么，不然容易陷入“蝴蝶效应”，导致系统复杂化。别迷信大而全的监控，够用就行，否则维护成本能把项目组拖垮。

为了解决这个问题，讲者分享了他们的工具思路，核心是把数据收集做得轻量和自动化。传统做法是把所有原始日志存下来再分析，太占资源。他们的方法是在服务器进程里埋探针 (Probe)，直接在本地汇总成平均值或总数，像 Esper 这个专用工具一样，只把“结果”发给数据库，而不是发“过程”。这样既减少了网络开销，又能实时看到服务器的负载情况。这就好比给每个 CPU 都装了个智能电表，不用拉总闸就能知道哪台机器吃电最多，从而优化系统的扩展性 (Scalability)。

这套体系实际用处大了，主要帮了三类忙。第一是性能方面，结合负载测试 (Load Testing) 模拟高峰流量，提前发现服务器瓶颈。第二是经济系统，盯着玩家的钱从哪赚花到哪，防止通货膨胀或者卡死循环。第三是运营和客服，参考哈拉斯赌场的经验，利用客户关系管理 (CRM) 数据分析谁是大客户，谁是捣乱者。通过观察玩家行为数据，比如聊天频率、房间停留时间，甚至像“新年之吻”这种活动热度，都能反推玩法好不好玩。

最后总结一下经验教训。千万别等上线了再想数据统计的事，越早介入越省力。系统要做得足够轻量，不能影响游戏本身运行速度。另外一定要集中化管理，之前因为各自为战搞了好几个独立系统，后来才发现不如整合成一个能自动汇总的大平台。总之，别被数据绑架，要让数据成为帮你做决策的辅助线，这样才能稳稳当当做好一款服务型网游。

- **Category:** Programming

### Overview


### Content Summary
[TLDR]
别每帧死算光照，利用画面连续性复用旧数据，将高开销的全局光照变成实时互动效果。

[Background]
2004 年显卡只能画贴图，想算真实光线传播太卡。演讲者想搞一套软件方案，在不牺牲太多画质的前提下，让复杂的全局光照也能跑飞，解决实时渲染的性能痛点。

[Recaps]
先把光照原理捋清楚。光线直着走，撞墙会反弹或者穿透，这就产生了 **全局光照 (Global Illumination)**。要把这个算准，得解一个 **渲染方程 (Rendering Equation)**，还要考虑表面的 **双向反射分布函数 (BRDF)**。以前靠 **光线追踪 (Ray Tracing)** 最准但慢如蜗牛，后来的 **辐射度 (Radiosity)** 虽然快但只能处理漫反射，都很难满足游戏里那种随时互动的需求。

当时的瓶颈在于硬件太偏向固定功能。硬件搞 **光栅化 (Rasterization)** 是一把好手，靠 **深度缓冲 (Z-buffer)** 能飞快确定谁在前面，但它不懂灵活的反射折射逻辑。软件渲染器虽然能随便改算法，但速度跟不上。所以大神们的对策就是“不浪费”，利用时空 **相干性 (Coherence)**。上一帧算过的颜色，如果下一帧位置没啥变化，就直接拿来用，没必要从头算起。

具体怎么用呢？比如搞个 **渲染缓存 (Render Cache)**，存一堆采样点，相机一动就把旧点投影到新画面，缺的地方再补。还有 **边缘和点渲染 (Edge-and-Point Rendering)**，专门把轮廓线和阴影边缘这种容易出问题的地方重点算，中间平滑的大片区域就糊弄过去。另外还有 **校正纹理 (Corrective Texturing)**，先用硬件快速画个底子，再把高精度的光照差值叠加上去。这一套组合拳下来，能在当时机器上跑出 8-14fps 的高保真效果。

总的来说，这技术证明了软件也能搞定实时高质量光照。不过当时还面临分辨率太高、物体乱动导致缓存失效等挑战，但这份“重用着色”的思路，确实给后来的图形技术铺了平路，让咱们现在的游戏光影没那么费劲。

[Background]
CPU 单核性能触顶后，多核普及已成定局。许多开发者面对多线程既想要性能又害怕代码崩溃，本演讲由 EA 与 Intel 专家结合三款商业大作案例，传授如何在现有项目中安全落地多线程技术。

[Background]

[Recaps]
先把核心两派捋清楚：阴影体积 (Shadow Volume) 和阴影缓冲 (Shadow Buffer)。体积法就是把物体往光源方向拉长成个封闭盒子，利用模板缓冲 (Stencil Buffer) 计数来决定黑影在哪。这方法画质稳，边缘不渗，但要是遇到动画骨骼或者近处裁剪平面，容易出洞或者鬼影。而且画太多面会卡顿，还得找艺术配合闭合模型，门槛挺高。

实际项目里别指望一个灯管一个地图够用，得玩多重视锥体 (Multiple Frustums)。动态选择省资源但画面会闪烁，静态持久化更稳但要预留空间。还要配合剔除算法，看不见的地方别浪费资源去算阴影。最后拿 StarTopia 举例子，这游戏当年没为阴影设计过，全靠后期硬怼引擎，证明了不管什么方法，只要策略对，烂泥也能扶上墙。总的来说，没最好的技术，只有最适合当下的取舍，填坑靠的是多手准备。

告别罚函数！利用基于费瑟斯通算法的解析约束方法，构建稳定高效的关节角色实时物理引擎。

[Background]
传统关键帧动画在处理不可预测的物理碰撞和交互时显得僵硬无力。本文分享了索尼团队如何从零构建支持复杂约束的实时物理引擎，解决了多约束同步计算难、数值不稳定的痛点，适合想深挖角色物理效果的程序猿阅读。

[Recaps]
这篇干货主要是教咱们怎么用物理手段让游戏角色动起来更真实，而不是全靠人工搓动作。作者来自索尼 R&D，核心思路是抛弃传统的“罚函数法”(Penalty Method)，改用“解析约束”(Analytical Constraint)。说白了，就是把限制条件变成精确的力，直接在每一帧把加速度算准，而不是等穿模了再用力推回来。这样不仅稳，还能用更大的步长进行积分而不崩溃。基础骨架动力学的底层算法选的是“费瑟斯通关节体法”(Featherstone's Articulated Body Method)，这玩意儿效率高，计算复杂度是线性的 O(n)，对复杂的骨骼层次支持很好。

最硬核的技术点在于约束求解。以前写这种引擎，很多人被复杂的数学公式劝退，但这文章给了个聪明的“暴力”解法：通过施加“测试力”(Test Force) 来反推矩阵元素。你不需要从头推导公式，只要给每个约束加个已知大小的假力，跑一遍基础算法看看加速度变没变，就能凑出需要的方程组。当多个约束同时存在（比如脚踩地还不能穿墙）时，把这些力扔进一个线性方程组里一次性解完，保证所有条件同时被满足。

最后说说实际跑起来的流程。遇到撞车要瞬间变向，得用“冲量约束”(Impact Constraints)，相当于给速度打补丁，避免帧间穿透太严重。对于摩擦力这种只能单向受力的情况（比如脚蹬地但不吸地），属于“单向约束”(Unilateral Constraint)，这里采用的是投影 Gauss-Seidel 迭代求解器来处理“线性互补问题”(Linear Complementarity Problem)。整个循环很清晰：先算约束力 -> 算加速度 -> 积分更新状态 -> 检查新碰撞并回退步长 -> 处理冲量。这套流程下来，不仅能做简单的碰撞，还能精准控制关节限位和动作轨迹，实现起来比想象中要 tractable 多了。

[TLDR]
物理引擎的核心不是堆算法，而是用缓存、Shader 约束和严格时序，在保证帧率下实现逼真的物理交互。

[Background]
很多独立开发者或新人常被物理引擎搞得头大，要么卡顿要么效果假。这篇是实战干货，教你怎么在现代化引擎里低成本搞定高性能物理，避免踩坑。

[Recaps]
说到碰撞，别迷信复杂的三角形网格 (**Triangle Mesh**)，除非非要不可，平时多用球体 (**Sphere**) 或包围盒 (**Bounding Box**) 这种简单形状。核心大招是搞了个 **碰撞缓存 (Collision Cache)**，静态物体直接加载缓存，动态物体才现场算，不然加载慢到起飞。还得自研一个 **射线检测 (Raycast)** 系统，按规则过滤对象，别浪费 CPU 去检测无关碰撞，效率直接拉满。

## Fast Yet Realistic Deformation and Fracture
- **Speaker:** James O'Brien ()
- **Duration:** 0 分钟
- **Category:** Programming
- **Video Page:** 
- **Slide Page:** https://www.gdcvault.com/play/1022865
- **Custom ID:** 1022865

### Overview


### Content Summary
[TLDR]
利用模态分析与有限元技术，实现实时交互式变形、碎裂及音效模拟，平衡性能与画面表现。

[Background]
传统物理引擎算大物体太费 CPU，做不了复杂变形。这篇讲怎么用预计算加简化模型，让游戏里物体摔打、撕裂还能自带音效，适合追求特效又卡配置的开发组看。

[Recaps]
硬核物理模拟最怕算不动，这里介绍了一个叫**模态分析 (Modal Analysis)** 的招数。简单说就是把物体复杂的震动状态提前在电脑上算好存起来，比如把它拆成几个基本的振动模式。运行时直接调用这些模式，而不是实时解方程，这样就算跑在 PS2 这种老旧主机上，也能搞出几百个顶点的复杂物体动态变形。**线性近似 (Linear Approximation)** 带来的误差在卡通风格或小幅形变里完全可接受，但大变形会有点假。

接着是物体碎了怎么办。作者分成了两种情况：**脆性断裂 (Brittle Fracture)** 和**延性断裂 (Ductile Fracture)**。玻璃这类硬货是脆性的，受力直接炸裂；金属塑料则是延性的，会先发生**塑性变形 (Plastic Deformation)** 也就是扭曲后才断。算法核心是根据内部应力张量判断裂纹走向，配合**局部重网格化 (Local Remeshing)**，让网格沿着裂缝自动分裂。虽然不能完全预测现实世界的微观裂缝，但视觉冲击力足够，而且不用人工关键帧。

最后是音效合成。一般游戏里的碰撞声是放录音文件，但这个方法是根据刚体碰撞产生的力，映射到之前算好的物体**固有频率 (Natural Frequency)** 上生成声音。比如碗掉地上，它的材质决定了撞击后怎么震，程序就能算出对应的音频波形。整个过程不需要实时测距，只需在建模阶段做一次繁重的**特征值分解 (Eigen-decomposition)**，运行时就快得很，能做出很有辨识度的物体质感。

### Content Summary
[TLDR]
靠给美术自定义工具配合简化的物理逻辑，在 PS2 这种老硬件上实现了大量可破坏物体而不卡帧的核心方法论。

[Background]
Incognito 团队在 PS2 时代开发了多款强调环境互动的游戏，面临的主要挑战是如何在性能吃紧的情况下维持 60 帧流畅运行，同时赋予美术对破坏效果的完全控制权，这套经验非常适合资源受限的主机开发项目。

[Recaps]
核心首先在于解放程序员的创造力，直接把活儿丢给了美术。他们没搞复杂的脚本，而是让美术在 Maya 里连线搭**动作图 (Action Graph)**，把每个能拆的物体变成一个**状态机 (Finite State Machine)**。美术只需设定受多少伤害进入哪个状态，触发什么粒子或动画，甚至能通过“链接动作”让大楼倒下砸扁邻居，这种逻辑链条全由数据驱动，极大降低了维护成本，让非技术人员也能轻松搞定复杂的交互逻辑。

面对环境被玩家拆得七零八落的情况，传统的路径规划根本跟不上节奏。于是采用了基于 C4 架构的**反应式 AI (Reactive AI)**，它不依赖死板的**导航地图 (Navigation Maps)**，而是根据实时感知到的地形高度和障碍物来动态调整移动策略。即使脚下的路塌了，AI 也能像人一样随机应变走捷径，保证在动态变化的战场上还能正常跑打，大大提升了系统的容错率。

性能优化方面完全是往极致压榨。既然无法对所有物体进行高精度的物理计算，那就按远近和可见度分级处理。看不见的地方直接降权或用统计模型替代，碰撞检测上也用了偷奸耍滑的手段，用简单的**代理碰撞体 (Proxy Collider)** 快速判定方向，再通过**时间步长跳跃 (Time Skipped Updates)** 减少每秒的检测频率。只要结果看着 plausible（合理），哪怕稍微有点穿模也不影响玩家体验，最终在 PS2 上稳稳跑出了 60 帧，为同类项目提供了极具价值的避坑指南。
